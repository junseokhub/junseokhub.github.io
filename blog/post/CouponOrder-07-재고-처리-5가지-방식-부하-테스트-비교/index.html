Kafka 구현 변경 사항

6편에서 Kafka는 단순히 "주문 요청을 토픽에 발행하고 Consumer가 순차적으로 처리한다"는 계획이었다. 그런데 막상 구현하면서 문제가 생겼다.

다른 방식들은 전부 요청 -> 처리 -> 응답이 동기적으로 이루어진다. 비관적 락이든 Redis Lua든 처리가 완료된 후에 응답을 준다. 그런데 Kafka 비동기 방식은 토픽에 발행하고 즉시 응답한다. 실제 재고 차감과 주문 저장은 Consumer가 백그라운드에서 처리한다.

이 상태로 비교하면 공정하지 않다고 판단했다. 처리 결과도 모르면서 즉시 응답하는 방식이 처리량이 높게 나오는 건 당연하다.

그래서 두 가지로 분리했다. WebFlux 환경이라 reactor-kafka의 KafkaSender와 KafkaReceiver를 사용했다.

KAFKA_ASYNC: 발행 후 즉시 응답. WebFlux의 논블로킹 철학과 가장 잘 맞는 패턴이다.

return Mono.fromCallable(() -> objectMapper.writeValueAsString(message))
        .flatMap(payload -> {
            SenderRecord<String, String, String> record = SenderRecord.create(
                    new ProducerRecord<>("order-requests", correlationId, payload),
                    correlationId
            );
            return kafkaSender.send(Mono.just(record))
                    .next()
                    .thenReturn(Order.pending(userId, productId, couponIssueId));
        });

KAFKA_SYNC: 발행 후 Consumer가 처리를 완료할 때까지 대기. correlationId로 요청과 응답을 매칭한다. 다른 동기 방식들과 공정하게 비교하기 위한 방식이다.

// KafkaSyncOrderService
return Mono.<Order>create(sink -> {
            pendingOrders.put(correlationId, sink);

            SenderRecord<String, String, String> record = SenderRecord.create(
                    new ProducerRecord<>("order-requests", correlationId, payload),
                    correlationId
            );
            kafkaSender.send(Mono.just(record)).next().subscribe();
        })
        .timeout(Duration.ofSeconds(10));

// order-results 수신 시 (KafkaReceiver로 구독)
MonoSink<Order> sink = pendingOrders.remove(result.correlationId());
sink.success(order);

Producer -> order-requests 토픽 -> Consumer -> 재고 차감 + 주문 저장
                                           -> order-results 토픽으로 결과 발행
                                                       -> KafkaReceiver -> correlationId 매칭 -> sink 완료

Consumer는 OrderKafkaConsumer로 별도 분리했다. order-requests를 소비해서 재고를 차감하고 주문을 저장한 뒤, 결과를 order-results 토픽으로 발행한다. KAFKA_ASYNC와 KAFKA_SYNC 모두 같은 Consumer를 공유한다.

@PostConstruct
public void start() {
    subscription = KafkaReceiver.create(receiverOptions)
            .receive()
            .flatMap(this::processRecord, 32)
            .subscribe();
}

Optimistic Lock (낙관적 락) - 무한 재시도

결과

http_reqs: 약 1,000건 / 5/s 미만
p(95): 60s (타임아웃)
http_req_failed: 약 50% 이상 (타임아웃)
checks 성공: 거의 0% 수준 (대부분 타임아웃)

분석

처참하다. 500명이 동시에 같은 상품을 때리니 충돌 -> 즉시 재시도 -> 또 충돌 -> 즉시 재시도가 타임아웃 날 때까지 반복된다.

.onErrorResume(OptimisticLockingFailureException.class,
        e -> decrementStock(productId)); // 무한 재귀

재시도에 딜레이도 없고 횟수 제한도 없으니 당연한 결과다. 낙관적 락은 충돌이 적은 환경을 가정한 전략이다. 500명이 동시에 같은 레코드를 건드리는 상황은 애초에 낙관적 락이 맞지 않는다.

Optimistic Lock (낙관적 락) - 재시도 제한

무한 재시도 결과가 예상대로 처참했다. 그래서 재시도에 딜레이와 횟수 제한을 두면 얼마나 달라지는지 확인해봤다. 최대 3회, 충돌 시 50ms 대기 후 재시도하도록 변경했다.

// 변경 전
.onErrorResume(OptimisticLockingFailureException.class,
        e -> decrementStock(productId)); // 무한 재귀

// 변경 후
.retryWhen(Retry.backoff(3, Duration.ofMillis(50))
        .filter(e -> e instanceof OptimisticLockingFailureException)
        .onRetryExhaustedThrow((spec, signal) ->
                new BusinessException(ErrorCode.PRODUCT_ORDER_FAILED)));

결과

http_reqs: 1,536건 / 7.17/s
p(95): 60s (k6 타임아웃 한계)
http_req_failed: 30.53%
checks 성공: 63.24%
iteration p(50): 51.54s

분석

재시도 제한을 걸어도 여전히 처참하다. checks 성공률은 63%로 올랐지만(재시도 3회 소진 후 PRODUCT_ORDER_FAILED를 정상 응답으로 받기 때문), 처리량은 7건/초밖에 안 된다. 응답 시간 중간값(median)이 51.54초로, 절반 이상의 요청이 50초가 넘게 걸렸다는 뜻이다. p(95)가 정확히 60초로 찍힌 건 k6의 기본 HTTP 타임아웃이 60초이기 때문이고, 실제로는 더 걸린 요청도 많았을 것이다.

흐름을 따라가보면 명확하다. 한 요청이 충돌 -> 50ms 대기 -> 재시도하는 동안에도 다른 수백 개의 요청이 같은 row를 노린다. 결국 재시도해도 또 충돌하고, 3번 다 써도 끝나지 않는다. 운 좋게 성공해도 이미 수십 초가 흘러간 후다.

고경쟁 환경에서 낙관적 락은 재시도 제한을 걸어도 근본적인 해결책이 되지 않는다. "충돌이 드물 것"이라는 가정 위에 성립하는 전략이기 때문이다. 선착순 쿠폰이나 재고 차감처럼 본질적으로 같은 row를 노리는 환경에서는 그 가정이 깨진다.

Pessimistic Lock (비관적 락)

R2DBC는 @Lock을 지원하지 않기 때문에 DatabaseClient로 직접 SELECT FOR UPDATE 쿼리를 작성했다.

databaseClient.sql("SELECT * FROM products WHERE id = :id FOR UPDATE")
        .bind("id", productId)
        ...

결과

http_reqs: 132,049건 / 718/s
p(95): 328ms
checks 성공: 100%
http_req_failed: 91.66% (재고 소진 후 409 응답)

분석

낙관적 락 대비 압도적인 차이다. 락을 걸고 순차적으로 처리하니 충돌 자체가 발생하지 않는다. 재시도도 없고 타임아웃도 없다.

http_req_failed: 91.66%는 에러가 아니다. 재고 10,000개가 소진된 이후 들어오는 요청에 대해 409(Conflict)로 응답한 비율이다. checks는 201과 409 모두 성공으로 처리했기 때문에 100%가 나왔다. 정상적인 비즈니스 로직이다.

p(95) 328ms는 락 대기 시간 때문이다. 동시 요청이 많아질수록 뒤에 들어온 요청은 앞 요청이 끝날 때까지 기다려야 한다. 안정적이지만, 락 대기가 곧 응답 시간으로 직결된다.

Atomic Update

SELECT FOR UPDATE 없이 UPDATE 조건절 하나로 재고 차감과 검증을 동시에 처리한다.

락을 잡는 시간이 UPDATE 실행 순간뿐입니다. 애플리케이션이 값을 읽어서 계산하는 과정 없이 DB가 직접 stock - 1을 계산하고 조건까지 검증해 락 보유시간이 최소화 된다.

databaseClient
    .sql("UPDATE products SET stock = stock - 1 WHERE id = :id AND stock > 0")
    .bind("id", productId)
    .fetch()
    .rowsUpdated()
    .flatMap(updatedRows -> {
        if (updatedRows == 0) {
            return Mono.error(new BusinessException(ErrorCode.PRODUCT_OUT_OF_STOCK));
        }
        return productRepository.findById(productId);
    })
    .flatMap(product -> defaultOrderService.saveOrder(userId, product, couponIssueId, correlationId));

핵심은 AND stock > 0 조건이다. 재고 확인과 차감이 DB 레벨에서 원자적으로 처리되고, rowsUpdated() == 0이면 재고가 없었다는 의미다. 별도의 SELECT 없이 판단할 수 있다.

결과

http_reqs:     126,874  686/s
p(95):         304.63ms
checks:        100%
정합성:        orders 10,000건, stock 0

분석

내 예상은 Pessimistic(718/s)보다 빠르고 Redis Lua(1,624/s)보다 느린 결과였다. DB 왕복이 2번에서 1번으로 줄어드니 당연히 빠를 거라고 봤다.

병목이 쿼리 횟수가 아니라 row 락 경합이었다.

Pessimistic은 SELECT FOR UPDATE + UPDATE, Atomic은 UPDATE 1번으로 쿼리 횟수는 다르다. 하지만 둘 다 결국 같은 row(products WHERE id = 1)를 수정한다. MySQL은 UPDATE 실행 시 내부적으로 row-level 락을 걸기 때문에, 500명이 동시에 같은 row를 때리는 상황에서 락 경합이 발생하는 건 동일하다. 쿼리 1번 줄인 효과가 락 대기 시간에 완전히 묻혀버렸다.

로컬 환경이라 네트워크 레이턴시가 거의 없었다.

서버와 DB가 같은 머신에 있으니 DB 왕복 1번의 차이가 실질적으로 의미 있는 시간이 아니었다. 실제 프로덕션 환경처럼 네트워크 레이턴시가 수 ms라도 있었다면 쿼리 횟수 차이가 유의미하게 드러났을 것이다.

@Transactional이 동일하게 걸려있다.

Atomic UPDATE도 @Transactional이 붙어있어서 트랜잭션 오버헤드는 Pessimistic과 동일하게 발생한다. 락 보유 시간의 차이가 있긴 하지만 미미한 수준이다. Pessimistic은 SELECT FOR UPDATE 시점부터 커밋까지 락을 유지하는 반면, Atomic은 UPDATE 실행 순간에만 락이 걸린다. 이 차이가 p(95) 응답시간에서 304ms vs 328ms로 미세하게 나타났다.

결론적으로 "DB 왕복 횟수 = 성능"이라는 단순한 가정이 틀렸다. 고경쟁 환경에서는 락 경합이 지배적인 병목이고, 쿼리 최적화의 효과는 그 뒤에 온다.

Redis Lua 스크립트

Redis에서 먼저 재고를 차감하고, 성공하면 DB에 주문을 저장한다. Redis는 싱글 스레드로 동작하고 Lua 스크립트는 원자적으로 실행되기 때문에 race condition이 발생하지 않는다.

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1
end
redis.call('DECR', KEYS[1])
return 1

결과

http_reqs: 약 290,000건 / 1,600/s
p(95): 약 160ms
checks 성공: 100%
http_req_failed: 약 85% (재고 소진 후 409)

분석

비관적 락(718/s) 대비 약 2.2배 빠르다. DB 락 없이 Redis에서 재고를 원자적으로 처리하니 병목이 훨씬 줄어든다. 응답 시간도 160ms 수준으로 비관적 락(328ms)의 절반 정도다.Redis가 인메모리이고 싱글 스레드로 처리되기 때문에 락 자체가 필요 없다. DB는 재고 차감이 아닌 주문 저장만 담당하니 부담도 줄어든다.단, Redis 재고와 DB 재고 간 동기화 문제가 있다. Redis에서 차감에 성공했지만 DB 주문 저장이 실패하면 재고 불일치가 생긴다. 실제 서비스라면 보상 트랜잭션이나 Outbox 패턴이 필요하다. 해당 부분은 다음 편에서 작업해 볼 예정이다.

Kafka

주문 요청을 Kafka 토픽에 발행하고 즉시 응답한다. Consumer가 백그라운드에서 재고 차감과 주문 저장을 처리한다.

Producer -> order-requests 토픽 -> Consumer -> 재고 차감 + 주문 저장
                                           -> order-results 토픽 (결과 발행)

결과

http_reqs: 382,315건 / 2,100/s
p(95): 115ms
checks 성공: 100%
http_req_failed: 0%

분석

처리량이 압도적이다. Redis Lua(1,624/s) 대비 약 1.3배 빠르다. 발행 후 즉시 응답하니 서버 입장에서는 빠를 수밖에 없다.

http_req_failed: 0%가 흥미롭다. 재고가 10,000개인데 약 38만 건 요청이 전부 성공했다. 알고보니 k6 테스트가 끝난 후에도 Consumer가 계속 처리하고 있었고, 결국 주문은 정확히 10,000건만 저장됐다.

SELECT COUNT(*) FROM orders;   -- 10000
SELECT stock FROM products;    -- 0

WebFlux 기반 비동기 서버와 Kafka의 조합은 자연스럽다. 요청을 받고 즉시 응답하는 패턴이 WebFlux의 논블로킹 철학과 잘 맞는다.

Kafka Sync

발행 후 Consumer가 처리를 완료할 때까지 대기한다. correlationId로 요청과 응답을 매칭한다.

return Mono.<Order>create(sink -> {
            String correlationId = UUID.randomUUID().toString();
            pendingOrders.put(correlationId, sink);

            SenderRecord<String, String, String> record = SenderRecord.create(
                    new ProducerRecord<>("order-requests", correlationId, payload),
                    correlationId
            );
            kafkaSender.send(Mono.just(record)).next().subscribe();
        })
        .timeout(Duration.ofSeconds(10));

Consumer가 처리를 완료하면 order-results 토픽으로 결과를 발행하고, 별도의 KafkaReceiver가 받아서 대기 중인 sink에 결과를 전달한다.

결과

http_reqs: 3,447건 / 18/s
p(95): 10.02s (타임아웃)
checks 성공: 0%

분석

500명이 동시에 요청하면서 Consumer가 처리 속도를 따라가지 못했다. 10초 타임아웃이 걸리면서 거의 모든 요청이 실패했다.

Kafka의 장점인 비동기 처리를 억지로 동기로 만들었으니 당연한 결과다. Kafka를 동기 방식으로 쓰면 Kafka의 장점을 전혀 활용하지 못하면서 복잡도만 올라간다.

정리

낙관적 락은 이런 경쟁 환경에서 쓰면 안 된다. 재시도 제한을 걸어도 근본적인 해결이 안 된다. 충돌이 거의 없는 환경, 예를 들어 유저별로 독립적인 데이터를 수정하는 경우에 적합하다.

비관적 락은 정합성을 완벽하게 보장하면서도 적절한 성능을 낸다. DB만으로 모든 걸 처리하고 싶을 때 선택할 수 있는 안정적인 방식이다.

Atomic UPDATE는 SELECT FOR UPDATE 없이 UPDATE 조건절 하나로 원자적으로 처리하기 때문에 코드가 더 단순하다. 애플리케이션이 값을 읽고 계산하는 과정 없이 DB가 직접 처리하기 때문에 락 보유 시간도 최소화된다. 그러나 고경쟁 환경에서는 쿼리 횟수를 줄여도 row 락 경합 자체가 병목이라 기대만큼 빠르지 않다. 네트워크 레이턴시가 있는 환경에서는 DB 왕복 1번 차이가 유의미하게 나타날 수 있다. 코드 단순성, 굳이 락을 길게 잡을 이유가 없을 때 사용하면 될 것 같다. 

Redis Lua는 비관적 락보다 약 2.2배 빠르다. DB 락 없이 Redis에서 원자적으로 처리하기 때문이다. 단, Redis와 DB 간 동기화 문제를 고려해야 한다.

Kafka는 처리량이 가장 높다. WebFlux의 논블로킹 특성과 잘 어울리는 방식이다. 단, 요청 시점에 처리 결과를 알 수 없다는 점을 고려해야 한다. 주문 완료 알림은 별도 메커니즘(웹소켓, 폴링 등)이 필요하다.

Kafka Sync는 안 쓰는 게 낫다. Kafka를 굳이 동기로 쓸 이유가 없다.그냥 어떤 결과가 나올지 궁금해서 테스트만 해본거다.

로컬 환경 테스트라 절대적인 수치보다는 방식 간 상대적인 차이에 집중해서 보면 된다. 실제 프로덕션 환경에서는 네트워크 레이턴시, DB 커넥션 풀, Kafka 브로커 성능 등 여러 변수가 추가된다.
