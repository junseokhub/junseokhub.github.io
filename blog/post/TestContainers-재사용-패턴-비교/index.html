TestContainers 재사용 패턴 비교

Test · 2026-07-12

Intro

통합 테스트를 짤 때마다 컨테이너를 매번 새로 띄우면 테스트 스위트 전체가 눈에 띄게 느려진다. 그래서 여러 테스트 클래스가 같은 컨테이너를 공유하게 만드는 방법을 찾아보다가, 크게 세 가지 방식(상속, 전역 공유용 별도 클래스, 인터페이스 컴포지션)을 써봤다.

그래서 이 세 가지를 실제로 비교해보고, 공식 문서 기준으로는 뭘 권장하는지, 실무에서는 어떤 게 더 널리 쓰이는지 정리해보려고 한다.

왜 재사용이 필요할까?

가장 기본적인 형태는 테스트 클래스 안에 @Testcontainers + @Container를 바로 붙이는 거다.

@Testcontainers
@SpringBootTest
class OrderControllerTest {

    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0");

    @Test
    void someTest() { /* ... */ }
}

이렇게 하면 이 컨테이너는 이 클래스가 실행되는 동안만 살아있고, 클래스가 끝나면 Testcontainers 확장이 알아서 정지시킨다. 문제는 다른 테스트 클래스(PaymentControllerTest 등)도 같은 MySQL이 필요하면, 거기서도 또 새로 띄운다는 거다. 클래스 수가 늘어날수록 컨테이너를 반복해서 기동하는 시간이 그대로 쌓인다.

예전엔 프로퍼티를 직접 매핑했다

세 가지 재사용 패턴을 보기 전에 짚고 갈 게 하나 있다. 컨테이너를 띄우는 것과, 그 컨테이너의 접속 정보(URL, 포트, 계정)를 스프링 애플리케이션에 실제로 연결하는 건 별개의 일이다. @ServiceConnection이 나오기 전에는(Spring Boot 3.1, 2023년 6월 이전) 이 연결을 @DynamicPropertySource로 사람이 직접 매핑해야 했다.

@DynamicPropertySource
static void configureProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", mysql::getJdbcUrl);
    registry.add("spring.datasource.username", mysql::getUsername);
    registry.add("spring.datasource.password", mysql::getPassword);
}

이 방식의 문제는 프로퍼티 이름(spring.datasource.url 같은)을 문자열로 직접 타이핑해야 한다는 거다. spring.datasource.url을 spring.datasource.urls처럼 오타 내도 컴파일은 멀쩡히 되고, 테스트를 돌려봐야 연결이 안 되는 걸로 뒤늦게 알게 된다. 그리고 Redis, Kafka처럼 컨테이너 종류가 늘어날수록 이 매핑 코드도 그만큼 반복해서 늘어난다.

Spring Boot에서 이 문제를 정확히 짚어서 낸 게 @ServiceConnection이다. Spring Boot 3.1 공식 블로그 제목이 아예 Improved Testcontainers Support였을 정도로, 이 보일러플레이트를 없애는 게 이 기능이 나온 이유였다고 한다. 컨테이너 필드나 빈에 @ServiceConnection만 붙이면, 프로퍼티 이름 매핑 자체를 Spring이 컨테이너 타입을 보고 알아서 해준다.그리고 이 매핑 정보를 우리 코드가 아니라 Spring Boot가 들고 있으니, 나중에 Spring Boot 버전이 올라가면서 프로퍼티 이름이 바뀌어도 우리가 신경 쓸 일이 없어진다.

그래서 뒤에 나오는 방법들의 코드에 @ServiceConnection이 들어가 있는 거고, 상속하는 방법)에서도 필드에 그대로 붙이면 똑같이 쓸 수 있다.

사용 방법

상속 (Abstract 클래스)

공식 Testcontainers 문서에서 오래전부터 소개해온 방식이다. 추상 클래스에 static 초기화 블록으로 컨테이너를 딱 한 번만 띄우고, 각 테스트 클래스가 이 추상 클래스를 상속한다.

abstract class AbstractIntegrationTest {

    static final MySQLContainer<?> MYSQL;

    static {
        MYSQL = new MySQLContainer<>("mysql:8.0");
        MYSQL.start();   // 클래스가 로드될 때 딱 한 번 실행
    }
}

@SpringBootTest
class OrderControllerTest extends AbstractIntegrationTest {

    @Test
    void someTest() {
        // MYSQL은 이미 떠 있는 상태
    }
}

여기서 중요한 함정이 하나 있다. 이 패턴을 @Testcontainers/@Container 애노테이션과 같이 쓰면 안 된다. 정확한 이유를 따져보면 두 단계로 나뉜다.

첫 번째는, static 필드에 @Container를 붙이면 그 필드가 부모 클래스에 선언돼 있어도 Testcontainers Extension은 클래스 단위(per-class)로 생명주기를 관리한다는 거다. 그래서 이 부모 클래스를 상속한 자식 클래스가 실행될 때마다 컨테이너가 떴다가, 그 클래스가 끝나면 죽는 걸 반복한다. 여기까지는 Extension이 원래 그렇게 동작하도록 만들어진 거라 문제가 아니다.

진짜 문제는 두 번째 단계에서 생긴다. 컨테이너는 자식 클래스가 바뀔 때마다 새로 죽고 새로 뜨는데, Spring의 테스트 컨텍스트 캐싱(Context Caching) 메커니즘은 부모 클래스(설정)가 같으니 같은 ApplicationContext를 재사용해도 된다고 판단해버린다. 그래서 두 번째 자식 클래스는 이전 컨테이너의 접속 정보를 담고 있는, 이미 캐싱된 컨텍스트를 그대로 재사용하려고 하는데, 정작 그 컨테이너는 이미 죽고 새로운 컨테이너가 다른 포트로 떠 있는 상태다. 이 어긋남 때문에 연결 오류가 난다. 그래서 이 패턴은 애노테이션 없이, static 블록으로 직접 시작하고 멈추는 시점은 Testcontainers의 Ryuk 컨테이너가 JVM 종료 시점에 알아서 정리하도록 맡겨야 한다.

이 방식은 코드가 짧고 직관적이라 처음 배울 때 가장 이해하기 쉬웠다. 다만 자바는 클래스 다중 상속이 안 되기 때문에, 테스트 클래스가 이미 다른 베이스 클래스를 상속하고 있다면 이 패턴을 못 쓴다. 그리고 프로젝트가 커질수록 모든 통합 테스트는 이 거대한 베이스 클래스 하나를 상속하는 구조가 되기 쉬운데, 그러면 그 베이스 클래스가 점점 여러 컨테이너를 다 짊어지는 God class가 되기 쉬운 것 같다.

이 방식이 실제로 유리한 지점도 하나 있긴 하다. 순수하게 static 블록만으로 동작하기 때문에, Spring 컨텍스트가 아예 없어도 그대로 쓸 수 있다.Spring Bean을 쓰는 방법은 컨테이너를 빈으로 등록하는 방식이라 애초에 Spring 테스트 컨텍스트가 있어야 성립하는데, 이 방식은 순수 자바/JUnit 테스트에서도 그대로 동작한다. 다만 이것도 상속만의 고유한 장점은 아니다. 인터페이스를 사용하는 방법도 @ImportTestcontainers 없이 그냥 implements만 하는 거라면 똑같이 Spring 없이 동작한다. 그러니 정확히는 Spring 빈으로 관리하는 방식 vs 순수 Testcontainers 생명주기로 관리하는 방식(상속,인터페이스 컴포지션)의 차이지, 상속과 인터페이스 사이의 차이는 아니다. 초기화 로직을 자유롭게 짤 수 있다는 것 자체도 상속만의 장점은 아니다.

전역 공유 (Spring Bean으로 관리)

Spring Boot 공식 문서에서 제일 먼저 소개하는 방법이다. 컨테이너를 @TestConfiguration 클래스 안에 @Bean으로 등록하고, 필요한 테스트 클래스에서 @Import로 갖다 쓰는 방식이다. 상속이 아니라 합성(composition)이다.

@TestConfiguration(proxyBeanMethods = false)
class ContainerConfiguration {

    @Bean
    @ServiceConnection
    MySQLContainer<?> mysqlContainer() {
        return new MySQLContainer<>("mysql:8.0");
    }
}

@SpringBootTest
@Import(ContainerConfiguration.class)
class OrderControllerTest {

    @Test
    void someTest() { /* ... */ }
}

이 방식의 핵심은 컨테이너 생명주기를 Spring이 직접 관리하는 것이다. 컨테이너 빈은 다른 모든 빈보다 먼저 뜨고, 다른 모든 빈이 정리된 뒤에 내려간다. 그래서 상속으로 하는 방법에서 조심해야 했던 컨테이너는 죽었는데 캐싱된 컨텍스트가 그걸 참조하는 문제가 구조적으로 안 생긴다. Spring Boot 공식 문서도 애플리케이션 빈이 컨테이너 기능에 의존한다면 컨테이너를 Spring 빈으로 구성하는 쪽을 우선하라고 명시하고 있다.

다만 이것도 컴포넌트가 전역적으로 딱 하나만 뜬다는 게 코드에 명시적으로 보장된 장치는 아니다. 같은 @TestConfiguration을 @Import하는 테스트 클래스들끼리, Spring의 테스트 컨텍스트 캐싱 메커니즘(설정이 같으면 컨텍스트를 재사용하는 규칙) 덕분에 결과적으로 공유되는 것이다. 그래서 이 방식을 제대로 쓰려면 Spring 테스트 컨텍스트 캐싱이 어떻게 동작하는지를 어느 정도 알아야 하는 것 같다.

인터페이스 컴포지션

컨테이너를 인터페이스 안에 static 필드로 선언하고, 테스트 클래스가 그 인터페이스를 구현(implements)하는 방식이다.Spring Boot 공식 문서에 Testcontainers에서 흔히 쓰이는 패턴으로 그대로 소개되고있다.

interface MySqlTestContainer {

    @Container
    @ServiceConnection
    MySQLContainer<?> MYSQL = new MySQLContainer<>("mysql:8.0");
}

@ServiceConnection은 필드에도, @Bean 메서드에도 붙일 수 있는데, 이 둘이 완전히 동등하지는 않다는 걸 찾아보다 알게 됐다. @Bean 메서드 방식은 Spring이 그 메서드를 미리 호출해서 컨테이너 인스턴스를 들여다보지 않는다(호출하면 즉시 초기화 문제가 생기기 때문이라고 한다). 그래서 @Bean 방식은 메서드에 선언된 반환 타입만 보고 어떤 연결 정보를 만들지 판단한다. MySQLContainer처럼 타입 자체가 DB 종류를 말해주는 전용 클래스면 문제없지만, GenericContainer(Redis처럼 전용 클래스가 따로 없는 경우)를 반환 타입으로 쓰면 그 타입만으로는 안에 뭐가 들었는지 Spring이 알 방법이 없다.

반면 static 필드 방식(인터페이스 컴포지션 포함)은 이미 만들어진 인스턴스에 바로 접근할 수 있어서, Docker 이미지 이름의 레포지토리 부분(예: redis:7-alpine -> redis)을 보고 자동으로 추론해준다. 그래서 필드 방식에서는 웬만한 경우 별도 설정 없이도 잘 동작한다. 다만 이미지 이름이 표준적이지 않은 커스텀 이미지를 쓴다면, 필드 방식에서도 @ServiceConnection(name = "redis")처럼 name 속성으로 명시적으로 알려줘야 한다. @Bean 방식에서 GenericContainer를 꼭 써야 한다면 이 name 속성이 사실상 필수인 셈이다. (type 속성은 이것과는 다른 용도로, 여러 ConnectionDetails 후보 중 특정 타입으로 제한하고 싶을 때 쓰는 별도 옵션이다.)

컨테이너 종류에 따라서는 이렇게 인터페이스 컴포지션(필드 기반) 쪽이 오히려 Spring Bean 방식보다 더 안정적으로 동작하는 지점도 있는 셈이다.

@SpringBootTest
class OrderControllerTest implements MySqlTestContainer {

    @Test
    void someTest() { /* ... */ }
}

인터페이스는 자바에서 여러 개를 동시에 구현할 수 있다.그래서 MySqlTestContainer, KafkaTestContainer, RedisTestContainer처럼 컨테이너별로 인터페이스를 쪼개두면, 테스트 클래스는 자기가 필요한 것만 골라서 조합할 수 있다.

@SpringBootTest
class OrderServiceTest implements MySqlTestContainer, RedisTestContainer, KafkaTestContainer {

    @Test
    void someTest() { /* 세 컨테이너 다 사용 가능 */ }
}

상속 방식이었다면 MySQL만 필요한 테스트, MySQL+Redis가 필요한 테스트, 셋 다 필요한 테스트 등등 모든 테스트마다 조합별로 별도의 abstract 클래스를 계속 만들어야 했을 거다. 인터페이스는 그때그때 필요한 것만 implements에 나열하면 되니까, 조합이 늘어나도 새 클래스를 따로 안 만들어도 된다.

Spring 설정 클래스에서 이 인터페이스를 쓰고 싶다면 @ImportTestcontainers로 가져다 쓸 수도 있다. 이건 인터페이스에 선언된 static 필드들(컨테이너 필드, @DynamicPropertySource 메서드)을 Spring이 스캔해서 직접 빈으로 등록해주는 애노테이션이다.

@TestConfiguration(proxyBeanMethods = false)
@ImportTestcontainers(MySqlTestContainer.class)
class ContainerConfiguration {
}

이 방식은 조합의 자유도가 가장 높다는 게 장점인 것 같다. 다만 인터페이스에 static 필드로 선언하는 방식이다 보니, 필드 초기화 시점이나 인터페이스 여러 개를 동시에 구현했을 때 초기화 순서 같은 부분은 클래스 상속보다 살짝 덜 직관적으로 느껴질 수 있다.

중요한 내용 @ImportTestcontainers를 썼다고 해서 무조건 Spring이 생명주기를 관리해주는 게 아니다. 공식 문서에 정확히 이렇게 나와 있다. Testcontainers가 제공하는 애노테이션과 확장(@Testcontainers, @Container)을 함께 썼다면, 생명주기는 전적으로 Testcontainers가 관리한다. 즉, 인터페이스에 선언된 필드에 @Container가 붙어 있고, 테스트 클래스에 @Testcontainers 확장까지 같이 붙였다면, @ImportTestcontainers를 썼어도 상속하는 방법과 똑같이 클래스 단위로 껐다 켜는 생명주기를 그대로 물려받는다. 그러면 상속하는 방법에서 짚었던 Context Caching 어긋남이 인터페이스 방식에서도 똑같이 재현될 수 있다. @ImportTestcontainers의 진짜 이점(Spring이 관리하는 안전한 생명주기)을 온전히 받으려면, 테스트 클래스에 @Testcontainers 확장 애노테이션을 같이 붙이지 않아야 한다. 정리하면, 어떤 방식을 쓰든 결국 Context Caching의 규칙을 깨뜨리지 않는 구조여야 한다는 원칙 하나로 귀결된다. 상속이든 인터페이스든, 생명주기를 Testcontainers 확장에 맡기는 순간 이 위험을 안고 가는 거고, 생명주기를 Spring(정적 초기화 블록 + @ServiceConnection, @Bean, 또는 @Testcontainers 없는 @ImportTestcontainers)에 맡기면 이 위험에서 벗어난다.

withReuse

세 방식 중 뭘 쓰든, 별개로 컨테이너 자체를 테스트 스위트가 끝나도 계속 살려두는 옵션이 있다. .withReuse(true)를 걸고, 로컬 홈 디렉토리에 ~/.testcontainers.properties 파일을 만들어서 testcontainers.reuse.enable=true를 설정하면, Testcontainers가 정리 담당인 Ryuk 컨테이너를 아예 안 띄워서 컨테이너가 JVM이 끝나도 안 죽는다. 그러면 다음번 테스트 실행 때도 같은 설정이면 그 컨테이너를 그대로 재사용한다.

이건 앞의 세 패턴과는 다른 이야기다. 세 패턴이 같은 실행 안에서 여러 테스트 클래스가 공유하는가의 문제라면, withReuse는 테스트 실행 자체가 끝나도 컨테이너가 살아남는가의 문제다. 다만 이 기능은 아직 실험적(experimental)이고, 매번 새로운 환경에서 컨테이너를 새로 받는 CI 환경에는 안 맞는다고 한다. 로컬 개발 중 반복 실행 속도를 올리는 용도로 보는 게 맞는 것 같다.

MSA/멀티모듈에서는 어떻게?? (testFixtures)

여기까지는 한 모듈 안에서 테스트 클래스끼리 컨테이너를 공유하는 얘기였다. 근데 서비스가 여러 모듈(MSA면 서비스별 모듈)로 나뉘어 있으면, 이 컨테이너 정의(인터페이스 컴포지션이든 뭐든)를 모듈 하나에만 두고 다른 모듈들이 가져다 쓰고 싶을 때가 생긴다. 이럴 때 쓰는 게 Gradle의 java-test-fixtures 플러그인이다.

// libs/test-support/build.gradle.kts
plugins {
    id("java-test-fixtures")
}

dependencies {
    testFixturesApi("org.springframework.boot:spring-boot-starter-test")
    testFixturesApi("org.springframework.boot:spring-boot-testcontainers")   // @ServiceConnection, BOM 적용
    testFixturesApi("org.testcontainers:testcontainers")
    testFixturesApi("org.testcontainers:jdbc")
    testFixturesApi("org.testcontainers:junit-jupiter")
    testFixturesApi("org.testcontainers:mysql")
    testFixturesApi("org.testcontainers:kafka")
    testFixturesApi("org.testcontainers:mongodb")
    testFixturesApi("junit:junit")
    // .................
}

왜 그냥 test 소스셋에 두면 안 되나??

Gradle의 기본 test 소스셋은 그 모듈 안에서만 쓰라고 만들어진 거라, 다른 모듈이 의존성으로 끌어다 쓸 수가 없다. java-test-fixtures 플러그인을 적용하면 main, test와는 별개로 testFixtures라는 소스셋이 하나 더 생기는데(디렉토리는 src/testFixtures/java), 이건 처음부터 다른 모듈이 가져다 쓸 수 있게 만들어진 소스셋이다. 그래서 컨테이너 인터페이스 같은 재사용 코드는 test가 아니라 여기에 둔다.

왜 api를 써야하지?

testFixturesApi와 testFixturesImplementation 둘 다 있는데, 여기서는 전부 Api를 썼다. 이유는 이 모듈의 testFixtures가 다른 모듈에 노출해야 하는 타입을 다루기 때문이다. MySQLContainer, KafkaContainer 같은 타입을 가져다 쓰는 쪽(소비하는 모듈)의 코드에서 이 타입이 직접 보여야 하는데, testFixturesImplementation으로 선언하면 그 의존성이 밖으로 안 드러나서 소비하는 쪽에서 컴파일 에러가 난다. java-library 플러그인의 api/implementation 구분과 똑같은 원리다.

spring-boot-testcontainers를 넣은 이유는 @ServiceConnection을 쓰려면 이 모듈이 필요하기 때문이고, 주석에 적어둔 것처럼 여기서 Spring Boot의 BOM(의존성 버전 관리)도 같이 적용되니까 이 모듈에 기대는 다른 모듈들도 버전을 따로 안 맞춰도 된다는 이점이 있다.

쓰고싶은 쪽에서 사용 방법

// 다른 모듈의 build.gradle.kts
dependencies {
    testImplementation(testFixtures(project(":libs:test-support")))
}

testFixtures(project(...))라는 게 핵심이다. 그냥 project(":libs:test-support")라고만 쓰면 그 모듈의 main 소스셋(운영 코드)을 가져오는 거고, testFixtures(...)로 감싸야 그 모듈의 testFixtures 아티팩트를 가져온다. 그리고 이걸 받는 쪽에서 testImplementation으로 선언했으니, 이 모듈의 test 소스셋 안에서만 그 컨테이너 인터페이스를 쓸 수 있게 되는 거다.

유의할 점

  • java-test-fixtures 플러그인은 컨테이너를 두는 모듈에 적용해야 한다. 쓰는 쪽 모듈에는 이 플러그인이 필요 없고, 그냥 testFixtures(project(...))로 의존성만 추가하면 된다
  • 버전 정합성을 이 모듈이 책임지게 된다. 여러 서비스 모듈이 다 이 공유 모듈에 기대므로, Testcontainers나 Spring Boot 버전을 올릴 때 이 모듈 하나만 바꾸면 전체에 반영된다는 장점이 있지만, 반대로 이 모듈이 프로젝트 전체의 병목이 될 수도 있다
  • 컨테이너 생명주기 원칙은 그대로 적용된다. 공유 모듈에 인터페이스 컴포지션으로 정의해뒀다고 해도, 앞서 짚은 Context Caching 문제(@Testcontainers/@Container를 어떻게 조합하느냐)는 똑같이 적용된다. 여러 서비스 모듈이 같은 정의를 가져다 쓰는 거라, 이 정의 하나가 잘못돼 있으면 그 문제가 모든 소비 모듈에 그대로 퍼진다

그래서 뭐가 좋은걸까?

찾아본 바로는 이렇게 정리되는 것 같다.

  • 상속 방식은 역사적으로 가장 오래되고 널리 퍼진 방법이라, 예제나 블로그 글에서 여전히 제일 많이 보인다. 구현이 직관적이라 처음 배우기엔 좋다.
  • Spring Bean 방식은 공식 문서가 명시적으로 우선 권장하는 방법이다. 특히 애플리케이션 빈이 컨테이너 기능에 실제로 의존하는 상황(연결이 끊기면 안 되는 경우)이라면 이쪽이 생명주기 보장 면에서 제일 안전하다.
  • 인터페이스 컴포지션은 비교적 최근에 공식 문서에 정식으로 실린 패턴이고, 여러 컨테이너를 유연하게 조합해야 하는 프로젝트에서 점점 더 많이 채택되는 것 같다. 자바가 다중 상속을 지원하지 않는다는 근본적인 제약을 생각하면, 컨테이너 종류가 늘어날수록 상속보다 이쪽이 구조적으로 더 유리해 보인다.

결국 세 방식 다 공식적으로 문서화 된 방법이라는 것이다. 다만, 공식 문서가 미는 최신 방식이 항상 모든 상황에 우월한 건 아닌 것 같다. Spring 컨텍스트 없이 순수 Testcontainers만으로 동작한다는 특성은 상속과 인터페이스를 사용하는 방법 둘 다 공유하는 지점이고, 이건 Spring Bean 방법에는 없는 특징이다. 정답이 하나로 정해져 있다기보다는, Spring을 꼭 써야 하는지, 프로젝트가 컨테이너를 몇 종류나 쓰는지, 애플리케이션 빈이 그 컨테이너에 얼마나 밀접하게 의존하는지에 따라 고르면 될 것 같다.

정리

  • 매번 새로 띄우는 기본형은 테스트 클래스가 늘어날수록 반복 기동 비용이 쌓인다.
  • 상속은 직관적이지만 자바의 단일 상속 제약 때문에 유연성이 떨어지고, @Testcontainers/@Container 애노테이션과 같이 쓰면 안 된다는 함정이 있다.
  • **Spring Bean(전역 공유)**은 생명주기가 Spring 컨텍스트에 명시적으로 묶여서 가장 안전하지만, 진짜 공유 여부는 Spring의 테스트 컨텍스트 캐싱 규칙에 달려있다.
  • 인터페이스 컴포지션은 여러 컨테이너를 자유롭게 조합할 수 있고, Spring Boot 공식 문서에도 나온 정식 패턴이다.
  • withReuse(true)는 이 세 패턴과 별개로, 테스트 실행이 끝나도 컨테이너를 살려두는 실험적 옵션이다. -> CI에는 부적합

결국 세 방식 다 컨테이너를 어떻게 여러 테스트가 같이 쓰게 만들 것인가라는 같은 문제를 다른 자바 기능(상속, DI, 인터페이스)으로 푼 것뿐이라, 프로젝트 상황에 맞게 고르면 되는 것 같다.
