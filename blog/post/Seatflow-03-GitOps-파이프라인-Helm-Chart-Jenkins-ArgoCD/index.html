[Seatflow] 03. GitOps 파이프라인 Helm Chart + Jenkins + ArgoCD

Lab/SeatFlow · 2026-06-11

Intro

코드를 작성하고 푸시하면 자동으로 K8s에 배포되는 구조를 만들었다. 이번 편에서는 그 파이프라인 전체를 다룬다.
이미 기존에 GitOps 방식은 개인서버에서도 사용하고 있었기 떄문에 크게 어려움은 없었다.

간단하게 설명하자면, 크게 세 가지다. Helm Chart로 배포 명세를 관리하고, Jenkins가 이미지를 빌드해서 레지스트리에 올리고, ArgoCD Image Updater가 변경을 감지해서 ArgoCD가 K8s에 배포한다.

전체 흐름

git push (seatflow-msa)
    |
Jenkins
    변경된 서비스 감지
    Gradle 빌드
    Docker 이미지 빌드 (ARM64)
    GHCR push (tag: git-sha 앞 7자리)
    |
ArgoCD Image Updater
    GHCR 새 이미지 digest 감지
    deploy-manifests 레포 values.yaml image.tag 업데이트
    git commit + push
    |
ArgoCD
    deploy-manifests 레포 변경 감지
    K8s sync → 배포

코드 레포(seatflow-msa)와 매니페스트 레포(deploy-manifests)를 분리했다. 코드 레포에는 코드만, 매니페스트 레포에는 Helm Chart만 있다. 이게 GitOps의 핵심이다. 모든 인프라 상태가 Git에 기록된다.

Helm Chart 구성

ApplicationSet vs App of Apps

ArgoCD에서 여러 서비스를 관리하는 방법은 크게 두 가지다.

App of Apps: 루트 Application 하나가 나머지 Application들을 관리한다. 각 서비스마다 Application yaml 파일을 직접 작성한다. 서비스별로 세밀한 설정이 가능하지만 파일이 늘어난다.

ApplicationSet: 하나의 리소스로 여러 Application을 템플릿 기반으로 생성한다. 서비스 추가 시 elements에 한 줄만 추가하면 된다. 서비스 구조가 동일할 때 유리하다.

seatflow는 6개 서비스 구조가 거의 동일해서 ApplicationSet을 선택했다.

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: seatflow
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - service: show-service
          - service: auth-service
          - service: user-service
          - service: reservation-service
          - service: seat-service
          - service: payment-service
  template:
    metadata:
      name: 'seatflow-{{service}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/<YOUR_GITHUB>/deploy-manifests
        targetRevision: master
        path: 'seatflow/charts/{{service}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: seatflow
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true

{{service}}가 각 element의 값으로 치환된다. kubectl apply -f seatflow-applicationset.yaml -n argocd 한 번으로 6개 Application이 자동 생성된다.

values.yaml

서비스마다 다른 값들을 정의한다. 이미지 태그, 포트, 환경변수 키 목록이 핵심이다.

replicaCount: 1

image:
  repository: ghcr.io/<YOUR_GITHUB>/seatflow-show-service
  tag: 1.0.1
  pullPolicy: IfNotPresent

imagePullSecrets:
  - name: ghcr-secret

namespace: seatflow
appName: show-service

containerPort: 8086
managementPort: 9086

service:
  type: ClusterIP
  port: 8086

nodeSelector:
  kubernetes.io/arch: arm64 // oci arm서버에 올릴거라 arm 명시 필수

resources:
  requests:
    cpu: "50m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

deployment:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

secretName: show-service-secret

envKeys:
  - SPRING_DATA_MONGODB_URI

ingress:
  enabled: false
  path: /api/shows

envKeys가 중요하다. application.yml을 이미지에 포함하지 않고, 모든 설정을 K8s Secret에서 환경변수로 주입받는다. envKeys에 나열된 키들이 Secret에서 읽혀서 컨테이너 환경변수로 주입된다.

deployment.yaml

containers:
  - name: {{ .Values.appName }}
    image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
    env:
      - name: SERVER_PORT
        value: "{{ .Values.containerPort }}"
      - name: MANAGEMENT_SERVER_PORT
        value: "{{ .Values.managementPort }}"
      {{- range .Values.envKeys }}
      - name: {{ . }}
        valueFrom:
          secretKeyRef:
            name: {{ $.Values.secretName }}
            key: {{ . }}
      {{- end }}
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: {{ .Values.managementPort }}
      initialDelaySeconds: 60
      periodSeconds: 10
      failureThreshold: 5
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: {{ .Values.managementPort }}
      initialDelaySeconds: 30
      periodSeconds: 5
      failureThreshold: 5

SERVER_PORT와 MANAGEMENT_SERVER_PORT는 values.yaml에서 직접 주입한다. Secret이 아니라 values에서 가져오는 이유는 포트는 민감 정보가 아니고, 서비스마다 다른 값이 values.yaml에 이미 정의되어 있기 때문이다.

Pod Anti-Affinity

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - {{ .Values.appName }}
          topologyKey: kubernetes.io/hostname

preferredDuringScheduling은 강제가 아니라 선호다. 같은 앱의 Pod가 같은 노드에 배치되는 것을 피하되, 불가능하면 무시한다. 처음부터 분산 배치되도록 설정해두었다.

Jenkins 파이프라인

설계

모노레포 변경 감지: 푸시할 때마다 6개 서비스 전부 빌드하면 낭비다. git diff로 변경된 서비스만 빌드한다.

stage('Detect Changes') {
  steps {
    script {
      def changedFiles = sh(
        script: 'git diff --name-only HEAD~1 HEAD',
        returnStdout: true
      ).trim()

      env.BUILD_SHOW        = changedFiles.contains('services/show-service') ? 'true' : 'false'
      env.BUILD_AUTH        = changedFiles.contains('services/auth-service') ? 'true' : 'false'
      // ...
    }
  }
}

stage('Build show-service') {
  when { environment name: 'BUILD_SHOW', value: 'true' }
  // ...
}

services/show-service 하위 파일이 변경됐을 때만 해당 stage가 실행된다.

ARM64 빌드: K8s Worker 노드가 OCI ARM A1이다. Jenkins 빌드 Pod 자체를 ARM 노드에서 띄우면 별도 크로스 컴파일 설정 없이 ARM 이미지가 나온다.

spec:
  nodeSelector:
    kubernetes.io/arch: arm64

x86에서 ARM 이미지를 빌드하려면 QEMU가 필요하고 복잡해진다. 빌드 Pod를 ARM에서 띄우는 게 훨씬 단순하다.

Layered JAR: Spring Boot Layered JAR을 활용해 Docker 레이어 캐싱을 최적화한다. 코드만 바뀌면 application/ 레이어만 다시 빌드되고 나머지는 캐시에서 가져온다.

FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY build/libs/*.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./

ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Pod 구성

빌드 Pod에 컨테이너가 두 개 있다.

  • jdk: Gradle 빌드 담당. ./gradlew :services:show-service:bootJar
  • buildkitd: Docker 이미지 빌드 + GHCR push 담당

Jenkins는 이미지 빌드까지만 한다. 매니페스트 레포는 건드리지 않는다.

ArgoCD Image Updater

CRD 방식 (v1.1.1+)

ArgoCD Image Updater v1.1.1부터 어노테이션 방식 대신 CRD 방식으로 변경됐다.

apiVersion: argocd-image-updater.argoproj.io/v1alpha1
kind: ImageUpdater
metadata:
  name: seatflow-show-service
  namespace: argocd
spec:
  applicationRefs:
    - namePattern: seatflow-show-service
      images:
        - alias: app
          imageName: ghcr.io//seatflow-show-service
          commonUpdateSettings:
            updateStrategy: alphabetical
      writeBackConfig:
        method: git
        gitConfig:
          branch: master

이미지 태그 전략: Jenkins에서 IMAGE_TAG = "${env.GIT_COMMIT[0..6]}"으로 git commit sha 앞 7자리를 태그로 사용한다. abc1234 같은 형식이라 버전 숫자 비교가 불가능하다. 어떤 커밋이 배포됐는지 바로 추적할 수 있다는 장점이 있다.

updateStrategy

semver

  • 태그를 시맨틱 버전(1.0.0, 2.1.3)으로 인식해서 가장 높은 버전으로 업데이트
  • 1.0.x 형식 태그에 적합
  • git-sha 태그엔 사용 불가

digest

  • 태그는 그대로, 이미지 내용(sha256 digest)이 바뀌면 업데이트
  • latest 같은 고정 태그에 새 이미지를 계속 덮어쓰는 방식에 적합
  • git-sha처럼 매번 새 태그 생기는 방식엔 부적합

alphabetical

  • 태그 이름을 알파벳/사전순으로 비교해서 가장 마지막 태그로 업데이트
  • abc, bcd, xyz 순서로 비교
  • git-sha 태그는 사전순이 시간순과 다를 수 있어서 부정확할 수 있음

newest-build

  • 이미지 빌드 타임스탬프 기준으로 가장 최근에 빌드된 이미지로 업데이트
  • 태그 형식 무관
  • GHCR Private 레포에서 타임스탬프 메타데이터를 못 읽는 경우가 있음

writeBackTarget: helmvalues: 접두사로 Helm values 파일의 특정 키를 지정한다. Image Updater가 deploy-manifests 레포의 values.yaml에서 image.tag 값을 새 태그로 교체하고 자동으로 커밋한다. ArgoCD가 이 커밋을 감지해서 K8s에 sync한다.

Jenkins Pipeline에서  직접 Manifests 수정 방식으로 전환

Image Updater를 어느 정도 써보고 나서 Jenkins에서 직접 values.yaml을 수정하는 방식으로 전환했다.

Image Updater 방식 문제점

  • v1.1.x에서 writeBackTarget 경로 설정이 까다로움
  • manifestTargets 누락 시 .argocd-source- 파일로 fallback되어 values.yaml에 반영 안 됨
  • git-sha 태그 방식과 전략(semver/digest/alphabetical) 궁합 맞추기 번거로움
  • 파이프라인 흐름이 Jenkins → GHCR → Image Updater → ArgoCD로 분산되어 추적이 불편

Jenkins 직접 방식

stage('Update Manifest') {
  steps {
    withCredentials([usernamePassword(credentialsId: '', ...)]) {
      sh """
        git clone https://...@github.com/${repo}
        sed -i 's|tag:.*|tag: ${IMAGE_TAG}|' /tmp/${repo}/seatflow/charts/${svc}/values.yaml
        git commit -m "build: [seatflow - ${svc}] update image tags to ${IMAGE_TAG}"
        git push
      """
    }
  }
}

K8s Secret 관리

application.yml을 이미지에 포함하지 않는다. 모든 설정은 K8s Secret에서 환경변수로 주입받는다.

kubectl create secret generic show-service-secret \
  --from-literal=SPRING_DATA_MONGODB_URI="mongodb://..." \
  -n seatflow

JPA 서비스는 DB 연결 정보 외에 드라이버, Dialect 등도 환경변수로 넣어야 한다. application.yml 없이 Spring Boot가 뜨려면 JPA auto-configuration이 필요로 하는 설정이 전부 환경변수로 있어야 한다.

kubectl create secret generic payment-service-secret \
  --from-literal=SPRING_DATASOURCE_URL="jdbc:mysql://..." \
  --from-literal=SPRING_DATASOURCE_USERNAME="..." \
  --from-literal=SPRING_DATASOURCE_PASSWORD="..." \
  --from-literal=SPRING_DATASOURCE_DRIVER_CLASS_NAME="com.mysql.cj.jdbc.Driver" \
  --from-literal=SPRING_JPA_HIBERNATE_DDL_AUTO="validate" \
  --from-literal=SPRING_JPA_PROPERTIES_HIBERNATE_DIALECT="org.hibernate.dialect.MySQLDialect" \
  --from-literal=SPRING_THREADS_VIRTUAL_ENABLED="true" \
  --from-literal=SERVER_SHUTDOWN="graceful" \
  --from-literal=SPRING_KAFKA_BOOTSTRAP_SERVERS="..." \
  -n seatflow

Secret은 Git에 올리지 않는다. K8s 클러스터에만 존재한다.

Ingress 세팅

내 개인 서버에 nginx ingress controller가 이미 클러스터에 설치되어 있어서 별도 설치 없이 바로 사용했다.

kubectl get svc -n nginx-ingress
# nginx-ingress-ingress-nginx-controller   LoadBalancer   192.168.0.250   80:32337/TCP,443:31062/TCP

서비스마다 LoadBalancer를 붙이는 대신 Ingress 하나로 path 기반 라우팅을 구성했다. MetalLB IP를 아끼고 관리 포인트를 줄이기 위해서다.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: seatflow-ingress
  namespace: seatflow
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /api/shows
            pathType: Prefix
            backend:
              service:
                name: show-service
                port:
                  number: 8086
          - path: /api/users
            pathType: Prefix
            backend:
              service:
                name: user-service
                port:
                  number: 8082
          # 나머지 서비스 동일한 패턴

kubernetes.io/ingress.class 어노테이션 방식은 deprecated되었고 spec.ingressClassName을 사용해야 한다.

테스트:

curl http://192.168.0.250/api/users/3
# {"success":true,"data":{"id":3,"email":"test@test.com",...}}

이제 기본적인 CI/CD 구성은 끝냈다. 추후에는 manifests와 secret에 env값 추가나 배포 상태만 계속 확인하면 될 것으로 생각된다.
