[Seatflow] 08. 실시간 좌석 현황 SSE와 멀티 인스턴스 fanout

Lab/SeatFlow · 2026-06-26

Intro

지금 좌석 현황은 조회 API 하나로 끝난다.

@GetMapping("/{showId}")
public ... getSeats(@PathVariable String showId) {
    return seatService.getSeats(showId);   // 그 순간의 스냅샷
}

화면 들어올 때 한 번 불러서 좌석 배치도를 그리는 건데, 문제는 이게 그 순간의 스냅샷이라는 거다. 내가 화면 보는 동안 옆 사람이 5번을 잡아도 내 화면엔 여전히 비어 보이고, 내가 5번을 누르는 순간에야 "이미 점유됨"이 뜬다. 티켓팅에서 제일 답답한 그 경험이다.

그래서 이번 편은 좌석이 바뀌면 보고 있는 사람 화면에 바로 반영되게 만든다. 방식은 SSE를 골랐고, 인스턴스가 여러 개일 때 깨지는 문제를 Redis Pub/Sub으로 풀었다.

왜 SSE로 했나??

실시간을 만드는 길은 폴링, WebSocket, SSE가 있다. 간단히만 보면:

  • 폴링 - 몇 초마다 조회 반복. 안 바뀌어도 계속 요청을 쏘고, 주기만큼 늦다.
  • WebSocket - 양방향. 채팅·협업처럼 클라도 서버로 수시로 보내야 할 때.
  • SSE - 서버 -> 클라 단방향 push. 연결을 열어두고 바뀔 때만 밀어준다.

좌석 현황은 서버가 클라에 일방적으로 알려주기만 하면 된다. 좌석을 잡고 푸는 건(클라 -> 서버) 이미 REST(/hold, /release)로 한다. 클라가 그 연결로 서버에 보낼 게 없으니 WebSocket의 양방향은 안 쓰는 기능이 된다. 그래서 단방향 push인 SSE로 갔다. 그냥 HTTP라 별도 프로토콜·라이브러리도 없고 브라우저 자동 재연결도 공짜다.

한 인스턴스 SSE

SSE는 두 조각이다**.** 연결을 보관하고(열어둔 채 들고 있기), 좌석이 바뀌면 그 연결에 push하기.

연결 보관은 인메모리로 한다. show별로 연결(SseEmitter)을 모아둔다.

@Component
public class SeatEmitterStore {
    private final Map<String, List<SseEmitter>> emitters = new ConcurrentHashMap<>();

    public SseEmitter create(String showId) {
        SseEmitter emitter = new SseEmitter(30 * 60 * 1000L);
        emitters.computeIfAbsent(showId, k -> new CopyOnWriteArrayList<>()).add(emitter);
        emitter.onCompletion(() -> remove(showId, emitter));   // 끝나면 정리 (메모리 누수 방지)
        emitter.onTimeout(() -> remove(showId, emitter));
        emitter.onError(e -> remove(showId, emitter));
        return emitter;
    }
    public List<SseEmitter> findByShowId(String showId) { return emitters.getOrDefault(showId, List.of()); }
    public void remove(String showId, SseEmitter e) { /* ... */ }
}

구독 엔드포인트는 이 연결을 만들어 돌려주기만 한다.

@GetMapping(value = "/{showId}/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter streamSeats(@PathVariable String showId) {
    return seatEmitterStore.create(showId);
}

text/event-stream으로 응답하면 스프링이 연결을 안 끊고 열어둔다. 

점유 로직 변경

7편에서 좌석 점유는 Redis로 끝났다. 단일은 SET NX, 멀티는 Lua로 원자적으로 잡고, 그게 전부였다. 흐름이 이랬다.

[7편]  hold 요청 -> Redis 점유(SET NX / Lua) -> DB 검증 -> 끝

점유에 성공해도 그 사실은 점유한 사람만 안다. 같은 좌석을 보고 있는 다른 사람들은 모른다. 

[8편]  hold 요청 -> Redis 점유(SET NX / Lua) ->DB 검증
                -> "좌석 상태 바뀜" 발행       <- 추가된 부분
                -> (구독자들에게 SSE push)

점유 로직(7편) 자체는 안 건드렸다. 그 성공 뒤에 발행 한 줄을 얹었을 뿐이다. release도 마찬가지로, 점유 해제에 성공하면 "AVAILABLE로 바뀜"을 발행한다.

직접 호출 대신 이벤트로

여기서 한 가지 정한 게 있다. 좌석이 바뀌는 건 SeatService인데, 거기서 SSE 전송을 직접 부르면 비즈니스 로직이 전송 수단을 알게 된다. 점유 로직과 SSE가 묶이는 거다.

그래서 SeatService는 좌석 상태가 바뀐 사실만 발행하고, SSE는 그 사실을 구독해서 알아서 전송하게 했다. 스프링의ApplicationEventPublisher를 쓴다.

// SeatService: 점유 성공 후, 사실만 발행 (SSE를 모름)
seatIds.forEach(id ->
    eventPublisher.publishEvent(new SeatStatusChangedEvent(showId, id, "HELD")));

// 듣는 쪽: 커밋된 뒤에만 동작
@TransactionalEventListener(phase = AFTER_COMMIT)
public void onSeatStatusChanged(SeatStatusChangedEvent event) { ... }

이러면 점유 로직은 누가 듣는지 모른다. 나중에 점유되면 알림도 보내자가 생겨도 리스너만 하나 더 붙이면 되고 점유 로직은 안 바뀐다. AFTER_COMMIT을 쓴 건, 점유가 롤백됐는데 마치 된거처럼 알리는걸 막으려고 사용했다.

여기까지 하면 한 인스턴스에선 잘 된다. 터미널 하나로 /stream 구독하고 다른 터미널로 hold하면, 구독한 쪽에 seat-update가 즉시 뜬다.

인스턴스가 여러 개면 깨진다

문제는 실제 배포는 인스턴스를 여러 개 띄운다는 거다. 그러면 이 그림이 나온다.

구독(/stream) -> 로드밸런서 -> 인스턴스 A   [연결은 A의 메모리에]
hold 요청     -> 로드밸런서 -> 인스턴스 B   [이벤트는 B 안에서만]

연결은 A의 인메모리 SeatEmitterStore에 있는데, hold는 B가 처리한다. B가 발행한 SeatStatusChangedEvent는 B 프로세스 안에서만 돈다(ApplicationEventPublisher는 같은 프로세스 한정). B의 Store엔 그 연결이 없으니 아무에게도 push가 안 가고, A에 매달린 연결은 영영 못 받는다.

인메모리 보관소는 그 프로세스 안에서만 보인다. A의 연결을 B는 모른다. 그래서 어느 인스턴스에서 좌석이 바뀌든, 그 사실을 모든 인스턴스에 전파(fanout)해서 각자 자기 연결에 push하게 해야 한다.

Redis Pub/Sub으로 fanout

전파를 뭘로 하느냐가 다음 결정이다. 후보는 Redis Pub/Sub과 Kafka.

좌석 현황 push는 놓쳐도 치명적이지 않다.

연결이 잠깐 끊겨 "5번 잡힘"을 한 번 못 받아도, 재연결하거나 조회 API로 현재 상태를 다시 받으면 된다. 마지막 상태만 맞으면 되지 중간 변화를 하나도 안 놓치는 게 중요한 게 아니다. 그래서 Kafka의 영속성·순서보장·재처리는 이 용도엔 과하다. fire-and-forget인 Redis Pub/Sub으로 갔다. (Kafka는 결제·예약 같은 돈 걸린 흐름에 계속 쓰고, UI fanout만 Redis로 간다.)

구조는 이렇게 바뀐다. 로컬 broadcast를 없애고, 모든 인스턴스가 "Redis에서 받아서 자기 연결에 push"로 통일한다.

B: 좌석 바뀜 -> SeatStatusChangedEvent(AFTER_COMMIT)
   -> Redis 채널 "seat:updates"에 publish
        -> (Redis가 모든 인스턴스에 전달, 자기 자신 포함)
A, B, ...: 채널에서 받음 -> 자기 EmitterStore의 연결들에 SSE push

발행:

@TransactionalEventListener(phase = AFTER_COMMIT)
public void publish(SeatStatusChangedEvent event) {
    redisTemplate.convertAndSend("seat:updates", objectMapper.writeValueAsString(event));
}

구독:

public class SeatUpdateSubscriber implements MessageListener {
    public void onMessage(Message message, byte[] pattern) {
        SeatStatusChangedEvent event = objectMapper.readValue(message.getBody(), ...);
        for (SseEmitter emitter : store.findByShowId(event.showId())) {
            emitter.send(SseEmitter.event().name("seat-update").data(...));
        }
    }
}

이렇게 하면 hold를 처리한 인스턴스도 Redis 한 바퀴 돌아서 자기 연결에 쏜다. 모든 인스턴스가 똑같이 "Redis에서 받아 push"라 동작이 통일된다.

이제 점유부터 화면까지 전체 흐름을 다시 그리면 이렇다. 7편의 점유 위에, 8편의 발행→전파→push가 얹힌 모양이다.

hold 요청 → Redis 점유(SET NX / Lua)        ← 7편
         → DB 검증
         → SeatStatusChangedEvent 발행(커밋 후)  ← 8편 (로컬 발행)
         → Redis 채널 publish                    ← 8편 (인스턴스 간 전파)
         → 각 인스턴스가 받아 SSE push            ← 8편 (브라우저까지)

Redis Cluster의 일반 PUBLISH는 클러스터 전체 노드로 퍼져서, 어느 노드에 붙은 구독자든 다 받는다. 그래서 단일 채널 fanout이 클러스터에서도 동작한다.

테스트

인스턴스 두 개를 같은 Redis로 띄운다(8084, 8085).

# 8084에 구독
curl -N http://localhost:8084/api/seats/show1/stream

# 8085로 hold (연결은 8084에, 요청은 8085에)
curl -X POST http://localhost:8085/api/seats/show1/hold \
  -H 'Content-Type: application/json' -H 'X-User-Id: userA' -d '{"seatIds":[3]}'

event:seat-update
data:{"seatId":3,"status":"HELD"}

연결은 8084에 있고 hold는 8085가 처리했는데 8084에 떴다. fanout이 없었으면 8085의 이벤트는 8085 안에서만 돌아서 8084는 못 받았을 거다. 인메모리 보관소는 프로세스 경계를 못 넘으니까. Redis Pub/Sub이 그 경계를 넘겨준 것이다.

NEXT

지금은 변화만 push한다. 실제로는 두 가지가 더 필요한데, 필요해지는 시점에 붙일 예정이다.

  • 구독 시 현재 상태 1회 전송 막 연결한 클라가 화면을 그리려면 "지금 좌석 현황"을 한 번 받아야 한다. 지금은 변화만 보내서 초기 그림이 없다.
  • heartbeat  오래 조용하면 중간 프록시가 연결을 끊을 수 있어, 주기적 더미 이벤트로 살아있음을 알린다.
  • per-show 채널 지금은 단일 채널이라 모든 인스턴스가 모든 show의 이벤트를 받아 거른다. show별 채널로 좁히면 불필요한 수신이 준다.
