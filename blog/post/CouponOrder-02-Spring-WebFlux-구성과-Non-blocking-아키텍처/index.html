Lab/Coupon&Order · 2026-04-18

Intro

  • 1편에서 왜 WebFlux를 선택했는지 이유를 설명했다면, 이번 편에서는 WebFlux가 실제로 어떻게 동작하는지 살펴본다.
  • MVC와의 차이점, Reactor의 핵심 개념, 그리고 Non-blocking 체인이 어떻게 구성되는지 코드와 함께 정리한다.

MVC vs WebFlux

  • Spring MVC는 Thread-per-Request 모델이다. 요청이 들어오면 스레드 풀에서 스레드를 하나 꺼내 요청이 끝날 때까지 붙잡고 있는다.
요청 -> 스레드 할당 -> DB 조회 (대기) -> 응답 -> 스레드 반환
               ↑
        DB 응답 올 때까지 스레드가 블로킹
  • 동시 요청이 수천 건이 되면 스레드 풀이 고갈되고, 새 요청은 큐에서 대기하거나 거절된다.
  • 반면 Spring WebFlux는 Event Loop 모델이다. 소수의 스레드(CPU 코어 수)로 수만 건의 요청을 처리할 수 있다.
요청 -> 이벤트 루프 -> DB 조회 요청 후 즉시 반환 -> 다른 요청 처리
                                    ↓
                         DB 응답 오면 콜백으로 처리
  • I/O 대기 시간에 스레드를 낭비하지 않기 때문에 처리량이 훨씬 높다.

CompletableFuture

  • 먼저 WebFlux 이전에도 Java에서 비동기 처리를 할 수 있는 방법이 있었다. 바로 CompletableFuture다.
// CompletableFuture 예시
CompletableFuture<User> future = CompletableFuture.supplyAsync(() -> {
  return userRepository.findById(1L); // 별도 스레드에서 실행
});

// 변환  
CompletableFuture<UserResponse> response = future.thenApply(UserResponse::from);

// 체이닝  
CompletableFuture<Order> order = future  
    .thenApplyAsync(user -> orderRepository.findByUserId(user.getId()))  
    .thenApply(orders -> orders.get(0));
  • Mono/Flux와 비슷해 보이지만 핵심적인 차이가 있다.
    • CompletableFuture는 스레드 풀에서 별도 스레드를 꺼내 비동기로 실행하는 방식이다. 결국 스레드를 쓰기 때문에 요청이 많아지면 스레드 풀 고갈 문제가 여전히 발생할 수 있다.
    • 반면 Reactor(Mono/Flux)는 이벤트 루프 기반으로 스레드 자체를 점유하지 않는다.
// CompletableFuture -> 스레드 풀에서 스레드 꺼내서 실행
CompletableFuture.supplyAsync(() -> heavyTask(), threadPool);

// Mono -> 이벤트 루프에서 콜백으로 처리  
Mono.fromCallable(() -> heavyTask())  
    .subscribeOn(Schedulers.boundedElastic());

CompletableFuture vs Mono/Flux

  • CompletableFuture와 Mono/Flux는 둘 다 비동기 처리를 한다는 점에서 비슷해 보이지만, 몇 가지 핵심적인 차이가 있다.
  • 데이터 개수
    • CompletableFuture는 단 하나의 결과만 처리할 수 있다.
    • Flux는 0개부터 N개까지 스트림으로 처리할 수 있다.
  • 취소 (Cancellation)
    • CompletableFuture는 cancel()을 호출해도 이미 실행 중인 작업을 실제로 멈추지 못하는 경우가 많다.
    • Reactor의 Mono/Flux는 구독을 취소하면 체인 전체가 정리된다.
CompletableFuture<User> future = CompletableFuture.supplyAsync(() -> {
    return heavyTask();
});

future.cancel(true); // 실제로 멈춘다는 보장이 없음
  • 백프레셔 (Backpressure)
    • 소비자가 처리 가능한 만큼만 데이터를 요청하는 메커니즘
    • CompletableFuture는 지원하지 않음
// CompletableFuture -> 100만 건을 한 번에 메모리에 올림 (OOM 위험)
CompletableFuture<List<User>> future =
    CompletableFuture.supplyAsync(() -> userRepository.findAll());

// Flux -> 소비자가 처리할 수 있는 만큼만 요청
userRepository.findAll()
    .buffer(100)
    .flatMap(batch -> processBatch(batch))
    .subscribe();

Reactor(Mono와 Flux)

  • WebFlux의 핵심은 Reactor 라이브러리다. 비동기 데이터 스트림을 선언적으로 처리할 수 있다.

Mono

  • 0 또는 1개의 데이터를 비동기로 처리한다.
// 단건 조회
Mono<User> user = userRepository.findById(1L);

// 변환
Mono<UserResponse> response = user.map(UserResponse::from);

// 에러 처리
Mono<User> result = userRepository.findById(1L)
    .switchIfEmpty(Mono.error(new BusinessException(ErrorCode.USER_NOT_FOUND)));

Flux

  • 0 또는 N개의 데이터를 비동기로 처리한다.
// 전체 조회  
Flux<Coupon> coupons = couponRepository.findAll();

// 변환  
Flux<CouponResponse> responses = coupons.map(CouponResponse::from);

flatMap vs map

// map -> 동기 변환 (값 -> 값)
Mono<String> name = userMono.map(user -> user.getUsername());

// flatMap -> 비동기 변환 (값 -> Mono)
Mono<Order> order = userMono.flatMap(
    user -> orderRepository.findByUserId(user.getId())
);
  • flatMap은 내부에서 또 다른 비동기 작업이 필요할 때 사용한다. Non-blocking 체인의 핵심이다.

Non-blocking 체인 구성

  • WebFlux에서는 여러 비동기 작업을 체인으로 연결한다.
public Mono<CouponIssue> issueCoupon(Long couponId, Long userId) {
    return reactiveRedisTemplate.execute(
            RedisScript.of(ISSUE_COUPON_SCRIPT, Long.class),
            keys,
            List.of(String.valueOf(userId))
        )
        .next()
        .flatMap(result -> {
            if (result == 0L) {
                return Mono.error(
                    new BusinessException(ErrorCode.COUPON_ALREADY_ISSUED)
                );
            }
            if (result == -1L) {
                return Mono.error(
                    new BusinessException(ErrorCode.COUPON_OUT_OF_STOCK)
                );
            }
            return couponIssueRepository.save(
                CouponIssue.builder()
                    .couponId(couponId)
                    .userId(userId)
                    .build()
            );
        });
}
  • 이 코드에서 스레드는 블로킹되지 않는다. Redis 응답을 기다리는 동안 다른 요청을 처리하고, 응답이 오면 콜백으로 이어서 처리한다.

Netty(내장 서버)

  • Spring MVC의 기본 서버가 Tomcat이라면, WebFlux의 기본 서버는 Netty다.
  • Netty는 Event Loop 기반의 비동기 네트워크 프레임워크다.
Client 요청
    │
    ▼
Netty (Event Loop)
    │
    ├── Boss Group: 연결 수락
    └── Worker Group: 실제 처리 (CPU 코어 수 × 2)
  • 별도 설정 없이 spring-boot-starter-webflux 의존성만 추가하면 Netty가 기본으로 동작한다.

R2DBC(Non-blocking DB 연결)

  • JPA는 블로킹 방식이라 WebFlux와 함께 쓰면 이벤트 루프를 블로킹해버린다.
// JPA (블로킹)
User user = userRepository.findById(1L);

// R2DBC (Non-blocking)
Mono<User> user = userRepository.findById(1L);
  • JPA와 다른 점은 연관관계 매핑이 없다는 것이다.
orderRepository.findById(orderId)
    .flatMap(order ->
        Mono.zip(
            userRepository.findById(order.getUserId()),
            productRepository.findById(order.getProductId())
        )
        .map(tuple ->
            new OrderDetailResponse(order, tuple.getT1(), tuple.getT2())
        )
    );

블로킹 코드 금지!!

  • 이벤트 루프 스레드를 블로킹하면 전체 처리량이 급격히 떨어진다.
// 잘못된 코드
public Mono<User> findUser(Long id) {
    Thread.sleep(1000);
    return userRepository.findById(id);
}

// 올바른 코드
public Mono<User> findUser(Long id) {
    return userRepository.findById(id)
        .delayElement(Duration.ofSeconds(1));
}

그래서 언제 어떻게 해야하지?

WebFlux가 항상 정답은 아니다.

  • MVC
    • 직관적
    • 디버깅 쉬움
    • 유지보수 용이
  • WebFlux
    • 비동기 I/O에 강함
    • 연결 수 많을 때 유리
  • CompletableFuture 사용 시점
    • 기존 MVC 유지하면서 일부 병렬 처리
  • WebFlux 사용 시점
    • SSE / WebSocket
    • I/O 중심 서비스
    • 높은 동시성 요구
  • 핵심 기준은 “트래픽”이 아니라 “I/O 대기 시간”이다.
