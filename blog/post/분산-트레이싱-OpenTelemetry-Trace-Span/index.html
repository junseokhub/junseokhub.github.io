분산 트레이싱 (OpenTelemetry, Trace, Span)

Devops · 2026-09-20

Intro

서비스가 여러 개로 나뉘고 나니, 요청 하나가 느려졌을 때 어느 서비스에서 시간을 잡아먹었는지 알아내는 게 훨씬 어려워졌다. 각 서비스의 로그를 따로 열어서 타임스탬프를 손으로 맞춰보는 건 금방 한계에 부딪혔다. 이 문제를 풀려고 나온 게 분산 트레이싱이고, 그 표준으로 자리잡은 게 OpenTelemetry라는 것까지는 알았는데, trace와 span이 정확히 뭐고 서비스 경계를 어떻게 넘나드는지는 따로 짚어봐야 했다.

Trace와 Span

Span

Span은 무언가 한 덩어리의 작업이 언제 시작해서 언제 끝났는지를 기록하는 단위다. HTTP 요청 처리 하나, DB 쿼리 하나, 외부 API 호출 하나가 각각 하나의 span이 될 수 있다.

Span
 ㄴ span id: 고유 식별자
 ㄴ 이름: "GET /orders" 같은 작업 이름
 ㄴ 시작 시각 / 종료 시각
 ㄴ 부모 span id: 이 작업을 누가 호출해서 시작됐는지

Trace

하나의 요청이 여러 서비스, 여러 작업을 거치면 그만큼 span이 여러 개 생긴다. 이 span들이 전부 같은 trace id를 공유하면서, 부모-자식 관계로 엮여 하나의 트리를 이룬다. 이 트리 전체를 trace라고 부른다.

[trace id: abc123]
Span: API Gateway 처리 (0ms ~ 120ms)
  ㄴ Span: Order Service 호출 (5ms ~ 118ms)
       ㄴ Span: DB 쿼리 (10ms ~ 25ms)
       ㄴ Span: Inventory Service 호출 (30ms ~ 110ms)
            ㄴ Span: DB 쿼리 (35ms ~ 105ms)   <- 여기가 제일 오래 걸림

이 구조 덕분에 전체 120ms 중 어느 구간이 얼마나 걸렸는지, 그리고 그 구간이 어느 서비스의 어떤 작업이었는지가 트리 형태로 한눈에 드러난다.

Context Propagation

문제는 각 서비스가 독립된 프로세스라는 거다. Order Service가 만든 span과 Inventory Service가 만든 span이 같은 trace의 일부라는 걸 어떻게 서로 알 수 있을까?

답은 trace의 맥락 정보를 요청과 함께 전달하는 것이다. 서비스 A가 서비스 B를 호출할 때, 지금 진행 중인 trace id와 현재 span id를 HTTP 헤더에 실어서 같이 보낸다. 이걸 표준화한 게 W3C Trace Context 규격이고, 보통 traceparent라는 헤더로 전달된다.

traceparent: 00-abc123...-span456...-01
             ㅣ  ㅣ           ㅣ           ㅣ
           버전 trace id   부모 span id  플래그(샘플링 여부 등)

[서비스 A]                          [서비스 B]
주문 처리 시작 span 생성
  ㄴ HTTP 호출 (traceparent 헤더에 trace id + 현재 span id 실어 보냄)
                                       ㅣ
                                 헤더를 읽어서 같은 trace id로
                                 새 span을 생성, 부모를 A의 span으로 설정

이 전파가 안 되면, 각 서비스는 자기만의 독립된 trace를 만들게 되고, 하나의 요청이 여러 조각으로 끊어져 보인다. 그래서 분산 트레이싱이 제대로 동작하려면 서비스 간 호출(HTTP 클라이언트, 메시지 발행 등) 전부가 이 맥락 전파를 지원해야 한다.

OpenTelemetry

예전에는 트레이싱 도구(Zipkin, Jaeger 등)마다 각자의 방식으로 애플리케이션에 계측 코드를 심어야 했다. 그러다 보니 도구를 바꾸면 계측 코드도 다시 짜야 하는 문제가 있었다. OpenTelemetry는 이 계측 방식 자체를 표준화한 것이다. 애플리케이션은 OpenTelemetry의 API/SDK로 trace와 span을 만들고, 그걸 어디로 보낼지는 나중에 설정만 바꾸면 된다.

@Service
public class OrderService {

    private final Tracer tracer;

    public void processOrder(String orderId) {
        Span span = tracer.spanBuilder("process-order").startSpan();
        try (Scope scope = span.makeCurrent()) {
            // 처리 로직
            span.setAttribute("order.id", orderId);
        } finally {
            span.end();
        }
    }
}

Spring 환경에서는 보통 이런 span 생성 코드를 다 직접 짜지 않아도 된다. Micrometer Tracing이 OpenTelemetry와 연동되면서, HTTP 요청 처리나 DB 호출 같은 흔한 작업에 대해 자동으로 span을 만들어준다. 직접 span을 만드는 코드는 비즈니스적으로 의미 있는 구간(예: 복잡한 계산 로직 하나)을 별도로 추적하고 싶을 때 정도만 필요한 것 같다.

OpenTelemetry로 만들어진 span 데이터는 OTLP(OpenTelemetry Protocol)라는 공통 포맷으로 내보내지고, 이걸 수집하는 Collector를 거쳐 실제로 보여주는 백엔드(Jaeger, Zipkin, Grafana Tempo 등)로 전달된다.

애플리케이션 (OpenTelemetry SDK) -> OTLP -> Collector -> 트레이싱 백엔드(Jaeger 등) -> 대시보드

계측 표준과 보여주는 백엔드가 분리돼 있어서, 나중에 백엔드를 바꾸더라도 애플리케이션의 계측 코드는 그대로 둘 수 있다는 게 이 구조의 장점인 것 같다.

샘플링

trace를 하나도 빠짐없이 다 기록하면 그만큼 오버헤드와 저장 비용이 커진다. 그래서 보통 일부 요청만 골라서 추적하는 샘플링을 쓴다.

  • Head-based 샘플링
    • 요청이 시작되는 시점에 미리 이 요청을 추적할지 말지를 정한다. 구현이 간단하지만, 나중에 알고 보니 에러가 났던 요청인데 처음부터 샘플링 대상이 아니어서 못 잡은 경우가 생길 수 있다.
  • Tail-based 샘플링
    • 요청이 다 끝난 뒤에 이 요청이 느렸는지, 에러가 났는지를 보고 나서 추적 여부를 정한다. 문제가 있었던 요청을 놓치지 않고 잡을 수 있지만, 끝날 때까지 모든 span 정보를 어딘가에 잠깐 들고 있어야 해서 구조가 더 복잡하다.

정상적인 요청은 낮은 비율로만 샘플링하고, 에러가 나거나 느린 요청은 우선적으로 잡아내고 싶다면 tail-based 쪽이 유리하지만, 그만큼 인프라 구성이 더 필요해진다.

정리

  • Span은 작업 하나의 시작과 끝을 기록하는 단위이며, Trace는 그 span들이 부모-자식 관계로 엮여 이루는 요청 전체의 여정이다.
  • 서비스 경계를 넘어 trace id를 유지하려면 요청과 함께 맥락 정보를 전달해야 한다(Context Propagation, traceparent 헤더).
  • OpenTelemetry는 이 계측 방식을 표준화해서, 애플리케이션 코드는 그대로 두고 트레이싱 백엔드만 바꿀 수 있게 해준다.
  • 모든 요청을 다 추적하면 비용이 커서, 보통 일부만 샘플링한다.
    • 문제 있는 요청을 놓치지 않으려면 tail-based 샘플링이 유리하지만 그만큼 구조가 복잡해진다.

로그를 여러 서비스에서 손으로 짜맞추던 걸 생각하면, trace id 하나로 전체 여정이 트리로 이어져 보이는 게 훨씬 낫다는 걸 알게 됐다. 다만 이게 자동으로 되는 게 아니라 서비스 간 호출마다 맥락이 제대로 전파되고 있는지를 신경 써야 한다는 것도 같이 알게 됐다.
