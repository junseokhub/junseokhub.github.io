동시성 테스트 (레이어별 도구와 실전 설정)

Test · 2026-09-27

Intro

락을 걸고, 원자적 연산을 쓰고, 버전 번호로 충돌을 막는 코드를 짜놓고 나면 한 가지 질문이 남는다. 이게 진짜로 동시에 요청이 몰렸을 때도 막아주는가. 단위 테스트는 요청을 하나씩 순서대로 실행하니까 race condition이 있어도 절대 안 드러난다. 동시성 코드는 동시에 실행해봐야만 검증이 된다.

찾아보니 동시성 테스트 도구는 생각보다 많았고, 각 도구가 검증하는 레이어가 완전히 달랐다. 이 글은 레이어별로 어떤 도구가 있는지, 그리고 각 도구를 실제로 설치하고 스크립트를 짜고 실행해서 결과를 확인하는 데까지 따라 할 수 있게 정리해 볼 것이다.

동시성 테스트는 무엇을 검증할까?

부하 테스트와 헷갈리기 쉬운데, 목적이 다르다. 부하 테스트는 성능(응답 시간, 처리량)을 재고, 동시성 테스트는 정합성을 확인한다. 그래서 합격 기준도 응답 시간이 아니라 불변식이 된다.

  • 재고 100개에 200명이 동시에 구매하면, 성공은 정확히 100건이고 재고는 0이어야 한다.
  • 같은 요청이 동시에 두 번 들어와도, 결과는 한 번 처리한 것과 같아야 한다.
  • 한도가 있는 카운터는 동시 요청이 몰려도 한도를 넘지 않아야 한다.

어떤 도구를 쓰든 테스트의 뼈대는 같다.

1. 초기 상태를 만든다        (재고 100개)
2. 최대한 동시에 요청을 보낸다 (200명이 동시에 구매)
3. 최종 상태로 불변식을 검증한다 (성공 100건, 재고 0, 음수 없음)

도구마다 다른 건 2번을 얼마나 정확하게 동시에 만들어주는지, 그리고 그 요청이 어느 레이어를 거치는지다.

네 개의 레이어

동시성 문제는 어느 레이어에서 경합이 일어나느냐에 따라 잡을 수 있는 도구가 달라진다.

[레이어 4] 분산 시스템 자체     DB/브로커가 네트워크 분리 속에서 일관성을 지키나?   -> Jepsen
[레이어 3] 스레드 인터리빙       락 없는 저수준 코드가 모든 실행 순서에서 맞나?    -> JCStress, Lincheck
[레이어 2] 전체 요청 경로        게이트웨이/로드밸런서/여러 인스턴스를 거쳐도 맞나?  -> Gatling, JMeter, k6, Locust
[레이어 1] JVM 안의 서비스 로직  서비스 빈을 여러 스레드가 동시에 호출해도 맞나?    -> JUnit + ExecutorService 등

일반적인 Spring 서비스 개발에서 주력은 레이어 1과 2다. 레이어 1로 서비스 로직의 경합을 빠르게 잡고, 레이어 2로 실제 배포 구조에서만 드러나는 경합을 확인한다. 레이어 3은 락 없이 직접 짠 동시성 자료구조가 있을 때, 레이어 4는 인프라 자체를 검증할 때 필요하다.

레이어 1 (JVM 안에서 서비스 로직 검증하기)

ExecutorService + CountDownLatch

스레드 풀로 여러 작업을 동시에 실행하고, CountDownLatch로 출발 시점을 맞춘다.

@SpringBootTest
class PurchaseConcurrencyTest {

    private static final int STOCK = 50;
    private static final int THREAD_COUNT = 100;

    @Autowired PurchaseService purchaseService;
    @Autowired ItemRepository itemRepository;

    @AfterEach
    void cleanUp() {
        itemRepository.deleteAllInBatch();   // @Transactional 대신 직접 정리
    }

    @RepeatedTest(5)   // 타이밍에 따라 드러나는 경합을 잡기 위해 반복
    void 동시에_100명이_구매해도_재고만큼만_성공한다() throws Exception {
        Long itemId = itemRepository.save(new Item(STOCK)).getId();

        ExecutorService executor = Executors.newFixedThreadPool(THREAD_COUNT);
        CountDownLatch ready = new CountDownLatch(THREAD_COUNT);   // 전원이 출발선에 섰는지
        CountDownLatch start = new CountDownLatch(1);              // 출발 신호
        List<Future<Boolean>> futures = new ArrayList<>();

        for (int i = 0; i < THREAD_COUNT; i++) {
            futures.add(executor.submit(() -> {
                ready.countDown();
                start.await();                     // 출발 신호가 올 때까지 대기
                try {
                    purchaseService.purchase(itemId);
                    return true;
                } catch (SoldOutException e) {
                    return false;                  // 예상된 실패
                }
            }));
        }

        assertThat(ready.await(5, TimeUnit.SECONDS)).isTrue();   // 모든 스레드가 출발선에 설 때까지
        start.countDown();                                        // 동시에 출발

        int success = 0;
        for (Future<Boolean> future : futures) {
            if (future.get(10, TimeUnit.SECONDS)) success++;   // 예상 못한 예외는 여기서 터진다
        }
        executor.shutdown();

        Item item = itemRepository.findById(itemId).orElseThrow();
        assertThat(success).isEqualTo(STOCK);
        assertThat(item.getStock()).isZero();
    }
}

CountDownLatch를 하나만 쓰는 예제가 많은데, 그러면 먼저 만들어진 스레드부터 바로 실행을 시작해서 요청이 시간차를 두고 흩어진다. ready로 모든 스레드가 준비될 때까지 기다린 다음 start로 한꺼번에 풀어주는 두 단계 구조여야 경합 구간에 요청이 최대한 몰린다.

결과는 Future로 모으는 게 중요하다. 스레드 안에서 예상 못한 예외가 터지면 그 예외는 스레드 안에서 조용히 사라지고, 테스트는 통과해버릴 수 있다. future.get()을 호출해야 그 예외가 테스트 스레드로 다시 던져진다.

JDK 기본 도구만으로 출발 시점을 정밀하게 맞출 수 있고, 결정적이고 빨라서 CI에서 매번 돌리기 좋다. 서비스 로직의 race condition을 검증하는 기본값으로 가져가는 게 맞는 것 같다. 대신 보일러플레이트가 길고, 스레드 풀 크기와 latch 개수가 안 맞으면 테스트가 멈춘다(아래 함정에서 다시 짚는다).

CyclicBarrier + CompletableFuture

CyclicBarrier는 정해진 수의 스레드가 모두 도착해야 다 같이 통과하는 배리어라, ready와 start 두 latch를 하나로 합친 것처럼 동작한다.

@Test
void 동시_구매_검증() {
    CyclicBarrier barrier = new CyclicBarrier(THREAD_COUNT);
    ExecutorService executor = Executors.newFixedThreadPool(THREAD_COUNT);

    List<CompletableFuture<Boolean>> futures = IntStream.range(0, THREAD_COUNT)
            .mapToObj(i -> CompletableFuture.supplyAsync(() -> {
                awaitBarrier(barrier);          // 전원 도착 시 동시에 통과
                try {
                    purchaseService.purchase(itemId);
                    return true;
                } catch (SoldOutException e) {
                    return false;
                }
            }, executor))
            .toList();

    long success = futures.stream()
            .map(f -> f.orTimeout(10, TimeUnit.SECONDS).join())   // 예상 못한 예외는 여기서 터진다
            .filter(Boolean::booleanValue)
            .count();

    assertThat(success).isEqualTo(STOCK);
}

private static void awaitBarrier(CyclicBarrier barrier) {
    try {
        barrier.await(5, TimeUnit.SECONDS);
    } catch (Exception e) {
        throw new IllegalStateException(e);
    }
}

코드가 스트림 기반으로 짧아지고 결과 수집이 자연스럽다. 검증 능력은 방법 1과 같아서, 팀이 더 읽기 편한 스타일을 고르면 된다. 배리어에 도착하지 못하는 스레드가 하나라도 있으면 나머지가 전부 대기하기 때문에, await()에 타임아웃을 거는 헬퍼가 사실상 필수다.

Virtual Thread로 대량 동시 실행

Java 21의 가상 스레드는 요청마다 하나씩 만들어도 부담이 적어서, 요청 수를 크게 늘려 드물게 일어나는 경합까지 잡아보고 싶을 때 유리하다.

@Test
void 동시에_5000건_요청() throws Exception {
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        CountDownLatch ready = new CountDownLatch(5_000);
        CountDownLatch start = new CountDownLatch(1);
        // 이하 방법 1과 동일한 구조
    }   // try-with-resources로 모든 작업이 끝날 때까지 기다린 뒤 닫힌다
}

스레드 풀 크기를 신경 쓸 필요가 없어서 풀 크기와 latch 불일치 문제도 사라진다. 다만 DB 앞에서는 커넥션 풀 크기(HikariCP 기본값 10)가 실제 동시성의 상한이 된다. 5000개의 가상 스레드도 DB 앞에서는 10개씩 줄을 서기 때문에, 테스트가 검증하는 건 사실상 커넥션 풀 크기만큼의 경합이다. 커넥션 대기 타임아웃으로 나는 실패가 섞일 수 있으니, 그 실패를 비즈니스 실패와 구분해서 봐야 한다.

Awaitility로 비동기 결과 검증하기

처리가 비동기로 일어나는 경우(Kafka 컨슈머, @Async, 이벤트 리스너)는 요청 직후에 검증하면 아직 처리가 안 끝났을 수 있다. Awaitility는 조건이 만족될 때까지 짧은 간격으로 반복 확인한다.

@Test
void 같은_이벤트가_동시에_여러_번_와도_한_번만_처리된다() {
    OrderCreatedEvent event = new OrderCreatedEvent(UUID.randomUUID().toString(), 1L);

    IntStream.range(0, 10).parallel()
            .forEach(i -> kafkaTemplate.send("order-created", event.eventId(), event));

    // 처리가 한 번 일어날 때까지 기다리고
    await().atMost(Duration.ofSeconds(10))
           .untilAsserted(() -> assertThat(pointRepository.countByEventId(event.eventId())).isEqualTo(1));

    // 그 뒤 3초 동안 계속 1건으로 유지되는지까지 확인
    await().during(Duration.ofSeconds(3)).atMost(Duration.ofSeconds(5))
           .untilAsserted(() -> assertThat(pointRepository.countByEventId(event.eventId())).isEqualTo(1));
}

동시성을 만드는 도구가 아니라 결과를 검증하는 도구라서, 방법 1~3과 조합해서 쓴다. 조건이 만족된 순간 바로 통과하기 때문에, 한 번만 처리돼야 하는데 나중에 한 번 더 처리되는 경우는 첫 번째 await만으로는 못 잡는다. 그래서 during()으로 일정 시간 동안 유지되는지까지 보는 게 안전하다.

레이어 2 (전체 요청 경로에서 검증하기)

레이어 1은 서비스 빈을 직접 호출하기 때문에, 게이트웨이, 로드밸런서, 여러 인스턴스를 거치는 실제 경로는 검증하지 못한다. 특히 인스턴스별 메모리에 상태가 있는 코드는 레이어 1에서 완벽하게 통과하다가 파드가 두 개 이상이 되는 순간 깨진다. 로컬 캐시나 JVM 안의 synchronized가 대표적이다. 반면 Redis 기반 분산 락처럼 상태가 외부에 있는 동기화는 레이어 1의 여러 스레드로도 락 로직 자체는 충분히 검증된다.

도구를 고르는 기준

부하 테스트용으로 도구를 고를 때와 기준이 다르다. 동시성 테스트에서는 이 세 가지가 중요하다.

  • 동시 출발을 보장하는지?
    • 레이어 1의 CountDownLatch처럼, 모든 가상 사용자가 모일 때까지 붙잡았다가 한꺼번에 풀어주는 배리어가 있는지?
  • 실행 전후로 초기화와 검증을 붙일 수 있는지?
    • 초기 상태를 만들고, 끝난 뒤 최종 상태로 불변식을 검증하는 흐름을 도구 안에서 표현할 수 있는지?
  • 예상된 실패를 성공으로 셀 수 있는지?
    • 품절(409) 같은 응답은 동시성 테스트에서는 정상 결과다. 이걸 실패로 세면 결과가 왜곡된다.

동시 출발 배리어가 있는지가 동시성 테스트에서는 결정적이라, Spring 개발자 기준으로는 Gatling을 기본으로 추천한다. 배리어가 있으면서 Java로 스크립트를 짜고 Gradle로 실행할 수 있어서, 기존 프로젝트에 그대로 붙일 수 있다. GUI로 시나리오를 만드는 게 편하다면 JMeter가 대안이고, 이미 부하 테스트를 k6로 하고 있다면 k6로 통일하되 배리어가 없다는 한계를 감안하면 된다.

테스트용 초기화 API

레이어 2 도구들은 외부에서 HTTP로만 접근하기 때문에, 초기 상태를 만들 방법이 필요하다. 테스트 프로필에서만 활성화되는 초기화 API를 하나 두는 게 편하다.

@Profile("loadtest")   // 운영에는 절대 노출되지 않게 프로필로 격리
@RestController
@RequestMapping("/test")
@RequiredArgsConstructor
class TestFixtureController {

    private final ItemRepository itemRepository;

    @PostMapping("/items/{id}/stock")
    void resetStock(@PathVariable Long id, @RequestBody StockRequest request) {
        itemRepository.resetStock(id, request.quantity());   // 재고 재설정, 판매량 0으로 초기화
    }
}

이 API를 운영에서 열어두면 그 자체로 보안 사고가 되니까, 반드시 프로필이나 별도 포트로 격리해야 한다. DB에 직접 접근할 수 있는 환경이라면 초기화 SQL을 도구 밖에서 실행하는 방법도 있다.

아래 예시들은 모두 같은 시나리오를 쓴다. 재고 100개인 상품에 200명이 동시에 구매 요청을 보내고, 성공은 200, 품절은 409를 받는다고 가정한다.

package race;

import static io.gatling.javaapi.core.CoreDsl.*;
import static io.gatling.javaapi.http.HttpDsl.*;

import io.gatling.javaapi.core.*;
import io.gatling.javaapi.http.*;

public class PurchaseRaceSimulation extends Simulation {

    private static final int USERS = 200;
    private static final int STOCK = 100;

    HttpProtocolBuilder httpProtocol = http
            .baseUrl(System.getProperty("baseUrl", "http://localhost:8080"))
            .contentTypeHeader("application/json");

    // 1. 초기 상태 만들기
    ScenarioBuilder init = scenario("초기화")
            .exec(http("reset-stock")
                    .post("/test/items/1/stock")
                    .body(StringBody("{\"quantity\": " + STOCK + "}"))
                    .check(status().is(200)));

    // 2. 동시에 구매
    ScenarioBuilder race = scenario("동시 구매")
            .rendezVous(USERS)                        // 200명이 모일 때까지 대기 후 동시 출발
            .exec(http("purchase")
                    .post("/api/items/1/purchase")
                    .check(status().in(200, 409)));   // 품절(409)도 예상된 결과

    // 3. 최종 상태로 불변식 검증
    ScenarioBuilder verify = scenario("불변식 검증")
            .exec(http("check-item")
                    .get("/api/items/1")
                    .check(jmesPath("stock").ofInt().is(0))
                    .check(jmesPath("sold").ofInt().is(STOCK)));

    {
        setUp(
                init.injectOpen(atOnceUsers(1))
                        .andThen(race.injectOpen(atOnceUsers(USERS)))
                        .andThen(verify.injectOpen(atOnceUsers(1)))
        ).protocols(httpProtocol)
         .assertions(global().failedRequests().count().is(0L));   // 하나라도 실패하면 테스트 실패
    }
}

atOnceUsers(200)만으로도 200명을 한 번에 주입하긴 하지만, 사용자들이 요청 지점에 도착하는 시점은 조금씩 흩어진다. rendezVous(200)가 레이어 1의 CountDownLatch와 같은 역할을 한다. 200명이 그 지점에 모일 때까지 붙잡아뒀다가 한꺼번에 풀어준다. 한 가지 주의할 점은 rendezVous가 한 번만 동작한다는 것이다. 반복문 안에 넣으면 첫 번째 반복에서만 모이고, 그 뒤로는 그냥 통과한다. 그래서 동시성 시나리오는 한 사용자가 한 번만 요청하는 구조로 짜는 게 맞다.

andThen으로 초기화, 경합, 검증 시나리오를 순서대로 이어서, 앞 시나리오의 모든 사용자가 끝나야 다음 시나리오가 시작된다. 검증 시나리오의 check가 실패하면 그 요청이 실패로 기록되고, 마지막 assertions에서 실패가 하나라도 있으면 전체가 실패로 끝난다.

실행과 결과 확인

./gradlew gatlingRun --simulation=race.PurchaseRaceSimulation

# 다른 환경을 대상으로 실행할 때
./gradlew gatlingRun --simulation=race.PurchaseRaceSimulation -DbaseUrl=http://api.example.local

assertion이 실패하면 Gradle 태스크가 실패로 끝나기 때문에 CI에 그대로 붙일 수 있다. HTML 리포트는 build/reports/gatling/ 아래에 생성되고, 요청별 응답 코드 분포에서 200과 409가 각각 몇 건인지 바로 확인할 수 있다.

JMeter

설치

# macOS
brew install jmeter

# 또는 Apache JMeter 공식 사이트에서 바이너리를 받아 압축을 풀고 bin/jmeter 실행 (Java 필요)

JMeter는 GUI로 시나리오를 만들고, 실제 실행은 CLI로 하는 게 공식 권장 방식이다. GUI 모드로 실행하면 화면 갱신에 자원을 쓰느라 측정이 왜곡된다.

시나리오 구성 (GUI)

Test Plan 아래에 세 개의 Thread Group을 만든다. setUp과 tearDown Thread Group은 일반 Thread Group의 앞뒤로 자동으로 실행된다.

Test Plan
 ㄴ HTTP Request Defaults       (서버 주소, 포트)
 ㄴ HTTP Header Manager         (Content-Type: application/json)
 ㅣ
 ㄴ setUp Thread Group          스레드 1, 반복 1
 ㅣ   ㄴ HTTP Request            POST /test/items/1/stock   Body: {"quantity": 100}
 ㅣ
 ㄴ Thread Group                스레드 200, Ramp-up 1초, 반복 1
 ㅣ   ㄴ HTTP Request            POST /api/items/1/purchase
 ㅣ       ㄴ Synchronizing Timer     Number of Simulated Users to Group by: 200
 ㅣ       ㅣ                          Timeout in milliseconds: 10000
 ㅣ       ㄴ Response Assertion      Field: Response Code, Rule: Matches, Pattern: 200|409
 ㅣ
 ㄴ tearDown Thread Group       스레드 1, 반복 1
     ㄴ HTTP Request            GET /api/items/1
         ㄴ JSON Assertion          JSON Path: $.stock, Expected Value: 0
         ㄴ JSON Assertion          JSON Path: $.sold,  Expected Value: 100

핵심은 Synchronizing Timer다. 지정한 수(200)의 스레드가 이 타이머에 도착할 때까지 붙잡아뒀다가, 다 모이면 한꺼번에 풀어준다. Gatling의 rendezVous와 같은 역할이다. 두 가지를 조심해야 한다.

  • Group by 값은 스레드 수보다 크면 안 된다. 모일 수 없는 인원을 기다리느라 영원히 멈춘다
  • Timeout은 0이 아닌 값으로 둔다. 0이면 무한 대기라서, 스레드 하나라도 시작이 늦으면 테스트 전체가 멈춘다

Response Assertion에서 200|409를 둘 다 허용하지 않으면, 품절 응답 100건이 전부 실패로 잡혀서 에러율 50%라는 왜곡된 결과가 나온다.

실행과 결과 확인

GUI에서 race.jmx로 저장한 뒤 CLI로 실행한다.

jmeter -n -t race.jmx -l result.jtl -e -o report/

-n은 GUI 없이 실행, -t는 시나리오 파일, -l은 결과 로그, -e -o는 HTML 리포트를 생성할 폴더다. report/index.html에서 요청별 성공/실패와 assertion 실패 내역을 확인할 수 있다. 시나리오 파일이 XML이라 코드 리뷰나 변경 이력 추적이 불편하다는 게 JMeter의 가장 큰 단점이다.

// race.js
import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
const USERS = 200;
const STOCK = 100;

export const options = {
  scenarios: {
    race: {
      executor: 'per-vu-iterations',   // 각 VU가 정해진 횟수만 실행
      vus: USERS,
      iterations: 1,
    },
  },
  thresholds: {
    checks: ['rate==1.0'],   // check가 하나라도 실패하면 테스트 실패
  },
};

export function setup() {
  const res = http.post(`${BASE_URL}/test/items/1/stock`,
      JSON.stringify({ quantity: STOCK }),
      { headers: { 'Content-Type': 'application/json' } });
  check(res, { '초기화 성공': (r) => r.status === 200 });
}

export default function () {
  const res = http.post(`${BASE_URL}/api/items/1/purchase`);
  check(res, { '200 또는 409': (r) => r.status === 200 || r.status === 409 });
}

export function teardown() {
  const res = http.get(`${BASE_URL}/api/items/1`);
  check(res, {
    '재고가 0이다': (r) => r.json('stock') === 0,
    '판매량이 재고와 같다': (r) => r.json('sold') === STOCK,
  });
}

실행과 결과 확인

k6 run -e BASE_URL=http://localhost:8080 race.js

threshold가 깨지면 k6가 0이 아닌 종료 코드로 끝나서 CI에서 실패로 처리된다. 터미널 요약에서 check별 통과율을 바로 볼 수 있다.

k6에는 Gatling이나 JMeter 같은 배리어가 없다. 200개의 VU가 거의 같이 시작하긴 하지만, 요청이 수 ms씩 흩어져 도착할 수 있어서 경합 구간이 아주 짧은 race condition은 재현이 안 될 수 있다. 한 VU 안에서 http.batch()로 여러 요청을 병렬로 보내면 좀 더 몰아서 보낼 수 있는데, 동시 요청 수 상한이 batch, batchPerHost 옵션으로 제한돼 있어서 필요하면 올려야 한다. 이미 부하 테스트를 k6로 하고 있어서 도구를 통일하고 싶은 경우에 쓰고, 반복 실행으로 재현 확률을 보완하는 게 현실적이다.

# race.py
import requests
from locust import HttpUser, task, constant, events
from locust.exception import StopUser

STOCK = 100

@events.test_start.add_listener
def init(environment, **kwargs):
    requests.post(f"{environment.host}/test/items/1/stock", json={"quantity": STOCK})

class Buyer(HttpUser):
    wait_time = constant(0)

    @task
    def purchase(self):
        with self.client.post("/api/items/1/purchase", catch_response=True) as res:
            if res.status_code in (200, 409):
                res.success()          # 품절도 예상된 결과로 처리
        raise StopUser()               # 한 번만 요청하고 종료

@events.test_stop.add_listener
def verify(environment, **kwargs):
    item = requests.get(f"{environment.host}/api/items/1").json()
    if item["stock"] != 0 or item["sold"] != STOCK:
        print(f"불변식 위반: {item}")
        environment.process_exit_code = 1   # CI에서 실패로 처리되게

레이어 3 (스레드 인터리빙 검증하기)

레이어 1과 2는 여러 번 돌려서 운 좋게 문제가 드러나기를 기다리는 방식이다. 레이어 3의 도구들은 접근이 다르다. 스레드들이 실행될 수 있는 순서의 조합을 체계적으로 만들어내서, 문제가 되는 순서를 찾아낸다.

이 레이어가 필요한 건 락 없이 volatile, AtomicXxx, CAS로 직접 짠 동시성 코드가 있을 때다. 일반적인 Spring 서비스는 동시성 제어를 DB나 Redis의 락과 원자적 연산에 맡기기 때문에 이 레이어까지 내려갈 일은 드물다. 반대로 인메모리 rate limiter나 직접 만든 캐시처럼 JVM 안에서 공유 상태를 락 없이 다루는 코드가 있다면 반드시 필요하다.

JCStress (JVM 메모리 모델 수준의 검증)

OpenJDK 프로젝트에서 만든 도구로, 여러 스레드가 공유 변수에 동시에 접근했을 때 나올 수 있는 결과를 전부 수집해서, 허용되지 않는 결과가 나왔는지를 검사한다.

설정

Gradle 플러그인을 쓰면 src/jcstress/java라는 별도 소스셋이 생긴다.

// build.gradle.kts
plugins {
    java
    id("io.github.reyerizo.gradle.jcstress") version "0.9.0"   // 작성 시점 최신
}

테스트 작성

// src/jcstress/java/stress/CounterStressTest.java
package stress;

import org.openjdk.jcstress.annotations.*;
import org.openjdk.jcstress.infra.results.II_Result;

import static org.openjdk.jcstress.annotations.Expect.*;

@JCStressTest
@Outcome(id = {"1, 2", "2, 1"}, expect = ACCEPTABLE, desc = "정상: 두 증가가 모두 반영됨")
@Outcome(id = "1, 1", expect = FORBIDDEN, desc = "갱신 유실: 두 스레드가 같은 값을 읽고 덮어씀")
@State
public class CounterStressTest {

    private int value;   // volatile이어도 ++는 원자적이지 않다

    @Actor
    public void actor1(II_Result r) {
        r.r1 = ++value;
    }

    @Actor
    public void actor2(II_Result r) {
        r.r2 = ++value;
    }
}

@State 객체 하나를 @Actor 메서드들이 동시에 건드리고, 각자 본 값을 결과 객체(II_Result, 정수 두 개)에 기록한다. JCStress는 이걸 수백만 번 반복하면서 나온 결과 조합을 전부 센다. @Outcome으로 각 결과가 허용되는지(ACCEPTABLE), 절대 나오면 안 되는지(FORBIDDEN)를 선언해두면, FORBIDDEN 결과가 한 번이라도 나오면 실패로 판정한다.

실행과 결과 확인

./gradlew jcstress

리포트는 build/reports/jcstress/index.html에 생성되고, 결과 조합별로 몇 번 관측됐는지가 표로 나온다. 위 예시는 1, 1이 관측되면서 실패한다. value를 AtomicInteger로 바꾸고 incrementAndGet()을 쓰면 통과한다.

Lincheck (동시성 자료구조의 정합성 검증)

JetBrains가 만든 도구로, 자료구조의 연산들을 선언만 해두면 동시 실행 시나리오를 자동으로 생성해서, 그 결과가 어떤 순차 실행 결과와도 맞아떨어지는지(선형화 가능성, linearizability)를 검사한다. 모델 체킹 모드에서는 문제를 발견하면 그 문제를 만들어낸 스레드 실행 순서를 추적 로그로 보여준다.

설정

// build.gradle.kts
dependencies {
    testImplementation("org.jetbrains.lincheck:lincheck:3.6")   // 작성 시점 기준, 최신 버전 확인
}

테스트 작성

import org.jetbrains.lincheck.datastructures.ModelCheckingOptions;
import org.jetbrains.lincheck.datastructures.Operation;
import org.jetbrains.lincheck.datastructures.StressOptions;
import org.junit.jupiter.api.Test;

class BoundedCounterLincheckTest {

    // 검증 대상: 한도까지만 증가하는, 락 없이 직접 짠 카운터
    private final BoundedCounter counter = new BoundedCounter(3);

    @Operation
    public boolean tryIncrement() {
        return counter.tryIncrement();
    }

    @Operation
    public int get() {
        return counter.get();
    }

    @Test
    void modelCheckingTest() {
        new ModelCheckingOptions().check(this.getClass());   // 실행 순서를 체계적으로 탐색
    }

    @Test
    void stressTest() {
        new StressOptions().check(this.getClass());          // 실제 스레드로 반복 실행
    }
}

@Operation을 붙인 메서드들이 검사 대상 연산이 된다. BoundedCounter가 값을 확인한 다음 증가시키는 식으로 짜여 있어서 그 사이에 다른 스레드가 끼어들 수 있다면, 모델 체킹 모드가 한도를 넘기는 실행 순서를 찾아내고, 어느 스레드가 어느 줄에서 끼어들었는지를 보여준다. 일반 JUnit 테스트로 실행되기 때문에 ./gradlew test로 그대로 돌아간다. JDK 버전에 따라 필요한 JVM 옵션이 있을 수 있어서, 처음 설정할 때는 공식 문서의 설정 부분을 확인하는 게 좋다.

JCStress가 변수 하나, 연산 몇 개 수준의 메모리 모델 문제에 강하다면, Lincheck은 여러 메서드를 가진 자료구조 단위의 정합성 검증에 강하다.

레이어 4 (분산 시스템 자체 검증하기)

Jepsen은 DB나 메시지 브로커 같은 분산 시스템이, 네트워크 분리나 노드 장애 속에서도 약속한 일관성을 지키는지를 검증하는 도구다. 여러 유명 DB의 일관성 버그를 찾아낸 것으로 알려져 있다.

다만 이건 애플리케이션이 아니라 인프라 자체를 검증하는 레이어라서, 일반적인 서비스 개발에서 직접 쓸 일은 거의 없다. 대신 우리가 쓰는 DB나 브로커의 Jepsen 분석 결과를 찾아 읽어보는 건 도움이 된다. 그 인프라가 어떤 장애 상황에서 어떤 보장을 깨뜨리는지 알고 나면, 애플리케이션 레벨에서 무엇을 추가로 방어해야 하는지가 보인다.

테스트 자체가 틀리게 만드는 함정들

동시성 테스트는 테스트 코드가 잘못돼서 통과하거나 실패하는 경우가 유독 많다.

  • 레이어 1 테스트에 @Transactional을 붙이면 안 된다.

    • 테스트 메서드에 @Transactional을 붙이면, 테스트 안에서 저장한 초기 데이터가 커밋되지 않아서 각자 다른 트랜잭션에서 도는 작업 스레드들이 이 데이터를 못 본다. 반대로 작업 스레드들이 커밋한 데이터는 테스트 끝의 롤백으로 지워지지 않는다. @Transactional을 빼고 @AfterEach에서 직접 정리해야 한다.

  • 스레드 풀이 latch보다 작으면 영원히 멈춘다.

    • 스레드 풀이 32개인데 ready latch를 100으로 잡으면, 먼저 실행된 32개가 start.await()에서 대기하느라 나머지 68개 작업이 실행될 기회가 없다. JMeter에서 Group by를 스레드 수보다 크게 잡는 것도 같은 문제다. 모든 대기에는 타임아웃을 걸어서, 멈추더라도 무한 대기 대신 실패로 끝나게 해야 한다.

  • 예상된 실패를 실패로 세면 결과가 왜곡된다.

    • 품절 응답은 동시성 테스트에서 정상 결과다. 레이어 2 도구에서 409를 성공으로 처리하지 않으면, 에러율이 부풀려져서 진짜 문제(500 에러 등)가 섞여도 구분이 안 된다.

  • 게이트웨이의 rate limit이 테스트를 가릴 수 있다.

    • 레이어 2 테스트는 실제 경로를 거치기 때문에, 게이트웨이의 rate limit에 걸려 429가 대량으로 나오면 경합 자체가 서비스까지 도달하지 못한다. 테스트 환경에서는 rate limit 설정을 확인하거나 테스트 트래픽을 예외로 처리해야 한다.

  • H2로는 실제 DB의 동작을 검증할 수 없다.

    • 락의 범위, 격리 수준의 세부 동작, 데드락 발생 조건은 DB마다 다르다. MySQL InnoDB의 갭 락은 H2에는 없다. 운영과 같은 DB 위에서 검증해야 한다.

  • 한 번의 통과는 증거가 아니다.

    • race condition은 타이밍에 따라 드러나기도 하고 안 드러나기도 한다. 레이어 1은 @RepeatedTest로, 레이어 2는 여러 번 실행해서 재현 확률을 올려야 한다. 이 한계가 없는 건 실행 순서를 체계적으로 탐색하는 레이어 3뿐이다.

그래서 어떻게 조합하나

서비스 로직 하나의 race condition          -> 레이어 1: ExecutorService + CountDownLatch (기본값)
요청 수를 크게 늘려 드문 경합까지          -> 레이어 1: Virtual Thread (커넥션 풀이 실제 상한)
비동기 처리(Kafka, @Async)의 최종 상태     -> 레이어 1: Awaitility로 결과 검증 조합
여러 인스턴스, 전체 경로에서의 경합         -> 레이어 2: Gatling (배리어 + Java DSL, 기본값)
                                             대안: JMeter (GUI 선호), k6 (도구 통일)
락 없이 직접 짠 동시성 코드                 -> 레이어 3: JCStress (변수 수준), Lincheck (자료구조 수준)
사용하는 DB·브로커의 일관성 보장 수준        -> 레이어 4: Jepsen 분석 결과 참고

CI에서 매번 돌리는 건 레이어 1과 레이어 3이다. 둘 다 JUnit이나 Gradle 태스크로 돌아가서 결정적이고 빠르다. 레이어 2는 실제 배포 구조가 필요하기 때문에, 스테이징 환경에 배포한 뒤 실행하는 단계로 파이프라인에 넣는 게 현실적이다.

정리

  • 동시성 테스트는 성능이 아니라 정합성을 검증한다. 합격 기준은 응답 시간이 아니라 불변식이다.
  • 동시성 문제는 경합이 일어나는 레이어에 따라 잡는 도구가 다르다.
    • JVM 안의 서비스 로직(레이어 1), 전체 요청 경로(레이어 2), 스레드 인터리빙(레이어 3), 분산 시스템 자체(레이어 4)
  • 레이어 1은 ExecutorService + CountDownLatch가 기본값이다. 두 단계 latch로 출발을 맞추고, 결과는 Future로 모아야 예외가 숨지 않는다.
  • 레이어 2는 동시 출발 배리어가 있는지가 도구 선택의 핵심이다.
    • Gatling(rendezVous)과 JMeter(Synchronizing Timer)는 배리어가 있고, k6와 Locust는 없다.
    • Spring 프로젝트에는 Java DSL과 Gradle로 붙는 Gatling이 가장 자연스럽다.
  • 레이어 3은 반복 실행에 기대지 않고 실행 순서를 체계적으로 탐색한다.
    • 락 없이 직접 짠 코드가 있다면 JCStress나 Lincheck이 필요하다.
  • 모든 레이어에서 예상된 실패를 성공으로 세고, 모든 대기에 타임아웃을 걸고, 실제 DB 위에서 검증해야 테스트 자체가 거짓말을 하지 않는다.

동시성 제어 코드를 짜는 것만큼, 그걸 제대로 검증하는 테스트를 짜는 게 어렵다는 걸 알게 됐다. 테스트가 통과했다는 사실보다, 그 테스트가 정말로 요청을 동시에 몰아넣었는지, 그리고 실패를 숨기고 있지는 않은지를 먼저 의심해보는 게 순서인 것 같다.
