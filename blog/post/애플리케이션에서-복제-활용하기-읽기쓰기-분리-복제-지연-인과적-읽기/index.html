애플리케이션에서 복제 활용하기 (읽기/쓰기 분리, 복제 지연, 인과적 읽기)

Database/RDB · 2026-10-31

Intro

replica를 두 대 붙여놨는데 애플리케이션은 여전히 source에만 접속하고 있다면, replica는 장애에 대비한 예비 서버일 뿐이다. 읽기 요청이 대부분인 서비스라면 그 읽기를 replica로 보내서 source의 부담을 덜고 싶어진다. 스프링에서는 트랜잭션에 readOnly = true만 붙이면 replica로 가게 만들 수 있어서 시작은 어렵지 않다.

문제는 그다음이다. replica는 항상 source보다 조금 늦다. 방금 저장한 데이터를 바로 다시 조회했는데 없다고 나오고, 잘 돌던 코드가 어떤 요청에서만 replica에 쓰기를 시도하다 실패한다. 읽기/쓰기 분리는 설정 몇 줄로 켤 수 있지만, 복제 지연을 애플리케이션이 떠안게 되는 구조라서 그걸 어떻게 다룰지까지 정해야 끝나는 작업인 것 같다.

이번엔 쿠버네티스 위의 source 1대, replica 2대 환경에 스프링 애플리케이션을 붙여서 읽기/쓰기 분리를 구성하고, 복제 지연이 만드는 문제를 하나씩 일으켜본다. 그리고 방금 쓴 데이터를 읽어야 하는 경우를 GTID로 해결하고, 지연이 큰 replica를 읽기 대상에서 자동으로 빼는 방법까지 정리해본다.

실험 환경

MySQL 8.4 파드 세 개를 StatefulSet으로 띄우고 GTID 기반 복제를 구성했다. 애플리케이션이 접속할 Service는 두 개를 따로 만든다.

  • mysql-writer
    • role=source 라벨이 붙은 파드로만 보낸다. 쓰기와, 반드시 최신이어야 하는 읽기가 여기로 간다
  • mysql-reader
    • role=replica 라벨이 붙은 파드들로 나눠 보낸다. 읽기 전용 트랜잭션이 여기로 간다

replica에는 super_read_only를 걸어 직접 쓰기를 막았고, 레디니스 프로브는 복제 지연을 반영하도록 바꿨다. 이 내용은 뒤에서 다룬다.

스프링에서 읽기와 쓰기를 나누는 방법

읽기/쓰기 분리의 기준은 대부분 트랜잭션의 readOnly 속성이다. @Transactional(readOnly = true)인 트랜잭션은 replica로, 나머지는 source로 보낸다. 판단 단위가 쿼리가 아니라 트랜잭션이라는 점이 중요하다. 쓰기 트랜잭션 안에서 실행되는 SELECT는 전부 source로 가고, 그래서 쓰기 직전의 확인용 조회가 replica의 오래된 데이터를 보고 잘못된 결정을 내리는 일은 생기지 않는다.

LazyConnectionDataSourceProxy에 읽기 전용 DataSource 지정하기

Spring Boot 3.2.1 이상부터 LazyConnectionDataSourceProxy가 읽기 전용 DataSource를 직접 받는다. 읽기 전용으로 표시된 스프링 트랜잭션 안에서는 이 DataSource에서 커넥션을 꺼내고, 나머지는 기본 DataSource를 쓴다. 라우팅 클래스를 직접 만들 필요가 없어서 가장 간단하다.

# application.yml
app:
  datasource:
    writer:
      jdbc-url: jdbc:mysql://${WRITER_IP}:3306/lab
      pool-name: writer
    reader:
      jdbc-url: jdbc:mysql://${READER_IP}:3306/lab
      pool-name: reader
      read-only: true          # 읽기 전용 풀의 커넥션은 처음부터 읽기 전용으로 만든다
      max-lifetime: 60000      # 이 값을 짧게 둔 이유는 뒤의 엔드포인트 실험에서 다룬다

spring:
  jpa:
    open-in-view: false        # 이 설정이 왜 필요한지는 뒤의 OSIV 실험에서 다룬다

@Configuration
public class DataSourceConfig {

    @Bean
    @ConfigurationProperties("app.datasource.writer")
    public HikariDataSource writerDataSource() {
        return new HikariDataSource();
    }

    @Bean
    @ConfigurationProperties("app.datasource.reader")
    public HikariDataSource readerDataSource() {
        return new HikariDataSource();
    }

    @Bean
    @Primary
    public DataSource dataSource(@Qualifier("writerDataSource") DataSource writer,
                                 @Qualifier("readerDataSource") DataSource reader) {
        LazyConnectionDataSourceProxy proxy = new LazyConnectionDataSourceProxy(writer);
        proxy.setReadOnlyDataSource(reader);
        return proxy;
    }
}

공식 문서에 적힌 조건이 두 가지 있다. 읽기 전용 DataSource의 커넥션은 처음부터 읽기 전용으로 설정돼 있어야 하고(위의 read-only: true), auto-commit과 격리 수준의 기본값은 기본 DataSource와 같아야 한다. 프록시가 트랜잭션마다 이 값들을 바꿔주지 않기 때문이다.

왜 lazy 프록시여야 할까?

트랜잭션 매니저는 트랜잭션을 시작할 때 먼저 커넥션을 가져오고, 그 커넥션에 auto-commit 끄기 같은 설정을 한 다음, 마지막에 지금 트랜잭션이 읽기 전용이라는 정보를 스레드에 기록한다. 커넥션을 고르는 시점에는 아직 읽기 전용인지 알 수 없는 거다.

LazyConnectionDataSourceProxy는 커넥션을 요청받으면 껍데기를 돌려주고, 첫 SQL을 실행하는 순간에야 진짜 커넥션을 꺼낸다. 그때는 읽기 전용 여부가 확정돼 있으니 올바른 풀을 고를 수 있다.

AbstractRoutingDataSource로 직접 라우팅하기

Spring Boot 3.2.1 이전 버전이거나, 읽기 전용 여부 말고 다른 기준(테넌트, 리전 등)으로도 나눠야 한다면 라우팅 DataSource를 직접 만든다.

public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "reader" : "writer";
    }
}

여기서도 바깥을 LazyConnectionDataSourceProxy로 감싸는 게 핵심이다. 감싸지 않으면 isCurrentTransactionReadOnly()가 커넥션을 고르는 시점에 항상 false라서, 모든 트랜잭션이 조용히 source로 간다. 에러가 나지 않으니 replica가 놀고 있다는 걸 한참 뒤에 알게 되는 경우가 많다.

트랜잭션 속성에 따라 커넥션이 갈리는지 확인

조회 결과에 SELECT @@hostname을 같이 담아서 어느 서버가 응답했는지 보이게 했다.

  • 가설

    • 읽기 전용 트랜잭션은 replica 중 하나로, 나머지는 source로 간다. 읽기 전용 풀의 커넥션은 서버 쪽에서도 읽기 전용 세션이다.

  • 절차

curl -s $APP/whoami/write; echo
curl -s $APP/whoami/read; echo

# 순서대로 20번
for n in $(seq 1 20); do curl -s $APP/whoami/read; echo; done | sort | uniq -c

# 동시에 20번
seq 1 20 | xargs -P 20 -I{} sh -c "curl -s $APP/whoami/read; echo" | sort | uniq -c
항목예상관찰
/whoami/write의 host, readOnlymysql-0, 0
/whoami/read의 host, readOnlymysql-1 또는 mysql-2, 1
순서대로 20번 보냈을 때 host 분포한쪽으로 쏠릴 수 있음
동시에 20번 보냈을 때 host 분포mysql-1, mysql-2가 섞여 나옴
  • 관찰 포인트
    • mysql-reader Service가 부하를 나누는 단위는 요청이 아니라 TCP 연결이다. Hikari 풀의 커넥션은 만들어지는 순간 각각 replica 하나에 고정되고, Hikari는 방금 쓴 커넥션을 다시 쓰는 경향이 있다. 그래서 요청을 순서대로 보내면 같은 replica만 계속 보일 수 있다. 이건 뒤의 엔드포인트 실험에서 다시 중요해진다.

방금 쓴 데이터가 안 보인다.

실제 지연은 몇 밀리초에서 길어야 몇 초라서 매번 재현하기 어렵다. 그래서 replica에 일부러 3초의 지연을 건다.

STOP REPLICA SQL_THREAD;
CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 3;
START REPLICA SQL_THREAD;

  • 가설

    • 저장 직후 같은 데이터를 읽기 전용 트랜잭션으로 조회하면 replica에는 아직 없어서 name이 null로 나온다. 3초가 지나면 보인다.

  • 절차

ID=$(curl -s -X POST "$APP/items?name=first" | jq -r .id)
curl -s $APP/items/$ID; echo
sleep 4
curl -s $APP/items/$ID; echo
항목예상관찰
저장 직후 조회의 namenull
4초 뒤 조회의 namefirst
  • 관찰 포인트
    • 저장은 성공했고, 조회도 에러 없이 성공했다. 다만 조회 결과가 틀렸다. 사용자 입장에서는 방금 등록한 글이 목록에 없는 화면을 보게 되고, 다시 새로고침하면 보이니 재현도 어렵다. 읽기/쓰기 분리를 켜는 순간, 이런 요청이 있다는 걸 전제로 설계해야 한다.

Open Session In View가 켜져 있으면 라우팅이 틀어진다.

Spring Boot는 spring.jpa.open-in-view가 기본으로 켜져 있다. OSIV가 켜져 있으면 한 요청 안에서 처음 실행된 트랜잭션이 고른 커넥션을 요청이 끝날 때까지 계속 쓴다. 첫 트랜잭션이 읽기 전용이었다면 그 요청의 이후 트랜잭션은 전부 replica 커넥션을 쓰게 된다.

읽기 전용 트랜잭션으로 대상이 있는지 확인하고, 이어서 쓰기 트랜잭션으로 수정하는 컨트롤러가 바로 이 모양이다.

@PostMapping("/items/{id}/rename")
public ResponseEntity<Void> rename(@PathVariable Long id, @RequestParam String name) {
    if (!itemService.exists(id)) {          // readOnly = true
        return ResponseEntity.notFound().build();
    }
    itemService.rename(id, name);           // 쓰기 트랜잭션
    return ResponseEntity.noContent().build();
}

  • 가설

    • OSIV가 켜져 있으면 rename의 UPDATE가 replica 커넥션에서 실행되어 실패한다. 꺼져 있으면 각 트랜잭션이 자기 커넥션을 새로 고르기 때문에 성공한다.

  • 절차

./gradlew bootRun --args='--spring.jpa.open-in-view=true'
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$APP/items/$ID/rename?name=renamed-1"

./gradlew bootRun
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$APP/items/$ID/rename?name=renamed-2"
항목예상관찰
OSIV 켬: 응답 코드500
OSIV 켬: 로그의 SQL 에러읽기 전용 트랜잭션 또는 super_read_only 관련 에러
OSIV 끔: 응답 코드204
  • 관찰 포인트
    • 에러가 나서 다행인 경우다. 반대 순서, 즉 쓰기 트랜잭션이 먼저 실행된 요청에서는 이후의 읽기 전용 트랜잭션이 전부 source로 가는데, 이건 에러 없이 조용히 일어난다. 읽기/쓰기 분리를 쓴다면 OSIV는 끄는 게 맞는 것 같다. 끄면 컨트롤러에서 지연 로딩을 할 수 없으니, 화면에 필요한 데이터는 트랜잭션 안에서 DTO로 만들어서 넘긴다.

방금 쓴 데이터를 읽어야 할 때

모든 읽기가 이 문제를 가지는 건 아니다. 다른 사용자가 쓴 글 목록, 검색 결과, 통계처럼 몇 초 늦어도 아무도 모르는 읽기가 대부분이다. 그래서 먼저 어떤 읽기가 자기가 방금 쓴 걸 봐야 하는지를 골라내고, 그 읽기에만 아래 방법을 적용한다.

그 읽기는 source에서 한다.

가장 단순하고 확실하다. 저장 직후 상세 화면처럼 방금 쓴 걸 봐야 하는 조회는 readOnly를 빼서 source로 보낸다. 다만 어떤 조회가 그런지를 매번 판단해야 하고, 이 판단이 늘어날수록 source로 가는 읽기가 같이 늘어난다.

GTID로 replica가 따라잡았는지 확인하고 읽는다

쓰기 직후의 source의 GTID 집합을 기억해뒀다가, replica에서 읽기 전에 replica가 그 집합을 다 실행했는지 확인하면 된다.

SELECT WAIT_FOR_EXECUTED_GTID_SET('<gtid 집합>', 1);
-- 0: 전부 실행됨, 1: 1초 안에 따라잡지 못함
  1. 쓰기 트랜잭션이 커밋된 뒤, source에서 @@GLOBAL.gtid_executed를 읽어서 응답 헤더로 돌려준다. 이 값을 일관성 토큰이라고 한다.
  2. 클라이언트는 이어지는 조회 요청에 이 토큰을 그대로 실어 보낸다.
  3. 서버는 읽기 전용 트랜잭션을 열고, 그 안에서 WAIT_FOR_EXECUTED_GTID_SET으로 replica가 따라잡기를 짧게 기다린 뒤 조회한다.
  4. 시간 안에 따라잡지 못하면 그 조회만 source에서 한다.

놓치기 쉬운 부분이 3번이다. 대기와 조회는 반드시 같은 커넥션에서 해야 한다. 대기는 mysql-1 커넥션에서 하고 조회는 mysql-2 커넥션에서 하면 확인한 의미가 없다. 하나의 읽기 전용 트랜잭션 안에서 둘을 실행하면 같은 커넥션이 보장된다.

@Component
public class CausalReader {

    private final TransactionTemplate replicaTx;
    private final TransactionTemplate sourceTx;
    private final JdbcTemplate jdbc;

    public CausalReader(PlatformTransactionManager transactionManager, JdbcTemplate jdbc) {
        this.replicaTx = new TransactionTemplate(transactionManager);
        this.replicaTx.setReadOnly(true);
        this.sourceTx = new TransactionTemplate(transactionManager);
        this.jdbc = jdbc;
    }

    public <T> T read(@Nullable String token, Supplier<T> query) {
        if (token == null || token.isBlank()) {
            return replicaTx.execute(status -> query.get());
        }

        // 대기와 조회를 한 트랜잭션 = 한 커넥션 = 한 replica에서
        Attempt<T> attempt = replicaTx.execute(status -> {
            Integer result = jdbc.queryForObject(
                    "SELECT WAIT_FOR_EXECUTED_GTID_SET(?, 1)", Integer.class, token);
            if (!Integer.valueOf(0).equals(result)) {
                return Attempt.<T>notCaughtUp();
            }
            return Attempt.done(query.get());
        });
        if (attempt.caughtUp()) {
            return attempt.value();
        }

        // 1초 안에 따라잡지 못했다 -> 이 조회만 source에서
        return sourceTx.execute(status -> query.get());
    }

    private record Attempt<T>(boolean caughtUp, T value) {
        static <T> Attempt<T> done(T value) { return new Attempt<>(true, value); }
        static <T> Attempt<T> notCaughtUp() { return new Attempt<>(false, null); }
    }
}

토큰 발급은 커밋이 끝난 뒤에 해야 하니, 트랜잭션 메서드가 반환된 다음 writer 풀로 SELECT @@GLOBAL.gtid_executed를 바로 조회한다. 이 값은 내 트랜잭션 이후 커밋된 몇 건까지 포함해서 필요한 것보다 조금 더 기다릴 수 있지만, 실제 차이는 크지 않다.

이 방법의 대가도 분명하다. 토큰을 클라이언트가 들고 다녀야 하니 API 계약이 바뀐다. 대기하는 동안 replica 커넥션을 쥐고 있으니, 지연이 길어지면 읽기 풀이 대기 중인 요청으로 가득 찰 수 있다. 그리고 이 함수는 복제가 멈춰 있는지를 따지지 않아서, 멈춘 replica를 읽기 대상에서 빼는 건 따로 해야 한다.

GTID로 따라잡은 replica에서만 읽기

  • 가설

    • 지연 3초, 대기 1초 조건에서는 토큰을 실은 조회가 1초 대기 후 source에서 처리되어 최신 데이터를 돌려준다. 지연을 없애면 같은 조회가 replica에서 바로 처리된다.

  • 절차

curl -s $APP/items/$ID; echo                                                  # 토큰 없음
curl -s -H "X-Consistency-Token: $TOKEN" -w '  %{time_total}s\n' $APP/items/$ID/causal
항목예상관찰
지연 3초, 토큰 없음: name / servedBynull / mysql-1 또는 mysql-2
지연 3초, 토큰 있음: name / servedBycausal-1 / mysql-0
지연 3초, 토큰 있음: 응답 시간1초 남짓
지연 0초, 토큰 있음: name / servedBycausal-2 / mysql-1 또는 mysql-2
  • 관찰 포인트
    • 지연이 대기 시간보다 길면 이 방법은 느린 source 읽기가 된다. 그래서 대기 시간은 평소의 복제 지연보다 약간 긴 정도로 잡는 게 맞는 것 같다.

쓴 직후 일정 시간 동안 source에서 읽는다.

쓰기가 일어나면 그 사용자의 세션에 몇 초 뒤의 시각을 기록해두고, 그 시각 전까지는 그 사용자의 읽기를 source로 보내는 방식이다. 구현은 간단하지만 몇 초가 충분한지는 추측이다. GTID를 쓸 수 없는 환경이라면 고려할 만하다.

ProxySQL

이 판단을 DB 앞단의 프록시에 맡길 수도 있다. ProxySQL은 2.0부터 GTID 기반의 인과적 읽기를 지원해서, 클라이언트 세션의 마지막 쓰기 GTID를 이미 실행한 replica로만 읽기를 보낸다. 애플리케이션 코드는 거의 바뀌지 않지만 운영 대상이 늘고 프록시가 장애 지점이 된다.

지연이 큰 replica를 읽기 대상에서 빼기

replica 하나만 크게 뒤처지는 일이 생긴다. 무거운 분석 쿼리가 테이블 잠금을 오래 쥐고 있거나, 그 노드의 디스크가 느려지는 경우다.

쿠버네티스에서는 레디니스 프로브로 이걸 처리할 수 있다. replica라면 수신과 적용 스레드가 모두 돌고 있고 Seconds_Behind_Source가 5초 이하일 때만 Ready를 낸다. Ready가 아닌 파드는 Service의 엔드포인트에서 빠진다.

# readiness.sh
MAX_LAG=5
status=$(mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW REPLICA STATUS\G" 2>/dev/null) || exit 1
[ -z "$status" ] && exit 0     # 복제 채널이 없는 서버(source)는 응답만 하면 Ready
io=$(awk '/ Replica_IO_Running:/ {print $2}' <<<"$status")
sql=$(awk '/ Replica_SQL_Running:/ {print $2}' <<<"$status")
lag=$(awk '/ Seconds_Behind_Source:/ {print $2}' <<<"$status")
[ "$io" = "Yes" ] && [ "$sql" = "Yes" ] && [ "$lag" != "NULL" ] && [ "$lag" -le "$MAX_LAG" ]

복제 연결에 쓰는 headless Service에는 publishNotReadyAddresses: true를 준다. 이 설정이 없으면 Ready가 아닌 파드의 mysql-N.mysql 이름이 DNS에서 빠져서, source의 프로브가 잠깐 실패하는 순간 replica들이 source를 찾지 못하게 된다.

Seconds_Behind_Source는 수신 스레드가 새 트랜잭션을 못 받고 있으면 실제로는 뒤처졌는데도 0으로 보일 수 있다. 정확한 지연이 필요하면 heartbeat 테이블을 두거나 performance_schema의 복제 상태 테이블을 쓴다.

지연된 replica가 엔드포인트에서 빠지는 과정

  • 가설

    • mysql-2의 지연이 5초를 넘으면 10초 안에 Ready가 풀리고 mysql-reader의 엔드포인트에서 빠진다. 하지만 애플리케이션이 이미 맺어둔 mysql-2 커넥션은 끊기지 않아서, 그 커넥션이 수명을 다할 때까지 읽기 일부가 계속 mysql-2로 간다.

  • 절차

    • source에 1초마다 쓰기를 넣는 동안, mysql-2에서 LOCK TABLES items READ; SELECT SLEEP(90);로 적용 스레드를 막는다. 그 사이 파드 상태, 엔드포인트, 읽기 분포를 10초 간격으로 본다.
항목예상관찰
mysql-2가 NotReady가 되는 시점지연이 5초를 넘고 10초 이내
mysql-reader 엔드포인트mysql-1만 남음
엔드포인트에서 빠진 직후의 읽기 분포mysql-2가 여전히 섞여 나옴
mysql-2가 읽기에서 완전히 사라지는 시점빠진 뒤 최대 60초 (max-lifetime)
  • 관찰 포인트
    • 레디니스로 엔드포인트에서 빠지는 건 새 연결에만 영향을 준다. kube-proxy는 이미 맺어진 TCP 연결을 끊지 않기 때문에, Hikari 풀이 들고 있던 mysql-2 커넥션은 계속 살아서 오래된 데이터를 돌려준다. Hikari의 max-lifetime 기본값은 30분이라, 기본 설정이었다면 지연된 replica를 최대 30분 동안 계속 읽었을 거다.

그래서 읽기 풀의 max-lifetime을 60초로 짧게 줬다. 커넥션이 1분마다 새로 만들어지면서 그때마다 Ready인 replica로만 다시 붙는다. 대신 커넥션을 자주 다시 맺는 비용이 생기고, 1분이라는 창은 여전히 남는다.

replica 두 대가 모두 지연되면 mysql-reader의 엔드포인트가 비고 읽기 전용 트랜잭션은 실패한다. 이때 읽기를 source로 돌리면 서비스는 살지만 읽기가 한꺼번에 source로 몰리니, 그 부하에 source가 버티는지부터 확인해야 한다.

지연된 replica에서 계속 읽는다엔드포인트에서 빠져도 기존 커넥션은 유지됨지연 기반 레디니스 + 읽기 풀의 짧은 max-lifetime
  • 읽기/쓰기 분리의 판단 단위는 트랜잭션이다. 쓰기 트랜잭션 안의 조회는 전부 source로 간다.
  • Spring Boot 3.2.1 이상이면 LazyConnectionDataSourceProxy.setReadOnlyDataSource() 하나로 충분하다. 직접 라우팅한다면 반드시 lazy 프록시로 감싼다.
  • replica 간 부하 분산은 Service가 연결 단위로 한다. 커넥션 풀을 쓰면 요청 단위로 고르게 나뉘지 않는다.
  • 방금 쓴 걸 봐야 하는 읽기는 많지 않다. 먼저 그 읽기를 골라내고, 그 읽기에만 source 읽기나 GTID 대기를 적용한다.
  • 레디니스로 지연된 replica를 빼도 이미 맺어진 커넥션은 남는다. 읽기 풀의 커넥션 수명을 짧게 둬야 실제로 빠진다.

설정 몇 줄로 replica에 읽기를 보내는 건 금방이었는데, 그 뒤에 따라온 건 전부 replica가 늦을 수 있다는 사실을 애플리케이션이 어디서 받아낼지에 대한 결정이었다. 읽기/쓰기 분리는 DB 설정이라기보다 애플리케이션이 일관성을 어디까지 양보할지 정하는 설계인 것 같다.
