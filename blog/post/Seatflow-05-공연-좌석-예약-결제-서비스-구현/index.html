Intro

이번 편에서는 show-service, seat-service, reservation-service, payment-service를 구현한다. 티켓팅의 핵심 흐름 전체를 담당하는 서비스들이다. 공연이 등록되고, 좌석이 점유되고, 예약이 생성되고, 결제가 완료되는 일련의 과정이다. 특히 seat-service에서는 수천 명이 동시에 같은 좌석을 선택하는 상황을 어떻게 처리할지가 핵심이다.

MongoDB Document (show-service)

공연 정보는 스키마가 자주 바뀔 수 있다. 공연마다 추가 정보가 다르고, 좌석 구성이나 할인 정책도 공연마다 다르다. 이런 유연성이 필요한 데이터는 MongoDB가 더 적합하다.

@Document(collection = "shows")
@Getter
public class Show {

    @Id
    private String id;
    private String title;
    private String venue;
    private LocalDateTime showDate;
    private int totalSeats;
    private BigDecimal price;
    private LocalDateTime createdAt;
}

서비스 레이어 파라미터 전달 방식

공연 등록 API를 구현하면서 서비스 레이어에 파라미터를 어떻게 전달할지 고민했다. 선택지는 크게 네 가지다.

인자 직접 받기

public Show createShow(String title, String venue, LocalDateTime showDate, int totalSeats, BigDecimal price)

파라미터가 많아지면 가독성이 떨어지고, 필드가 추가될 때마다 시그니처가 바뀌어 호출부를 전부 수정해야 한다.

DTO 직접 받기

public Show createShow(ShowRequest request)

단순하고 빠르지만 서비스가 웹 레이어의 DTO에 의존한다. 레이어 경계가 무너지고, REST 외 다른 입력 소스(Kafka, 배치)가 생기면 DTO를 재사용할 수 없다.

Command 객체

public Show createShow(CreateShowCommand command)

서비스가 웹 레이어와 완전히 분리된다. REST, Kafka, 배치 어디서든 Command 객체로 변환해서 서비스를 호출할 수 있다. 대규모 서비스에서 표준으로 쓰이는 방식이다.

UseCase 패턴 클린 아키텍처에서 비즈니스 로직을 서비스 대신 UseCase 클래스로 분리하는 방식이다. 단일 책임 원칙을 극단적으로 적용한 형태로, 테스트 용이성이 높지만 클래스 수가 많아진다.

현재 프로젝트에서는 Command 패턴을 선택했다. 나중에 Kafka consumer에서도 같은 서비스 메서드를 재사용할 수 있고, 서비스가 웹 레이어에 의존하지 않는다.

public record CreateShowCommand(
        String title,
        String venue,
        LocalDateTime showDate,
        int totalSeats,
        BigDecimal price
) {
    public static CreateShowCommand from(ShowRequest request) {
        return new CreateShowCommand(
                request.title(),
                request.venue(),
                request.showDate(),
                request.totalSeats(),
                request.price()
        );
    }
}

컨트롤러에서는 Request를 Command로 변환해서 서비스에 전달한다.

@PostMapping
public ResponseEntity<ApiResponse<ShowResponse>> createShow(
        @RequestBody @Valid ShowRequest request) {
    return ResponseEntity.ok(ApiResponse.ok(
            ShowResponse.from(showService.createShow(CreateShowCommand.from(request)))
    ));
}

동시성 제어 (seat-service)

티켓팅 오픈 순간 수천 명이 동시에 같은 좌석을 선택한다. 동시성 제어가 핵심이다.

동시성 제어 방법 비교

낙관적 락 (Optimistic Lock) @Version으로 충돌을 감지하고 충돌 시 재시도한다. 충돌이 적을 때 유리하다. 티켓팅처럼 충돌이 폭발적으로 많은 상황에서는 재시도를 반복하며, 재시도 요청이 다시 충돌을 일으키고, 그 재시도가 또 DB 부하를 만드는 재시도 폭풍 (retry storm)이 발생해 DB가 과부하로 다운될 수 있다.

비관적 락 (Pessimistic Lock) SELECT FOR UPDATE로 DB에서 좌석을 잠근다. 구현은 단순하지만 DB 커넥션을 점유한 채로 대기하기 때문에 대규모 트래픽에서 커넥션 풀이 고갈된다.

Atomic UPDATE

UPDATE seats SET status = 'RESERVED' WHERE id = ? AND status = 'AVAILABLE'

별도의 명시적 락 절차(SELECT FOR UPDATE, @Version) 없이 단일 쿼리로 처리한다. DB는 UPDATE 실행 중 해당 row에 짧게 락을 잡지만, 비관적 락처럼 애플리케이션 왕복 구간 동안 락을 점유하지 않는다.

업데이트된 row가 1이면 성공, 0이면 이미 선점된 것이다. 낙관적 락보다 단순하고 재시도가 없다. 다만 수천 명의 요청이 동시에 DB로 집중된다.

Redis 분산 락 (Redisson) 좌석별로 Redis 락을 걸고 처리한다. DB 부하를 줄일 수 있고 실무 티켓팅에서 많이 쓰인다.

Lua 스크립트 싱글 스레드로 동작하기 때문에 Lua 스크립트 실행 중에는 다른 명령이 끼어들 수 없다. 조건 확인과 값 설정 같은 여러 명령을 하나의 원자적 블록으로 묶어야 할 때 사용한다. 현재 프로젝트처럼 단순 점유라면 setIfAbsent()로 충분하지만, 좌석 수량 차감이나 복합 조건 체크가 필요한 경우 Lua 스크립트가 유용하다.

Redis 원자적 연산 + Kafka Redis에서 좌석 가용 여부를 1차로 빠르게 처리하고, 통과한 요청만 Kafka를 통해 비동기로 처리한다. 가장 빠르고 DB 부하가 최소화되지만 구현이 복잡하다.

나는 우선 Redis + Kafka 조합을 선택했다. Redis가 1차 필터로 수천 명의 요청을 빠르게 처리하고, Kafka로 예약 생성을 비동기 처리한다. 추후 고도화 작업이 있을 때 구역별 잔여 좌석 관리나 중복 예약 방지 같은 복합 조건이 필요해지면 Lua 스크립트도 고려해볼 것 같다.

Redis로 원자적 점유

setIfAbsent(key, userId, TTL, TimeUnit)는 값 설정과 TTL 지정을 단일 원자적 명령으로 처리한다.

락 없이도 동시 요청에서 단 하나의 요청만 성공할 수 있고, 중간에 애플리케이션 서버가 죽어도 TTL 없는 키가 남아 좌석이 영구적으로 잠기는 문제가 발생하지 않는다.

public boolean hold(String showId, Long seatId, String userId) {
    String key = SEAT_HOLD_PREFIX + showId + ":" + seatId;
    Boolean result = redisTemplate.opsForValue()
            .setIfAbsent(key, userId, HOLD_TTL_MINUTES, TimeUnit.MINUTES);
    return Boolean.TRUE.equals(result);
}

TTL을 5분으로 설정했다. 결제를 완료하지 않으면 5분 후 자동으로 점유가 해제된다. 별도 스케줄러 없이 Redis가 알아서 처리한다.

seat:hold:{showId}:{seatId} → userId (TTL: 5분)

좌석 점유 성공 시 seat.held 이벤트를 Kafka에 발행한다. reservation-service가 이 이벤트를 수신해서 예약을 생성한다.

kafkaTemplate.send(
        EventTopic.SEAT_HELD,
        userId,
        EventEnvelope.of(
                EventTopic.SEAT_HELD,
                "seat-service",
                new SeatHeldEvent(userId, showId, seatId)
        )
);

reservation-service

예약 도메인 설계

예약 번호(reservationNumber)를 별도로 관리했다. DB의 auto increment id를 외부에 노출하면 총 예약 수와 순서가 유추 가능하다. 외부 노출용 식별자는 UUID로 별도 관리한다. 단, UUID는 완전 무작위라 DB 인덱스 페이지 분할이 잦아 대량 insert 성능이 저하될 수 있다. 이 문제가 중요하다면 시간 순 정렬이 가능한 ULID나 UUIDv7이 대안이다. 현재 구조처럼 내부 PK는 auto increment로 유지하고 UUID는 외부 노출용으로만 쓰면 이 문제를 크게 완화할 수 있다.다만 reservationNumber 유니크 인덱스에는 무작위 UUID의 보조 인덱스 단편화가 일부 남는다(클러스터 인덱스가 순차 유지되므로 영향은 작다)

부수적으로, String(VARCHAR(36)) 대신 BINARY(16) 저장이면 인덱스 크기와 분할 부담을 더 줄일 수 있다.

@Entity
@Table(name = "reservations")
public class Reservation {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;  // 내부 PK

    @Column(nullable = false, unique = true, updatable = false)
    private String reservationNumber;  // 외부 노출용 UUID

    private String userId;
    private String showId;
    private Long seatId;

    @Enumerated(EnumType.STRING)
    private ReservationStatus status;  // PENDING, CONFIRMED, CANCELLED
}

cancel() 메서드를 서비스가 아닌 엔티티에 두었다. 예약 취소는 예약 도메인의 책임이다. 서비스가 reservation.setStatus(CANCELLED)를 직접 호출하면 도메인 로직이 서비스에 분산된다. 도메인 로직은 도메인 객체가 책임진다는 원칙을 따랐다.

// 서비스에서 직접 상태를 바꾸는 대신
public void cancel() {
    this.status = ReservationStatus.CANCELLED;
}

seat.held 이벤트를 수신해서 예약을 생성한다. 제네릭 타입 역직렬화는 TypeReference로 처리한다. (04편 참고)

@KafkaListener(topics = EventTopic.SEAT_HELD, groupId = "reservation-service")
public void consume(String message) {
    EventEnvelope<SeatHeldEvent> event = kafkaObjectMapper.readValue(
            message,
            new TypeReference<EventEnvelope<SeatHeldEvent>>() {}
    );
    reservationService.createReservation(
            new CreateReservationCommand(
                    event.payload().userId(),
                    event.payload().showId(),
                    event.payload().seatId()
            )
    );
}

결제 (payment-service)

전략 패턴 + 레지스트리

결제 수단은 여러 가지다. 토스, 카카오페이, 신용카드, 계좌이체 등등 각 PG사마다 연동 방식이 다르고 나중에 새로운 수단이 추가될 수 있다. 이걸 단순하게 구현하면 이렇게 된다.현재 프로젝트에선 PG연동은 생략하고 그냥 있다고 가정만하고 진행 할 예정이다.

먼저 여러개의 결제 수단이 있다고 한다면, 어떤 방식들이 있는지 정리해보자

단순 if-else 가장 빠르게 구현할 수 있지만 새 결제 수단이 생길 때마다 서비스 코드를 직접 수정해야 한다. OCP(개방-폐쇄 원칙) 위반이다.

인터페이스 추상화 PG사 교체는 쉽지만 여러 PG사를 동시에 지원하거나 런타임에 교체하기 어렵다. 결제 수단 선택 로직이 여전히 서비스에 남는다.

팩토리 패턴 조건에 따라 구현체를 생성하는 팩토리를 두는 방식이다. 생성 로직은 분리되지만 새 수단 추가 시 팩토리도 수정해야 한다.

전략 패턴 + 레지스트리 패턴 각 결제 수단을 독립적인 전략으로 구현하고, 레지스트리가 이를 관리한다. 새 결제 수단 추가 시 전략 구현체만 추가하면 된다. 서비스 코드는 수정이 필요없다. 

내가 선택한 방법은 전략 패턴 + 레지스트리 패턴이다.

**전략 패턴(Strategy Pattern)**은 알고리즘을 인터페이스로 정의하고 각 구현체로 캡슐화하는 패턴이다. 여기서 "결제 수단"이 곧 전략이다. 토스, 카카오페이, 신용카드 등 각각 결제 처리 방식은 다르지만 process()라는 동일한 행위를 수행한다. 이 공통 행위를 PaymentStrategy 인터페이스로 추상화하고 각 PG사별 로직을 구현체로 분리했다.

**레지스트리 패턴(Registry Pattern)**은 객체를 중앙에서 등록하고 조회하는 패턴이다. 전략 패턴과 함께 쓰면 새 전략 추가 시 레지스트리가 자동으로 감지한다. Spring의 DI를 활용하면 List<PaymentStrategy>로 모든 구현체를 주입받아 Map으로 관리할 수 있다.

public interface PaymentStrategy {
    boolean process(String paymentNumber, BigDecimal amount);
    PaymentMethod supportedMethod();
}

@Component
public class PaymentStrategyRegistry {

    private final Map<PaymentMethod, PaymentStrategy> registry;

    public PaymentStrategyRegistry(List<PaymentStrategy> strategies) {
        // Spring이 PaymentStrategy 구현체를 모두 자동 주입
        // 구현체가 없으면 서버 시작 시점에 즉시 감지
        if (strategies == null || strategies.isEmpty()) {
            throw new IllegalStateException("등록된 결제 전략이 없습니다.");
        }

        // PaymentMethod를 키로 전략 구현체를 Map에 등록
        // 같은 PaymentMethod 구현체가 2개 이상이면 시작 시점에 예외 발생
        // unmodifiableMap으로 초기화 이후 외부 변경 차단
        this.registry = Collections.unmodifiableMap(
                strategies.stream()
                        .collect(Collectors.toMap(
                                PaymentStrategy::supportedMethod,
                                s -> s,
                                (existing, duplicate) -> {
                                    throw new IllegalStateException(
                                        "중복된 결제 전략이 등록되었습니다: " + existing.supportedMethod()
                                    );
                                }
                        ))
        );
    }

    // 결제 수단에 맞는 전략 반환
    // 등록되지 않은 수단이면 예외 발생
    public PaymentStrategy get(PaymentMethod method) {
        PaymentStrategy strategy = registry.get(method);
        if (strategy == null) {
            throw new IllegalArgumentException("지원하지 않는 결제 수단입니다: " + method);
        }
        return strategy;
    }
}

Spring이 List<PaymentStrategy>에 모든 구현체를 자동으로 주입한다. 새 PG사가 추가되면 구현체만 추가하면 Registry에 자동 등록된다. 서비스는 전혀 수정할 필요가 없다.

PaymentService 인터페이스와 DefaultPaymentService는 전략 패턴과는 별개다. 결제 비즈니스 로직(저장, Kafka 발행, 상태 관리) 자체를 추상화한 것으로, 나중에 결제 플로우 전체가 바뀌어도 구현체만 교체하면 된다. 현재 지원하는 결제 수단은 토스, 카카오페이, 신용카드, 계좌이체, 현금(테스트용)이다. 실제 PG 연동 시 각 전략의 process() 메서드 내부에서 PG사 SDK를 호출하면 된다.

현재 구조의 한계

첫번째로 클라이언트가 amount를 직접 전달하고 있다. 금액 조작이 가능한 보안 취약점이다. 실무에서는 클라이언트가 금액을 전달하지 않는다. 추후엔 클라이언트가 금액을 전달하는 구조 자체를 없애야 한다. 올바른 흐름은 SeatHeldEvent에 가격 정보를 포함시켜 reservation 생성 시 서버가 금액을 저장하고, payment-service는 reservationId로 금액을 조회해 결제한다. 클라이언트는 금액에 관여하지 않는다.

두번째 문제는 우선 seat-service에만 해당되지 않는다.

04편의 auth-service에서도 동일하게 발생했다. DB 저장과 Kafka 이벤트 발행이 하나의 트랜잭션으로 묶여있지 않아, 한쪽이 실패하면 데이터 불일치가 생긴다.

seat-service도 마찬가지다. Redis 점유는 성공했는데 Kafka 발행이 실패하면 예약이 생성되지 않는다. Kafka 이벤트는 발행됐는데 reservation-service가 처리 도중 죽으면, at-least-once 전달(스프링 카프카 기본)에서는 재시작 시 메시지가 재전달되어 예약이 중복 생성될 수 있다(오프셋을 처리 전에 커밋하는 구성이라면 유실도 가능). 그래서 consumer 멱등성이 필요하다. MSA에서 서비스 간 데이터 일관성 문제는 구조적으로 발생한다. 

auth-service: DB+Kafka -> Outbox 패턴 적합할 것으로 보인다.

seat-service: Redis+Kafka -> 점유 상태를 DB에도 적재해 Outbox를 적용하거나, at-least-once + consumer 멱등성 + 보정(reconciliation)으로 접근해 보면 좋을 것 같다.
