헥사고날 아키텍처와 DDD

Architecture · 2026-07-10

Intro

포트와 어댑터, 도메인 로직은 순수하게 유지해야해와 같은 말은 여기저기서 많이 들어봤다. 근데 막상 그래서 패키지는 어떻게 나누고, 클래스는 어떤 이름으로 뭘 넣어야 하는데? 라고 물으면 대답이 애매했다. 이론은 그럴듯한데 실제 코드로 옮기려니 감이 안 잡히는 느낌이었다.

그래서 이번엔 개념 설명보다 실제로 어떻게 패키지를 나누고, 어떤 클래스에 뭘 넣는지를 코드 위주로 정리해보려고 한다.

왜 이렇게까지 나눠야 하는거지?

보통 처음 배우는 구조는 이런 식이다.

Controller -> Service -> Repository

여기서 Service가 비즈니스 로직을 갖고, Repository가 JPA로 DB에 접근한다. 문제는 보통 Service가 다루는 엔티티 자체가 @Entity가 붙은 JPA 엔티티라는 거다. 그러다 보면 도메인의 핵심 규칙(예: "잔액은 마이너스가 될 수 없다")이 JPA 엔티티의 세터를 호출하는 Service 코드 여기저기에 흩어지기 쉽다.

이러면 두 가지가 뒤엉킨다.

  • 비즈니스 규칙이 인프라(JPA)와 묶여버린다. 엔티티 클래스가 JPA 애노테이션투성이라, 이 클래스를 인프라 없이 단위 테스트하기가 애매해진다
  • 규칙이 한 곳에 안 모여있다. "잔액 검증"이 어떤 서비스 메서드에는 있고 어떤 데는 빠져있어도, 컴파일러가 잡아주지 못한다

헥사고날 아키텍처(포트와 어댑터)는 이 문제를, 도메인을 인프라로부터 완전히 떼어놓는 것으로 푼다.

포트와 어댑터

가운데에 도메인(비즈니스 규칙)을 두고, 바깥 세계(웹 요청, DB, 외부 API)와 맞닿는 지점은 전부*인터페이스(포트)로만 정의한다. 그 인터페이스의 실제 구현체(어댑터)는 바깥에 둔다.

[웹 요청] -> (인바운드 어댑터: Controller)
                    |
            (인바운드 포트: 인터페이스)
                    |
              [애플리케이션 서비스] -- 여기서 도메인을 조립해서 씀
                    |
            (아웃바운드 포트: 인터페이스)
                    |
            (아웃바운드 어댑터: JPA 구현체) -> [DB]

핵심은 화살표의 방향이다. 안쪽(도메인, 애플리케이션)은 바깥쪽(Controller, JPA)을 전혀 모른다. 오히려 바깥쪽이 안쪽에서 정의한 인터페이스(포트)를 구현해서 안쪽에 "꽂히는" 구조다. 그래서 나중에 DB를 JPA에서 다른 걸로 바꾸거나, REST 대신 메시지 큐로 요청을 받게 바뀌어도, 도메인 코드는 한 줄도 안 건드려도 된다.

패키지 구조로 보면

글로만 보면 추상적이니 실제 패키지로 나눠보자. 계좌에서 돈을 출금하는 기능을 예로 들어보겠다.

domain/
  Account.java              # 애그리거트 루트 - 순수 자바, JPA 애노테이션 없음
  Money.java                 # 값 객체(Value Object)
  AccountRepository.java     # 아웃바운드 포트 (인터페이스)

application/
  WithdrawUseCase.java       # 인바운드 포트 (인터페이스)
  WithdrawService.java       # 애플리케이션 서비스 (WithdrawUseCase 구현체)

adapter/
  in/web/AccountController.java          # 인바운드 어댑터
  out/persistence/AccountEntity.java     # JPA 매핑 전용, domain.Account와는 별개
  out/persistence/AccountJpaRepository.java  # 아웃바운드 어댑터 (AccountRepository 구현체)

도메인 (순수 자바로만)

// domain/Account.java
public class Account {

    private final AccountId id;
    private Money balance;

    public Account(AccountId id, Money balance) {
        this.id = id;
        this.balance = balance;
    }

    public void withdraw(Money amount) {
        if (balance.isLessThan(amount)) {
            throw new InsufficientBalanceException(id, amount);
        }
        this.balance = balance.subtract(amount);
    }

    public Money balance() {
        return balance;
    }
}

// domain/Money.java
public record Money(long amount) {
    public Money {
        if (amount < 0) throw new IllegalArgumentException("금액은 음수일 수 없다");
    }

    public boolean isLessThan(Money other) {
        return this.amount < other.amount;
    }

    public Money subtract(Money other) {
        return new Money(this.amount - other.amount);
    }
}

Account에는 @Entity도, import jakarta.persistence.*도 없다. 잔액이 부족하면 출금할 수 없는 규칙이 정확히 한 곳(withdraw 메서드)에만 있다. 이 클래스는 DB나 스프링 없이도 그냥 new Account(...) 해서 단위 테스트를 돌릴 수 있다.

아웃바운드 포트 (도메인이 원하는 인터페이스)

// domain/AccountRepository.java
public interface AccountRepository {
    Account findById(AccountId id);
    void save(Account account);
}

이 인터페이스는 domain 패키지에 있다는 게 중요하다. 도메인이 저장소에 뭘 원하는지를 도메인이 직접 정의하는 거고, 실제 구현(JPA든 뭐든)은 바깥에서 이 규격에 맞춰 만든다.

애플리케이션 서비스 (도메인을 조립해서 쓰기만)

// application/WithdrawUseCase.java
public interface WithdrawUseCase {
    void withdraw(AccountId accountId, Money amount);
}

// application/WithdrawService.java
@Service
public class WithdrawService implements WithdrawUseCase {

    private final AccountRepository accountRepository;

    public WithdrawService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Override
    @Transactional
    public void withdraw(AccountId accountId, Money amount) {
        Account account = accountRepository.findById(accountId);
        account.withdraw(amount);          // 규칙 판단은 전부 도메인 안에서
        accountRepository.save(account);
    }
}

여기서 중요한 건 WithdrawService가 잔액 부족 여부를 직접 판단하지 않는것이다. if (balance < amount) 같은 코드가 여기 있으면 안 된다. 서비스는 그냥 도메인 객체를 가져오고, 도메인 메서드를 부르고, 저장하는 조율자(orchestrator) 역할만 한다. 판단은 전부 Account.withdraw() 안에서 일어난다.

어댑터 (도메인 바깥에서 인터페이스를 구현)

// adapter/in/web/AccountController.java
@RestController
@RequestMapping("/accounts")
public class AccountController {

    private final WithdrawUseCase withdrawUseCase;

    public AccountController(WithdrawUseCase withdrawUseCase) {
        this.withdrawUseCase = withdrawUseCase;
    }

    @PostMapping("/{id}/withdraw")
    public ResponseEntity<Void> withdraw(@PathVariable String id, @RequestBody WithdrawRequest request) {
        withdrawUseCase.withdraw(new AccountId(id), new Money(request.amount()));
        return ResponseEntity.ok().build();
    }
}

// adapter/out/persistence/AccountEntity.java
@Entity
@Table(name = "account")
public class AccountEntity {

    @Id
    private String id;
    private long balance;

    // JPA 요구사항용 기본 생성자, getter/setter 생략
}

// adapter/out/persistence/AccountJpaRepository.java
@Repository
public class AccountJpaRepository implements AccountRepository {

    private final SpringDataAccountRepository springDataRepository;

    public AccountJpaRepository(SpringDataAccountRepository springDataRepository) {
        this.springDataRepository = springDataRepository;
    }

    @Override
    public Account findById(AccountId id) {
        AccountEntity entity = springDataRepository.findById(id.value())
                .orElseThrow(() -> new AccountNotFoundException(id));
        return new Account(new AccountId(entity.getId()), new Money(entity.getBalance()));  // 엔티티 -> 도메인 변환
    }

    @Override
    public void save(Account account) {
        AccountEntity entity = new AccountEntity(account.id().value(), account.balance().amount());
        springDataRepository.save(entity);   // 도메인 -> 엔티티 변환
    }
}

AccountEntity(JPA 매핑용)와 Account(도메인)가 의도적으로 분리돼 있고, AccountJpaRepository가 그 사이를 변환해주는 어댑터 역할을 한다. 이 변환 코드가 좀 귀찮아 보일 수 있는데, 이게 바로 "도메인이 인프라를 모르게" 만드는 대가인 것 같다.

DDD는 어떻게?

헥사고날이 안과 밖을 어떻게 나눌지에 대한 답이라면, DDD(도메인 주도 설계)는 그 안쪽(도메인)을 어떻게 채울지에 대한 답인 것 같다. 둘이 자연스럽게 맞물린다.

  • 애그리거트(Aggregate) 위 예시의 Account가 애그리거트 루트다. "잔액은 마이너스가 될 수 없다"는 불변식(invariant)을 지키는 책임이 이 객체 하나에 모여있다. 이 불변식을 지키기 위한 조작은 반드시 Account의 메서드(withdraw)를 통해서만 가능하고, 바깥에서 필드를 직접 건드릴 방법이 없다
  • 값 객체(Value Object) Money처럼 식별자 없이 값 자체로 동등성이 결정되는 객체. record로 만들면 불변성이 자연스럽게 따라온다
  • 리포지토리는 도메인의 것 DDD에서는 "리포지토리 인터페이스는 도메인 모델의 일부"라고 본다. 헥사고날에서 "아웃바운드 포트는 안쪽에 정의된다"는 규칙과 정확히 같은 얘기다. 그래서 AccountRepository 인터페이스가 domain 패키지에 있는 거다

이 둘이 왜 같이 다뤄지는지 이제 좀 알 것 같다. 헥사고날이 그려주는 안/밖 경계와, DDD가 그 안쪽에 채워 넣는 애그리거트, 값 객체, 리포지토리같은 재료가 서로 맞아떨어지는 구조인 거다.

자주 놓치는 지점

공부하면서, 그리고 코드를 보면서 자주 보이는 실수들이 있었다.

JPA 엔티티를 그대로 도메인으로 쓰는 것. @Entity가 붙은 클래스 안에 withdraw() 같은 비즈니스 메서드를 넣는 경우가 많다. 이러면 도메인이 JPA에 의존하게 되고, 위에서 나눈 이유가 전부 무의미해진다. 엔티티와 도메인은 귀찮아도 분리하고 변환하는 게 맞는 것 같다.

애플리케이션 서비스가 판단을 대신하는 것. WithdrawService에 if (balance < amount) 같은 코드가 들어가는 경우도 흔하다. 이러면 규칙이 도메인과 서비스 두 군데로 흩어지고, 나중에 어디를 고쳐야 하는지 헷갈리게 된다. 판단은 도메인 객체 메서드 안에만 있어야 하는 것 같다.

포트를 너무 많이 만드는 것. 뭐든지 인터페이스로 감싸다 보면 클래스 수만 계속 늘어난다. 정말 구현체가 바뀔 가능성이 있거나, 테스트에서 가짜 구현으로 대체해야 하는 경계에만 포트를 두는 게 낫다. 도메인 내부의 사소한 헬퍼까지 다 인터페이스로 뺄 필요는 없어 보인다.

어댑터에 비즈니스 판단 로직이 들어가는 것. Controller에서 요청값 검증을 넘어서는 비즈니스 판단(예: 금액 한도 체크)을 하는 경우도 있다. 어댑터는 바깥 형식을 안쪽 형식으로 바꿔주는 통로에 머물러야 하는 것 같다.

그래서 항상 이렇게 나눌까?

지금까지 본 구조가 유지보수성이나 테스트 용이성 면에서는 명확히 더 나은 것 같다. 도메인이 인프라 변경에 흔들리지 않고, 규칙이 한 곳에 모여있어서 테스트도 인프라 없이 순수하게 돌릴 수 있다. 하지만 이 구조를 유지하려면 클래스 수가 확실히 늘어나고, 엔티티-도메인 변환 코드처럼 겉보기엔 반복적인 코드도 늘어난다. 정말 단순한 조회 API 하나 정도라면 이 정도까지 나누는 게 과할 수도 있겠다는 생각은 든다.

이건 예외적인 경우로 두고, 기본적으로는 도메인 규칙이 존재하는 이상 이 구조를 기본값으로 가져가는 게 맞다고 생각한다.

정리

  • 흔한 구조(Controller-Service-Repository)의 문제는 도메인 규칙이 JPA 같은 인프라와 뒤엉킨다.
  • 헥사고날은 도메인을 가운데 두고, 바깥과의 접점을 포트(인터페이스)로만 정의해서 안쪽이 바깥을 모르게 만든다.
  • 아웃바운드 포트(리포지토리 인터페이스)는 안쪽(도메인)에 있고, 그 구현(어댑터)은 바깥에서 갖다 붙인다.
  • DDD는 그 안쪽을 채우는 재료이다.애그리거트가 불변식을 지키고, 값 객체가 값 동등성을 표현하고, 리포지토리는 도메인의 일부로 취급된다.
  • 엔티티를 도메인으로 합쳐버리기, 서비스가 판단까지 대신하기, 포트 남발, 어댑터에 비즈니스 판단 로직 들어가기는 주의

포트와 어댑터라는 말만 들었을 땐 막연했는데, 실제로 패키지를 나누고 클래스 하나하나에 역할을 정확히 배정해보니 왜 이렇게 나누는지 이해가 됐다. 결국 핵심은 하나다.
