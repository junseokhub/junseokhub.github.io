부하 테스트와 장애 주입

Test · 2026-09-26

Intro

기능 테스트를 다 통과한 코드도, 요청이 몰리거나 의존하는 시스템이 느려지는 순간 전혀 다르게 동작할 수 있다. 재시도나 서킷브레이커 같은 장치를 넣어두고도, 실제로 그게 장애 상황에서 의도대로 동작하는지는 한 번도 확인해본 적이 없었다. 코드상으로는 있는데 검증은 안 된 상태였던 거다.

그래서 시스템이 얼마나 버티는지 확인하는 부하 테스트와, 일부러 장애를 일으켜서 버티는 방식을 확인하는 장애 주입(chaos)을 정리해보려고 한다. 둘은 목적이 다르다. 부하 테스트는 한계를 찾고, 장애 주입은 한계를 넘었을 때의 동작을 확인한다.

부하 테스트

부하 테스트라고 다 같은 테스트가 아니다. 알고 싶은 질문에 따라 부하를 주는 모양이 달라진다.

  • Load 테스트
    • 예상되는 평상시 트래픽에서 응답 시간과 에러율이 목표 안에 들어오는지
  • Stress 테스트
    • 부하를 계속 올렸을 때 어느 지점에서 무너지는가, 무너질 때 어떻게 무너지는지
  • Spike 테스트
    • 트래픽이 순간적으로 몇 배로 튀었을 때 버티는가, 그리고 다시 정상으로 돌아오는지
  • Soak 테스트
    • 적당한 부하를 몇 시간 이상 유지했을 때, 메모리 누수나 커넥션 고갈처럼 시간이 지나야 드러나는 문제가 생기는지

질문을 정하지 않고 그냥 부하를 걸어보면, 숫자는 나오는데 그 숫자로 뭘 판단해야 할지 모르는 상태가 되기 쉽다.

k6로 부하 테스트 짜기

k6는 JavaScript로 시나리오를 작성하는 오픈소스 부하 테스트 도구다. 테스트 스크립트가 코드라서 버전 관리와 CI 연동이 자연스럽고, 합격 기준(threshold)을 스크립트 안에 같이 정의할 수 있다는 게 큰 장점이다.

import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',   // 초당 요청 수를 고정
      rate: 200,
      timeUnit: '1s',
      duration: '5m',
      preAllocatedVUs: 100,
      maxVUs: 500,
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<300', 'p(99)<800'],   // 95%는 300ms, 99%는 800ms 이내
    http_req_failed: ['rate<0.01'],                   // 에러율 1% 미만
  },
};

export default function () {
  const res = http.get('http://localhost:8080/api/items');
  check(res, { 'status is 200': (r) => r.status === 200 });
}

threshold를 넘으면 k6가 실패 코드로 종료되기 때문에, CI 파이프라인에 넣으면 성능이 기준 밑으로 떨어진 변경을 자동으로 걸러낼 수 있다.

평균이 아니라 백분위로

응답 시간은 평균으로 보면 안 된다. 요청 100개 중 99개가 50ms고 1개가 5초면 평균은 100ms 정도로 괜찮아 보이지만, 그 1%의 사용자는 5초를 기다린 거다. 그래서 p95, p99 같은 백분위로 꼬리 구간(tail latency)을 봐야 실제 사용자 경험을 반영할 수 있다.

가상 사용자 수와 요청 도착률을 고정할까?

여기서 한 가지 자주 놓치는 함정이 있다. k6의 executor는 크게 두 모델로 나뉜다.

  • 가상 사용자(VU) 수를 고정하는 방식(ramping-vus 등, closed model)
    • 각 VU는 응답을 받아야 다음 요청을 보낸다. 그래서 서버가 느려지면 VU들도 같이 느려지고, 결과적으로 서버에 들어가는 요청 수 자체가 줄어든다
  • 요청 도착률을 고정하는 방식(constant-arrival-rate 등, open model)
    • 서버가 느려지든 말든 정해진 속도로 새 요청을 계속 보낸다

첫 번째 방식은 서버가 느려질수록 부하가 알아서 줄어드는 구조라, 서버가 실제보다 더 잘 버티는 것처럼 보이는 착시가 생길 수 있다. 이 현상을 coordinated omission이라고 부른다. 실제 서비스의 사용자들은 서버가 느리다고 요청을 덜 보내주지 않는다. 그래서 외부 트래픽을 받는 API의 한계를 측정할 때는 도착률을 고정하는 open model 쪽이 현실에 더 가까운 것 같다.

대안들

  • Gatling
    • Scala/Java DSL로 시나리오를 짠다. JVM 생태계에 익숙하면 자연스럽고, 리포트가 상세하다.
  • JMeter
    • 가장 오래되고 널리 쓰인 도구다. GUI로 시나리오를 만들 수 있지만, 시나리오 파일이 XML이라 코드 리뷰나 버전 관리가 불편하고 대규모 부하 생성 시 자원을 많이 쓴다.
  • nGrinder
    • 국내에서 많이 쓰이는 도구로, 여러 에이전트에 부하를 분산시키는 구조가 기본으로 들어있다.

시나리오를 코드로 관리하고 CI에 threshold로 붙이는 걸 기준으로 보면 k6가 제일 가볍게 맞는 것 같다. JVM 기반으로 통일하고 싶다면 Gatling이 대안이다.

부하 생성기 자체가 병목이 되지 않게해야 한다.

부하를 주는 쪽의 머신이 CPU나 네트워크 한계에 먼저 도달하면, 측정된 숫자는 서버의 한계가 아니라 부하 생성기의 한계가 된다. 테스트 중에는 부하 생성기의 자원 사용량도 같이 봐야 하고, 가능하면 테스트 대상과 같은 머신에서 부하를 걸지 않는 게 맞다.

장애 주입

부하 테스트가 얼마나 버티는지를 본다면, 장애 주입은 의존하는 무언가가 망가졌을 때 시스템이 어떻게 동작하는지를 본다. 재시도가 실제로 백오프를 타는지, 서킷브레이커가 정말 열리는지, 타임아웃이 설정대로 걸리는지는 장애를 실제로 일으켜봐야 확인할 수 있다.

장애를 어느 레이어에서 주입하느냐에 따라 쓰는 도구가 달라진다.

애플리케이션 레이어

Toxiproxy는 애플리케이션과 의존 대상(Redis, DB 등) 사이에 프록시를 끼워 넣고, 그 프록시에서 지연이나 연결 끊김을 일부러 만들어내는 도구다. Testcontainers에 Toxiproxy 모듈이 있어서, 통합 테스트 안에서 장애 시나리오를 코드로 재현할 수 있다.

// Redis 앞에 Toxiproxy를 두고, 애플리케이션은 프록시 주소로 접속하게 한다
ToxiproxyClient client = new ToxiproxyClient(toxiproxy.getHost(), toxiproxy.getControlPort());
Proxy redisProxy = client.createProxy("redis", "0.0.0.0:8666", "redis:6379");

// 응답을 1초씩 지연시킨다
redisProxy.toxics().latency("redis-latency", ToxicDirection.DOWNSTREAM, 1_000);

// 테스트: 타임아웃과 fallback이 설정대로 동작하는지 확인

// 연결 자체를 끊어버린다
redisProxy.disable();

이 방식은 개발 단계에서, 로컬과 CI에서 빠르게 반복해서 돌릴 수 있다는 게 가장 큰 장점이다. 다만 프록시를 통과하는 네트워크 장애만 흉내 낼 수 있어서, 파드가 통째로 죽거나 노드가 사라지는 것 같은 인프라 수준의 장애는 재현하지 못한다.

인프라 레이어

쿠버네티스 환경에서는 Chaos Mesh나 LitmusChaos 같은 도구로 클러스터 안에서 직접 장애를 일으킬 수 있다. 둘 다 CNCF 프로젝트이고, 장애 시나리오를 쿠버네티스 리소스(YAML)로 선언한다.

# 특정 파드를 강제로 종료
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: kill-one-order-pod
spec:
  action: pod-kill
  mode: one                 # 대상 중 하나만
  selector:
    labelSelectors:
      app: order-service

# Redis로 가는 네트워크에 지연을 주입
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: redis-delay
spec:
  action: delay
  mode: all
  selector:
    labelSelectors:
      app: redis
  delay:
    latency: 500ms
  duration: 5m

파드 종료, 네트워크 지연, 손실, 분리, CPU·메모리 압박처럼 실제 운영 환경에서 일어나는 장애를 그대로 재현할 수 있다는 게 장점이다. 대신 클러스터가 있어야 하고, 잘못 설정하면 의도하지 않은 범위까지 장애가 퍼질 수 있어서 다루는 데 더 신중해야 한다.

장애 주입의 원칙

도구보다 중요한 게 절차인 것 같다.

  • 정상 상태를 먼저 정의
    • 장애를 주입하기 전에, 정상일 때의 지표(에러율, 응답 시간, 처리량)가 어떤지를 기준으로 잡아둔다. 기준이 없으면 장애 중에 뭐가 나빠졌는지 판단할 수 없다.
  • 가설 정의
    • Redis가 500ms 느려져도 fallback 덕분에 에러율은 1% 미만으로 유지될 것이다처럼, 결과를 미리 예측하고 그게 맞는지 확인하는 방식으로 진행한다.
  • 영향 범위를 작게 시작
    • 파드 하나, 짧은 시간부터 시작해서 점점 넓힌다.
  • 관측성이 먼저
    • 메트릭과 트레이싱이 없으면 장애를 일으켜놓고도 무슨 일이 일어났는지 볼 수가 없다.

둘을 같이 쓰기

가장 현실적인 검증은 둘을 겹치는 것이다. 평상시 트래픽을 k6로 계속 흘려보내는 상태에서 장애를 주입하면, 부하가 걸린 상태에서 의존성이 망가졌을 때 시스템이 어떻게 반응하는지를 볼 수 있다. 부하 없는 상태에서 장애를 주입하면 멀쩡해 보이던 fallback이, 부하가 걸린 상태에서는 스레드 풀이 고갈되면서 같이 무너지는 경우가 있기 때문이다.

1. k6로 평상시 트래픽을 일정하게 흘린다 (정상 상태 지표 확보)
2. 부하를 유지한 채로 장애 주입 (예: Redis 지연 500ms)
3. 에러율·응답 시간·서킷브레이커 상태 변화를 관측
4. 장애 해제 후 정상 상태로 회복되는지, 얼마나 걸리는지 확인

회복 과정까지 보는 게 중요하다. 장애 중에 버티는 것만큼, 장애가 끝난 뒤 밀린 요청이 한꺼번에 몰리면서 두 번째 장애를 만들지 않는지도 확인해야 한다.

정리

  • 부하 테스트는 한계를 찾고, 장애 주입은 한계를 넘었을 때의 동작을 확인한다.
  • 부하 테스트는 Load, Stress, Spike, Soak처럼 알고 싶은 질문부터 정하고, 응답 시간은 평균이 아니라 p95, p99로 본다.
  • VU 수를 고정하는 closed model은 서버가 느려질수록 부하가 줄어드는 착시(coordinated omission)가 생긴다 — 외부 트래픽을 받는 API라면 도착률을 고정하는 open model이 현실에 가깝다.
  • k6는 시나리오와 합격 기준을 코드로 관리하고 CI에 붙이기 좋다. JVM으로 통일하고 싶다면 Gatling이 대안이다.
  • 장애 주입은 애플리케이션 레이어(Toxiproxy + Testcontainers)와 인프라 레이어(Chaos Mesh, LitmusChaos)로 나뉜다. 앞은 빠르게 반복 검증하기 좋고, 뒤는 실제 운영 장애에 가깝다.
  • 정상 상태 정의, 가설, 작은 범위, 관측성의 순서가 도구보다 중요하다.

재시도, 서킷브레이커, fallback을 코드에 넣어두는 것까지는 했는데, 그게 진짜 동작하는지는 장애를 일으켜보기 전까지 아무도 모른다는 걸 알게 됐다. 결국 이 두 테스트는 지금까지 넣어둔 방어 장치들이 실제로 방어를 하는지 확인하는 마지막 단계인 것 같다.
