API Gateway 비교 (Ingress vs Kong vs Spring Cloud Gateway)

Devops · 2026-08-24

Intro

서비스가 여러 개로 나뉘고 나니, 클라이언트가 어떤 서비스로 요청을 보내야 하는지를 매번 알아야 하는 게 불편해졌다. 그리고 인증이나 rate limit처럼 모든 서비스에 공통으로 필요한 걸 서비스마다 각자 구현하는 것도 비효율적으로 느껴졌다. 이 자리에 놓을 수 있는 게 Ingress, Kong, Spring Cloud Gateway 세 가지였는데, 다 요청을 받아서 적절한 곳으로 보낸다는 점에서는 비슷해 보여서 뭐가 다른지 헷갈렸다.

셋이 실제로 어느 레이어에서 동작하고, 뭘 잘하고 뭘 못하는지 정리해보려고 한다.

왜 이런 게 필요할까?

서비스가 하나일 땐 클라이언트가 그 서비스 하나만 알면 됐다. 서비스가 여러 개로 나뉘면 몇 가지 문제가 새로 생긴다.

  • 클라이언트가 이 요청은 어느 서비스로 가야 하는지를 다 알아야 한다
  • 인증, 로깅, rate limit처럼 모든 서비스에 공통으로 필요한 관심사를 서비스마다 각자 구현하게 된다
  • 서비스 내부 구조가 바뀔 때(분리, 통합)마다 클라이언트도 같이 바뀌어야 한다

API Gateway는 클라이언트와 여러 서비스 사이에 하나의 진입점을 두고, 라우팅과 공통 관심사를 여기서 처리하게 만든다.

[게이트웨이 없이]  클라이언트 -> 서비스 A / 서비스 B / 서비스 C (각각 인증, 로깅 등 중복 구현)
[게이트웨이 있이]  클라이언트 -> 게이트웨이 (인증, 로깅, 라우팅) -> 서비스 A / B / C

Ingress

Ingress는 쿠버네티스 자체의 리소스 스펙이다. 클러스터 바깥에서 들어오는 HTTP(S) 요청을, 정해둔 규칙(호스트, 경로)에 따라 클러스터 안의 서비스로 라우팅해준다.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /orders
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80

Ingress 자체는 스펙(규칙의 형식)일 뿐이고, 실제로 이 규칙을 해석해서 트래픽을 처리하는 건 별도의 Ingress Controller(nginx-ingress 등)다. 쿠버네티스를 이미 쓰고 있다면 추가 인프라 없이 이 리소스 하나로 기본적인 라우팅을 처리할 수 있다는 게 장점이다. 다만 기본 Ingress 스펙 자체는 라우팅에 집중돼 있어서, 복잡한 인증 로직이나 세밀한 트래픽 제어까지 하려면 컨트롤러별 확장 기능(annotation)에 의존해야 하고, 그 확장 기능은 컨트롤러마다 다르다.

Kong

Kong은 nginx(OpenResty) 위에 만들어진 전용 API Gateway다. 라우팅뿐 아니라 인증, rate limiting, 요청/응답 변환 같은 기능을 플러그인으로 조립해서 쓰는 구조가 핵심이다.

# Kong 라우트 + 플러그인 설정 예시
routes:
  - name: order-route
    paths: ["/orders"]
    service: order-service
plugins:
  - name: rate-limiting
    route: order-route
    config:
      minute: 100
  - name: jwt
    route: order-route

라우팅 규칙과 정책(인증, rate limit 등)을 선언적으로 조립할 수 있고, 필요한 기능 대부분이 이미 플러그인으로 존재해서 직접 구현할 일이 적다. 쿠버네티스 환경에서는 Kong Ingress Controller로 Ingress 리소스와 통합해서 쓸 수도 있고, 쿠버네티스 밖에서 독립적으로 운영할 수도 있다. 다만 이 모든 기능을 쓰려면 Kong이라는 컴포넌트 자체를 별도로 운영해야 하고(데이터베이스가 필요한 모드도 있다), 플러그인 조합이 늘어날수록 그 설정을 관리하는 부담도 커진다.

Spring Cloud Gateway

Spring Cloud Gateway는 이름 그대로 Spring 애플리케이션으로 동작하는 게이트웨이다. 라우팅 규칙과 필터를 자바 코드(또는 설정 파일)로 직접 정의한다.

@Bean
public RouteLocator routes(RouteLocatorBuilder builder) {
    return builder.routes()
            .route("order-route", r -> r.path("/orders/**")
                    .filters(f -> f.addRequestHeader("X-Gateway", "true")
                            .circuitBreaker(c -> c.setName("orderCB")))
                    .uri("lb://order-service"))
            .build();
}

Ingress나 Kong과 다르게, 이건 쿠버네티스 클러스터 경계나 별도 인프라 컴포넌트가 아니라 하나의 Spring 애플리케이션이다. 그래서 인증·로깅 로직을 자바 코드로 직접 짤 수 있고, 이미 Spring/스프링 클라우드 생태계(서비스 디스커버리, 서킷브레이커 등)를 쓰고 있다면 그 생태계와 자연스럽게 붙는다. 반면 Kong처럼 다양한 플러그인을 미리 갖춘 게 아니라서, 필요한 기능은 대부분 직접 구현하거나 관련 스프링 라이브러리를 조합해야 한다. 그리고 게이트웨이 자체가 애플리케이션이라, 이것도 하나의 배포 단위로 스케일링·모니터링 대상에 포함시켜야 한다.

그래서 뭐가 다를까?

  • 동작 레이어
    • Ingress는 쿠버네티스 클러스터의 네트워크 진입점(인프라 레이어)이고, Kong은 그 위에서 동작하는 전용 게이트웨이 컴포넌트, Spring Cloud Gateway는 아예 하나의 애플리케이션이다.
  • 기능 확장 방식
    • Ingress는 컨트롤러별 annotation, Kong은 플러그인 조립, Spring Cloud Gateway는 자바 코드 작성.
  • 생태계 결합도
    • Ingress는 쿠버네티스에, Kong은 자체 생태계에, Spring Cloud Gateway는 Spring 생태계에 각각 묶여 있다.
  • 운영 부담
    • Ingress는 이미 쿠버네티스를 쓰고 있다면 추가 컴포넌트가 거의 없고, Kong은 별도 컴포넌트를 운영해야 하고, Spring Cloud Gateway는 애플리케이션 하나를 통째로 더 운영하는 셈이다.

그래서 언제 뭘 쓰는게 좋을까?

  • 단순한 경로/호스트 기반 라우팅만 필요하고, 이미 쿠버네티스 위에서 돌고 있다면 Ingress만으로 충분한 경우가 많은 것 같다.
  • 인증, rate limiting처럼 정책성 기능이 여러 개 필요하고, 그걸 코드 작성 없이 선언적으로 관리하고 싶다면 Kong 같은 전용 게이트웨이가 잘 맞는다.
  • 이미 Spring 생태계로 서비스들을 짜고 있고, 게이트웨이 로직 자체를 세밀하게 자바 코드로 통제하고 싶다면 Spring Cloud Gateway가 자연스럽다.

셋은 겹치는 부분도 있지만 완전히 대체 관계는 아닌 것 같다. 실제로는 Ingress로 기본 진입점을 만들고, 그 뒤에 Kong이나 Spring Cloud Gateway를 두어 세밀한 정책을 처리하는 식으로 같이 쓰는 구성도 흔하다.

클라이언트 -> Ingress(기본 진입, TLS 종료) -> Kong 또는 Spring Cloud Gateway(정책, 라우팅 세부 제어) -> 각 서비스

정리

  • API Gateway는 클라이언트와 여러 서비스 사이의 진입점을 통일하고, 공통 관심사(인증, 로깅, rate limit)를 한곳에 모으는 역할이다.
  • Ingress는 쿠버네티스 네이티브 진입점이라 추가 인프라 없이 기본 라우팅을 처리한다.
  • Kong은 플러그인으로 정책을 조립하는 전용 게이트웨이라, 다양한 기능을 코드 없이 선언적으로 붙일 수 있다.
  • Spring Cloud Gateway는 애플리케이션 자체라 자바 코드로 세밀하게 통제할 수 있고 Spring 생태계와 잘 붙는다.
  • 셋은 서로 대체하기보다, 계층을 나눠서 같이 쓰는 경우도 많다.

처음엔 이 셋 중 하나를 골라야 한다고 생각했는데, 실제로는 각자 동작하는 위치가 달라서 오히려 같이 쓰는 조합이 더 자연스러운 경우가 많은 것 같다. 어디까지를 인프라 레이어에서 처리하고, 어디부터를 애플리케이션 코드로 통제하고 싶은지부터 정하는 게 먼저인 것 같다.
