[Seatflow] 15. 쿠폰 시스템

Lab/SeatFlow · 2026-07-21

Intro

14편에서 인증/인가를 구현했으니, 이제 그 위에서 실제 관리자 기능을 채울 차례다. 이번 편에서 다루는 건 세 가지다. 쿠폰(선착순 발급과 결제 할인), 공연 생성 검증 강화, 좌석 배치 정보다. 가장 비중이 큰 건 쿠폰이다. 새 서비스를 하나 만들고, 그 서비스가 기존 결제 흐름에 어떻게 끼어드는지가 이번 편의 핵심이다.

쿠폰을 어디에 둘까?

쿠폰은 발급, 만료, 사용, 복원이라는 자기 라이프사이클을 가진 도메인이다. 다른 서비스(payment나 reservation)에 얹기보다 독립된 서비스로 분리하는 게 맞다고 판단했다. coupon-service를 새로 만들었다.

발급 방식

쿠폰을 어떻게 나눠줄지부터 정해야 했다.

  • 지정 발급

    • 관리자가 특정 사용자에게 쿠폰을 콕 집어 준다. 구현이 단순하다. 대신 누구에게 줄지를 관리자가 일일이 판단해야 해서, 이벤트성 쿠폰(선착순 100명 등)에는 안 맞는다.

  • 선착순 발급

    • 관리자는 쿠폰 N장, 할인 X원짜리 쿠폰만 만들고, 실제로 누가 받는지는 사용자들이 몰려서 정해진다. 재고를 여러 사용자가 동시에 두고 경쟁하는 구조라 동시성 제어가 필요해진다.

나는 선착순으로 갔다. 이전 쿠폰/재고 블로그에서도 해봤고, 재고를 동시에 여러 명이 다투는 문제는 9편에서 좌석 정원을 다룰 때 이미 풀어본 문제라, 그 경험을 그대로 재사용할 수 있다는 것도 이유였다.

선착순 발급의 동시성 제어

쿠폰을 만들 때 총 수량과 발급 수량을 따로 두고, 발급 수량 증가를 원자적 UPDATE로 처리한다.

@Modifying
@Query("UPDATE CouponCampaign c SET c.issuedQuantity = c.issuedQuantity + 1 " +
       "WHERE c.id = :campaignId AND c.issuedQuantity < c.totalQuantity")
int increaseIssuedQuantity(@Param("campaignId") Long campaignId);

엔티티를 읽어서 +1 하고 저장하는 방식은 두 요청이 동시에 같은 값을 읽어 둘 다 성공한 것처럼 처리해버릴 위험이 있다. WHERE 절의 조건 자체가 재고가 남아있어야만 이 UPDATE가 성공한다는 락 역할을 하게 만들면, 여러 요청이 동시에 몰려도 DB가 순서를 강제한다. 결과가 0이면 이미 소진된 것이다. 1인 1매 제약은 (campaignId, userId) 유니크 제약으로 DB에 맡겼다. 같은 사용자가 광클로 여러 번 요청해도, 재고 차감은 성공하더라도 두 번째 insert부터는 유니크 제약에 걸려 실패한다. 즉, 이미 차감된 재고는 되돌리지 않는다. 그 재고는 이미 이 요청이 정당하게 차지한 몫이고, 이후 실패는 같은 쿠폰에 같은 사람이 중복 요청했다는 별개의 제약이기 때문이다.

결제 시점에 쿠폰을 적용하는 이유

쿠폰 적용 시점을 정할 때 좌석을 고를 때, 예매가 만들어질 때, 결제할 때 몇 가지 지점을 검토했다.

나는 결제 시점으로 정했다. 이유는 단순하다. 할인이라는 개념 자체가 얼마를 낼지를 결정하는 일이고, 그건 결제의 책임이다. 여기서 중요한 제약이 하나 있다. 결제는 PG(지금은 mock)를 통해 이루어지는데, PG는 우리가 통제할 수 없는 외부다.

할인을 PG에 적용하는 건 애초에 불가능한 개념이다. 대신 PG를 부르기 전에 할인이 반영된 최종 금액을 내 쪽에서 확정하고, PG에는 그 최종 금액만 전달한다. PG는 할인이 있었는지, 얼마였는지 전혀 몰라도 되고 몰라야 한다고 생각한다.

BigDecimal payAmount = reservation.amount();
BigDecimal discountAmount = BigDecimal.ZERO;
if (command.couponId() != null) {
    var validation = validateCoupon(command.couponId(), command.userId());
    discountAmount = validation.discountAmount();
    payAmount = reservation.amount().subtract(discountAmount);
}
// PG는 이 payAmount만 받는다. 할인이 있었는지 모른다.
strategyRegistry.get(command.paymentMethod()).process(payment.getPaymentNumber(), payAmount);

이건 10편에서 결제 금액을 서버가 재검증했던 것과 같은 자리다. 클라이언트가 보낸 금액을 그대로 믿지 않고 서버가 진짜 금액을 계산했던 것처럼, 할인 계산도 서버(payment) 쪽에서 PG 호출 전에 끝낸다.

검증과 확정을 분리한 이유

coupon-service의 내부 API는 하나가 아니라 둘이다.

validate(couponId, userId) // 유효성만 확인, 상태 안 바꿈
confirm(couponId, userId, reservationId) // 실제로 이 결제에 확정 적용

처음엔 하나로 합쳐서 검증하면서 바로 확정하는 API를 생각했다. 문제는 확정에는 어느 결제/예매에 쓰였는지 식별자가 필요한데, 검증은 PG를 부르기 전에 일어나서 아직 그 식별자가 없다는 점이었다. 반대로 확정을 결제 성공 후로 미루면, 검증과 확정 사이에 시간차가 생기지만 그게 오히려 안전하다. 즉, PG가 실패했는데 쿠폰만 소진되는 상황을 막을 수 있다.

결제 흐름:
  1. validate: PG 호출 전, 할인액 확인 (쿠폰 상태 안 바뀜)
  2. PG 처리
  3. 성공 시에만 confirm: 쿠폰을 이 결제에 확정

실패(2번)하면 3번(confirm)을 아예 안 부르니, 쿠폰은 검증만 되고 상태가 그대로 남아 재사용 가능하다. 별도 롤백 로직이 필요 없다.

서비스 경계 

취소 시 쿠폰을 복원하는 로직도 payment 안에 있다.

if (payment.getCouponId() != null) {
    try {
        couponClient.restoreCoupon(reservationId);
    } catch (Exception e) {
        log.error("Coupon restore failed, needs manual recovery: ...", e);
    }
}

취소 Saga의 오케스트레이터는 reservation에 있다(11, 12편). 쿠폰 복원을 오케스트레이터가 직접 호출하게 만들 수도 있었지만, 그러면 reservation이 이 예매가 쿠폰을 썼는지, coupon-service를 어떻게 부르는지 같은 결제 도메인의 지식을 갖게 된다. 환불을 처리하는 쪽(payment)이 환불과 같은 타이밍에 쿠폰 복원까지 맡는 게, 각 서비스가 자기 책임 범위 밖의 내용을 갖지 않는게 맞다고 판단했다. reservation은 여전히 환불됐다라는 이벤트만 받아 Saga를 완료 처리할 뿐, 쿠폰의 존재 자체를 모른다.

여기서도 13편의 원칙이 그대로 적용된다. 환불은 이미 끝난 뒤라, 쿠폰 복원이 실패해도 그 실패가 환불 자체를 되돌리면 안 된다. 실패하면 로그로 남기고 운영에서 확인한다.

공연 생성과 좌석 등급 

공연 생성 요청을 검증하면서, 좌석 등급(grade)을 문자열로 받아 서비스 계층에서 enum.valueOf()로 변환하던 부분을 손봤다. 문자열로 받으면 잘못된 값이 들어왔을 때 IllegalArgumentException이 서비스 로직 한가운데서 터지고, 이게 처리되지 않으면 500으로 이어진다. 요청 DTO 단계에서 처음부터 enum(SeatGradeType)으로 받으면, Jackson이 역직렬화 시점에 걸러줘서 잘못된 값은 400으로 명확하게 응답된다. 같은 검증이라도 어느 계층에서 걸리느냐가 응답의 성격을 바꾼다.

public record SeatGradeRequest(
        @NotNull SeatGradeType grade,   // String이 아니라 처음부터 enum
        @NotNull @Positive Integer capacity,
        @NotNull @PositiveOrZero BigDecimal price
) {}

공연 날짜도 @Future를 추가해 과거 날짜로 공연이 만들어지는 걸 막았다.

좌석 배치

관리자가 좌석 배치도를 지정할 수 있도록 좌표(posX, posY) 컬럼을 추가했다. 다만 이번 편에서는 이 값을 채우는 API나 조회 응답에 반영하는 로직은 만들지 않았다. 프론트엔드가 없는 지금 시점에 배치도 UI를 채울 수단이 없어서, 컬럼만 미리 마련해두는 선에서 멈췄다. 스키마를 미리 열어두면 나중에 필요할 때 마이그레이션 없이 기능만 얹을 수 있다는 정도의 실용적 이유다. 나중에 FE는 AI를 활용해서 만들어 볼 계획이니까 그때 만들어 둔 컬럼 기반으로 UI를 만들어보면 좋을 것 같다.

정리

  • 쿠폰을 지정 발급이 아니라 선착순으로 설계했고, 재고 경쟁은 9편의 좌석 정원 문제와 같은 방식(원자적 UPDATE)으로 풀었다.
  • 할인은 결제 시점에, PG를 부르기 전에 계산이 끝나야 한다. PG는 할인 개념을 몰라도 되는 게 아니라 몰라야 한다.
    • 최종 금액만 받는다.
  • 쿠폰 검증과 확정을 분리했다.
    • 검증은 상태를 안 바꾸고, 확정은 결제 성공 후에만 일어나 실패 시 별도 롤백이 필요 없다.
  • 쿠폰 도메인 지식(사용 여부, 복원 방법)은 payment 안에만 두었다.
    • 환불을 처리하는 쪽이 복원까지 같은 타이밍에 맡는 게 서비스 경계를 지키는 선택이었다.
  • 검증을 어느 계층에서 하느냐가 실패의 성격을 바꾼다.
    • 서비스 로직 안에서 걸리면 500이 될 수 있는 것이, 요청 DTO 단계에서 걸리면 400으로 명확해진다.
