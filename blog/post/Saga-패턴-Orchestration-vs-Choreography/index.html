Saga 패턴 (Orchestration vs Choreography)

Architecture · 2026-08-10

Intro

여러 서비스에 걸친 하나의 작업을 처리해야 하는데, 각 서비스가 자기 DB를 따로 갖고 있으면 전체를 하나로 묶는 트랜잭션이 없다. 서비스 A는 성공했는데 서비스 C에서 실패하면, A와 B를 되돌릴 방법이 마땅치 않다. 이 문제를 푸는 게 Saga 패턴이라는 건 알고 있었는데, 막상 구현하려니 그래서 이걸 누가 지휘하는데?라는 질문이 남았다. 중앙에서 순서를 관리하는 방식(Orchestration)과, 각 서비스가 알아서 반응하는 방식(Choreography) 둘 다 Saga라고 불리는데, 실제로 뭐가 다른지 정리해보려고 한다.

Saga가 푸는 문제

여러 서비스에 걸친 작업을 각 서비스의 로컬 트랜잭션 여러 개로 쪼개고, 각 단계가 다음 단계를 이벤트로 트리거하는 게 Saga의 기본 발상이다. 중간에 실패하면 전역 롤백 대신, 이미 끝난 단계를 거꾸로 상쇄하는 보상 트랜잭션으로 되돌린다.

정상:  A 커밋 -> B 커밋 -> C 커밋
실패:  A 커밋 -> B 커밋 -> C 실패
보상:  A 보상 <- B 보상 <- (C는 애초에 실패해서 커밋된 게 없음)

문제는 A가 끝나면 B를 부르고, B가 끝나면 C를 부르는 이 흐름을 누가 관리하느냐다. 여기서 두 방식이 갈린다.

Orchestration

Orchestration은 전체 흐름을 아는 지휘자(orchestrator) 하나를 두고, 그 지휘자가 각 서비스에게 이제 네 차례라고 직접 명령을 내리는 방식이다.

[Orchestrator]
   │ "A 실행해" -> A 서비스 -> 완료 응답
   │ "B 실행해" -> B 서비스 -> 완료 응답
   │ "C 실행해" -> C 서비스 -> 실패 응답
   │ "B 보상해" -> B 서비스
   │ "A 보상해" -> A 서비스

@Component
@RequiredArgsConstructor
public class OrderSagaOrchestrator {

    private final OrderServiceClient orderService;
    private final InventoryServiceClient inventoryService;
    private final ShippingServiceClient shippingService;

    public void execute(OrderCommand command) {
        OrderResult order = orderService.createOrder(command);
        try {
            InventoryResult inventory = inventoryService.reserve(order.orderId(), command.items());
            try {
                shippingService.prepare(order.orderId());
            } catch (Exception e) {
                inventoryService.release(inventory.reservationId());   // 보상
                throw e;
            }
        } catch (Exception e) {
            orderService.cancel(order.orderId());   // 보상
            throw e;
        }
    }
}

전체 흐름이 OrderSagaOrchestrator 클래스 하나에 순서대로 다 적혀 있다. 그래서 지금 이 작업이 어느 단계까지 왔는지, 실패하면 어떤 순서로 보상해야 하는지를 이 한 곳만 보면 파악할 수 있다. 각 서비스(A, B, C)는 자기가 전체 흐름의 몇 번째 단계인지 몰라도 된다. 그냥 지휘자가 시키는 대로 실행하고 결과만 돌려주면 끝이다.

Choreography

Choreography는 중앙 지휘자가 없다. 각 서비스가 자기 일을 끝내면 나 끝났다는 이벤트를 발행하고, 다음 단계를 담당하는 서비스가 그 이벤트를 구독해서 알아서 반응한다.

A 서비스: 작업 완료 -> A 완료 이벤트 발행
                              │
B 서비스: "A 완료"를 구독하고 있다가 -> 작업 시작 -> 완료되면 "B 완료" 이벤트 발행
                                                            │
C 서비스: "B 완료"를 구독하고 있다가 -> 작업 시작 -> 실패하면 "C 실패" 이벤트 발행
                                                            │
B 서비스: "C 실패"를 구독하고 있다가 -> 자기 작업을 보상
A 서비스: "B 보상됨"을 구독하고 있다가 -> 자기 작업을 보상

// A 서비스
@Transactional
public void createOrder(OrderCommand command) {
    Order order = orderRepository.save(Order.from(command));
    eventPublisher.publishEvent(new OrderCreatedEvent(order.getId(), command.items()));
}

// B 서비스 - A가 발행한 이벤트를 구독
@KafkaListener(topics = "order-created")
public void onOrderCreated(OrderCreatedEvent event) {
    try {
        inventoryService.reserve(event.orderId(), event.items());
        eventPublisher.publish(new InventoryReservedEvent(event.orderId()));
    } catch (Exception e) {
        eventPublisher.publish(new InventoryReservationFailedEvent(event.orderId()));
    }
}

// A 서비스 - 뒷단에서 실패했다는 이벤트를 구독해서 스스로 보상
@KafkaListener(topics = "inventory-reservation-failed")
public void onInventoryReservationFailed(InventoryReservationFailedEvent event) {
    orderService.cancel(event.orderId());   // 스스로 보상
}

각 서비스는 자기 앞뒤 단계가 누구인지만 알면 된다. A는 자기가 끝났다는 것만 알리고, 그 뒤를 누가 처리하는지 몰라도 된다. 새로운 단계를 흐름에 끼워 넣고 싶으면, 기존 서비스들을 건드리지 않고 그냥 관련 이벤트를 구독하는 서비스 하나만 추가하면 된다.

그래서 뭐가 다른데?

  • 흐름의 가시성
    • Orchestration은 지휘자 코드 한 곳만 보면 전체 흐름을 알 수 있다. Choreography는 흐름이 각 서비스에 흩어져 있어서, 전체 그림을 파악하려면 관련된 모든 서비스의 이벤트 구독 관계를 다 따라가야 한다.
  • 결합도
    • Orchestration은 지휘자가 각 서비스를 다 알아야 한다(지휘자 -> 서비스 방향의 의존). Choreography는 서비스끼리 직접 알 필요가 없고, 오직 이벤트 스펙에만 의존한다.
  • 변경 용이성
    • Choreography는 새 단계를 추가할 때 기존 코드를 거의 안 건드려도 된다. Orchestration은 지휘자 코드를 수정해야 한다.
  • 디버깅
    • Orchestration은 실패했을 때 지휘자 로그만 봐도 어디서 멈췄는지 바로 보인다. Choreography는 이벤트가 여러 서비스를 거쳐가기 때문에, 분산 트레이싱 같은 도구 없이는 실패 지점을 추적하기 어려워진다.
  • 순환 의존 위험
    • Choreography는 서비스가 늘어날수록 누가 누구의 이벤트를 구독하는지 복잡하게 얽히기 쉽다. 이벤트 구독 관계를 잘못 설계하면 서비스 간에 사실상 순환 의존이 생길 수도 있다.

그래서 언제 뭘 쓰면될까?

  • 참여하는 서비스 수가 적고, 전체 흐름을 한눈에 파악하는 게 중요하다면 Orchestration이 맞는 것 같다. 특히 흐름이 복잡한 조건 분기를 많이 포함한다면, 그 분기를 지휘자 코드 하나에 모아두는 게 각 서비스에 흩어놓는 것보다 관리하기 쉽다
  • 참여하는 서비스가 각자 독립적으로 진화해야 하고, 새로운 단계가 자주 추가되는 구조라면 Choreography가 어울린다. 서비스 간 결합을 최소화하고 싶을 때도 이쪽이 낫다
  • 다만 서비스 수가 많아질수록 Choreography의 흐름이 안 보인다는 단점이 급격히 커지는 것 같다. 그래서 어느 정도 규모가 커지면 Orchestration으로 가거나, Choreography를 유지하더라도 분산 트레이싱을 반드시 같이 갖추는 게 맞는 것 같다

정리

  • Saga는 여러 서비스의 로컬 트랜잭션을 이어 붙이고, 실패하면 보상 트랜잭션으로 되돌리는 패턴이다.
  • Orchestration은 중앙 지휘자가 순서를 관리한다. 흐름이 한 곳에 보이지만, 지휘자가 모든 서비스를 알아야 한다.
  • Choreography는 각 서비스가 이벤트를 듣고 알아서 반응한다. 결합도는 낮지만, 흐름이 흩어져서 전체 그림을 보기 어렵다.
  • 서비스 수가 적고 흐름이 복잡하면 Orchestration, 서비스가 독립적으로 진화해야 하면 Choreography 쪽이 잘 맞는 것 같다.

같은 이름(Saga)으로 불리지만, 실제로는 누가 흐름을 아는지에 대한 질문에 정반대로 답하는 두 가지 방식이었다. 지휘자에게 지식을 모을 것인가?, 아니면 각자에게 나눠줄 것인가? 결국 이 결정이 Saga를 구현할 때 제일 먼저 해야 하는 선택인 것 같다.
