Virtual Thread가 뭔데?

Java 21에서 정식 도입된 경량 스레드다. 기존 플랫폼 스레드는 OS 스레드와 1:1로 매핑되어 블로킹 시 스레드가 점유된다. Virtual Thread는 JVM이 관리하는 경량 스레드로, 블로킹 시 OS 스레드를 반환하고 다른 작업을 처리한다.

Spring MVC에서는 설정 하나로 활성화할 수 있다.

spring:
  threads:
    virtual:
      enabled: true

코드 변경 없이 Tomcat의 모든 요청 처리 스레드가 Virtual Thread로 동작한다.

또 추가로 설정하려면

@Async 별도 설정

@Configuration 
@EnableAsync 
public class AsyncConfig {
     @Bean public Executor asyncExecutor() {
         return Executors.newVirtualThreadPerTaskExecutor();
    } 
}

Scheduled Task

@Configuration 
public class SchedulerConfig {
     @Bean public TaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setThreadFactory(Thread.ofVirtual().factory()); 
        return scheduler;
    }
}

Pinning JDK 21에서는 synchronized 블록 안에서 블로킹 호출이 발생하면 Virtual Thread가 캐리어 스레드에 고정(pinning)되어 장점이 사라지므로 주의해야 한다. 이런 경우 ReentrantLock 사용이 권장된다.

참고로 JDK 24(JEP 491)부터는 synchronized에서도 pinning이 발생하지 않도록 개선되었기 때문에, 향후 JDK 업그레이드 시점에는 이 제약이 사라진다.

커넥션 풀 조정 Virtual Thread는 거의 무제한으로 생성되기 때문에, 결국 DB 커넥션 풀이 동시성의 병목이 된다. 수천 개의 Virtual Thread가 동시에 커넥션을 요구하면 HikariCP에서 대기가 길어져 오히려 응답 시간이 악화될 수 있다. maximum-pool-size를 적절히 늘리거나, 필요하다면 Semaphore로 동시 실행 수를 제한하는 전략이 필요할 것 같다.

PESSIMISTIC에서 MVC가 더 높은 TPS를 보였다. SELECT FOR UPDATE는 락을 잡은 트랜잭션이 끝날 때까지 다른 요청이 대기해야 하는 본질적으로 직렬화되는 작업이다. 이런 상황에서는 논블로킹의 장점이 발휘될 여지가 거의 없다. 오히려 R2DBC의 리액티브 컨텍스트 스위칭 오버헤드만 추가되는 셈이라, 단순한 HikariCP 커넥션 풀 + Virtual Thread 조합이 더 효율적으로 동작했다.

REDIS_LUA에서는 WebFlux가 앞선다. 논블로킹 Redis 클라이언트(Lettuce)와 R2DBC가 조합되면서 DB 대기 중에도 다른 요청을 처리할 수 있기 때문이다.

KKAFKA 에서 MVC가 압도적이다. 좀 이상한 결과라고는 생각하는데 아마 Reactor Kafka의 스케줄러 오버헤드, 테스트 환경 변수 등이 복합적으로 작용했을 가능성이 있다. 정확한 비교를 위해서는 동일 환경에서 반복 측정이 필요하다.
Kafka Producer는 기본적으로 메시지를 내부 배치 버퍼에 넣고 즉시 반환하는 비동기 구조다(acks=1 기준). 즉, API 응답까지의 경로에서 실제 I/O 대기가 거의 없다. 논블로킹이 빛을 발하려면 "오래 걸리는 I/O 대기"가 있어야 하는데, 이 시나리오에는 그게 없다. 결과적으로 MVC + Virtual Thread가 리액티브 오버헤드 없이 그대로 빠르게 처리한다.

Consumer 처리 시간은 WebFlux가 더 빠르다. 특히 LUA Consumer에서 차이가 크다. WebFlux는 R2DBC 비동기 DB 처리로 Consumer 3개가 논블로킹으로 동시에 처리하는 반면, MVC는 블로킹 JDBC로 처리하기 때문이다.

LUA Consumer에서 MVC가 특히 느린 이유는 Outbox Scheduler 때문이다. Scheduler가 1초마다 PENDING 이벤트를 읽어 DB stock을 차감하는 구조라서 오버헤드가 크다. fixedDelay를 100ms로 줄이면 103초 → 85초로 개선됐지만 대신 TPS가 떨어졌다.

코드 복잡도 비교

이번 시리즈를 구현하면서 가장 크게 느낀 점은 코드 복잡도의 차이다.

WebFlux 비관적 락 재고 차감:

return databaseClient.sql("SELECT * FROM products WHERE id = :id FOR UPDATE")
        .bind("id", productId)
        .map((row, metadata) -> row.get("stock", Integer.class))
        .one()
        .flatMap(stock -> {
            if (stock == null || stock <= 0) {
                return Mono.error(new BusinessException(ErrorCode.PRODUCT_OUT_OF_STOCK));
            }
            return databaseClient.sql("UPDATE products SET stock = stock - 1 WHERE id = :id")
                    .bind("id", productId)
                    .fetch()
                    .rowsUpdated()
                    .then(productRepository.findById(productId));
        })
        .flatMap(product -> defaultOrderService.saveOrder(userId, product, couponIssueId))
        .as(transactionalOperator::transactional);

MVC 비관적 락 재고 차감:

@Transactional
public Order createOrder(Long userId, Long productId) {
    Product product = productRepository.findByIdWithLock(productId)
            .orElseThrow(() -> new BusinessException(ErrorCode.PRODUCT_NOT_FOUND));
    if (product.getStock() <= 0) {
        throw new BusinessException(ErrorCode.PRODUCT_OUT_OF_STOCK);
    }
    product.decrementStock();
    return orderRepository.save(Order.builder()
            .user(userService.findById(userId))
            .product(product)
            .originalPrice(product.getPrice())
            .finalPrice(product.getPrice())
            .build());
}

같은 로직인데 가독성 차이가 크다. WebFlux는 flatMap 체인을 이해하고 TransactionalOperator까지 직접 관리해야 한다.

@Transactional 자체는 R2DBC에서도 동작하지만, 일반적인 PlatformTransactionManager가 아니라ReactiveTransactionManager(R2dbcTransactionManager) 위에서 동작한다. Spring Boot가 자동 구성해주긴 하지만, 메서드 반환 타입이 반드시 Mono/Flux여야 하고 리액티브 체인 안에서 호출되어야 정상적으로 트랜잭션이 적용된다. MVC처럼 "그냥 붙이면 끝"이 아니라는 점이 함정이라 조심해야한다.

현재 WebFlux에서는 @Transactional 대신 TransactionalOperator.transactional()로 체인을 감쌌다. 리액티브에서는 트랜잭션 컨텍스트가 Reactor Context를 통해 전파되기 때문에, 이렇게 명시적으로 묶어주는 방식이 더 안전하고 직관적이다.
반면, MVC는 그냥 읽히는 대로 동작한다. @Transactional 붙이고 @Lock으로 비관적 락 걸면 끝이다.

느낀 점

이번 시리즈를 통해 WebFlux와 MVC + Virtual Thread를 모두 구현해보면서 몇 가지를 느꼈다.

WebFlux의 강점은 분명하다. 논블로킹 처리가 진가를 발휘하는 상황, 특히 많은 I/O 대기가 발생하는 환경에서 적은 스레드로 높은 처리량을 낸다. Consumer 처리 시간 비교에서 WebFlux가 일관되게 앞선 것이 그 증거다.

하지만 대가가 크다. Mono, Flux, flatMap 체인, subscribe(), TransactionalOperator, ReactiveTransactionManager... 반응형 프로그래밍 패러다임을 팀 전체가 이해하고 있어야 한다. 디버깅도 어렵다. 스택 트레이스가 Netty 내부 구조까지 뒤섞여 나오고, 어디서 에러가 발생했는지 찾기가 힘들다.

Virtual Thread는 MVC의 동시성 한계를 크게 완화했다. 이전의 MVC는 블로킹 I/O가 많으면 스레드가 고갈되는 문제가 있었다. Virtual Thread로 이 문제가 해결되면서 MVC도 충분한 동시성을 낼 수 있게 됐다. KAFKA에서 MVC가 WebFlux보다 빠르게 나온 것은 흥미로운 결과다. 실제 원인이 Virtual Thread의 효율성인지, Reactor Kafka의 오버헤드인지, 측정 환경의 변수인지 확실하지 않지만, 적어도 "단순한 비동기 발행"에서는 MVC + Virtual Thread도 충분한 경쟁력을 보여준다는 점은 분명하다.

"WebFlux를 써야 하는가?" 에 대한 답은 상황에 따라 다를 것으로 생각된다. 처리량이 극도로 중요하고, 팀이 반응형 프로그래밍에 익숙하다면 WebFlux가 유리하다. 그렇지 않다면 MVC + Virtual Thread가 코드 가독성과 생산성 측면에서 더 현실적인 선택이다.

전체 시리즈 마무리

단순히 어떤 기술이 빠른지 측정하는 것을 넘어, 각 기술의 트레이드오프를 이해하는 과정이었다. 낙관적 락이 고경쟁 환경에서 처참하게 실패하는 것도, Redis와 DB 사이에 정합성 문제가 왜 발생하는지도, Outbox Pattern이 왜 필요한지도 직접 삽질하면서 이해했다.

전체 시리즈를 마무리하면서 좀 더 파보고 싶은 것도 보이기 시작했다.

  1. SagaPattern
    Outbox는 단일 서비스 안에서 메시지 발행과 DB 트랜잭션의 원자성을 보장하는 패턴이다. 주문 → 결제 → 배송처럼 여러 서비스에 걸친 트랜잭션은 Choreography 방식과 Orchestration 방식의 차이, 보상 트랜잭션 설계, 실패 시 롤백 전략 등 여러 전략을 직접 도전해보고 싶다.
  2. CQRS + Event Sourcing
    재고 차감 같은 시나리오에서 읽기와 쓰기 모델을 분리하면 성능과 확장성을 더 끌어올릴 수 있다고 한다. 특히 Event Sourcing과 결합한다면 모든 상태 변경이 이벤트로 남아 감사 로그나 시점 복구가 자연스럽게 가능해진다고 한다. 복잡도가 꽤 있는 패턴이라 들었는데, 어느 규모부터 도입할 가치가 있을지 측정해보고 싶다.
  3. 분산 락의 한계와 대안
    Redis Lua 스크립트로 이번 시리즈에서 원자성을 확보했지만, Redis가 단일 장애점(SPOF)이 될 수 있다. Redisson의 RedLock, ZooKeeper, etcd 같은 대안들을 비교해보고 각각의 장애 시나리오에서 어떻게 동작하는지도 검증해보면 좋을 것 같다.
  4. Kafka Exactly-Once Sementics
    이번 시리즈에선 At-Least-Once를 기반으로 멱등성을 직접 구현했는데, Kafka 트랜잭셔널 프로듀서와 isolation.level=read_committed를 활용한 Exactly-Once 처리도 다뤄보면 좋을 것 같다. 성능 오버헤드와 실제 효용 사이의 트레이드오프를 측정해보고 싶다.
  5. 관측성
    부하 테스트로 TPS와 p95는 측정했지만, 실제로 병목이 어디인지는 별도 도구가 필요하다. Micrometer + Prometheus + Grafana로 메트릭을 수집하고, OpenTelemetry로 분산 트레이싱을 걸어 WebFlux와 MVC의 내부 동작을 시각화해보면 좋을 것 같다. 원래 이번 시리즈에서 진행하려고 했는데 개인 서버 용량이 마땅치 않아 미루다가 못하게 됐다. 추후 서버를 신규 개설해서 꼭 해봐야겠다.

기술 선택에 정답은 없다. 상황에 맞는 트레이드오프를 이해하고 선택하는 것이 중요하고 생각한다.
