분산 락 (SET NX, Redisson, Fencing Token)

Database/NoSQL · 2026-07-09

Intro

한 서버 안에서만 돌아가는 애플리케이션이었다면 synchronized나 ReentrantLock으로 이 자원은 한 번에 하나만 건드리게 하면 끝났을 거다. 근데 서버가 여러 대로 늘어나면 이게 안 통한다. 각 서버는 자기 프로세스 안에서만 락을 걸 수 있으니까, 서버 A의 락은 서버 B가 보지도 못한다. 결국 여러 서버가 동시에 같은 자원을 건드리는 걸 막으려면, 그 서버들이 다 같이 보고 있는 공유된 곳에 락을 걸어야한다. 이게 분산 락이 필요한 이유인 것 같다.

Redis로 분산 락을 만드는 방법을 알아보다가, 처음에는 SET NX 하나면 되는 줄 알았는데 파고들수록 신경 쓸 게 계속 나왔다. TTL이 끝나는 타이밍 문제, 락을 해제할 때 진짜 내가 건 락이 맞는지 확인하는 문제, 그리고 그걸 다 해결해도 여전히 남는 문제(fencing token)까지 정리해보려고 한다.

여러 서버가 동시에 같은 자원을 건드릴 때

서버가 여러 대인 상황에서, 인스턴스 A와 B가 동시에 같은 자원에 대한 요청을 받았다고 하자. 락이 없으면 둘 다 지금은 아무도 안 쓰고 있다고 판단하고 동시에 작업을 시작해버릴 수 있다.

[인스턴스 A] 자원 상태 확인 -> 사용 가능 -> 작업 시작
                    [인스턴스 B] 자원 상태 확인 -> 사용 가능 -> 작업 시작
-> 둘 다 동시에 작업 (원래 한 번에 하나만 해야 하는데)

이걸 막으려면 지금 이 자원은 내가 쓰고 있다는 걸 모든 인스턴스가 같이 보는 곳에 표시해야 한다. Redis처럼 여러 서버가 공유해서 접근할 수 있는 저장소가 이 역할을 할 수 있다.

SET NX로 직접 만들어보기

가장 기본적인 방법은 SET key value NX다. 이미 있으면 실패하고, 없으면 그 순간 나만 설정에 성공하니까, 이 자체로 락을 획득하게 된다.

@Service
public class LockService {

    private final StringRedisTemplate redisTemplate;

    public LockService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public boolean tryLock(String lockKey, String ownerId, Duration ttl) {
        Boolean acquired = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, ownerId, ttl);
        return Boolean.TRUE.equals(acquired);
    }
}

여기서 value에 아무 값이나 넣지 않고 락을 건 주체를 식별할 수 있는 값(ownerId, 보통 UUID 같은 걸 씀)을 넣어둔 게 포인트다. 이걸 왜 넣어야 하는지는 뒤에서 설명하겠다.

TTL(만료 시간)을 반드시 걸어야 한다는 것도 중요하다. TTL이 없으면, 락을 잡은 서버가 처리 도중에 죽어버렸을 때 그 락이 영원히 안 풀린다. 아무도 못 쓰는 자원이 돼버리는 거다. 그래서 이 시간 안에는 끝나겠지라는 만료 시간을 걸어두고, 혹시 그 안에 못 끝내도 어쨌든 시간이 지나면 자동으로 풀리게 해야 한다.

문제

TTL이 작업 시간보다 먼저 끝나버리면

TTL을 걸어두면, 이번엔 반대 문제가 생긴다. 락을 잡은 서버의 작업이 예상보다 오래 걸려서, 작업이 끝나기도 전에 TTL이 먼저 만료돼버리면 어떻게 될까?

[서버 A] 락 획득 (TTL 10초) -> 작업 시작 (근데 이 작업이 15초 걸림)
                       10초 뒤 -> TTL 만료, 락 풀림
                       [서버 B] 락 획득 -> 작업 시작
[서버 A] 아직 작업 중... (15초째) -> 이제 끝남
-> A와 B가 같은 자원을 동시에 건드리는 순간이 생겨버림

TTL을 무작정 길게 잡으면 이번엔 서버 A가 정말로 죽었을 때 락이 너무 오래 안 풀리는 문제가 생긴다. 그래서 나온 방법이 작업이 끝날 때까지, TTL을 살아있는 동안 계속 연장해주는 방식이다. 이걸 보통 watchdog(감시견)이라고 부르는데, 별도 스레드가 주기적으로 아직 작업 중이니 TTL 늘려줘라고 반복해주고, 작업이 끝나면 그 갱신을 멈추고 락을 해제한다. 이걸 직접 구현하려면 스레드를 하나 더 관리해야 해서 코드가 금방 복잡해진다.

내 락이 맞는지 확인 안 하고 지우면

락을 다 쓰고 해제할 때, 그냥 DEL lockKey를 날리면 되지 않을까 싶었는데, 여기에도 함정이 있었다. 방금 문제 1처럼 TTL이 먼저 만료돼서 다른 서버가 이미 그 자리에 새 락을 잡은 상황이라면, 원래 주인이 뒤늦게 DEL을 날리는 순간 남의 락을 지워버리게 된다.

[서버 A] TTL 만료로 락이 이미 풀림
[서버 B] 락 획득
[서버 A] 뒤늦게 작업 끝내고 DEL 호출 -> 사실은 B가 잡은 락을 지워버림

그래서 해제할 땐 지우기 전에 이게 진짜 내 락인지 확인하는 절차가 필요하다. 아까 value에 넣어둔 ownerId가 여기서 쓰인다. 지우려는 값이 내가 저장했던 값과 같을 때만 지우게 해야 한다. 근데 이것도 확인하고 지운다는 단계가 두 개라서, 이 사이에 다른 요청이 끼어들면 또 문제가 생길 수 있다. 그래서 이 확인+삭제를 Lua 스크립트로 원자적으로 묶는다.

-- unlock.lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end

private static final RedisScript<Long> UNLOCK_SCRIPT = RedisScript.of("""
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('DEL', KEYS[1])
        else
            return 0
        end
        """, Long.class);

public boolean unlock(String lockKey, String ownerId) {
    Long result = redisTemplate.execute(UNLOCK_SCRIPT, List.of(lockKey), ownerId);
    return result != null && result > 0;
}

Redisson

여기까지 오면서 느낀 건, 락 하나 제대로 만들려면 신경 쓸 게 생각보다 많다는 거다. TTL 자동 연장(watchdog), 안전한 해제(Lua), 락을 못 잡았을 때 재시도 방식까지. 이걸 전부 직접 구현하는 것보다, Redisson 같은 라이브러리를 쓰는 게 훨씬 안전한 것 같다. Redisson은 이 모든 걸 이미 구현해서 제공한다.

@Service
public class LockService {

    private final RedissonClient redissonClient;

    public LockService(RedissonClient redissonClient) {
        this.redissonClient = redissonClient;
    }

    public void doWithLock(String lockKey, Runnable task) {
        RLock lock = redissonClient.getLock(lockKey);
        try {
            boolean acquired = lock.tryLock(5, TimeUnit.SECONDS);   // 최대 5초 대기
            if (!acquired) {
                throw new IllegalStateException("락 획득 실패");
            }
            task.run();
            // 작업이 오래 걸려도 Redisson이 내부적으로 TTL을 알아서 연장해준다(watchdog)
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("락 대기 중 인터럽트", e);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();   // 내부적으로 소유자 확인 후 안전하게 해제
            }
        }
    }
}

코드가 훨씬 짧아졌는데, 이 짧은 코드 뒤에서 watchdog이 자동으로 TTL을 연장해주고, unlock()도 내부적으로 아까 했던 내 락 맞는지 확인 후 삭제까지 Lua로 처리해준다. 직접 짠 SET NX 버전은 이 동작들을 공부하고 원리를 이해하는 데는 좋지만, 실제로 쓸 땐 검증된 라이브러리에 맡기는 게 맞는 것 같다.

Fencing Token

여기까지 다 해결해도, 이론적으로 남는 문제가 하나 있다고 한다. 락을 가진 서버가 GC(가비지 컬렉션)로 아주 길게 멈추거나, 네트워크가 잠깐 끊기는 것처럼 살아는 있는데 응답을 못 하는 상황이 생기면 어떻게 될까?

[서버 A] 락 획득 -> 작업 시작
[서버 A] GC로 5초간 멈춤 (그 사이 TTL 만료)
[서버 B] 락 획득 -> 작업 시작
[서버 A] GC 끝나고 다시 깨어남 -> 자기가 아직 락을 가진 줄 알고 작업 계속
-> A와 B가 동시에 같은 자원을 건드림

서버 A는 자기가 멈췄다 깨어난 걸 몰라서, 락이 이미 만료돼 B에게 넘어간 걸 인지하지 못한 채로 작업을 계속한다. 락을 안전하게 잡고 해제하는 것만으로는 이 상황을 못 막는다.

이걸 막는 방법이 fencing token이다. 락을 잡을 때마다 단조 증가하는 숫자(토큰)를 같이 발급해주고, 실제 자원에 접근하는 곳(예: 자원을 갱신하는 DB)에서 지금 들어온 토큰이 마지막으로 처리한 토큰보다 큰가를 확인한다.

[서버 A] 락 획득, 토큰=33 -> 작업 중 GC로 지연
[서버 B] 락 획득, 토큰=34 -> 작업 완료, 자원에 토큰 34로 기록
[서버 A] 깨어나서 토큰 33으로 자원 접근 시도 -> "33은 34보다 작으니 거부"

이러면 락 자체가 이미 넘어간 상황에서도, 자원을 실제로 건드리는 마지막 관문에서 옛날 토큰을 걸러낼 수 있다.락만 믿는 게 아니라, 자원에 접근하는 곳에서 한 번 더 검증하는 이중 방어인 셈이다. Redisson의 기본 락은 이 토큰까지 자동으로 챙겨주진 않아서, 정말 이 정도까지 안전해야 하는 상황이라면 토큰 비교 로직을 직접 자원 접근 코드에 넣어야 한다.

정리

  • 여러 서버가 동시에 같은 자원을 건드리는 걸 막으려면, 그 서버들이 같이 보는 곳(Redis 등)에 락을 걸어야 한다.
  • SET NX + TTL로 기본적인 락은 만들 수 있지만, TTL이 작업 시간보다 먼저 끝나거나 남의 락을 잘못 지우는 문제가 남는다.
  • TTL 자동 연장(watchdog)과 안전한 해제(소유자 확인 + Lua)까지 직접 짜려면 손이 많이 가서, Redisson 같은 라이브러리를 쓰는 게 실무적으로 맞는 것 같다.
  • 그래도 이론적으로는 살아있는데 응답 못 하는 상황에서 락이 넘어간 걸 모르고 계속 작업하는 문제가 남는데, 이건 fencing token으로 자원 접근 지점에서 한 번 더 걸러야 한다.

락을 그냥 SET NX 하나면 되는 거 아닌가로 시작했다가, TTL 타이밍부터 fencing token까지 파다 보니 생각보다 깊은 주제였다. 대부분의 상황에선 Redisson 정도로 충분하고, fencing token까지 필요한 경우는 정말 자원 접근 자체의 정합성이 엄격하게 요구되는 상황일 때인 것 같다.
