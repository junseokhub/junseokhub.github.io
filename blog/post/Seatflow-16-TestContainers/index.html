[Seatflow] 16. TestContainers

Lab/SeatFlow · 2026-07-30

Intro

지금까지는 기능을 만들고, curl로 몇 번 찔러보고, 문제없으면 넘어가는 식으로 작업했다. 이번에 전체 서비스에 테스트 코드를 붙여보면서, 이 방식으로는 절대 못 잡는 종류의 버그가 실제로 여러 개 나왔다. 그 버그 대한 내용은 16-1 번외편으로 다룰 예정이다.

애초에 어떤 방식으로 테스트 인프라를 구성했는지를 정리했다. 왜 이 방식을 택했는지, 다른 방법과 비교했을 때 무엇을 얻고 무엇을 포기했는지, 그리고 그 과정에서 겪은 문제와 대안까지 담았다.

TestContainers 사용 이유

테스트 코드를 짤 때 DB나 Redis 같은 외부 의존성을 다루는 방법은 크게 세 가지가 있다.

방법 비교

  • Mock으로 대체

    • Repository나 RedisTemplate 자체를 Mockito 같은 도구로 흉내 내는 방식이다. 제일 빠르고, 외부 인프라가 아예 필요 없다. 대신 진짜 DB나 Redis가 이 쿼리를 실행했을 때 실제로 어떻게 동작하는지는 전혀 검증이 안 된다. Mock은 이 메서드가 호출됐는지까지만 확인할 수 있다. 그 메서드가 실제로 어떤 값을 만들어내는지, 그 값이 프레임워크 내부 상태(트랜잭션 매니저, 영속성 컨텍스트)에 어떤 영향을 주는지는 Mock의 관심사 밖이다.

  • 인메모리 대체재 (H2 등)

    • MySQL 대신 H2를, 진짜 Redis 대신 embedded Redis를 쓰는 방식이다. 빠르고 외부 프로세스가 필요 없다는 장점은 있지만, SQL 방언이나 트랜잭션 처리 방식이 미묘하게 실제 운영 DB와 다를 수 있다. H2에서는 통과하는데 MySQL에서는 실패하는 괴리가 생길 위험을 감수해야 한다.

  • TestContainers로 진짜 인프라를 Docker로 띄우기

    • 운영에서 쓰는 것과 같은 이미지(MySQL, Redis, MongoDB, Kafka 등)를 컨테이너로 띄워서 테스트한다. 느리고 Docker가 반드시 필요하지만, 테스트에서 통과하면 운영에서도 될 가능성이 가장 높다는 신뢰를 준다.

이번에 실제로 겪은 문제들(16-1편 참고)을 보면 이유가 명확해진다. Redis 키가 미묘하게 잘못 조합된 문제, 트랜잭션이 catch로 예외를 잡았는데도 내부적으로 오염되는 문제, @Modifying 쿼리와 영속성 컨텍스트가 어긋나는 문제 전부 진짜 Redis, 진짜 Spring 트랜잭션 매니저, 진짜 영속성 컨텍스트가 있어야만 재현되는 것들이었다. Mock으로는 애초에 검증 대상 자체가 존재하지 않았다. 물론 그 대가로 속도는 잃는다. 테스트 하나당 컨테이너를 준비하는 비용이 있고, 오늘 겪었듯 여러 테스트가 컨테이너를 나눠 쓰는 과정에서 예상 못 한 문제도 생겼다. 그래도 테스트가 통과했다는 사실 자체의 신뢰도를 높이는 쪽을 택했다. 특히 동시성이나 트랜잭션처럼, 겉보기엔 멀쩡한 코드가 실제 환경에서만 문제를 드러내는 영역일수록 이 판단이 맞다고 봤다.

컴포지션으로 구성한 Support 인터페이스

서비스마다 필요한 인프라가 다르다. 예를 들어 어떤 서비스는 MySQL과 Redis가 둘 다 필요하고, 어떤 서비스는 MongoDB만 필요하고, 어떤 서비스는 MySQL만 필요하다. 매번 컨테이너 설정을 반복해서 쓰지 않도록, MysqlContainerSupport, RedisContainerSupport, MongoContainerSupport, KafkaContainerSupport처럼 인터페이스 형태로 만들어두고, 테스트 클래스가 필요한 것만 골라 구현하는 방식(컴포지션)으로 구성했다.

class SomeIntegrationTest implements MysqlContainerSupport, RedisContainerSupport {
    // MySQL과 Redis 둘 다 필요한 테스트
}

class AnotherRepositoryTest implements MongoContainerSupport {
    // MongoDB만 필요한 테스트
}

왜 상속이 아니라 컴포지션으로?

자바는 클래스 다중 상속을 지원하지 않지만, 인터페이스는 여러 개를 동시에 구현할 수 있다. 만약 각 인프라 조합마다 AbstractMysqlRedisTest, AbstractMysqlOnlyTest 같은 별도의 추상 클래스를 만들었다면, 조합이 늘어날 때마다(MySQL+Redis+Kafka 같은 새 조합이 필요해질 때마다) 클래스를 새로 만들어야 했을 거다.

인터페이스 조합 방식은 그럴 필요가 없다. 필요한 인터페이스만 나열해서 구현하면 그 조합이 그대로 성립한다.

다만 이 방식이 항상 정답인 건 아니다. 만약 거의 모든 테스트가 항상 똑같은 조합(MySQL+Redis)만 쓴다면, 오히려 그 조합 하나를 담은 추상 클래스를 만드는 게 더 간단할 수 있다. 인터페이스 조합의 이점은 조합의 가짓수가 실제로 다양할 때 발휘된다. 지금 상황은 서비스마다 필요한 인프라가 제각각이라 컴포지션 쪽이 맞다고 생각했다.

반복되는 설정을 선택적 기본값으로

컨테이너 자체는 컴포지션으로 잘 나눴는데, 그 컨테이너를 어떻게 쓸지(JPA의 ddl-auto, flyway.enabled 같은 것)는 거의 모든 테스트가 똑같이 반복해서 적고 있었다.

@DynamicPropertySource
static void properties(DynamicPropertyRegistry registry) {
    registry.add("spring.jpa.hibernate.ddl-auto", () -> "create-drop");
    registry.add("spring.flyway.enabled", () -> "false");
}

이걸 Support 인터페이스에 무조건 넣어버리면 컴포지션 원칙이 깨진다. 어떤 테스트는 Flyway 마이그레이션 자체를 검증하고 싶을 수도 있고, ddl-auto를 validate로 해서 엔티티와 스키마가 실제로 일치하는지 확인하고 싶을 수도 있다. Support 인터페이스는 어떤 인프라를 쓸 것인지를 제공하는 것이지, 그걸 어떻게 쓸지 강요하면 안 된다.

  • 대안 1) 아예 강제로 넣기

    • 반복은 줄지만, 다르게 쓰고 싶은 테스트가 원천적으로 그렇게 할 수 없어진다.

  • 대안 2) 매번 각 테스트가 직접 작성

    • 유연하지만, 똑같은 두 줄을 계속 복붙하게 된다. 게다가 이 두 줄을 깜빡 빠뜨리면 컴파일 에러 없이 조용히 기본 설정(원치 않는 것)으로 떨어질 위험이 있다.

  • 선택) 선택적 static 메서드로 기본값 제공

    • 강제하지 않으면서 반복은 줄이는 절충안이다.
public interface MysqlContainerSupport {
    // 연결정보(url/username/password)는 이 컨테이너를 쓰는 이상 항상 똑같이
    // 필요하므로 인터페이스 자체에서 자동 적용한다.
    @DynamicPropertySource
    static void mysqlProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", MYSQL::getJdbcUrl);
        registry.add("spring.datasource.username", MYSQL::getUsername);
        registry.add("spring.datasource.password", MYSQL::getPassword);
        registry.add("spring.jpa.hibernate.ddl-auto", () -> "create-drop");
        registry.add("spring.flyway.enabled", () -> "false");
    }
}

연결정보(host, port, url 같은 것)는 이 컨테이너를 쓰는 이상 항상 똑같이 필요한 값이라 선택의 여지가 없다. 그래서 이건 강제해도 컴포지션 원칙과 안 어긋난다. 반면 ddl-auto처럼 진짜 다르게 쓰고 싶을 수 있는 값은 처음엔 별도 static 메서드로 분리했다가, 실제로 반복 호출을 깜빡해서 스키마가 안 만들어지는 문제를 겪은 뒤로는 이것도 기본값으로 자동 적용하는 쪽으로 정리했다. 정말 다르게 쓰고 싶은 소수의 테스트는, 자기 @DynamicPropertySource에서 같은 키로 다시 등록해서 덮어쓰면 된다.

DynamicPropertyRegistry는 나중에 등록한 값이 우선한다.

컨테이너를 여러 테스트가 안전하게 나눠 쓰기 

여러 테스트 클래스가 매번 새 컨테이너를 띄우면 느리다. 그래서 컨테이너를 재사용(하나의 컨테이너를 여러 테스트 클래스가 나눠 쓰는 것)하려고 했는데, 여기서 예상 못 한 문제를 겪었다.

파일 하나는 되는데 여러 파일을 같이 돌리면 안 됨

MongoDB를 쓰는 통합 테스트 파일 하나만 단독으로 실행하면 항상 통과했다. 근데 여러 통합 테스트 파일을 한꺼번에 실행하면 Connection refused, Connection reset, MongoTimeoutException 같은 에러가 불규칙하게 났다.

시도했다가 효과 없었던 것들

  • 재사용 옵션을 껐다 켜보기
  • 방어적으로 컨테이너가 실행 중인지 체크 추가
  • Gradle의 병렬 실행 자체를 제한
  • 빌드 캐시를 완전히 지우고 재컴파일
  • 시스템의 파일 디스크립터 한도 확인 (이미 충분히 높았다)

원인 

컨테이너 라이프사이클을 여러 클래스가 각자 관리하려 든 것

JUnit5의 Testcontainers 확장은 특정 방식으로 컨테이너를 선언하면 이 테스트 클래스가 이 컨테이너의 시작과 종료를 책임진다고 이해한다. 여러 테스트 클래스가 인터페이스를 통해 같은 컨테이너 객체를 공유하더라도, 이 방식 그대로라면 각 클래스는 여전히 자신이 그 컨테이너의 관리 주체라고 판단할 수 있다. 그 결과 한 클래스의 테스트가 끝나는 시점에, 다른 클래스가 아직 쓰고 있는 컨테이너를 정리해버리는 상황이 생길 수 있다.

해결은 그 관리 방식을 걷어내고, 정적 초기화 블록에서 이미 실행 중이 아니면 시작한다는 조건으로 딱 한 번만 컨테이너를 띄우는 것이었다.

public interface MongoContainerSupport {
    MongoDBContainer MONGO = createAndStart();

    private static MongoDBContainer createAndStart() {
        MongoDBContainer container = new MongoDBContainer("mongo:7.0");
        container.start();
        return container;
    }
}

자바에서 인터페이스의 static 필드는 그 인터페이스가 처음 참조되는 시점에 딱 한 번만 초기화된다. 그래서 여러 테스트 클래스가 이 인터페이스를 구현해도, 컨테이너 시작 로직 자체는 한 번만 실행된다. 어떤 클래스도 이 컨테이너를 내가 종료해야 한다고 여기지 않으므로, 한 클래스가 끝난다고 다른 클래스가 쓰는 컨테이너가 사라지는 문제가 없어진다. 컨테이너는 전체 테스트 프로세스가 끝날 때 Testcontainers 자체의 정리 메커니즘이 처리한다.

  • 대안)컴포지션 대신 각 테스트가 매번 새 컨테이너를 띄우기
    • 이러면 애초에 공유로 인한 문제 자체가 없다. 다만 컨테이너를 띄우는 데 걸리는 시간(수 초)이 테스트 클래스 개수만큼 누적되어, 전체 테스트 실행 시간이 크게 늘어난다. 지금처럼 통합 테스트 클래스가 서비스마다 여러 개인 상황에서는 속도 손해가 상당히 커서 택하지 않았다.

연결 정보 자동 감지가 재사용 상황에서 최신 정보를 못 따라간 것

Spring Boot에는 컨테이너가 뜬 시점의 연결 정보를 자동으로 감지해서 애플리케이션 설정에 주입해주는 기능이 있다. 이 기능은 컨테이너가 매번 새로 뜨는 상황(단일 파일 실행처럼 그 컨테이너를 오직 그 테스트만 쓰는 경우)에서는 문제가 없었다. 하지만 여러 테스트 클래스가 이미 떠 있는 컨테이너를 재사용하는 상황에서는, 이 자동 감지가 최신 상태(포트 매핑, replica set 구성 등)를 정확히 못 따라가는 경우가 있었다. Redis에서도 비슷한 연결 오류가 났다.

대신 연결 정보를 메서드 참조 형태로 명시적으로 등록하는 방식으로 바꿨다.

@DynamicPropertySource
static void mongoProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.data.mongodb.uri", MongoContainerSupport.MONGO::getReplicaSetUrl);
}

메서드 참조(MONGO::getReplicaSetUrl)로 등록하면, Spring이 이 값이 실제로 필요한 시점에 그 메서드를 다시 호출해서 최신 값을 가져온다. 자동 감지 기능이 컨테이너가 뜨는 시점에 값을 한 번 캡처해서 넘기는 것과 달리, 이 방식은 필요할 때마다 다시 물어보는 것이라 재사용 상황에 더 안전했다.

  • 대안) 자동 감지 기능을 그대로 쓰되 재사용을 포기
    • 컨테이너를 재사용하지 않으면 자동 감지도 문제없이 동작한다. 다만 이러면 첫번째 원인에서 언급한 속도 문제와 똑같은 트레이드오프가 생긴다.

언제 이런 일이 발생할까? 

단독 실행에서는 그 클래스 하나만 컨테이너를 시작하고 자기가 끝날 때까지 쓰다가 끝난다. 다른 클래스와 라이프사이클이 겹칠 일이 없고, 연결 정보도 컨테이너가 막 시작된 직후의 신선한 상태라 재조회 안 해도 맞는다. 전체 실행에서는 여러 클래스가 시간차를 두고 같은 컨테이너에 접근하는데, 어느 한 클래스가 컨테이너를 자기 것처럼 착각해서 정리하거나, 연결 정보가 옛날 상태로 캐시돼 있으면 뒤이어 실행되는 클래스가 죽어있는 컨테이너나 어긋난 연결 정보로 접근을 시도하게 된다.

일부러 컨테이너를 공유하면 안 되는 경우

지금까지는 공유가 안되니까 문제였는데, 정반대로 일부러 공유하면 안 되는 경우도 있다. Redis 장애 상황을 재현하는 테스트가 있는데, 이 테스트는 Redis를 실제로 죽여서 장애 시 안전하게 처리되는지(요청을 거부하는지 등)를 검증하는 게 목적이다.

만약 이 테스트가 다른 테스트들과 공유하는 Redis 컨테이너를 죽여버리면, 같은 프로세스 안에서 실행되는 다른 모든 Redis 관련 통합 테스트가 전부 그 죽은 Redis를 참조하다 연쇄적으로 실패한다. 그래서 이 테스트만큼은 자기 전용 컨테이너를 따로 만들었다.

private static final GenericContainer<?> DEDICATED_REDIS =
        new GenericContainer<>(DockerImageName.parse("redis:7-alpine"))
                .withExposedPorts(6379);

static {
    DEDICATED_REDIS.start();
}

@AfterAll
static void tearDown() {
    DEDICATED_REDIS.stop();   // 이 클래스 전용이라 마음대로 정리해도 안전하다.
}

@AfterAll로 스스로 정리하는 것도, 앞서 겪은 문제(여러 클래스가 공유 컨테이너를 자기 것처럼 착각해서 정리하려는 것)와는 성격이 완전히 다르다. 이 컨테이너는 정말로 이 클래스만의 것이니, 이 클래스가 끝날 때 이 클래스가 치우는 게 맞다.

판단 기준

  • 컨테이너를 정상적으로 계속 살아있는 인프라로만 쓰는 테스트 -> 공유 컨테이너(위에서 정리한 방식)
  • 그 테스트 자체가 컨테이너를 죽이거나 비정상 상태로 만드는 게 검증 목적인 테스트 -> 반드시 전용 컨테이너로 격리

구독을 검증할 때 마주친 또 다른 문제

여기까지는 컨테이너를 여러 테스트가 안전하게 나눠 쓰는 문제였다. 이번엔 진짜로 Kafka에 메시지를 발행하고 그걸 구독해서 처리하는 통합 테스트를 만들면서, 컨테이너 공유와는 또 다른 종류의 문제를 만났다.

DB와 Kafka는 근본적으로 다르다

지금까지 다룬 MySQL, Redis, MongoDB는 전부 테스트가 요청하면 그 자리에서 바로 응답이 오는 방식이다.

테스트 코드 --- 저장 요청 ---> MySQL
테스트 코드 <--- 저장 완료 응답 ---

테스트가 저장 메서드를 호출하면, 그 호출 자체가 끝날 때 이미 DB에 반영이 끝나 있다. 누군가 미리 대기하고 있어야 받을 수 있다는 개념 자체가 없다. Kafka의 메시지 리스너는 다르게 동작한다.

1. 애플리케이션이 뜨면서 리스너로 등록된 메서드를 스프링이 찾아낸다
2. 그 메서드를 위해 컨슈머를 만들어서 Kafka 브로커에 연결한다
3. 컨슈머가 브로커에게 이 토픽을 구독하고 싶다고 요청한다
4. 브로커가 이 파티션을 배정해준다(이 협상 과정을 리밸런싱이라고 부른다)
5. 이 배정이 끝나야, 비로소 그 컨슈머가 실제로 메시지를 받을 수 있는 상태가 된다

이 과정은 시간이 걸린다. 그리고 이 시간 동안 애플리케이션 자체는 이미 다 떴다고 판단될 수 있다. 컨슈머가 브로커와 협상하는 건 애플리케이션이 뜨는 것과는 별개로, 조금 더 나중에 끝나는 비동기 과정이기 때문이다.

왜 파일 전체는 되고 단독은 안 됐을까?

파일 전체를 돌리면, 이 테스트가 실행되기 전에 다른 테스트 메서드들이 먼저 실행된다. 그 앞선 테스트들이 실행되는 동안 애플리케이션 컨텍스트는 계속 떠 있었고, 그 사이에 컨슈머들이 리밸런싱을 이미 끝냈을 시간이 충분히 있었다. 그래서 이 테스트 차례가 왔을 즈음엔 이미 메시지를 받을 준비가 끝난 상태였다.

반면 이 테스트 메서드 하나만 단독으로 돌리면, 컨텍스트가 막 뜨자마자 바로 이 테스트가 시작된다. 컨슈머가 아직 브로커와 협상을 끝내기 전에 테스트가 메시지를 발행해버린 것이다. 라디오 방송국이 막 전파를 쏘기 시작했는데, 청취자의 라디오는 아직 주파수를 맞추는 중이라 그 방송을 놓친 것과 비슷하다.

타임아웃을 늘리기

가장 먼저 든 생각은 더 오래 기다리면 되지 않을까였다. 타임아웃을 10초에서 20초로 늘려봤다. 결과는 가끔 되고 가끔 안 됐다. 어떤 실행에서는 20초 안에 리밸런싱이 끝나서 통과했고, 어떤 실행에서는 20초를 넘겨서 여전히 실패했다.

이건 정확한 해결이 아니었다. 타임아웃을 늘리는 건 얼마나 기다려야 하는지 모르는 채로 운에 맡기고 더 오래 기다리는 것뿐이다. 진짜 원인(컨슈머가 아직 준비 안 됨)을 없애주지는 않는다.

준비됐는지를 직접 확인하고 나서 시작하기

필요한 건 얼마나 기다릴지 추측하는 게 아니라, 정말 준비가 끝났는지를 확인하는 것이었다. Spring Kafka는 정확히 이 목적을 위한 테스트 전용 도구를 제공한다.

@Autowired
private KafkaListenerEndpointRegistry registry;

private void waitUntilAllListenersReady() {
    registry.getListenerContainers().forEach(container ->
            ContainerTestUtils.waitForAssignment(container, 1));
}

@BeforeEach
void setUp() {
    ...
    waitUntilAllListenersReady();   // 메시지를 발행하기 전에 항상 이걸 먼저 통과시킨다
}

KafkaListenerEndpointRegistry는 애플리케이션 안에 있는 모든 메시지 리스너 컨슈머들의 목록을 관리하는, 스프링이 자동으로 등록해주는 컴포넌트다. registry.getListenerContainers()로 그 컨슈머들을 하나씩 꺼내올 수 있다. ContainerTestUtils.waitForAssignment(container, 1)이 핵심인데, 이건 이 컨슈머가 정확히 1개의 파티션을 실제로 할당받을 때까지 기다린다는 뜻이다(테스트 환경은 파티션을 1개만 쓰도록 구성했으므로 1이다). 막연히 몇 초를 기다리는 게 아니라, 컨슈머 내부의 실제 할당 상태를 직접 확인하면서 기다린다.

이걸 각 테스트 메서드 실행 전에 항상 거치게 하니, 타임아웃을 20초에서 5초로 줄여도 안정적으로 통과했다. 리밸런싱을 기다리는 시간이 더 이상 이 대기 시간 안에 포함될 필요가 없어졌기 때문이다.

왜 이게 DB에는 필요 없고 Kafka에만 필요할까?

MySQL이나 Redis, MongoDB를 쓸 때는 테스트가 능동적으로 요청하는 쪽이다. 저장이나 조회 메서드를 호출하면, 그 호출 자체가 응답을 받을 때까지 기다려주는 동기 방식이라, 미리 준비하고 대기하는 무언가가 따로 필요 없다.

메시지 리스너는 반대로 수동적으로 기다리는 쪽이다. 테스트가 메시지를 보내는 시점과, 컨슈머가 그걸 받을 수 있는 상태가 되는 시점이 서로 별개의 타이밍이다. 그래서 받을 준비가 됐는지를 확인하는 절차가 Kafka를 쓰는 테스트에만 필요하다.

판단 기준

  • 진짜 Kafka 컨테이너를 띄우고, 그 안에서 테스트가 직접 메시지를 발행해서 진짜 리스너가 그걸 받아 처리하는지 확인하는 통합 테스트 -> 필요
  • Mock으로 리스너 메서드를 직접 호출하는 단위 테스트, 또는 발행만 확인하고(예: Outbox 스케줄러가 Kafka로 전송을 시도하는지) 그걸 받는 컨슈머 쪽은 안 보는 테스트 -> 필요 없음

정리

TestContainers를 쓰기로 한 이유 자체는 명확했다. Mock이나 H2로는 절대 못 잡는 버그들이 실제로 있었으니까. 근데 정작 시간을 제일 많이 잡아먹은 건 검증 대상 자체가 아니라, 그 검증을 위한 인프라(여러 테스트가 컨테이너 하나를 안전하게 나눠 쓰는 것, 비동기로 동작하는 컴포넌트가 진짜 준비됐는지 확인하는 것)를 제대로 세팅하는 일이었다.

  • 컨테이너의 라이프사이클을 특정 테스트 클래스가 독점하는 방식은, 여러 클래스가 공유할 때 문제가 될 수 있다. 여러 클래스가 공유하려면 그 관리를 직접(정적 초기화 시점에 한 번만 시작하는 방식으로) 해야 한다.
  • 연결 정보를 자동으로 감지하는 기능은, 컨테이너가 재사용되는 상황에서 최신 정보를 못 따라갈 수 있다. 메서드 참조로 명시적으로 재조회하게 만드는 게 더 안전하다.
  • 단독 실행은 되는데 전체는 안 된다는 증상이 나오면, 십중팔구 컨테이너 라이프사이클이나 연결 정보의 재사용 문제다
  • 컨테이너를 죽이는 게 테스트 목적 자체인 경우는 공유하면 안 된다.
  • Kafka처럼 미리 준비하고 기다리는 컴포넌트를 쓰는 테스트는, 요청-응답형 DB와 다르게 준비가 끝났는지를 명시적으로 확인하고 나서 시작해야 한다. 타임아웃을 늘리는 건 이 확인을 대신할 수 없다.
