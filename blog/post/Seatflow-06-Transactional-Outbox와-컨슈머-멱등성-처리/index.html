[Seatflow] 06. Transactional Outbox와 컨슈머 멱등성 처리

Lab/SeatFlow · 2026-06-20

Intro

이전에 문제는 DB에 저장하는 것과 Kafka로 이벤트를 보내는 것이 하나의 트랜잭션으로 묶여있지 않다는 것이었다.

auth-service는 credentials 저장과 UserRegisteredEvent 발행이 따로 놀고, seat-service도 Redis 점유와 seat.held 발행이 따로 논다. 한쪽은 성공했는데 다른 쪽이 실패하면 데이터가 어긋난다.

이번 편에서 그 문제를 해결해보려 한다.

auth-service에는 Transactional Outbox를 붙여서 이벤트를 확실히 내보내게 하고, user-service에는 컨슈머 멱등성(Inbox 패턴)을 붙여서 같은 이벤트를 두 번 받아도 문제가 없게 만든다. 보내는 쪽과 받는 쪽을 같이 손봐야 auth 에서 user 흐름 전체가 믿을 수 있게 된다.

04편에서 Outbox, Saga, CDC를 잠깐 비교하고 "Outbox가 제일 유력하다"고 적었는데, 이번 편에서 실제로 그걸 붙이는 셈이다.

dual-write 문제

dual-write

한 작업에서 서로 다른 두 저장소에 따로따로 쓰는 걸 dual-write라고 한다.

회원가입이 딱 이 경우다. credentials를 DB에 저장하고, UserRegisteredEvent를 Kafka에 보낸다. 문제는 이 둘을 한 번에 묶어서 둘 다 성공 아니면 둘 다 실패로 만들 방법이 없다는 거다. DB 트랜잭션은 DB까지만 책임지고, Kafka는 그 바깥에 있다.

가장 흔하게 하는 실수는 트랜잭션 안에서 그냥 보내버리는 것이다.

@Transactional
public void signup(...) {
    credentialsRepository.save(credentials);
    kafkaTemplate.send(...);   // DB 트랜잭션에 묶이지 않는다
}

별 문제가 없을 것 같지만 아니다. send()가 성공한 뒤에 트랜잭션이 롤백되면, DB에는 credentials가 없는데 이벤트는 이미 나가버린다. user-service는 존재하지도 않는 유저의 프로필을 만든다. 반대로 credentials는 저장됐는데 이벤트를 보내기 직전에 서버가 죽으면, 이벤트는 영영 안 나가고 user-service에는 유저가 안 생긴다. DB와 Kafka, 이렇게 두 군데에 따로 쓰는 한 이 문제는 어쩔 수 없이 생긴다.

Transactional Outbox 패턴

해결 방법의 핵심은 단순하다. 이벤트를 Kafka로 바로 보내지 말고, 일단 같은 DB에 같은 트랜잭션으로 적어둔다. credentials와 이벤트가 한 트랜잭션에 들어가니 둘은 같이 저장되거나 같이 취소된다. 그리고 보내는 일은 그 다음 문제로 떼어낸다. 별도의 작업이 DB에 쌓인 이벤트를 읽어서 Kafka로 내보낸다. 이렇게 이벤트를 임시로 적어두는 테이블을 outbox(보낼 편지함으로 이해)라고 부른다.

// auth-service에 outbox 테이블
CREATE TABLE outbox (
    id            BIGINT       NOT NULL AUTO_INCREMENT,
    event_id      VARCHAR(36)  NOT NULL UNIQUE,
    event_type    VARCHAR(100) NOT NULL,
    message_key   VARCHAR(36)  NOT NULL,
    payload       TEXT         NOT NULL,
    status        VARCHAR(20)  NOT NULL DEFAULT 'PENDING',
    retry_count   INT          NOT NULL DEFAULT 0,
    next_retry_at DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    created_at    DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    publishing_at DATETIME(6)  NULL,
    published_at  DATETIME(6)  NULL,
    PRIMARY KEY (id),
    INDEX idx_outbox_poll (status, next_retry_at, id),
    INDEX idx_outbox_created_at (created_at)
);

event_id는 이벤트마다 하나씩 붙는 고유 번호(UUID)다. 나중에 받는 쪽에서 "이거 전에 처리한 이벤트인가??"를 판단하는 기준이 된다. status는 PENDING(보낼 차례) → PUBLISHING(보내는 중) → PUBLISHED(보냄) 순서로 바뀌고, 계속 실패하면 FAILED로 따로 빼둔다.

next_retry_at은 다음에 다시 시도할 시각인데, 재시도를 다룰 때 설명 할 예정이다.

회원가입에서는 credentials 저장과 outbox 저장을 같은 트랜잭션에 넣는다.

@Transactional
public SignupResult signup(SignupCommand command) {
    if (credentialsRepository.existsByEmail(command.email())) {
        throw new BusinessException(...);
    }

    String userId = UUID.randomUUID().toString();
    credentialsRepository.save(
            Credentials.create(userId, command.email(),
                    passwordEncoder.encode(command.password())));

    // 같은 트랜잭션으로 이벤트를 outbox에 적재
    EventEnvelope<UserRegisteredEvent> envelope = EventEnvelope.of(
            EventTopic.USER_REGISTERED, "auth-service",
            new UserRegisteredEvent(userId, command.email(), command.name()));

    outboxRepository.save(Outbox.builder()
            .eventId(envelope.eventId())
            .eventType(EventTopic.USER_REGISTERED)   // 보낼 토픽
            .messageKey(userId)                      // 파티션 키
            .payload(objectMapper.writeValueAsString(envelope))
            .build());

    return ...;
}

여기에는 Kafka가 등장하지 않는다. 이 메서드가 책임지는 건 "DB에 어긋남 없이 쓰는 것"까지다. 보내는 일은 아래 섹션을 읽어보면 좋을것 같다.

발송 작업

이제 outbox에 쌓인 PENDING 이벤트를 꺼내 Kafka로 보내고, 성공하면 PUBLISHED로 바꾸는 작업이 필요하다. 이 작업은 일정 간격으로 테이블을 들여다보며 보낼 게 있는지 확인한다. 이렇게 주기적으로 확인하는 방식을 **폴링(polling)**이라고 한다.

단순해 보여도 두 가지를 신경 써야 한다.

서버를 여러 대 띄웠을 때 같은 이벤트를 두 번 보내지 않는 것, 그리고 보내는 도중에 죽어도 이벤트가 사라지지 않는 것.

같은 이벤트를 두 번 보내는 문제는 FOR UPDATE SKIP LOCKED로 막는다. 한 서버가 어떤 행을 집어서 처리하는 동안 그 행에 잠금을 거는데, SKIP LOCKED는 다른 서버가 그 잠긴 행을 기다리지 않고 그냥 건너뛰게 한다. 그래서 서버들이 서로 부딪히지 않고 일을 나눠 갖는다.

SELECT * FROM outbox
WHERE status = 'PENDING'
  AND next_retry_at <= :now
ORDER BY id
LIMIT :limit
FOR UPDATE SKIP LOCKED

보내는 순서는 "집기 -> 보내기 -> 표시하기"다. 먼저 PENDING 행들을 집어서 PUBLISHING으로 바꾸고(여기까지가 한 트랜잭션), 트랜잭션 밖에서 Kafka로 보낸 뒤, 성공하면 PUBLISHED로 바꾼다.

@Scheduled(fixedDelay = 1000)
public void publish() {
    List<Outbox> batch = outboxStore.claimPending(100);
    for (Outbox outbox : batch) {
        try {
            kafkaTemplate.send(outbox.getEventType(),
                    outbox.getMessageKey(), outbox.getPayload()).get();
            outboxStore.markPublished(outbox.getId());
        } catch (Exception e) {
            outboxStore.markFailedOrRetry(outbox.getId());
        }
    }
}

그런데 Kafka로는 잘 보냈는데 PUBLISHED로 바꾸기 직전에 서버가 죽으면? 그 행은 PUBLISHING(보내는 중)인 채로 남는다. 그냥 두면 영영 다시 안 보내진다. 그래서 PUBLISHING으로 너무 오래 머문 행을 다시 PENDING으로 되돌리는 작업을 따로 돌린다.

@Scheduled(fixedDelay = 60000)
public void recover() {
    outboxStore.recoverStuck(5);   // 5분 이상 PUBLISHING이면 PENDING으로 되돌림
}

되돌려진 행은 다시 보내지니까, 같은 이벤트가 두 번 나갈 수 있다. 이걸 at-least-once라고 한다. "적어도 한 번은 보내지만, 두 번 이상 갈 수도 있다"는 뜻이고, Kafka의 기본 동작이다. 05편 끝에서도 봤던 부분이다. 그래서 받는 쪽이 중복을 견디게 만들어야 하는데....이건 어떻게 할까? 

재시도는 어떻게할까?

보내다 실패했을 때 다시 시도하는 방식이 의외로 중요한데, 처음엔 단순하게 "실패하면 바로 PENDING으로 되돌려서 다음 폴링 때 또 시도"로 짰는데, 여기에 함정이 있었다.

발송 작업이 1초마다 도는데 실패한 행을 곧바로 되돌리면, Kafka가 잠깐 죽었을 때 1초마다 재시도가 쏟아진다. retry_count는 5초 만에 한계에 닿고, 그대로 FAILED로 떨어진다. 05편에서 낙관적 락을 설명하며 말한 재시도 폭풍(retry storm)  "재시도가 또 재시도를 부르며 부하만 키우는 상황" 이 여기서도 똑같이 일어난다. 게다가 5초짜리 잠깐의 장애에 이벤트를 영영 잃는 셈이라, 이벤트를 안 잃으려고 만든 outbox가 오히려 이벤트를 잃는다.

재시도 간격을 어떻게 줄지 정리하면 이렇다.

바로 재시도 가장 단순하지만 위의 재시도 폭풍을 그대로 맞는다. 장애가 난 동안 부하만 늘린다.

고정 간격 N초마다 재시도한다. 폭풍은 줄지만, 여러 행이 동시에 깨졌다면 다 같이 똑같은 순간에 몰려서 재시도한다.

지수 백오프 + jitter 재시도할수록 간격을 1초, 2초, 4초로 점점 늘리고 최대치를 정해둔다. 여기에 jitter를 더한다. jitter는 재시도 시각을 살짝 무작위로 흔드는 것인데, 안 그러면 동시에 깨진 행들이 정확히 같은 타이밍에 또 한꺼번에 몰리기 때문이다.

나는 지수 백오프 + jitter로 선택했다. 실패할 때마다 next_retry_at을 점점 더 뒤로 미루고, 발송 쿼리는 next_retry_at이 지난 행만 집어 온다.

// 실패 시: 한계 넘으면 따로 빼두고, 아니면 간격 두고 재시도
public void markFailedOrRetry(Long id) {
    outboxRepository.findById(id).ifPresent(outbox -> {
        if (outbox.isExceededRetry(MAX_RETRY)) {
            outbox.markFailed();
            log.warn("Outbox moved to FAILED: eventId={}, retryCount={}",
                    outbox.getEventId(), outbox.getRetryCount());
        } else {
            outbox.markRetry(nextRetryAt(outbox.getRetryCount() + 1));
        }
    });
}

// 간격을 점점 늘리되 절반은 무작위로 흔든다 (delay/2 + 0~delay/2 사이 랜덤)
private LocalDateTime nextRetryAt(int retryCount) {
    long expMs = (long) (BACKOFF_BASE.toMillis() * Math.pow(2, retryCount - 1));
    long delayMs = Math.min(expMs, BACKOFF_CAP.toMillis());   // 최대 5분
    long half = delayMs / 2;
    long jittered = half + ThreadLocalRandom.current().nextLong(half + 1);
    return LocalDateTime.now().plus(Duration.ofMillis(jittered));
}

이제 Kafka가 잠깐 죽어도 1,2,4,8초로 간격을 벌리며 버틴다. 재시도 한계를 10번, 최대 간격을 5분으로 두면 약 13분 동안 다시 시도하고, 그 안에 Kafka가 돌아오면 이벤트를 하나도 안 잃고 전부 내보낸다. 그래도 안 되면 FAILED로 빼두는데, 조용히 버리는 게 아니라 로그를 남겨서 나중에 사람이 보고 다시 보낼 수 있게 한다.

FAILED를 자동으로 다시 시도하지 않는 건 일부러 그런 거다. 만약 payload 자체가 깨진 이벤트라면 자동 재시도는 영원히 실패하는 무한 반복이 된다. 자동으로 다시 보내려면 "잠깐 실패한 것"과 "고쳐질 수 없는 것"을 구분하는 장치가 있어야 하고, 그건 나중에 DLQ 부분을 공부해서 적용해봐야할 것 같다.

같은 이벤트를 두 번 받아도 괜찮게 (user-service)

멱등성

같은 작업을 한 번 하든 여러 번 하든 결과가 똑같은 성질을 말한다.

엘리베이터 버튼을 한 번 누르나 다섯 번 누르나 결과가 같은 것과 비슷하다.

컨슈머가 멱등하다는 건, 같은 UserRegisteredEvent를 두 번 받아도 유저는 딱 한 명만 생긴다는 뜻이다.

이게 왜 필요하냐면, 앞에서 봤듯 outbox는 at-least-once라 같은 이벤트가 두 번 올 수 있기 때문이다. 그런데 04편에서의  컨슈머는 이 중복을 제대로 막지 못했다.

@KafkaListener(...)
public void consume(String message) {
    try {
        ...
        userService.createUser(...);
    } catch (Exception e) {
        log.error(...);   // 예외를 삼키고 넘어간다
    }
}

두 가지가 문제였다.

첫째, 중복은 existsByEmail이 던지는 예외 덕에 우연히 막혔을 뿐이다. 일부러 막은 게 아니라 이메일 중복 체크에 얹혀서 막힌 거라, 이메일 같은 제약이 없는 도메인에선 못 쓴다.

둘째, 예외를 catch해서 로그만 찍으니, 처리에 실패해도 "이 메시지 처리했음"으로 기록되어 이벤트가 사라진다. 이벤트 잃지 말자고 outbox를 만들었는데 받는 쪽에서 다시 흘리는 꼴이다.

그럼 중복은 어떻게 막아야 할까?

이메일 중복 체크에 기대기 unique 제약 덕에 중복 저장이 막히긴 한다. 하지만 매번 예외가 터지고, 그런 제약이 없는 도메인엔 못 쓴다. 멱등성을 우연에 맡기는 셈이다.

처리 전에 확인하기 처리한 event_id를 어딘가 적어두고, 처리하기 전에 이미 있는지 확인한다. 단순하지만, 확인하는 순간과 적는 순간 사이에 같은 이벤트가 또 들어오면 둘 다 통과해버릴 수 있다.

Inbox 패턴 처리한 event_id를 processed_event라는 테이블에 적되, 유저를 만드는 작업과 같은 트랜잭션에서 적는다. outbox가 "보낼 편지함"이었다면 inbox는 "받은 편지함"이다. 적을 때 INSERT IGNORE를 쓰면 이미 있는 event_id는 그냥 무시되고, 실제로 적힌 행 수만 0 또는 1로 돌아온다. 0이면 전에 처리한 이벤트, 1이면 처음 보는 이벤트다.

나는 Inbox 패턴을 선택했다. 동작 순서는 이렇다.

  1. 먼저 이 이벤트의 event_id를 processed_event에 적는다(INSERT IGNORE).
  2. 적힌 행이 0이면? 전에 처리한 이벤트다. 더 진행하지 않고 멈춘다.
  3. 적힌 행이 1이면? 처음 보는 이벤트다. 유저 생성을 진행한다.

왜 기록을 먼저 하냐면, "이 이벤트 처리했음"이라는 표시를 유저 생성보다 먼저 남겨야 둘을 같은 트랜잭션으로 묶을 수 있어서다. 그리고 왜 같은 트랜잭션에 넣냐면, 유저 생성이 중간에 실패하면 그 "처리했음" 표시도 같이 사라져야 다음에 다시 받았을 때 또 처리할 수 있기 때문이다. 표시만 남고 유저는 안 생기는 상황을 막는 것이다. 둘이 따로 놀면 결국 또 dual-write 문제가 되돌아온다.

INSERT IGNORE를 쓴 데도 이유가 있다. JPA에서 흔히 하듯 그냥 save() 하고 중복 예외(DataIntegrityViolationException)를 잡는 방식은, 그 예외가 트랜잭션을 "되돌릴 예정" 상태로 표시해버린다. 그 상태에서 같은 트랜잭션으로 유저 생성을 이어가려 하면 커밋 시점에 또 다른 예외가 터진다. INSERT IGNORE는 예외 없이 적힌 행 수만 돌려주기 때문에 이 문제가 없다.

CREATE TABLE processed_event (
    consumer_group VARCHAR(100) NOT NULL,
    event_id       VARCHAR(36)  NOT NULL,
    event_type     VARCHAR(100) NOT NULL,
    processed_at   DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (consumer_group, event_id)
);

기본 키를 (consumer_group, event_id) 두 개로 묶었다. 한 서비스가 여러 컨슈머 그룹으로 같은 이벤트를 받더라도, 그룹마다 따로 "처리했음"을 관리할 수 있게 하기 위해서다.

@Modifying
@Query(value = """
    INSERT IGNORE INTO processed_event (consumer_group, event_id, event_type, processed_at)
    VALUES (:consumerGroup, :eventId, :eventType, :processedAt)
    """, nativeQuery = true)
int insertIfAbsent(String consumerGroup, String eventId,
                   String eventType, LocalDateTime processedAt);

이 기록과 비즈니스 로직을 한 트랜잭션으로 묶는 곳이 아래다. 적힌 행이 0이면 멈추고, 1이면 넘겨받은 로직을 실행한다.

@Transactional
public void process(String consumerGroup, String eventId,
                    String eventType, Runnable businessLogic) {
    int inserted = processedEventRepository.insertIfAbsent(
            consumerGroup, eventId, eventType, LocalDateTime.now());

    if (inserted == 0) {
        log.info("Duplicate event skipped: group={}, eventId={}", consumerGroup, eventId);
        return;   // 전에 처리한 이벤트 → 그냥 넘어감
    }

    businessLogic.run();
}

컨슈머는 얇아졌다. 메시지를 객체로 바꾸는 일만 직접 하고(여기서 실패하면 다시 시도해도 소용없으니 일단 넘어가자..), 나머지는 위 처리기에 맡긴다. 비즈니스 예외는 더 이상 삼키지 않는다. 유저 생성이 실패하면 트랜잭션이 되돌려지고 메시지가 다시 들어온다.

@KafkaListener(topics = EventTopic.USER_REGISTERED, groupId = GROUP)
public void consume(String message) {
    EventEnvelope<UserRegisteredEvent> event;
    try {
        event = kafkaObjectMapper.readValue(
                message, new TypeReference<EventEnvelope<UserRegisteredEvent>>() {});
    } catch (Exception e) {
        log.error("Malformed event skipped: {}", e.getMessage(), e);
        return;   // 깨진 메시지 → DLQ는 뒤 편에서
    }

    UserRegisteredEvent payload = event.payload();
    idempotentProcessor.process(GROUP, event.eventId(), event.eventType(),
            () -> userService.createUser(payload.userId(), payload.email(), payload.name()));
}

이걸로 auth -> user 흐름이 닫혔다. auth-service는 outbox로 이벤트를 확실히 내보내고, user-service는 inbox로 중복을 막는다. 이벤트가 한 번 더 와도 유저는 한 명만 생긴다.

테스트

배포는 이전편에서 했으니 푸쉬만해도 어차피 알아서 배포된다. 

통합테스트나 단위테스트는 나중에 할 예정이니까 일단 패스하고.. 여기선 api로 직접 찔러보고 DB에서 조회하고보 Kafka도 끊어보고 하면서 원하는 방식의 동작이 이루어지는지 확인해 볼 것이다.

가입 요청

curl -X POST .../api/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"test1@seatflow.com","password":"...","name":"준석"}'

DB 확인

auth 쪽 outbox에는 가입 후 이벤트가 한 건 쌓이고, 잠깐 PENDING이었다가 발송 작업이 집어가서 PUBLISHED로 바뀐다.

id | event_type      | status    | published_at
 1 | user.registered | PUBLISHED | 2026-... 00:00:00

user 쪽에는 생성한 유저가 생기고, processed_event에 한 건 남는다.

outbox의 event_id와 processed_event의 event_id는 같아야하니까 확인해봐야 한다. 이게 같다는 건 하나의 이벤트가 보내는 쪽에서 받는 쪽까지 같은 id를 달고 끝까지 잘 흘렀다는 뜻이다.

타임스탬프도 생각했던 결과가 나왔다. processed_event가 먼저 기록되고, 유저 생성이 그 다음이다. 처리했다! 라고 먼저 적고, 그다음 비즈니스 로직! 이라는 순서가 실세로 구현이 되었다.

자 이제 Kafka를 죽여볼거다...

기존 서버에 있는 브로크를 전부 내리고 가입 요청을 했다. 여기서 두 가지가 눈에 띄었는데,

첫째, Kafka가 죽었는데 가입은 일단 200으로 성공했다. 가입은 DB(credentials + outbox) 에만 쓰고 발행은 발송 작업이 따로하니까 Kafka 상태와 상관없이 사용자는 가입에 성공하게 된다. 보내는 일을 떼어내니까 이런게 보였다.

둘째, 이벤트는 사라지지 않고 outbox에 잡혀있었다. 발행이 안됐으니까 받는 쪽도 당연히 움직이지 않는다. user-service에 유저도 생성이 안됐고 processed_event도 남아있지 않았다.

id | status     | retry_count | published_at
 2 | PUBLISHING |     0        |  (NULL)        << 못 나가고 대기 중

이제 다시 Kafka를 살려보면, 붙잡혀 있던 이벤트가 알아서 따라잡는다. PUBLISHED로 바뀌고, 유저와 processed_event가 생겼다.

Kafka가 죽어있는 동안 돌아온 이벤트가 살리고나서 데이터 유실 없이 끝까지 도달했다.

여기에 백오프가 실제로 일한 흔적이 남았다. 브로커가 한 30분 정도 죽어잇었는데 그 행의 retry_count는 5에 멈춰있었다. 만약 실패할 때마다 곧바로 재시도했다면 retry_count가 진작 한계를 넘겨서 FAILED로 빠졌을테고, 그러면 해당 이벤트는 영영 갈 곳을 잃었을것이다. 재시도 간격을 점점 벌린 덕에, 긴 장애 동안에도 횟수를 적게 쓰면서 버티다 복구된 것이다.

정리

테스트는 예상했던대로 설계한 시나리오대로 통과했다. 정상일 때는 한 이벤트가 같은 event_id를 달고 끝까지 흐르고, Kafka가 죽더라도 가입자체는 안되지 않으면서 이벤트를 잃지 않고 대기하다가 복구 하고 따라잡았다. 이번에 작업하면서 보내는 쪽의 Outbox와 받는 쪽의 Inbox가 실제로 동작하는걸 확인해봤다.

그럼 나머지 서비스는?

이번 편에서 손댄 건 auth-service(보내는 쪽)와 user-service(받는 쪽) 둘뿐이다.

그럼 show, seat, reservation, payment는 지금 뭘 해야 하나? "전부 outbox 박자"는 답이 아니다.

그 서비스가 이벤트를 보내는지, 받는지에 따라 해야 할 게 달라진다.

기준은 한 번 잡아보자!

  • DB에 쓰면서 이벤트도 보낸다 -> Outbox (보내는 쪽 dual-write 문제)
  • 이벤트를 받아서 처리한다 -> Inbox/멱등성 (받는 쪽 중복 문제)
  • 둘 다 한다 -> 둘 다

지금 기준으로 정리하면 이렇다.

서비스 하는 일 지금 필요한 것 메모

서비스역할 (DB/메시징)적용 패턴진행 상황
auth-service보냄 (DB+Kafka)Outbox이번 편 완료
user-service받음Inbox/멱등성이번 편 완료
show-service자체 등록 (보내는 거 거의 없음)당장 없음이벤트를 보내게 되면 그때
seat-service보냄 (Redis+Kafka)Outbox 계열점유가 Redis라 변형 필요
reservation-service받음 -> (나중에 보냄)지금은 InboxSaga 들어가면 Outbox 추가
payment-service받음 -> (나중에 보냄)지금은 Inbox결제 결과 보낼 때 Outbox

seat-service가 까다롭다. 좌석 점유 상태가 DB가 아니라 Redis에 있어서, "같은 트랜잭션으로 outbox에 적는다"는 게 안 된다. Redis는 DB 트랜잭션 안에 안 들어오기 때문이다. 05편 끝에서 적었듯, 점유를 DB에도 같이 적어서 outbox를 쓰거나, 아니면 at-least-once로 보내고 받는 쪽 멱등성 + 주기적 대조(reconciliation)로 맞추거나 둘 중 하나다. 이건 좌석 도메인 자체를 더 두껍게 만든 다음에 정하는 게 순서상 맞아서 나중에 진행 할 예정이다.

reservation과 payment는 지금은 이벤트를 받기만 해서 Inbox만 있으면 된다. 하지만 나중에 Saga로 들어가서 결제를 부르고 그 결과를 이벤트로 보내기 시작하면, 그때 보내는 책임이 생기고 Outbox가 추가된다.

즉 이벤트를 보내기 시작하는 시점에 그 서비스에만 붙이는 게 맞다. 아직 아무것도 안 보내는 서비스에 미리 outbox를 까는 건 쓰지도 않을 코드를 만드는 거다.

언제써야 할까?

이번에 쓴 두 패턴은 Seatflow에만 있는 게 아니라, 이벤트로 통신하는 시스템이면 어디서나 반복해서 나온다. 어떤 상황에 쓰는지 예를 들어두면 감이 잡힌다.

Outbox  "DB에 뭔가 쓰면서, 그 사실을 다른 서비스에도 알려야 하는데, 둘이 한 트랜잭션이 아닌" 모든 곳.

  • 주문을 만든 뒤 결제·배송·알림 서비스에 "주문 생겼다"를 알릴 때
  • 회원가입 후 환영 메일이나 포인트 적립을 걸 때 (이번 경우)
  • 재고를 깎은 뒤 정산이나 물류 쪽에 알릴 때

Inbox/멱등성 "메시지를 적어도 한 번은 받는데, 같은 걸 두 번 처리하면 큰일 나는" 모든 곳. Kafka처럼 at-least-once로 보내는 시스템에선 같은 메시지가 다시 오는 게 예외가 아니라 정상이다.

  • 결제 승인 이벤트를 두 번 받아 돈이 두 번 빠지면 안 될 때
  • 포인트 적립이나 쿠폰이 중복으로 지급되면 안 될 때
  • 같은 알림이 사용자에게 두 번 가면 안 될 때

04편에서 잠깐 비교했던 Saga, CDC도 이 근처에 있는 도구들인데, 서로 경쟁하는 게 아니라 맡는 일이 다르다. Outbox는 한 서비스가 이벤트를 확실히 내보내는 걸, 멱등성은 받는 쪽이 중복에 흔들리지 않는 걸 맡는다. Saga는 여러 서비스에 걸친 흐름 전체가 어긋나지 않게 맞추는 일을 맡는데, 이건 나중에 따로 다룰 예정이다.
