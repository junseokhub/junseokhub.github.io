[Seatflow] 16-1. 통합테스트를 하며 발생한 버그들

Lab/SeatFlow · 2026-08-04

Intro

16편에서는 테스트 인프라를 어떻게 세팅했는지, 그리고 그 과정에서 컨테이너 공유 때문에 겪은 문제들을 정리했다. 이번 편은 그렇게 세팅한 인프라 위에서 실제로 테스트를 짜다가 발견한 것들을 모았다. 진짜 운영 버그로 이어질 뻔했던 것부터, 테스트 코드 자체의 설계 실수, 처음엔 다른 곳을 의심했다가 정정한 사례까지 담았다.

각 이슈마다 원인만 적지 않고, 왜 그 방식으로 고쳤는지와 다른 대안은 없었는지도 같이 정리했다.

문제

Redis 키 하나가 미묘하게 달라서, 점유가 해제되지 않던 문제

좌석 점유(hold) 로직을 담당하는 클래스를 다시 보다가, Redis 키를 만드는 방식이 두 가지로 섞여 있는 걸 발견했다.

// 여러 좌석을 한 번에 다루는 메서드가 쓰는 방식
private String holdKey(String showId, Long seatId) {
    return SEAT_HOLD_PREFIX + "{" + showId + "}:" + seatId;   // 중괄호 있음
}

// 단일 좌석을 다루는 메서드들이 직접 조합하던 방식
String key = SEAT_HOLD_PREFIX + showId + ":" + seatId;         // 중괄호 없음

같은 좌석을 가리키려는 의도인데, 실제로는 완전히 다른 Redis 키였다. 점유할 때는 첫 번째 방식으로 키를 만들고, 점유 여부를 확인하거나 해제할 때는 두 번째 방식으로 키를 만드니, 서로 다른 키를 보고 있는 셈이라 해제가 정상적으로 안 됐다.

왜 처음에는 중괄호를?

{showId} 형태는 Redis Cluster의 해시 태그 문법이다. Redis Cluster는 키를 해시해서 여러 노드(슬롯)에 분산 저장하는데, 기본적으로는 키 전체를 해시 대상으로 삼기 때문에, 같은 공연의 다른 좌석이라도 서로 다른 슬롯에 흩어질 수 있다. 여러 좌석을 한 번에 원자적으로 다루는 연산은 그 키들이 반드시 같은 슬롯에 있어야 동작한다. 중괄호로 감싼 부분만 해싱 대상으로 삼는 게 이 문법의 규칙이라, {showId}를 공통으로 넣으면 같은 공연의 좌석 키들이 항상 같은 슬롯에 모인다.

문제는 단일 키만 다루는 메서드들이 이건 해시 태그가 필요 없을것이라고 판단해서 다른 형식으로 직접 조합해버린 것이었다. 같은 대상을 가리키는 키는 접근하는 메서드가 뭐든 항상 동일해야 하는데, 그 원칙이 깨졌다.

다른 해결 방법은?

  • 단일 키 메서드들도 해시 태그를 붙이는 것

    • 결과적으로 이 방식을 택했다. 모든 메서드가 하나의 키 생성 헬퍼를 공유하도록 정리해서, 형식이 갈라질 여지 자체를 없앴다.

  • 애초에 해시 태그를 쓰지 않는 것 

    • Redis Cluster를 안 쓰는 단일 노드 구성이라면 해시 태그가 필요 없다. 다만 이 프로젝트는 운영에서 Redis Cluster를 쓰는 걸 전제로 하고 있어서, 이 대안은 채택하지 않았다.

실제 운영에 미친 영향

이 해제 메서드는 결제가 확정되어 좌석이 최종 반영될 때 실제로 호출되는 경로였다. 결제가 완료될 때마다, Redis에 실제로 남아있던 점유 키는 안 지워지고, 존재하지도 않는 다른 키를 지우려는 헛수고만 반복되고 있었다. 좌석이 이미 확정됐으니 당장 기능이 망가지는 건 아니지만, TTL이 끝날 때까지 Redis에 불필요한 키가 계속 쌓이는 조용한 정합성 문제였다.

수동으로 API 테스트했으면 점유부터 결제까지 눈으로 보고 끝났을 거다. Redis 안의 키가 정확히 지워졌는지까지 매번 직접 확인하는 경우는 거의 없다. 통합 테스트가 이걸 명시적으로 검증했기 때문에 드러난 문제였다.

필수 헤더가 없으면 400이 아니라 500이 응답되던 문제

멱등성 키 헤더 없이 요청을 보내는 테스트를 짜다가 이상한 걸 발견했다. 400이 나와야 하는데 500이 나왔다.

Spring MVC는 @RequestHeader로 지정한 헤더가 요청에 없으면 특정 예외를 던진다. 공통 예외 처리기를 보니 이 예외를 처리하는 핸들러가 따로 없었다. 대신 어떤 예외든 다 잡아버리는 포괄적인 핸들러가 맨 마지막에 있어서, 처리되지 않은 예외는 전부 여기로 떨어져 500이 나가고 있었다.

왜 이게 문제일까?

필수 헤더를 빠뜨린 건 명백히 클라이언트 잘못이다. 클라이언트 잘못은 4xx로 응답하는 게 맞고, 서버 잘못(예상 못 한 내부 오류)만 5xx로 응답해야 한다. 이 둘을 구분 안 하면, 클라이언트 입장에서는 내가 뭘 잘못 보냈나 보다라고 판단할 기회를 잃고, 서버 쪽 모니터링 입장에서는 실제로는 문제없는 요청 실수까지 심각한 서버 오류로 잡혀서 알림이 울리게 된다.

여기서 끝이 아니었다

비슷한 검증을 다른 서비스에서도 반복하다 보니, 필수 쿠키가 없을 때, 그리고 요청 본문의 JSON 파싱이 실패할 때(예: 정의되지 않은 값을 enum 필드에 보낸 경우)도 똑같은 패턴으로 500이 나는 걸 발견했다. 같은 종류의 결함이 세 가지 다른 형태(헤더, 쿠키, 파싱 실패)로 반복해서 나온 셈이다.

해결

공통 예외 처리기는 여러 서비스가 공유하는 모듈 안에 있는 파일이었다. 여기에 각 예외를 위한 핸들러를 추가했다.

@ExceptionHandler(MissingRequestHeaderException.class)
public ResponseEntity<ApiResponse<Void>> handleMissingRequestHeader(MissingRequestHeaderException e) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(ApiResponse.fail("필수 헤더가 없습니다: " + e.getHeaderName()));
}

@ExceptionHandler(MissingRequestCookieException.class)
public ResponseEntity<ApiResponse<Void>> handleMissingRequestCookie(MissingRequestCookieException e) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(ApiResponse.fail("필수 쿠키가 없습니다: " + e.getCookieName()));
}

@ExceptionHandler(HttpMessageNotReadableException.class)
public ResponseEntity<ApiResponse<Void>> handleMessageNotReadable(HttpMessageNotReadableException e) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(ApiResponse.fail("요청 형식이 올바르지 않습니다."));
}

공통 모듈에 있는 파일을 한 번 고치니, 이 핸들러를 쓰는 모든 서비스에 동시에 적용됐다. 한 서비스에서 발견한 결함을 고친 게 전체 서비스에 파급되는 걸 보면서, 공통 모듈에 있는 결함은 그 영향 범위가 생각보다 크다는 걸 체감했다.

다른 방법은?

  • 포괄 핸들러 안에서 예외 타입을 분기하는 것
    • catch (Exception e) 안에서 instanceof로 나눠 처리하는 방법도 있다. 다만 이러면 새로운 예외 타입이 추가될 때마다 그 큰 분기문을 계속 늘려야 해서, @ExceptionHandler로 타입별 메서드를 나누는 쪽이 각 케이스를 독립적으로 다루기 쉽고 가독성도 좋다.

예외를 잡았는데도 트랜잭션이 이미 망가져 있던 문제

회원가입 로직에서, 같은 이벤트가 중복으로 와도 회원은 한 번만 생성되게 하려는 멱등 처리를 이런 형태로 짰다.

@Transactional(noRollbackFor = DataIntegrityViolationException.class)
public void createUser(String userId, String email, String name) {
    try {
        User user = User.builder().id(userId).email(email).name(name).build();
        userRepository.saveAndFlush(user);
    } catch (DataIntegrityViolationException e) {
        Throwable cause = e.getRootCause();
        if (cause instanceof SQLException sqlEx && sqlEx.getErrorCode() == 1062) {
            // 중복 - 조용히 넘어간다
            return;
        }
        throw e;
    }
}

단위 테스트(Mock 기반)는 다 통과했다. 근데 동시 회원가입을 재현하는 통합 테스트를 돌리자, 대부분이 트랜잭션 관련 예외로 실패했다.

왜 catch를 했는데도 문제가 생길까?

저장 메서드가 유일성 제약 위반으로 실패하는 순간, 트랜잭션 관리자가 그 트랜잭션을 내부적으로 롤백 전용으로 표시해버린다. catch로 예외를 잡아서 조용히 return해도, 이미 붙은 표시는 지워지지 않는다. 메서드가 정상 종료된 것처럼 보이지만, 트랜잭션을 커밋하려는 순간 이미 롤백 전용으로 표시된 트랜잭션을 커밋할 수 없다는 예외가 터진다.

noRollbackFor 옵션을 걸어뒀는데도 안 먹힌 이유는, 이 옵션이 예외가 메서드 밖으로 빠져나갈 때 롤백하지 말라는 뜻이기 때문이다. catch로 메서드 안에서 삼켜버리는 구조에는 처음부터 적용될 상황 자체가 오지 않는다.

Mock 기반 단위 테스트로는 이 문제가 재현되지 않는다. Mock은 메서드가 예외를 던진다는 것까지만 흉내 낼 뿐, 그 예외가 나는 순간 진짜 트랜잭션 관리자가 내부적으로 상태를 표시하는 것까지는 흉내 내지 않는다. 진짜 트랜잭션 관리자와 진짜 DB가 있어야만 드러나는 문제였다.

검토한 대안들과 최종 선택

  • 예외를 던지는 대신 예외가 안 나는 방식(upsert 문법)으로 바꾸기
    • 데이터베이스가 지원하는 있으면 무시하고 없으면 넣는 형태의 쿼리를 쓰면, 예외 자체가 안 나므로 트랜잭션이 오염될 여지가 원천적으로 사라진다. 이 엔티티가 필드 구성이 단순해서 이 쿼리를 직접 작성하는 부담이 크지 않았고, 최종적으로 이 방식을 채택했다.
@Transactional
public void createUser(String userId, String email, String name) {
    int inserted = userRepository.insertIgnore(userId, email, name, LocalDateTime.now());
    if (inserted == 0) {
        // 중복 - 조용히 넘어간다
    }
}

  • 문제가 되는 저장 시도를 별도 트랜잭션으로 격리하기

    • 독립된 트랜잭션에서 실패하면 그 트랜잭션만 롤백되고, 바깥 트랜잭션은 오염되지 않는다. 다만 이 방식은 자기 자신을 통한 호출로는 적용되지 않는다는 제약이 있어서(같은 클래스 안에서 메서드를 직접 호출하면 프록시를 안 거치므로 적용 안 됨), 별도의 빈으로 분리해야 하는 구조적 비용이 있다. 또한 이 별도 트랜잭션이 매번 새 DB 커넥션을 쓰기 때문에, 동시 요청이 많을 때 커넥션 풀에 부담이 될 수 있다.

  • 지금 방식(noRollbackFor + catch)을 유지하되 문제를 감수

    • 일단 이 방법은 채택하지 않았다. 이 이슈 자체가 이 방식의 근본적인 한계를 보여줬는데,이 하나의 버그를 겪으면서, 멱등 처리 방식 여러 가지(저장 후 catch, upsert 문법, 별도 트랜잭션 격리, noRollbackFor)를 나란히 구현해서 실제로 동시성 테스트로 비교해봤다. noRollbackFor 방식만 진짜 동시 요청에서 트랜잭션 예외가 재현되는 테스트를 남겨서, Mock으로는 절대 안 잡히고 진짜 DB가 있어야만 드러난다는 걸 코드로 증명해뒀다.

저장 메서드의 반환값을 안 받아서 생긴 조용한 버그

공연 생성 로직을 테스트하다가, 이벤트에 담긴 식별자가 항상 비어있는 걸 발견했다.

@Transactional
public Show createShow(CreateShowCommand command) {
    Show show = Show.builder()...build();
    showRepository.save(show);   // 반환값을 안 받음
    ShowCreatedEvent event = toEvent(show);
    ...
    .messageKey(show.getId())   // 원본 show는 id가 채워지지 않은 상태
    ...
}

MongoDB는 식별자 필드를 애플리케이션이 직접 지정하지 않으면, 저장 시점에 드라이버가 자동으로 값을 생성해준다. 이 새로 생성된 값은 저장 메서드가 반환하는 객체에 담기는 것이지, 원래 넘겼던 지역변수에 자동으로 반영되는 게 보장된 동작은 아니다. 원본 변수를 그대로 쓰면 식별자가 여전히 비어있을 수 있다.

해결

show = showRepository.save(show);   // 반환값을 다시 받아씀

반환값을 받아쓰는 걸로 고쳤다. 이 버그도 단위 테스트가 잡아냈다. Mock으로 "식별자가 생성됐다고 가정한 반환값"과 "원본 변수"를 서로 다르게 설정해뒀더니 이 차이가 그대로 드러났다.

왜 이걸 검증 대상으로 해야할까?

저장 메서드의 반환값을 반드시 받아써야 한다는 건 원칙적으로 알려진 이야기지만, 실제로 코드를 짤 때는 무심코 놓치기 쉬운 지점이다. 특히 애플리케이션이 직접 식별자를 지정하지 않는 데이터 저장소(자동 증가 컬럼, 자동 생성 식별자)를 쓸 때 이 실수가 나기 쉽다. 이런 실수는 컴파일 에러도 안 나고, 저장 자체는 성공하기 때문에 겉보기엔 문제없어 보인다는 게 특히 위험하다.

Repository를 트랜잭션 없이 직접 호출하면 안 되는 이유

캠페인의 재고를 원자적으로 차감하는 쿼리를 테스트하다가 겪은 문제다.

@Modifying
@Query("UPDATE CouponCampaign c SET c.issuedQuantity = c.issuedQuantity + 1 " +
        "WHERE c.id = :campaignId AND c.issuedQuantity < c.totalQuantity")
int increaseIssuedQuantity(@Param("campaignId") Long campaignId);

이 쿼리의 동시성을 검증하는 통합 테스트에서, 여러 스레드가 이 메서드를 직접 호출하게 했더니 매번 결과가 0으로 나왔다. 로그를 확인해보니 수정/삭제 쿼리를 트랜잭션 없이 실행하려 했다는 예외였다.

왜 이런 예외가 났을까?

데이터를 바꾸는 쿼리는 반드시 트랜잭션 안에서 실행돼야 한다. 트랜잭션은 저절로 생기지 않는다. 실제 운영 코드에서는 이 쿼리를 부르는 서비스 메서드에 트랜잭션이 걸려 있어서 문제가 없었는데, 테스트 코드가 서비스 계층을 건너뛰고 Repository 메서드를 직접 부르면서 그 트랜잭션이 아예 사라졌다.

검토한 대안들

  • Repository 메서드 자체에 트랜잭션을 거는 것

    • 처음엔 이렇게 해서 문제를 해결하려 했다. 실제로 예외는 사라졌다. 근데 Repository는 이 쿼리를 어떻게 실행할지만 정의하는 계층이고, 어디서부터 어디까지를 하나의 트랜잭션 단위로 묶을지는 그 위의 서비스 계층이 결정할 문제다. Repository가 자기 마음대로 트랜잭션을 만들어버리면, 서비스 계층이 여러 작업(재고 차감과 이벤트 기록 등)을 하나의 트랜잭션으로 묶으려는 설계 의도가 Repository 단계에서부터 깨질 위험이 있다. 이 대안은 기각했다.

  • 테스트가 실제 서비스 메서드를 호출하도록 바꾸기

    • 난 일단 이 방법으로 진행했다. Repository의 트랜잭션 어노테이션은 걷어내고, 대신 테스트가 이미 트랜잭션이 걸린 실제 서비스 메서드를 호출하도록 고쳤다.
// Repository를 직접 부르지 않고
mysqlCouponService.issueCoupon(campaignId, userId);

이건 검증을 우회하는 게 아니라 오히려 더 정확한 검증이었다. 실제 운영에서 Repository가 트랜잭션 없이 단독으로 호출되는 경우는 없으니, 테스트도 그 실제 경로를 그대로 재현하는 게 맞는 방향이라고 생각한다.

원자적 수정 쿼리와 영속성 컨텍스트가 어긋난 문제

같은 재고 쿼리를 테스트하면서 겪은 또 다른 문제다. 재고 차감 쿼리가 성공(1)을 반환했는데, 바로 이어서 다시 조회하면 값이 여전히 이전 그대로였다.

int updated = campaignRepository.increaseIssuedQuantity(campaign.getId());
// updated == 1 (성공)

CouponCampaign reloaded = campaignRepository.findById(campaign.getId()).orElseThrow();
// reloaded.getIssuedQuantity()가 여전히 이전 값

수정/삭제 쿼리는 JPA의 영속성 컨텍스트(이미 조회해둔 엔티티를 메모리에 캐싱해두는 1차 캐시)를 거치지 않고 DB에 직접 SQL을 날린다. 문제는 영속성 컨텍스트 안에 이미 로드돼 있던 엔티티가 이 사실을 전혀 모른다는 것이다. DB는 확실히 바뀌었는데, 다시 조회하는 메서드가 이미 캐시에 있는 식별자라고 판단해서 진짜 DB를 다시 안 보고 캐시된 이전 값을 그대로 돌려줬다.

해결

@Modifying(clearAutomatically = true)
@Query(...)
int increaseIssuedQuantity(@Param("campaignId") Long campaignId);

clearAutomatically = true를 붙이면, 이 수정 쿼리 직후 영속성 컨텍스트를 자동으로 비워준다. 그러면 이어지는 조회가 캐시된 값이 아니라 진짜 DB 값을 다시 읽어온다.

다른 대안

  • 수동으로 entityManager.clear()나 refresh()를 호출하는 것
    • clearAutomatically는 이걸 프레임워크 차원에서 자동화해주는 옵션이라, 쿼리를 호출하는 모든 지점마다 수동으로 정리 코드를 넣지 않아도 된다는 이점이 있다. 다만 컨텍스트 전체를 비우는 방식이라, 이 수정과 무관한 다른 엔티티들의 캐시도 같이 날아간다는 점은 감안해야 한다. 이 쿼리를 부르는 시점에 이미 다른 무거운 조회를 많이 해둔 상황이라면, 그 조회들도 다시 DB를 타게 되어 성능에 영향을 줄 수 있다.

이번 상황에서는 이 쿼리 이후 별다른 대량 조회가 없어서 부담이 크지 않았고, 매번 수동으로 정리 코드를 넣는 것보다 실수할 여지가 적어서 이 방식을 택했다.

테스트를 위해 생성자에 파라미터를 추가하는 것과 리플렉션 중 무엇이 나은가

엔티티들 중 일부는 상태 필드가 JPA의 저장 전 콜백에서만 초기화된다. 이 콜백은 실제로 저장할 때만 호출되기 때문에, 저장을 하지 않는 순수 단위 테스트에서는 상태가 계속 비어있다. 상태 전이 메서드들이 지금 상태가 뭔지에 따라 분기하니, 테스트에서 원하는 상태를 미리 만들 방법이 필요했다.

검토한 방법들

  • 리플렉션으로 private 필드를 직접 조작

    • 가장 먼저 떠올렸지만, 캡슐화를 깨고 컴파일 타임 안전성을 잃는 방식이라 기각했다. 필드 이름을 문자열로 참조하기 때문에, 필드명을 리팩터링해도 컴파일 에러 없이 조용히 깨질 수 있다.

  • 패키지 접근 제한자의 초기화 메서드를 테스트에서 직접 호출

    • 같은 패키지 안에서는 가능하지만, 다른 패키지의 테스트 클래스에서는 못 쓴다.

  • 빌더에 상태 파라미터를 추가

    • 나는 해당 방법으로 진행했다.
@Builder
private Reservation(String userId, String showId, Long seatId,
                    BigDecimal amount, LocalDateTime showDate,
                    ReservationStatus status) {   // 테스트 셋업 편의를 위해 추가
    ...
    this.status = status;
}

왜 이게 안전한걸까?

빌더를 private 생성자에 걸어둔 원래 의도는 운영 코드가 상태를 마음대로 초기 지정하지 못하게 막는 것이었다. 이 원칙이 지키려는 대상은 운영 코드이지 테스트 코드가 아니다. 단위 테스트의 셋업 단계는 애초에 특정 상황을 가정한다는 게 본질적인 역할이라, 그 상황을 빌더 파라미터로 지정하든 실제 전이 메서드를 순서대로 호출하든, 테스트가 운영 흐름을 우회하는 건 아니다.

빌더에 파라미터를 추가해도 외부에서 이 빌더를 호출할 수 있는 범위는 그대로다. 운영 코드는 여전히 상태를 안 넘기고, 실제 저장 시 초기화 콜백이 무조건 덮어쓴다. 이 파라미터가 실제로 의미를 갖는 곳은 저장을 거치지 않는 순수 단위 테스트뿐이다.

리플렉션처럼 컴파일 타임 안전성 자체를 포기하는 방법과, 빌더 파라미터처럼 타입 안전하고 명시적인 방법은 겉보기엔 비슷해 보여도 질적으로 다르다.

Mock으로 만든 객체가 이상하게 동작하는 것 같았지만, 진짜 원인은 생성자 인자 순서였다

한 서비스 클래스의 단위 테스트를 짜면서 여러 가지 이상한 예외를 겪었다. Mock 설정과 관련된 예외들이 예상 못 한 순간에 터졌고, 처음엔 이 환경에서 Mock을 쓰는 게 불안정한가 싶어서 Mock을 포기하고 진짜 객체로 돌아가려던 참이었다.

진짜 원인

// 테스트 코드에서
someService = new SomeService(a, b, c, d);

// 실제 필드 선언 순서
someService = new SomeService(b, a, d, c);

여러 필드를 한 번에 초기화하는 생성자를 자동으로 만들어주는 방식은 필드 선언 순서 그대로 생성자를 만드는데, 이 순서를 잘못 추측해서 테스트를 짰다. Mock 객체들이 서로 다른 자리에 잘못 주입되니, 서비스 내부에서 엉뚱한 Mock을 호출하게 되고, 그러다 보니 Mock 관련 내부 상태가 꼬여서 전혀 관계없어 보이는 예외들이 연쇄적으로 터진 것이었다.

생성자 순서만 맞추니 Mock 방식도 다시 정상적으로 동작했다. Mock 자체가 문제라고 결론 내리기 전에, 정말 기본적인 것부터(생성자 파라미터가 정확히 맞는지) 확인했어야 했다.

식별자가 자동 생성되는 필드를 빌더로 못 채우는 것

같은 서비스를 테스트하다가, 여러 좌석을 식별자 기준으로 매핑하는 과정에서 식별자 중복 예외를 만났다. 식별자가 자동 생성되는 필드라 빌더로 직접 못 채우는데, 테스트에서 만든 여러 엔티티가 전부 그 필드를 비워둔 채였기 때문이다.

  • 리플렉션으로 식별자 필드를 채우기

    • 가능은 하지만, 앞서 7번에서 다룬 것과 같은 이유로 피했다.

  • 엔티티 자체를 Mock으로 만들어서 식별자만 원하는 값으로 지정

    • 해당 방법을 선택했다.
private Seat mockSeat(Long id, SeatStatus status) {
    Seat seat = mock(Seat.class);
    given(seat.getId()).willReturn(id);
    given(seat.getStatus()).willReturn(status);
    return seat;
}

여기서 검증하려는 건 엔티티 자체가 어떻게 동작하는가가 아니라, 서비스가 엔티티의 상태와 식별자를 보고 올바르게 분기하는가였다. Mock으로도 이 목적은 충분히 달성됐다. 엔티티 자체의 상태 전이 로직은 별도의 도메인 단위 테스트에서 이미 검증했으니 중복 검증도 아니었다.

컨트롤러가 직접 던지는 예외가 원하는 상태 코드로 안 바뀌던 문제

한 컨트롤러 테스트에서 컨트롤러가 직접 비즈니스 예외(본인 예매가 아니라는 거부)를 던지는 경로를 테스트했더니, 원하는 상태 코드 대신 그 비즈니스 예외 자체가 그대로 터졌다.

다른 서비스의 비슷한 컨트롤러 테스트에서는 이런 문제가 없었는데, 이유를 따져보니 그 서비스들이 검증한 인증/인가 실패 응답은 전부 보안 프레임워크나 웹 프레임워크 자체가 직접 내는 응답이었다. 프레임워크가 자동으로 처리하는 검증 실패는 우리가 만든 예외 처리기를 거치지 않고 프레임워크가 알아서 처리한다.

이번엔 처음으로 컨트롤러나 서비스 코드가 직접 던지는 비즈니스 예외를 검증하는 테스트였다. 이 예외를 적절한 상태 코드로 바꿔주는 건 우리가 만든 공통 예외 처리기인데, 테스트에서 컨텍스트를 좁게 구성할 때(관련된 클래스들만 명시적으로 지정하는 방식) 이 예외 처리기를 명시적으로 포함시키지 않아서 생긴 문제였다.

@ContextConfiguration(classes = {
        SomeController.class,
        SecurityConfig.class,
        GlobalExceptionHandler.class   // 이게 없으면 비즈니스 예외가 변환 안 됨
})

정리

컨텍스트를 좁혀서 테스트할 때는, 그 테스트가 검증하려는 예외나 응답이 프레임워크가 자동으로 처리하는 것인지, 아니면 애플리케이션 코드(예외 처리기 등)가 처리하는 것인지 구분해야 한다는 걸 배웠다. 전자는 컨텍스트에 명시적으로 안 넣어도 동작하지만, 후자는 반드시 그 컴포넌트를 컨텍스트에 포함시켜야 한다.

저장 후 상태 전이 순서, 그리고 테스트 간 격리

여러 서비스에서 반복해서 겪은 패턴이다. 결제 엔티티를 저장하면서 빌더로 특정 상태를 지정했는데, 진짜 저장을 거치니 초기화 콜백이 항상 초기 상태(대기 중)로 덮어써서 원하는 상태로 안 만들어졌다.

해결

private Payment payment(Long reservationId, PaymentStatus status) {
    Payment saved = paymentRepository.save(Payment.builder()...build());   // 저장 시점엔 초기 상태

    if (status == PaymentStatus.COMPLETED) {
        saved.complete();
    } else if (status == PaymentStatus.FAILED) {
        saved.fail();
    }

    return paymentRepository.save(saved);   // 전이된 상태를 다시 DB에 반영
}

저장한 뒤 도메인 메서드로 상태를 전이시키고, 그걸 다시 저장해야 DB에 진짜로 원하는 상태가 들어간다. 이 순서를 지켜야 한다는 걸 여러 번 겪고 나서야 확실히 익혔다.

테스트 간 격리

@SpringBootTest(전체 애플리케이션 컨텍스트를 띄우는 방식)는 @DataJpaTest(가벼운 JPA 계층만 테스트하는 방식)와 달리 테스트 간 자동 롤백이 없다. 같은 클래스 안의 여러 테스트가 같은 식별자 같은 리소스를 공유하면, 실행 순서에 따라 서로 영향을 주고받는다. 각 테스트가 독립된 식별자를 쓰도록 격리해야 했다.

void completePaymentFlowPersistsCorrectly() {
    Long reservationId = 101L;   // 이 테스트 전용
    ...
}

void concurrentRequestsWithSameIdempotencyKeyProcessOnlyOnce() {
    Long reservationId = 102L;   // 다른 테스트 전용
    ...
}
  • 왜 자동 롤백을 안 쓰냐?
    • @DataJpaTest의 자동 롤백은 편리하지만, 이번처럼 진짜 동시성(여러 스레드가 동시에 요청하는 것)을 검증하려면 여러 스레드가 같은 트랜잭션을 공유할 수 없어서 이 방식 자체를 못 쓴다. @SpringBootTest로 진짜 애플리케이션처럼 동작하게 하는 대신, 롤백은 포기하고 데이터 격리를 테스트 코드가 직접 책임지는 쪽을 택했다.

커버리지를 채우려다 발견한, 단순히 흘려보내기만 하는 게 아니었던 코드

실시간 알림을 위한 두 컴포넌트는, 처음엔 판단 로직 없이 받은 메시지를 그대로 클라이언트에 흘려보내기만 하는 것처럼 보여서 테스트 대상에서 제외했다. 커버리지를 확인하다가 다시 코드를 읽어보니, 둘 다 전송 실패 시 연결을 정리하는 분기가 있었다.

try {
    emitter.send(...);
} catch (IOException e) {
    seatEmitterStore.remove(showId, emitter);   // 이 분기를 놓쳤었다
}

첫 인상만으로 판단하지 말고, 실제 코드를 다시 한번 읽어봐야 한다는 걸 새삼 느꼈다. 특히 예외 처리 블록은 눈에 잘 안 띄지만, 그 자체로 하나의 분기이자 검증 대상이다.

컴포넌트 스캔 범위 밖에 있던 공통 설정 클래스

컨테이너 세팅 방식을 바꾸는 작업(16편 참고)을 마치고 다시 테스트를 돌렸는데, Redis Cluster 모드에서만 나는 특정 에러가 났다. 처음엔 테스트용 Redis가 우연히 클러스터로 뜬 줄 알았다.

Redis 연결 설정을 다시 보니, 테스트 환경(단일 노드)과 운영 환경(클러스터)을 프로파일로 정확히 나눠뒀었다. 근데 각 설정 메서드에 로그를 찍어봤더니 둘 다 안 찍혔다. 둘 다 아예 생성 시도조차 안 되고 있었다.

애초에 컴포넌트 스캔 범위 밖에 있었다

메인 애플리케이션 클래스는 자기가 있는 패키지를 기준으로 그 패키지와 하위 패키지만 기본적으로 컴포넌트 스캔한다. 근데 이 Redis 설정 클래스는 공통 모듈(별도 라이브러리 모듈) 안의, 애플리케이션 패키지와는 다른 최상위 패키지에 있었다. 하위 패키지가 아니라서, 이 설정 클래스 자체가 스캔에서 완전히 빠져 있었다.

JPA 관련 스캔 범위는 명시적으로 넓혀뒀는데, 정작 일반 설정 클래스 스캔 범위는 넓히지 않았던 것이다.

왜 지금까지는 아무 문제 없었지?

이 부분이 특히 신기했다. 이 설정이 무시되고 있었다면 애초에 Redis 연결 자체가 안 됐어야 하는데, 이전까지는 Redis 관련 기능이 전부 잘 동작했다. 이유는 프레임워크가 기본으로 제공하는 자동 설정이 대신 동작하고 있었기 때문으로 보인다. 예전 컨테이너 설정에서 연결 정보 자동 감지 기능을 쓰고 있었는데, 이게 표준 프로퍼티 키를 자동으로 채워줬다. 우리가 만든 커스텀 설정은 스캔이 안 돼서 무용지물이었지만, 그 대신 프레임워크 기본 자동 설정이 그 표준 프로퍼티를 읽어서 단일 노드 연결을 만들어줬던 것이다. 결과적으로 원하던 것(테스트는 단일 노드)과 우연히 같은 결과가 나와서 문제가 겉으로 드러나지 않았다.

즉 테스트/운영을 구분하려고 만든 설정의 분기 코드는, 이전까지 단 한 번도 실제로 실행된 적이 없었다. 프레임워크의 기본 동작이 어쩌다 보니 원하는 결과와 일치했을 뿐이다.

왜 갑자기 나타났을까?

컨테이너 설정을 자동 감지 방식에서 명시적 등록 방식으로 바꾸는 과정에서, 설정 파일에 있던 클러스터 노드 설정과 새로 등록한 단일 노드 연결 정보가 충돌한 것으로 보인다. 프레임워크의 기본 자동 설정이 이번엔 클러스터 노드 쪽을 읽어버려서, 단일 컨테이너에 클러스터 모드로 접속을 시도했고 그게 에러로 이어졌다.

해결

메인 애플리케이션 클래스의 컴포넌트 스캔 범위를 공통 모듈까지 포함하도록 명시적으로 넓혔다. 그러니 설정 클래스가 정상적으로 스캔되기 시작했고, 프로파일 분기도 그제야 실제로 동작했다.

부수 효과

설정 클래스가 스캔되기 시작하면서, Redis 연결 팩토리 빈이 이제 정말로 생성 시도를 한다. 그동안 다른 저장소만 필요하다고 생각했던 테스트들이, 애플리케이션 컨텍스트 전체가 뜨는 이상 Redis 연결 정보가 없어서 실패하기 시작했다. Redis 컨테이너 관련 설정을 같이 구현해줘야 했다.

이것도 스캔 범위 버그를 고치면서 딸려 나온, 그동안 숨어있던 또 다른 결함이었다.

다른 방법

  • 각 설정 클래스를 애플리케이션 패키지 안으로 옮기기
    • 물리적으로 패키지를 옮기면 스캔 문제는 해결되지만, 공통 모듈이 여러 서비스에서 재사용되는 구조 자체가 깨진다. 여러 서비스가 각자 복붙해서 쓰게 되면, 하나를 고칠 때 나머지도 다 고쳐야 하는 유지보수 부담이 생긴다. 스캔 범위를 넓히는 쪽이 공통 모듈 구조를 유지하면서 문제를 푸는 방법이었다.

정리

이 발견이 특히 인상 깊었던 이유는, 버그가 있는데 우연히 정상 동작한 것처럼 보이는 상황이었기 때문이다. 코드 리뷰로는 절대 못 잡는다.설정 클래스 코드 자체는 완벽하게 맞게 짜여 있었다. 이 클래스가 애초에 실행조차 안 되고 있다는 건, 실제로 컨테이너 세팅을 바꾸면서 우연히 다른 자동 설정과의 균형이 깨지지 않았다면 영원히 몰랐을 수도 있다.

여러 모듈로 나뉜 프로젝트에서 공통 설정 클래스를 만들 때는, 그 클래스가 정말 스캔 범위 안에 있는지 로그를 찍어서라도 확인해보는 습관이 필요할 것 같다.

정리

같이 놓고 보니 몇 가지 패턴이 눈에 띈다.

  • 진짜 인프라로 검증해야만 드러나는 버그가 분명히 있다. Redis 키 불일치, 트랜잭션 오염, 영속성 컨텍스트 문제 전부 Mock으로는 재현조차 불가능했다
  • 공통 모듈의 결함은 여러 서비스에 동시에 영향을 준다
  • Mock이 이상하게 동작하는 것 같으면, 먼저 생성자 시그니처부터 의심한다
  • Repository, 트랜잭션, 영속성 컨텍스트는 서로 다른 레이어의 이야기다. 이 레이어를 헷갈리면 꼭 한 번씩은 발에 걸린다
  • 저장 메서드의 반환값은 항상 다시 받아쓴다
  • 단순히 흘려보내는 것 같다는 첫인상만으로 커버리지 대상에서 빼지 않는다
  • 여러 모듈로 나뉜 프로젝트에서는, 공통 설정 클래스가 정말 컴포넌트 스캔 범위 안에 있는지 확인해야 한다. 심지어 그게 우연히 잘 동작하는 것처럼 보일 수도 있다

각 이슈마다 검토했던 대안들을 되짚어보면, 대부분의 경우 예외를 잡아서 처리하는 방식보다 예외 자체가 안 나게 만드는 방식이 더 안전했고, 프레임워크에 트랜잭션이나 스캔 범위를 맡기는 것보다 명시적으로 경계를 지정하는 것이 더 예측 가능했다. 전부 코드를 눈으로 읽었을 때는 딱히 이상해 보이지 않는 것들이었다. 진짜 동시 요청을 흉내 내거나, 진짜 인프라를 띄워서 확인하지 않았다면 대부분 그대로 운영에 나갔을 것들이다.
