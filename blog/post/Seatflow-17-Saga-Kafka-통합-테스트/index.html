[Seatflow] 17. Saga, Kafka 통합 테스트

Lab/SeatFlow · 2026-08-10

Intro

지금까지 Saga(취소 흐름)를 검증한 통합 테스트는, 오케스트레이터의 메서드를 직접 호출하는 방식이었다. 예를 들어 좌석이 반환됐다는 응답을 흉내 낼 때, 진짜 이벤트를 발행하는 대신 orchestrator.onSeatReleased(sagaId, reservationId)를 코드에서 그냥 호출했다. 이 방식으로도 Saga의 상태 전이 로직 자체(어떤 순서로 상태가 바뀌는지, 보상이 제대로 트리거되는지)는 충분히 검증됐다.

근데 이 방식이 검증 못 하는 게 하나 있다. 이 서비스가 진짜 Kafka 브로커를 통해 정확한 형식으로 메시지를 발행하고, 진짜 컨슈머가 그 메시지를 정확히 파싱해서 처리하는지다. 오케스트레이터 메서드를 직접 호출하면, Kafka로 나가고 들어오는 그 왕복 구간 자체는 건너뛰게 된다.

왜 이 검증이 필요할까?

이미 검증된 것들

지금까지 만든 테스트들을 계층별로 나눠보면 이렇다.

계층 1 - 발행: 어떤 서비스 메서드가 실행되면, Outbox 테이블에 정확한 내용이
              기록되는가 (여러 서비스의 서비스 계층 테스트에서 검증)

계층 2 - Outbox에서 Kafka로: Outbox에 쌓인 메시지를 스케줄러가 진짜 Kafka로
                             발행하는가 (Outbox 스케줄러 테스트에서 검증)

계층 3 - Kafka에서 컨슈머로: 컨슈머가 받은 메시지를 정확히 파싱해서 올바른
                             서비스 메서드를 호출하는가 (각 서비스의 컨슈머
                             단위 테스트에서 검증)

이 세 계층을 각각 이미 검증했다면, 이걸 하나로 이어붙인 결과(계층 1을 통과한 서비스가 계층 2를 거쳐 계층 3까지 도달하는 것)도 문제없을 거라는 확신은 상당히 높다.

그럼에도 이어붙여서 검증하는 이유

계층을 나눠 검증하는 방식이 놓칠 수 있는 지점이 하나 있다. 발행하는 쪽과 구독하는 쪽이 같은 메시지 형식에 합의하고 있는지다. 이걸 계약이라고 부른다. 발행 쪽 테스트와 구독 쪽 테스트가 각자 독립적으로 통과해도, 두 쪽이 서로 다른 필드 이름이나 다른 형식을 전제로 하고 있다면 실제로 이어붙였을 때 문제가 생긴다.

이 프로젝트는 이 위험을 상당 부분 구조적으로 막아뒀다. 이벤트 데이터 클래스(발행되는 메시지의 형태를 정의하는 클래스)를 공통 모듈 하나에 두고, 발행하는 서비스와 구독하는 서비스가 똑같은 클래스를 가져다 쓴다. 필드 이름이나 타입이 서로 어긋나는 상황 자체가, 애초에 컴파일이 안 되기 때문에 발생할 수 없다.

그래서 발행 쪽과 구독 쪽의 형식이 다를까 봐 이어붙여서 검증할 필요는 크지 않다. 대신 이번에 검증하고 싶었던 건 조금 다른 지점이다.

형식이 아니라 진짜 브로커를 통한 전달 자체가 우리가 짠 코드로 실제로 동작하는지다. 예를 들어 토픽 이름을 잘못 적었거나, 발행할 때 쓰는 키와 구독할 때 기대하는 키가 다르거나 하는 실수는, 형식이 아니라 배선(어디로 보내고 어디를 듣는지) 문제라 계층별 단위 테스트로는 못 잡는다. 계층 1~3이 각자 자기 파트만 보기 때문에, 이 파트들이 실제로 맞물리는지는 별도로 확인해야 한다.

어디까지 진짜로 띄울까?

Saga는 reservation-service가 seat-service, payment-service와 메시지를 주고받는 흐름이다. 이 전체를 진짜로 검증하려면 이론적으로는 세 서비스를 다 띄워야 한다. 근데 이 방식과, reservation-service 하나만 띄우고 상대 서비스의 응답을 테스트 코드가 직접 흉내 내는 방식 중에 골라야 했다.

  • 세 서비스를 다 띄우는 방식

    • 가장 현실에 가까운 검증이지만, 여러 서비스의 애플리케이션 컨텍스트와 그에 딸린 인프라(각자의 DB 등)를 동시에 다뤄야 해서 훨씬 무겁다. 그리고 seat-service와 payment-service의 발행/구독 로직은 이미 각자의 컨슈머 테스트로 검증돼 있어서, 여기서 다시 검증하면 중복이다.

  • reservation-service만 띄우고 상대 서비스를 시뮬레이션하는 방식

    • 내가 선택한 방식이다. 다른 서비스가 이런 이벤트를 보냈다는 상황을 테스트 코드가 진짜 Kafka로 직접 발행해서 재현하고, reservation-service가 그걸 정확히 받아 처리하는지만 본다. reservation-service가 발행한 메시지도, 진짜 Kafka 토픽에 정확한 내용으로 나갔는지 별도의 컨슈머로 직접 확인한다. 이렇게 하면 reservation-service의 프로듀서/컨슈머가 진짜 Kafka와 올바르게 통신하는지, 정확히 검증하고 싶었던 지점에만 집중할 수 있다고 생각했다.

검증한 시나리오

reservation-service가 관여하는 Saga 흐름을 세 갈래로 나눠서 검증했다.

1. 정상 흐름 (좌석 점유부터 예매 확정까지)

좌석이 점유됐다는 이벤트를 진짜 Kafka로 발행하면, reservation-service의 컨슈머가 그걸 받아서 예매를 생성하는지 확인한다. 이어서 결제가 완료됐다는 이벤트를 발행하면, 그 예매가 확정 상태로 바뀌는지 확인한다.

publish(EventTopic.SEAT_HELD, showId,
        new SeatHeldEvent(userId, showId, seatId, price, showDate), "1.0");

awaitCondition().untilAsserted(() -> {
    List<Reservation> all = reservationRepository.findByUserId(userId);
    assertThat(all).hasSize(1);
    assertThat(all.get(0).getStatus()).isEqualTo(ReservationStatus.PENDING);
});

publish()는 테스트가 다른 서비스인 척 진짜 KafkaTemplate으로 이벤트 봉투를 만들어서 실제 토픽에 보내는 헬퍼다. 이 메시지가 컨슈머에 도달해서 처리되기까지는 시간이 걸리니, 결과를 곧바로 확인하지 않고 조건이 참이 될 때까지 반복 확인하는 방식(폴링 대기)을 쓴다.

2 발행 검증 (취소를 시작하면 정확한 명령이 나가나?)

취소를 시작하는 메서드를 호출하고 나서, 그 결과로 나가야 할 명령(좌석을 반환하라는 명령)이 진짜 Kafka 토픽에 정확한 내용으로 실렸는지, 별도의 관찰용 컨슈머로 직접 확인한다.

cancelSagaOrchestrator.startCancellation(reservation.getId(), "user1");

rawConsumer.subscribe(List.of(EventTopic.SEAT_RELEASE_COMMAND));
awaitCondition().untilAsserted(() -> {
    ConsumerRecords<String, String> records = rawConsumer.poll(Duration.ofMillis(500));
    boolean found = records.records(EventTopic.SEAT_RELEASE_COMMAND).iterator().hasNext()
            && /* 내용에 reservationId가 포함되어 있는지 확인 */ true;
    assertThat(found).isTrue();
});

이 관찰용 컨슈머는 reservation-service가 실제로 쓰는 컨슈머 그룹과는 별개의, 테스트만을 위한 임시 그룹이다. 매번 새로운 그룹 아이디를 써서 항상 토픽의 처음부터 읽도록 했다.

그래야 이 테스트가 언제 실행되든, 그 전에 이미 쌓여있던 메시지와 상관없이 확실하게 확인할 수 있다.

3. 취소 정상 완료 (전체 왕복)

취소를 시작한 뒤, seat-service가 좌석을 반환했다라는 응답을 테스트가 흉내 내서 발행하면 Saga가 다음 단계로 넘어가는지 확인한다. 이어서 payment-service가 환불을 완료했다고 응답도 흉내 내서 발행하면, 최종적으로 예매가 취소 완료 상태가 되고 Saga도 완료 상태가 되는지 확인한다.

cancelSagaOrchestrator.startCancellation(reservation.getId(), "user1");

awaitCondition().untilAsserted(() ->
        assertThat(reservationRepository.findById(reservation.getId()).orElseThrow().getStatus())
                .isEqualTo(ReservationStatus.CANCELLING));

CancelSaga saga = cancelSagaRepository.findByReservationId(reservation.getId()).orElseThrow();

publish(EventTopic.SEAT_RELEASED, String.valueOf(reservation.getId()),
        new SeatReleasedEvent(saga.getId(), reservation.getId(), seatId), "1.0");

awaitCondition().untilAsserted(() ->
        assertThat(cancelSagaRepository.findById(saga.getId()).orElseThrow().getStatus())
                .isEqualTo(CancelSagaStatus.SEAT_RELEASED));

publish(EventTopic.PAYMENT_REFUNDED, String.valueOf(reservation.getId()),
        new PaymentRefundedEvent(saga.getId(), reservation.getId(), refundAmount), "1.0");

awaitCondition().untilAsserted(() -> {
    assertThat(reservationRepository.findById(reservation.getId()).orElseThrow().getStatus())
            .isEqualTo(ReservationStatus.CANCELLED);
    assertThat(cancelSagaRepository.findById(saga.getId()).orElseThrow().getStatus())
            .isEqualTo(CancelSagaStatus.COMPLETED);
});

4 보상 흐름

환불이 실패했다는 응답을 흉내 내면, 좌석을 다시 점유 상태로 되돌리라는 보상 명령이 나가는지 확인하고, 그 응답(재점유 완료)까지 흉내 내면 예매가 원래 상태(확정)로 복구되는지 확인한다. 정상 흐름과 반대 방향으로 되돌아가는 경로라, 정상 흐름이 잘 되는 것만 확인해서는 놓칠 수 있는 부분이다.

겪은 문제

파일 전체는 통과하는데 특정 테스트 하나만 단독 실행하면 실패했다

정상 흐름 시나리오 중 하나(좌석 점유 이벤트를 받아서 예매를 만드는 것)를 검증하는 테스트가, 파일에 있는 다른 테스트들과 같이 실행하면 항상 통과했다. 근데 이 테스트 메서드 하나만 떼어서 단독으로 실행하면, 몇 초를 기다려도 예매가 하나도 안 생겼다며 실패했다.

원인 -  Kafka 컨슈머는 DB 요청과 다르게 동작한다

지금까지 다룬 MySQL, Redis, MongoDB 요청은 테스트가 요청하면 그 자리에서 바로 응답이 오는 방식이다. 요청 메서드를 호출하면, 그 호출 자체가 끝날 때 이미 처리가 끝나 있다.

Kafka 컨슈머는 다르다. 컨슈머가 실제로 메시지를 받으려면, 그 전에 브로커에게 이 토픽을 구독하고 싶다고 요청하고, 브로커가 그럼 이 파티션을 배정해줄게라고 응답하는 협상 과정(리밸런싱)을 거쳐야 한다. 이 과정이 끝나야 비로소 그 컨슈머가 메시지를 받을 수 있는 상태가 된다.

이 협상은 애플리케이션이 다 떴다고 판단되는 시점과는 별개의, 조금 더 나중에 끝나는 비동기 과정이다. 파일 전체를 돌릴 때는 이 테스트 앞에 다른 테스트들이 먼저 실행되면서, 애플리케이션 컨텍스트가 계속 떠 있는 동안 컨슈머들이 리밸런싱을 이미 끝냈을 시간이 충분히 있었다. 그래서 이 테스트 차례가 왔을 즈음엔 이미 준비가 끝난 상태였다.

반면 이 테스트 하나만 단독으로 돌리면, 컨텍스트가 막 뜨자마자 바로 테스트가 시작된다. 컨슈머가 아직 리밸런싱을 끝내기 전에 테스트가 메시지를 발행해버린 것이다. 라디오 방송국이 막 전파를 쏘기 시작했는데, 청취자의 라디오는 아직 주파수를 맞추는 중이라 그 방송을 놓친 것과 비슷한 상황이다.

처음 시도 - 타임아웃을 늘리는 것

먼저 생각한 건 더 오래 기다리면 되지 않을까였다. 대기 시간을 10초에서 20초로 늘렸다. 결과는 가끔 되고 가끔 안 됐다 — 어떤 실행에서는 20초 안에 리밸런싱이 끝나서 통과했고, 어떤 실행에서는 20초를 넘겨서 여전히 실패했다.

이건 정확한 해결이 아니었다. 타임아웃을 늘리는 건 얼마나 기다려야 하는지 모르는 채로 운에 맡기고 더 오래 기다리는 것뿐이다. 컨슈머가 준비되지 않았다는 진짜 원인을 없애주지는 않는다.

해결 - 준비됐는지를 직접 확인하고 나서 메시지를 보내기

필요한 건 얼마나 기다릴지 추측하는 게 아니라, 정말 준비가 끝났는지를 확인하는 것이었다. 스프링 카프카는 정확히 이 목적을 위한 테스트 전용 도구를 공식으로 제공한다.

@Autowired
private KafkaListenerEndpointRegistry registry;

private void waitUntilAllListenersReady() {
    registry.getListenerContainers().forEach(container ->
            ContainerTestUtils.waitForAssignment(container, 1));
}

@BeforeEach
void setUp() {
    ...
    waitUntilAllListenersReady();   // 메시지를 발행하기 전에 항상 이걸 먼저 통과시킨다
}

KafkaListenerEndpointRegistry는 애플리케이션 안에 있는 모든 컨슈머 컨테이너의 목록을 관리하는, 스프링이 자동으로 등록해주는 컴포넌트다. getListenerContainers()로 그 컨슈머들을 하나씩 꺼내올 수 있다. ContainerTestUtils.waitForAssignment(container, 1)이 핵심인데, 이건 이 컨슈머가 정확히 1개의 파티션을 실제로 할당받을 때까지 기다린다는 뜻이다(테스트 환경은 파티션을 1개만 쓰도록 구성했으므로 1이다). 막연히 몇 초를 기다리는 게 아니라, 컨슈머 내부의 실제 할당 상태를 직접 확인하면서 기다린다.

이걸 매 테스트 메서드 시작 전에 항상 거치게 하니, 대기 시간을 20초에서 5초로 줄여도 안정적으로 통과했다. 리밸런싱을 기다리는 시간이 더 이상 메시지 처리 확인 시간 안에 포함될 필요가 없어졌기 때문이다. 준비는 이미 그 전 단계에서 끝내고 왔으니까.

왜 이게 DB에는 필요 없고 Kafka에만 필요할까?

이 차이를 다시 짚어보면, MySQL이나 Redis, MongoDB를 쓸 때는 테스트가 능동적으로 요청하는 쪽이다. 저장이나 조회 메서드를 호출하면, 그 호출 자체가 응답을 받을 때까지 기다려주는 동기 방식이라, 미리 준비하고 대기하는 무언가가 따로 필요 없다.

메시지 리스너는 반대로 수동적으로 기다리는 쪽이다. 테스트가 메시지를 보내는 시점과, 컨슈머가 그걸 받을 수 있는 상태가 되는 시점이 서로 별개의 타이밍이다. 그래서 받을 준비가 됐는지를 확인하는 절차가 Kafka를 쓰는 테스트에만 필요하다.

이 판단 기준을 일반화하면 이렇다. 진짜 Kafka 컨테이너를 띄우고, 그 안에서 테스트가 직접 메시지를 발행해서 진짜 리스너가 그걸 받아 처리하는지 확인하는 통합 테스트라면 이 확인이 필요하다. 반대로 Mock으로 리스너 메서드를 직접 호출하는 단위 테스트나, 발행만 확인하고 그걸 받는 컨슈머 쪽은 안 보는 테스트(예: Outbox 스케줄러가 카프카로 전송을 시도하는지만 보는 테스트)라면 이 확인은 필요 없다.

정리

이번 편에서 검증한 건 reservation-service의 프로듀서와 컨슈머가 진짜 Kafka와 올바르게 통신하나? 였다. 이미 이벤트 클래스를 공유하는 구조 덕분에 발행 쪽과 구독 쪽의 형식 불일치 위험은 낮았지만, 토픽이나 키를 잘못 배선하는 실수는 계층별 단위 테스트만으로는 못 잡는다는 걸 확인하기 위한 검증이었다.

  • 여러 서비스를 다 띄우는 e2e 방식과, 검증 대상 서비스만 띄우고 상대는 시뮬레이션하는 방식 사이에서, 이미 다른 서비스들이 각자 검증돼 있다는 점을 고려해 후자를 선택했다.
  • 발행 검증은 별도의 관찰용 컨슈머로, 구독 검증은 진짜 KafkaTemplate으로 메시지를 흘려보내는 방식으로 나눠서 접근했다.
  • Kafka 컨슈머는 DB 요청과 다르게 파티션 할당이라는 비동기 준비 과정이 필요하다. 이걸 놓치면 파일 전체는 통과하는데 특정 테스트만 단독으로는 실패하는, 이해하기 까다로운 현상이 나타난다.
  • 타임아웃을 늘리는 건 이 문제를 운에 맡기는 임시방편이고, 준비 상태를 직접 확인하는 공식 도구를 쓰는 게 근본적인 해결이었다.

이 인프라(TestContainers 세팅 전반)와 그 위에서 발견한 다른 버그들 이야기는 16편과 16-1편에서 이어진다.
