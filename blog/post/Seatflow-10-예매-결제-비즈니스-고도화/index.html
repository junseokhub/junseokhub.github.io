[Seatflow] 10. 예매-결제 비즈니스 고도화

Lab/SeatFlow · 2026-07-02

Intro

9편에서 좌석을 자동 생성하면서 예매-결제 흐름을 한 번 쭉 돌려봤다. 그런데 돌려보니 흐름이 곳곳에서 끊겨 있었다.

가장 황당한 건 결제를 성공시켜도 예매가 PENDING에 그대로 머물렀다. 결제 서비스는 분명 결제를 끝냈는데, 예매는 영원히 확정되지 않았다. 돈만 빠지고 예매는 안 되는 상태다.

흐름을 뜯어보니 구멍이 한둘이 아니었다.

  • 결제 완료가 예매 확정으로 이어지지 않는다 (payment.completed를 아무도 받지 않음)
  • 결제가 Outbox 없이 Kafka로 직접 발행한다 (6편에서 고친 dual-write가 결제에 그대로 남아 있었다)
  • 결제가 끝나도 좌석이 확정되지 않는다 (Redis 점유만 있고 DB 좌석은 그대로라 이중 예매 위험)
  • 결제 멱등성이 없다 (같은 예매로 두 번 결제하면 중복 청구)
  • 예매에 금액이 없다 (할인을 얹을 토대조차 없다)
  • 결제 금액을 클라이언트가 보낸다 (가격을 조작할 수 있다)

이번 편은 새 기능을 더하는 게 아니다. 이미 있는 흐름의 구멍을 메워서, 예매가 결제를 거쳐 확정까지 정합성 있게 완결되도록 만든다.

할인·쿠폰과 취소·환불은 이 토대가 갖춰진 다음에야 의미가 있어서 뒤로 미뤘다. 취소/환불은 좌석 반환과 결제 환불을 같이 되돌려야 하는, 본질이 Saga인 작업이라 별도 편에서 다룰 예정이다.

결제가 끝나도 예매가 안 끝난다

결제 서비스는 결제가 끝나면 payment.completed를 발행한다. 그런데 이 이벤트를 받는 곳이 없었다.

payment 성공 -> payment.completed 발행 -> (아무도 안 받음) -> reservation 영원히 PENDING

예매를 확정하는 마지막 연결 고리가 없는 것이다. 그래서 reservation에 컨슈머를 추가했다. payment.completed를 받아 예매를 PENDING에서 CONFIRMED로 바꾼다.

@KafkaListener(topics = EventTopic.PAYMENT_COMPLETED, groupId = "reservation-service")
public void consume(String message) {
    EventEnvelope<PaymentCompletedEvent> event = deserialize(message);
    reservationService.confirmReservation(event.payload().reservationId());
}

컨슈머는 받아서 위임만 한다. 실제 상태 전이는 도메인이 한다.

public void confirm() {
    if (this.status == CONFIRMED) {
        return;   // 이미 확정 -> 멱등하게 무시
    }
    if (this.status == CANCELLED) {
        throw new IllegalStateException("취소된 예매는 확정할 수 없다");
    }
    this.status = CONFIRMED;
}

멱등성 처리 (상태 가드 vs REQUIRES_NEW)

Kafka는 at-least-once라 같은 payment.completed가 두 번 올 수 있다. 중복 확정을 막아야 한다.

9편에서 좌석을 만들 때는 REQUIRES_NEW + unique 충돌로 막았다. 그런데 여기선 그 방법을 안 썼다. 이유는 연산의 종류가 다르기 때문이다.

구분좌석 생성예매 확정
연산INSERT (새로 생성)UPDATE (상태 전이)
중복 판단DB unique 제약엔티티의 현재 status
충돌예외 발생예외 없음
처리REQUIRES_NEW + catch도메인 상태 가드

좌석 생성은 같은 좌석을 또 INSERT하려다 unique 충돌이 나고, 그 충돌이 예외라 트랜잭션을 오염시킨다. 그래서 REQUIRES_NEW로 독립 트랜잭션에 격리했다.

예매 확정은 INSERT가 아니다. 이미 있는 예매 행을 UPDATE하는 것이다. 충돌이 날 일이 없다. 그냥 현재 상태를 보고 이미 CONFIRMED면 아무것도 안 하면 된다. 그게 confirm() 안의 상태 가드다.

핵심은 이렇게 갈린다. 생성(INSERT)의 멱등성은 DB 키 제약으로, 상태 전이(UPDATE)의 멱등성은 도메인 상태 가드로 처리한다.

상태 전이 규칙(PENDING에서만 확정 가능, 취소된 건 확정 불가)을 도메인 메서드 안에 둔 것도 의도적이다. 이건 예매라는 객체가 지켜야 하는 불변 규칙이라 객체 자신이 갖는 게 맞다. 서비스나 컨슈머가 if status로 분기하면 그 규칙이 도메인 밖으로 노출된다.

참고로 도메인에 가드가 존재해도 조회 시점과 수정 시점의 공백으로 상태가 꼬일 수 있으니까 낙관적락이나 쿼리 조건에 상태를 포함시키는 방법으로 방지할 수 도 있다.

돈은 빠졌는데 이벤트가 유실된다

결제 서비스는 결제를 저장한 뒤 Kafka로 직접 발행하고 있었다.

paymentRepository.save(payment);                  // DB 커밋
kafkaTemplate.send(PAYMENT_COMPLETED, event);     // Kafka 직접 발행

6편에서 고친 dual-write가 결제에 그대로 남아 있었다. 결제 DB는 저장됐는데 발행이 실패하면, payment.completed가 나가지 않는다. 그러면 방금 구멍 1에서 연결한 흐름이 또 끊긴다. 돈은 빠졌는데 예매는 확정되지 않는다.

결제는 돈이 걸린 흐름이라 이 정합성이 특히 중요하다. 그래서 Outbox로 바꿨다.

대안 비교

방법 정합성 비고

방법 정합성비고
dual-write 유지깨짐발행 실패 시 이벤트 유실
@TransactionalEventListener부분적커밋 후 발행, 그래도 발행 자체 실패는 못 막음

CDC도 정합성은 보장하지만 커넥터라는 인프라가 더 붙는다. 이미 auth(JPA)와 show(Mongo)에서 Outbox를 쓰고 있었고, 9편에서 포트-어댑터로 추상화까지 해둔 상태였다. 결제도 MySQL이라 auth의 JpaOutboxStore 패턴을 그대로 가져오면 된다. 새 인프라 없이 기존 자산을 재사용하는 게 좋다고 생각했다.

@Transactional
public Payment processPayment(...) {
    paymentRepository.save(payment);              // 1. 결제 저장
    appendOutbox(PAYMENT_COMPLETED, ...);         // 2. 이벤트 적재 (같은 트랜잭션)
    return payment;
}

저장과 발행이 한 트랜잭션이라 둘이 어긋날 수 없다. 실제 Kafka 발행은 공통 OutboxScheduler가 폴링으로 한다. auth와 똑같은 구조고, 차이는 없다.

결제가 끝나도 좌석이 안 잡힌다

여기까지 하면 결제가 예매를 확정시킨다. 그런데 정작 좌석은 어떻게 되고 있었을까?

7편에서 좌석 점유는 Redis에 hold 키로만 했다. DB의 좌석 상태(status)는 건드리지 않았다. 점유는 결제 전까지의 임시 선점이라, TTL로 자동 해제되게 한 것이다. 문제는 결제가 끝난 뒤다. 결제를 완료해도 좌석의 DB 상태는 여전히 AVAILABLE이고, Redis hold는 TTL이 지나면 풀린다. 그러면 이미 결제까지 끝난 좌석을 다른 사람이 다시 잡을 수 있다. 

임시 점유(Redis)를 영구 확정(DB)으로 넘기는 단계가 빠져 있던 것이다. 그래서 예매가 확정되면 좌석도 확정(RESERVED)하도록 이었다.

결제 COMPLETED
  -> reservation CONFIRMED
  -> reservation.confirmed 발행
  -> seat 수신 -> 좌석 RESERVED (DB) + Redis hold 정리

왜 여기는 Saga가 아니라 이벤트일까?

좌석을 확정하려면 seat 서비스가 어느 좌석인지 알아야 한다. 그런데 payment.completed에는 seatId가 없다. 결제는 예매만 알지 좌석을 모른다. 반면 예매는 자기 좌석을 안다. 그래서 예매가 확정되는 시점에 reservation이 reservation.confirmed(seatId 포함)를 발행하고, seat이 그걸 받아 좌석을 확정한다.

이 흐름은 단순 이벤트로 이었다. 취소나 환불처럼 여러 서비스를 되돌려야 하는 작업은 Saga(명령, 응답, 보상)가 필요하지만, 좌석 확정은 되돌릴 게 없다. 결제가 성공해서 예매가 확정됐으면 좌석은 반드시 확정되면 되고, 중간에 실패하면 재시도하면 그만이다. 보상할 이전 단계가 없다. 이럴 땐 Saga가 과하다. 이벤트를 받아 확정하고, 중복이 오면 멱등하게 무시하면 된다.

reservation을 이벤트 발행자로 만들면서 여기에도 Outbox를 뒀다. 결제에 Outbox를 둔 것과 같은 이유다. 예매 확정과 reservation.confirmed 발행이 어긋나면 좌석이 영영 확정되지 않으므로, 저장과 발행을 한 트랜잭션으로 묶는다.

좌석 확정도 멱등해야 한다. 같은 reservation.confirmed가 두 번 오거나, 이미 확정된 좌석에 또 도착할 수 있다. 좌석의 상태 전이를 도메인 안에서 가드한다. 예매 확정과 같은 방식이다. 이미 RESERVED면 아무것도 하지 않는다.

public void reserve() {
    if (this.status == SeatStatus.RESERVED) {
        return;   // 이미 확정 -> 멱등하게 무시
    }
    this.status = SeatStatus.RESERVED;
}

확정과 함께 남은 Redis hold 키도 정리한다. 이제 좌석의 진실은 DB이고, Redis 점유는 결제 전까지의 임시 상태로만 남는다. 임시 점유(Redis, TTL)와 영구 확정(DB)의 역할이 분명해졌다.

중복 결제를 어떻게 막을까?

같은 예매로 결제가 두 번 들어오면 Payment가 두 개 생긴다. 중복 청구인데, 이걸 막아야 한다.

먼저 따져볼 게 있다. 중복에는 두 종류가 있다.

  • 인프라 레벨 중복 - 같은 요청이 물리적으로 여러 번 도착 (광클, 네트워크 재시도)
  • 비즈니스 레벨 중복 - 다른 요청이지만 이미 성공한 예매를 또 결제

이 둘은 막는 지점이 다르다. 그래서 2단계 레이어로 막았다.

Layer1) Redis Idempotency Key  -> 같은 요청(같은 키)의 광클/재시도 차단
Layer2) DB 부분 unique          -> 이미 성공한 예매의 중복 결제 최종 차단

2Layer (DB 부분 unique)

가장 단순한 생각은 reservation_id에 unique를 거는 것이다. 그런데 이러면 결제 실패 후 재시도가 막힌다. 카드 한도 초과로 한 번 실패하면, 다른 수단으로 다시 결제하려 해도 unique가 막아버린다. 결제 실패는 흔한 일이라 이건 말이 안 된다.

그래서 멱등성을 결제 시도가 아니라 결제 성공에 걸어야 한다. 실패(FAILED)는 여러 번 허용하고, 성공(COMPLETED)만 예매당 하나로 제한한다.

MySQL은 부분 unique를 직접 지원하지 않아서, 생성 컬럼으로 풀었다.

-- COMPLETED일 때만 reservation_id, 그 외(PENDING/FAILED)는 NULL
ALTER TABLE payments
    ADD COLUMN completed_reservation_id BIGINT
        GENERATED ALWAYS AS (
            CASE WHEN status = 'COMPLETED' THEN reservation_id ELSE NULL END
        ) STORED;

ALTER TABLE payments
    ADD CONSTRAINT uk_payments_completed_reservation
        UNIQUE (completed_reservation_id);

NULL은 unique 제약에서 중복이 허용된다. 그래서 FAILED 행은 여러 개 있어도 되고(재시도 가능), COMPLETED는 예매당 하나만 가능하다.

DB 락 vs unique 제약

비즈니스 중복을 막는 방법으로 DB 락(SELECT ... FOR UPDATE로 확인 후 INSERT)도 있다. 그런데 락은 확인과 삽입 사이를 잠그는 명시적 락 관리가 필요하고, 분산 환경에선 결국 분산 락 얘기로 번진다.

unique 제약은 그냥 INSERT를 시도하고 충돌하면 막힌다. DB가 원자적으로 처리하니 락을 직접 관리할 필요가 없다. 9편 좌석 생성에서 쓴 방식과 같다. 그래서 락 대신 부분 unique를 택했다.

생성 컬럼은 DB가 계산하는 값이라 JPA 엔티티에 매핑하면 안 된다. 매핑하면 JPA가 INSERT 때 값을 쓰려다 에러가 난다. DB에만 두고 JPA는 모르게 한다.

1Layer (Redis Idempotency Key)

2Layer(DB)만으로도 중복 결제는 막힌다. 광클이 들어와도 두 번째가 unique 충돌로 거절되기 때문이다.

그러면 1층(Redis)은 왜 두는걸까?

작은 서비스라면 안 둬도 된다. 광클이 들어와도 DB가 충분히 감당하면 DB 제약 하나로 끝이다. Redis는 트래픽이 커져서 DB 락 경합이나 불필요한 처리가 부담이 될 때, DB 앞에서 싸게 걸러주는 역할이다.

문제는 티켓팅이라는 도메인이다. 티켓팅은 오픈 순간 수만 명이 동시에 광클하는 게 기본이다. 인프라 레벨 중복이 예외가 아니라 일상이다. 그래서 여기선 1층이 정당화된다. 중복 요청이 DB까지 도달하기 전에 Redis에서 걸러서, DB 부하 자체를 줄인다.

Redis 키 선점은 Lua로 원자 실행한다. 확인과 선점 사이에 틈이 생기지 않게 하기 위해서다(7편 좌석 점유와 같은 이유).

local v = redis.call('GET', KEYS[1])
if v == false then
    redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[2])
    return 1            -- 처음 -> 진행
elseif v == ARGV[3] then
    return -1           -- 이미 완료
else
    return 0            -- 처리 중
end

Facade vs AOP vs Interceptor

Redis 멱등 처리를 결제 코드에 끼우는 방법은 여러가지였다.

그 중 난 Facade를 선택했는데, 이유는 DB에 결제 내역이 확실히 저장된 후에만 Redis의 멱등성 키 상태를 완료로 바꿔야한다. 만약 DB저장 중 에러가 나 롤백댔는데 Redis키만 완료로 바뀌면, 유저는 돈도 안나갔고 예매도 안됐는데 재시도를 못해버린다.

Facade가 이 흐름을 코드로 명시적으로 제어할 수 있다고 생각했다.

방법위치트레이드오프
AOP메서드 어노테이션키 추출(SpEL)이 까다롭고, 트랜잭션과 실행 순서 조정이 필요
Interceptor웹 진입HTTP 헤더 기반이라 자연스러우나, 트랜잭션 커밋과 완료 표시 타이밍을 맞추기 어렵다
Facade서비스 앞흐름이 명시적이고 트랜잭션 경계가 분명. 컨슈머에서도 재사용 가능

Idempotency-Key가 HTTP 헤더라 Interceptor가 교과서적이긴 하다. 그런데 결제는 트랜잭션 커밋 시점과 완료 표시(markDone) 타이밍을 정확히 맞춰야 한다. Interceptor의 afterCompletion은 이미 응답이 나간 뒤라 이걸 제어하기 까다롭다.

그래서 위에 말했듯 결론적으로 Facade로 결제 서비스 앞에 두었다. Redis 작업(트랜잭션 밖)이 결제 본체(트랜잭션 안)를 감싸는 구조다.

public Payment pay(String idempotencyKey, ProcessPaymentCommand command) {
    long acquired = idempotencyProvider.tryAcquire(idempotencyKey);
    if (acquired != 1) {
        throw new BusinessException(DUPLICATE_REQUEST);   // 처리 중이거나 완료된 요청
    }
    try {
        Payment payment = paymentService.executePayment(command);  // 결제 트랜잭션
        idempotencyProvider.markDone(idempotencyKey);
        return payment;
    } catch (RuntimeException e) {
        idempotencyProvider.release(idempotencyKey);      // 실패 시 키 해제 → 재시도 허용
        throw e;
    }
}

Facade를 별도 빈으로 둔 이유가 있다. Redis 처리와 결제 트랜잭션이 한 메서드에 섞이면, 같은 클래스 내부 호출이라 트랜잭션 프록시가 안 먹는다. 빈을 분리해서 프록시를 거치게 했다.

실패 시 키를 해제하는 게 중요하다. 결제가 실패하면 Redis 키를 풀어서 같은 키로 재시도할 수 있게 한다. 2층(DB)에서 FAILED를 막지 않는 것과 같은 맥락이다. 결제 실패는 막을 대상이 아니라 다시 시도할 대상이다.

두 Layer는 막는 게 다르다

같은 키로 광클        → Layer1(Redis)이 차단      → DUPLICATE_REQUEST
다른 키, 같은 완료 예매 → Layer2(DB unique)이 차단  → PAYMENT_ALREADY_COMPLETED
실패 후 다른 수단 재시도 → 둘 다 통과 (정상)      → 결제 성공

Layer1 만으로는 다른 키로 같은 예매를 또 결제하는 걸 못 막는다(키가 다르니까).

Layer2 만으로는 광클이 전부 DB까지 와서 부하가 된다. 두 레이어가 공존해야 인프라 중복은 싸게 걷고, 비즈니스 중복은 확실히 막는다.

클라이언트가 보낸 금액을 믿지 말자

결제 요청을 보면 금액(amount)을 클라이언트가 보내고 있었다.

public record PaymentRequest(Long reservationId, BigDecimal amount, PaymentMethod paymentMethod) {}

이러면 15만 원짜리 좌석을 1,000원으로 결제할 수 있다. 가격 조작이다. 결제 금액은 서버가 정해야 한다.

그러려면 먼저 예매가 금액을 알아야 하는데, reservation에는 금액 필드 자체가 없었다. 그래서 가격을 서버 쪽에서 흐르게 만들었다.

가격을 서버에서 흘리기

좌석마다 가격이 있다(9편에서 좌석에 price를 넣었다). 좌석을 점유할 때 그 가격을 seat.held 이벤트에 실어 보낸다.

BigDecimal price = BigDecimal.valueOf(seatById.get(seatId).getPrice());
kafkaTemplate.send(SEAT_HELD, userId,
        EventEnvelope.of(SEAT_HELD, "seat-service",
                new SeatHeldEvent(userId, showId, seatId, price)));

예매는 이 이벤트를 받아 amount로 저장한다.

seat 점유 → seat.held(price 포함) → reservation이 amount로 저장

이제 예매는 자기 금액을 안다. 공연마다 등급·가격이 다 다르지만, 각 좌석이 자기 가격을 들고 흐르니 코드는 그대로다. 공연 데이터만 다를 뿐이다.

결제 직전, 금액을 검증한다

이제 결제는 클라이언트가 보낸 금액을 신뢰하지 않는다. 결제 직전에 reservation을 조회해서, 요청 금액이 예매의 실제 금액과 맞는지 대조한다.

동기 호출 vs 비동기

금액을 가져오는 방법은 두 가지였다.

방법트레이드오프
비동기 (이벤트로 미리 받아 저장)결합은 낮으나, 미리 받은 값이 낡을 수 있다(할인 만료·쿠폰 취소 등)
동기 (결제 직전 조회)그 순간 정확한 값. 단 reservation에 의존(장애 전파 가능)

결제는 그 순간의 금액이 정확해야 한다. 미리 받아둔 값은 그 사이에 바뀌었을 수 있다. PG 연동도 결제 직전에 서버에서 금액을 검증하는 게 표준이다. 그래서 동기 호출을 택했다. 통신은 OpenFeign으로 했다(선언만으로 호출, Spring 표준).

@FeignClient(name = "reservation-service", url = "${seatflow.reservation.url}")
public interface ReservationClient {
    @GetMapping("/api/reservations/{id}")
    ApiResponse<ReservationView> getReservation(@PathVariable Long id);
}

검증은 두 가지를 본다. 예매가 결제 가능한 상태(PENDING)인지, 요청 금액이 예매 금액과 일치하는지.

ReservationView reservation = fetchReservation(command.reservationId());
if (!"PENDING".equals(reservation.status())) {
    throw new BusinessException(RESERVATION_NOT_PAYABLE);
}
if (reservation.amount().compareTo(command.amount()) != 0) {
    throw new BusinessException(AMOUNT_MISMATCH);
}
BigDecimal payAmount = reservation.amount();   // 실제 결제는 서버 값으로

클라이언트가 보낸 금액은 대조용일 뿐이다. 실제 결제는 reservation의 금액으로 한다. 금액의 진실 공급원은 reservation이다.

reservation 조회가 실패하면(네트워크·장애) 결제를 진행하지 않는다. 금액을 확인할 수 없는 상태로 결제하면 안 되기 때문이다. 동기 호출이라 reservation이 죽으면 결제가 막히는 결합이 생기는데, 이건 서킷 브레이커·타임아웃으로 보강할 영역이다. 지금은 조회 실패 시 결제를 막는 선에서 안전하게 뒀다.

공통 응답을 역직렬화 가능하게

배포하고 결제를 했더니 reservation을 조회하는 데서 깨졌다. 공통 ApiResponse를 OpenFeign이 역직렬화하지 못했다.

Cannot construct instance of ApiResponse (no Creators, like default constructor, exist)

ApiResponse는 정적 팩토리(ok/fail)만 있고 생성자가 private이었다. 응답을 만들 때(직렬화)는 문제없지만, 다른 서비스가 그 응답을 받아 객체로 되돌릴 때(역직렬화) Jackson이 인스턴스를 만들 방법이 없었다.

여기서 선택지가 있었다.

방법트레이드오프
payment 전용 응답 래퍼payment만 별도 타입. 다른 서비스가 또 호출하면 같은 문제 반복
공통 ApiResponse 수정한 번 고치면 모든 서비스가 혜택. 공통 모듈이라 영향 범위 확인 필요

payment에만 전용 래퍼를 두면 당장은 되지만, 나중에 다른 서비스가 OpenFeign으로 호출할 때 같은 문제를 또 겪는다. 그래서 공통 ApiResponse에 역직렬화 생성자를 추가했다.

@JsonCreator
public ApiResponse(
        @JsonProperty("success") boolean success,
        @JsonProperty("data") T data,
        @JsonProperty("message") String message) {
    this.success = success;
    this.data = data;
    this.message = message;
}

ok/fail 정적 팩토리는 그대로 둬서 응답 생성 코드는 안 바뀐다. 역직렬화만 새로 가능해졌다. 직렬화 동작은 동일하니 다른 서비스에 영향이 없고, 오히려 앞으로 서비스 간 동기 호출을 할 때 다 같은 규약을 쓴다.

전체 흐름

구멍을 다 메우고 나면 예매·결제가 이렇게 흐른다.

[좌석 점유]
seat: 좌석 가격을 seat.held에 실어 발행


[예매 생성]
reservation: seat.held 수신 -> PENDING + amount 저장


[결제 요청]  (Idempotency-Key 헤더 + reservationId)
payment Facade: Redis 키 선점 (Layer1)
          처음이면 진행, 광클이면 DUPLICATE_REQUEST

payment 본체: reservation 동기 조회 (OpenFeign)
          status=PENDING? amount 일치? (아니면 거절)
          이미 COMPLETED? (부분 unique, Layer2)

        결제 처리 -> COMPLETED
          payment.completed를 Outbox에 적재 (같은 트랜잭션)

OutboxScheduler: 폴링으로 payment.completed 발행


[예매 확정]
reservation: payment.completed 수신 -> confirm() -> CONFIRMED
          reservation.confirmed를 Outbox에 적재


[좌석 확정]
seat: reservation.confirmed 수신 -> 좌석 RESERVED (DB) + Redis hold 정리

클라이언트가 금액을 조작할 수 없고, 중복 결제가 막히고, 결제가 예매 확정으로 정확히 이어지고, dual-write 없이 정합성이 보장된다.

테스트

전체 흐름을 ingress를 통해 돌려본다.

공연을 만들면 좌석이 자동 생성된다(9편). 좌석을 점유하면 예매가 PENDING으로 생기는데, 이때 금액이 들어왔는지 본다.

curl -s http://<ingress>/api/reservations/user/u1 | jq '.data[-1] | {id, amount, status}'
# { "id": 14, "amount": 150000.00, "status": "PENDING" }

좌석 가격이 예매까지 흘러들어왔다. 이제 결제한다.

curl -X POST http://<ingress>/api/payments \
  -H 'X-User-Id: u1' -H 'Idempotency-Key: key-001' \
  -H 'Content-Type: application/json' \
  -d '{"reservationId":14,"amount":150000,"paymentMethod":"CREDIT_CARD"}'

# status: COMPLETED

결제 직후 예매를 다시 보면 확정돼 있다.

curl -s http://<ingress>/api/reservations/14 | jq '.data | {id, status, amount}'
# { "id": 14, "status": "CONFIRMED", "amount": 150000.00 }

예매가 확정되면 좌석도 확정된다. 결제한 좌석의 상태를 보면 RESERVED로 바뀌어 있다.

curl -s http://<ingress>/api/seats/<showId> | jq '.data[] | select(.id==<seatId>) | {id, status}'
# { "id": 61, "status": "RESERVED" }

결제가 예매 확정까지 이어졌다. 이제 멱등성과 검증을 확인한다.이제 결제한 좌석은 DB에서 확정 점유된다. Redis hold가 TTL로 풀려도 다른 사람이 잡을 수 없다. 이중 예매가 막힌 것이다. 이제 멱등성과 검증을 확인한다.

# Layer1 - 같은 Idempotency-Key 재요청
# -> "이미 처리 중이거나 처리된 결제 요청입니다." (DUPLICATE_REQUEST)

# 확정된 예매 재결제 (다른 키)
# -> "결제할 수 없는 예매 상태입니다." (RESERVATION_NOT_PAYABLE)

# 금액 조작 (1000원으로)
# -> "결제 금액이 예매 금액과 일치하지 않습니다." (AMOUNT_MISMATCH)

확정된 예매를 다시 결제하면 Layer2 unique까지 가기 전에 status 검증에서 먼저 막힌다. 이미 CONFIRMED라 결제 가능한 상태가 아니기 때문이다. 방어가 status 검증, 사전 COMPLETED 확인, DB 부분 unique 세 겹으로 걸려서, 단일 요청은 보통 앞 단계에서 막힌다. DB unique는 동시 요청이 status 검증을 동시에 통과했을 때의 최종 방어선으로 남는다.

정리

  • 결제 완료가 예매 확정으로 이어지도록 payment.completed 컨슈머를 reservation에 연결했다. 상태 전이(UPDATE) 멱등성은 도메인 상태 가드로 처리했다. 생성(INSERT) 멱등성을 DB 제약으로 처리한 9편과 다른 결이다.
  • 결제의 dual-write를 Outbox로 제거했다. auth·show와 같은 패턴이고 결제도 MySQL이라 그대로 재사용했다.
  • 결제가 끝나면 좌석도 확정(RESERVED)되도록 이었다. 임시 점유(Redis)를 영구 확정(DB)으로 넘기는 단계다.
  • reservation.confirmed 이벤트로 잇고, 되돌릴 게 없는 흐름이라 Saga가 아닌 단순 이벤트로 처리했다. 결제 중복을 2가지 레이어로 막았다.
  • 결제 중복을 2가지 레이어로 막았다. Layer1 Redis 키로 광클·재시도를, Layer2 DB 부분 unique로 이미 성공한 예매의 중복 결제를 차단한다. 작은 서비스면 Layer2(DB)만으로 충분하지만, 티켓팅은 순간 폭주가 기본이라 Layer1이 정당화된다.
  • 결제 금액을 서버가 검증한다. 좌석 가격을 seat.held로 예매까지 흘리고, 결제 직전 reservation을 동기 조회해 금액을 대조한다. 클라이언트가 보낸 금액은 신뢰하지 않는다.
