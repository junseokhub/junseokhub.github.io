[Coupon&Order] 09. Redis Lua 정합성 문제 해결 - 보상 트랜잭션 vs Outbox Pattern

Lab/Coupon&Order · 2026-05-02

Intro

8편에서 Redis Lua Consumer 방식을 테스트했을 때 정합성이 깨지는 것을 확인했다.

orders: 10,000건 
DB stock: 10,000   (차감 안 됨)
Redis stock: 0

Redis에서 재고를 차감했는데 DB stock은 그대로였다. Redis와 DB는 서로 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없기 때문이다. 이번 편에서 이 문제를 해결한다.

왜 정합성이 깨지는거지?

Redis Lua Consumer의 처리 흐름은 다음과 같다.

1. Redis Lua로 stock 차감
2. DB에 주문 저장

1번이 성공해도 2번이 실패하면 Redis stock은 차감됐는데 주문은 없는 상태가 된다. Redis와 DB는 서로 다른 시스템이라 네트워크 장애, 타임아웃, 예외 등 다양한 이유로 불일치가 발생한다.

이를 해결하는 방법으로 보상 트랜잭션과 Outbox Pattern 두 가지를 시도했다.

보상 트랜잭션

개념

Redis 차감 후 DB 저장이 실패하면 Redis 재고를 복구(INCR)하는 방식이다.

Redis 차감 성공
    → DB 저장 성공 → 완료
    → DB 저장 실패 → Redis INCR으로 복구 (보상)

구현

@Override
@Transactional
public Mono<Order> createOrder(Long userId, Long productId, Long couponIssueId) {
    String stockKey = "{product:" + productId + "}:stock";

    return reactiveRedisTemplate.execute(
                    RedisScript.of(DECREMENT_STOCK_SCRIPT, Long.class),
                    List.of(stockKey)
            )
            .next()
            .flatMap(result -> {
                if (result == -1L) {
                    return Mono.error(new BusinessException(ErrorCode.PRODUCT_OUT_OF_STOCK));
                }
                // Redis 차감 성공 이후 실패 시 복구
                return productRepository.findById(productId)
                        .switchIfEmpty(Mono.error(new BusinessException(ErrorCode.PRODUCT_NOT_FOUND)))
                        .flatMap(product -> defaultOrderService.saveOrder(userId, product, couponIssueId))
                        .onErrorResume(e -> compensateRedisStock(stockKey).then(Mono.error(e)));
            });
}

private Mono<Void> compensateRedisStock(String stockKey) {
    return reactiveRedisTemplate.opsForValue()
            .increment(stockKey)
            .retryWhen(Retry.backoff(3, Duration.ofMillis(50)))
            .doOnSuccess(v -> log.info("Redis 재고 복구 완료"))
            .doOnError(e -> log.error("Redis 재고 복구 최종 실패! 수동 처리 필요"))
            .then();
}

한계

보상 트랜잭션은 "최선을 다하는" 방식이지 "보장하는" 방식이 아니다.

복구 자체가 실패할 수 있다. Redis 차감은 성공했는데 DB 저장도 실패하고, 복구 INCR도 실패하면 재고가 영구적으로 사라진다.

타이밍 이슈가 있다. 복구 성공과 다른 사용자의 재고 차감 사이에 타이밍 문제가 생길 수 있다.

두 시스템의 원자성은 보장할 수 없다. Redis와 DB는 서로 다른 시스템이라 하나의 트랜잭션으로 묶는 것이 불가능하다. 보상 트랜잭션은 이 근본적인 문제를 해결하지 못한다.

결국 보상 트랜잭션은 이 구조에서 완벽한 해결책이 되지 못한다.

Outbox Pattern

개념

Outbox Pattern은 DB를 Source of Truth로 사용하는 메시지 전달 보장 패턴이다. 이벤트 유실 없이 다른 시스템과 동기화할 수 있다.

주문 요청
    -> DB: 주문 저장 + Outbox 이벤트 저장 (같은 트랜잭션)
    -> Scheduler: Outbox PENDING 읽어서 DB stock 차감
    -> 성공 -> Outbox PROCESSED
    -> 실패 -> 재시도 -> 최종 실패 -> FAILED

핵심은 주문 저장과 Outbox 이벤트 저장이 같은 DB 트랜잭션으로 묶인다는 점이다. DB 트랜잭션은 원자적이기 때문에 둘 다 성공하거나 둘 다 실패한다. 주문이 저장됐다면 Outbox 이벤트도 반드시 저장된 것이고, 그 반대도 마찬가지다. DB가 보장한다.

Outbox 테이블

CREATE TABLE outbox (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    aggregate_id BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    retry_count INT NOT NULL DEFAULT 0,
    failed_reason VARCHAR(500),
    created_at DATETIME(6) DEFAULT CURRENT_TIMESTAMP(6),
    updated_at DATETIME(6) DEFAULT CURRENT_TIMESTAMP(6)
);

status 컬럼으로 처리 상태를 추적한다. PENDING → PROCESSING → PROCESSED / FAILED 흐름으로 관리한다. PROCESSING 상태를 별도로 두는 이유는 Scheduler가 같은 이벤트를 중복 처리하는 것을 방지하기 위해서다.

RedisLuaOrderService 수정

@Override
@Transactional
public Mono<Order> createOrder(Long userId, Long productId, Long couponIssueId) {
    String stockKey = "{product:" + productId + "}:stock";

    return reactiveRedisTemplate.execute(
                    RedisScript.of(DECREMENT_STOCK_SCRIPT, Long.class),
                    List.of(stockKey)
            )
            .next()
            .flatMap(result -> {
                if (result == -1L) {
                    return Mono.error(new BusinessException(ErrorCode.PRODUCT_OUT_OF_STOCK));
                }
                return saveOrderWithOutbox(userId, productId, couponIssueId)
                        .onErrorResume(e -> compensateRedisStock(stockKey).then(Mono.error(e)));
            });
}

private Mono<Order> saveOrderWithOutbox(Long userId, Long productId, Long couponIssueId) {
    return productRepository.findById(productId)
            .switchIfEmpty(Mono.error(new BusinessException(ErrorCode.PRODUCT_NOT_FOUND)))
            .flatMap(product -> defaultOrderService.saveOrder(userId, product, couponIssueId))
            .flatMap(order -> {
                try {
                    String payload = objectMapper.writeValueAsString(
                            new OutboxPayload(productId, order.getId())
                    );
                    return outboxRepository.save(
                            Outbox.builder()
                                    .aggregateId(productId)
                                    .eventType("STOCK_DECREMENT")
                                    .payload(payload)
                                    .build()
                    ).thenReturn(order);
                } catch (Exception e) {
                    return Mono.error(e);
                }
            });
}

주문 저장과 Outbox 저장이 @Transactional 안에서 같이 실행된다.

OutboxScheduler

@Scheduled(fixedDelay = 1000)
public void processOutbox() {
    if (!running.compareAndSet(false, true)) {
        return;  // 이전 실행이 끝나지 않으면 스킵
    }
    outboxRepository.findByStatusOrderByCreatedAtAsc("PENDING")
            .flatMap(outbox -> {
                outbox.markProcessing();  // 중복 처리 방지
                return outboxRepository.save(outbox);
            })
            .flatMap(outbox -> {
                try {
                    OutboxPayload payload = objectMapper.readValue(
                            outbox.getPayload(), OutboxPayload.class);

                    return databaseClient.sql(
                            "UPDATE products SET stock = stock - 1 WHERE id = :id AND stock > 0")
                            .bind("id", payload.productId())
                            .fetch()
                            .rowsUpdated()
                            .flatMap(rows -> {
                                outbox.markProcessed();
                                return outboxRepository.save(outbox);
                            })
                            .onErrorResume(e -> {
                                outbox.markFailed(e.getMessage());
                                return outboxRepository.save(outbox);
                            });
                } catch (Exception e) {
                    outbox.markFailed(e.getMessage());
                    return outboxRepository.save(outbox);
                }
            })
            .doFinally(signal -> running.set(false))
            .subscribe();
}

AtomicBoolean으로 Scheduler 중복 실행을 방지한다. AND stock > 0 조건으로 음수 차감을 방지한다.

Redis-DB 정합성이 완벽하게 보장됐다.

Outbox Pattern의 트레이드오프

Outbox Pattern은 정합성을 완벽하게 보장하지만 처리 속도가 Scheduler에 의존한다. Scheduler가 1초마다 돌면서 DB stock을 차감하기 때문에 Consumer 처리가 완료된 후에도 DB 동기화까지 시간이 걸린다.

더 나은 방법들

현재 구현은 기본적인 Outbox Pattern이다. 실제 서비스에서는 다음과 같은 방법으로 개선하거나 대체할 수 있다.

CDC (Change Data Capture)
Debezium 같은 도구를 사용하면 DB의 변경 로그(binlog)를 직접 읽어서 이벤트를 발행할 수 있다. Scheduler 없이 DB 변경이 발생하는 즉시 처리되기 때문에 지연이 거의 없다. 별도 인프라가 필요하지만 대규모 서비스에서 가장 많이 채택하는 방식이다.

Scheduler 개선
현재 fixedDelay = 1000ms로 단일 스레드로 처리하고 있다. 딜레이를 줄이거나 여러 워커로 병렬 처리하면 처리량을 높일 수 있다. FAILED 이벤트를 자동으로 재처리하는 로직과 한계 초과 시 알림을 추가하면 운영 안정성도 높아진다.

이중 쓰기 (Dual Write)
Redis와 DB에 동시에 쓰는 방식이다. 구현이 단순하지만 두 쓰기 사이에 실패가 발생하면 불일치가 생기기 때문에 원자성 보장이 불가능해 권장하지 않는다.
