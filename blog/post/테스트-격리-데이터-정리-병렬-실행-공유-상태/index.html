테스트 격리 (데이터 정리, 병렬 실행, 공유 상태)

Test · 2026-09-29

Intro

테스트 하나를 단독으로 돌리면 통과하는데, 전체 테스트를 돌리면 실패하는 경우가 있었다. 순서를 바꾸면 또 통과하기도 했다. 코드에는 아무 문제가 없었고, 문제는 테스트끼리 서로의 흔적을 보고 있었다는 거다. 앞 테스트가 남긴 데이터가 뒤 테스트의 조회 결과를 바꿔놓고 있었다.

통합 테스트는 DB, Redis, Kafka, 스프링 컨텍스트처럼 여러 테스트가 같이 쓰는 자원 위에서 돈다. 테스트가 늘어날수록 이 공유 자원을 어떻게 격리하느냐가 테스트 신뢰도를 좌우한다. 격리 전략들과 각각 어디서 깨지는지, 병렬 실행까지 고려하면 어떻게 조합해야 하는지 정리해보려고 한다.

격리가 깨지면 어떻게 될까?

격리가 깨졌을 때 나타나는 증상은 꽤 일정하다.

  • 단독으로 돌리면 통과하고, 전체로 돌리면 실패한다.
  • 실행 순서에 따라 결과가 달라진다.
  • CI에서만 가끔 실패하고, 다시 돌리면 통과한다.

원인은 거의 항상 공유 상태다. 앞 테스트가 저장한 데이터, Redis에 남은 키, Kafka 토픽에 남은 메시지, 테스트 사이에 재사용되는 스프링 컨텍스트 안의 상태, static 변수 같은 것들이다. 테스트 격리는 결국 이 공유 상태를 테스트마다 깨끗하게 만들거나, 애초에 서로 겹치지 않게 만드는 문제다.

DB 격리 전략

트랜잭션 롤백

가장 먼저 떠올리는 방법이다. 테스트에 @Transactional을 붙이면, 스프링 테스트 프레임워크가 테스트가 끝날 때 트랜잭션을 롤백해준다.

@SpringBootTest
@Transactional   // 테스트가 끝나면 자동 롤백
class ItemServiceTest {

    @Autowired ItemService itemService;
    @Autowired ItemRepository itemRepository;

    @Test
    void 상품을_등록한다() {
        itemService.register(new RegisterCommand("상품", 1000));
        assertThat(itemRepository.count()).isEqualTo(1);
    }
}

정리 코드가 필요 없고, 커밋 자체를 안 하니까 빠르다. @DataJpaTest는 기본으로 @Transactional이 걸려 있어서, 리포지토리 단위의 슬라이스 테스트에서는 이 방식이 가장 자연스럽다.

문제는 롤백이 테스트 스레드의 트랜잭션 하나에만 적용된다는 거다. 그래서 이런 경우에는 롤백이 안 되거나, 테스트가 운영과 다르게 동작한다.

  • 실제 서버로 HTTP 요청을 보내는 테스트
    • webEnvironment = RANDOM_PORT로 서버를 띄우고 TestRestTemplate이나 WebTestClient로 요청하면, 요청은 서버의 다른 스레드에서 처리된다.
    • 그 스레드의 트랜잭션은 테스트 트랜잭션과 무관하게 커밋되고, 롤백되지 않는다. (MockMvc는 테스트 스레드에서 그대로 실행되기 때문에 롤백이 적용된다)
  • 다른 스레드나 비동기 처리
    • @Async, Kafka 리스너, 직접 만든 스레드가 저장한 데이터는 롤백 대상이 아니다.
  • REQUIRES_NEW
    • 새 트랜잭션으로 분리된 작업은 이미 커밋돼버린다.

그리고 롤백이 되는 경우에도 운영과 다른 동작을 숨길 수 있다.

  • flush가 안 일어나서 제약 조건 위반을 못 잡는다.
    • 커밋 직전까지 쓰기를 미루다가 롤백해버리면, 유일성 제약 같은 DB 레벨 검증이 한 번도 실행되지 않은 채 테스트가 통과할 수 있다.
  • 지연 로딩이 테스트에서만 된다.
    • 테스트 전체가 하나의 트랜잭션이라 영속성 컨텍스트가 계속 열려 있어서, 운영에서는 LazyInitializationException이 터질 코드가 테스트에서는 멀쩡히 통과한다.

그래서 트랜잭션 롤백은 리포지토리 슬라이스 테스트처럼 테스트 스레드 안에서 모든 게 끝나는 경우에만 쓰고, 서버를 띄우는 통합 테스트에서는 다른 전략을 쓰는 게 맞는 것 같다.

테이블 정리

각 테스트 전후로 테이블을 비우는 방법이다. 실제로 커밋이 일어나기 때문에 운영과 같은 조건에서 테스트할 수 있고, 어떤 스레드가 저장했든 다 지워진다.

정리 유틸리티

테이블을 하나하나 적어두면 테이블이 추가될 때마다 빠뜨리기 쉬워서, 현재 스키마의 테이블 목록을 조회해서 전부 비우는 식으로 만든다.

@Component
@RequiredArgsConstructor
public class DatabaseCleaner {

    private final JdbcTemplate jdbcTemplate;
    private List<String> tableNames;

    @PostConstruct
    void loadTableNames() {
        tableNames = jdbcTemplate.queryForList("""
                SELECT table_name FROM information_schema.tables
                WHERE table_schema = DATABASE()
                  AND table_name <> 'flyway_schema_history'
                """, String.class);
    }

    public void clean() {
        // 같은 커넥션 하나에서 전부 실행해야 한다
        jdbcTemplate.execute((ConnectionCallback<Void>) connection -> {
            try (Statement statement = connection.createStatement()) {
                statement.execute("SET FOREIGN_KEY_CHECKS = 0");
                for (String table : tableNames) {
                    statement.execute("TRUNCATE TABLE " + table);
                }
                statement.execute("SET FOREIGN_KEY_CHECKS = 1");
            }
            return null;
        });
    }
}

여기서 ConnectionCallback으로 커넥션 하나를 붙잡고 실행하는 게 중요하다. SET FOREIGN_KEY_CHECKS = 0은 세션(커넥션) 단위 설정이라, jdbcTemplate.execute()를 여러 번 따로 호출하면 매번 커넥션 풀에서 다른 커넥션을 받아올 수 있다. 그러면 외래 키 검사를 끈 커넥션과 TRUNCATE를 실행하는 커넥션이 달라져서, 외래 키 때문에 TRUNCATE가 실패한다. 스키마 관리 도구의 이력 테이블(flyway_schema_history 등)은 비우면 안 되니까 목록에서 빼둔다.

TRUNCATE는 DELETE보다 빠르고 auto increment 값도 초기화된다. 대신 MySQL에서는 암묵적으로 커밋이 일어나서 트랜잭션 안에서 롤백할 수 없다. 테스트 정리용으로는 오히려 이게 맞는 동작이다.

정리를 테스트 전에 할까, 후에 할까?

정리는 테스트 전에 하는 게 더 안전하다. 테스트 후에 정리하면, 테스트가 중간에 예외로 죽거나 디버깅하다 강제 종료했을 때 정리가 안 된 데이터가 남고, 그 다음 테스트가 오염된 상태에서 시작한다. 테스트 전에 정리하면 앞에서 무슨 일이 있었든 항상 깨끗한 상태에서 시작한다. 실패한 테스트가 남긴 데이터를 직접 들여다볼 수 있다는 부수적인 장점도 있다.

JUnit 확장으로 붙이기

모든 테스트 클래스에 @BeforeEach를 반복해서 쓰는 대신, JUnit 확장으로 만들어두면 애노테이션 하나로 붙일 수 있다.

public class DatabaseCleanupExtension implements BeforeEachCallback {

    @Override
    public void beforeEach(ExtensionContext context) {
        SpringExtension.getApplicationContext(context)
                .getBean(DatabaseCleaner.class)
                .clean();
    }
}

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ExtendWith(DatabaseCleanupExtension.class)
public @interface IntegrationTest {
}

@IntegrationTest
class OrderApiTest {
    // 매 테스트 전에 모든 테이블이 비워진다
}

스프링이 제공하는 @Sql 애노테이션으로 정리 SQL 파일을 실행하는 방법도 있다. 다만 테이블 목록을 SQL 파일에 직접 적어야 해서 테이블이 늘어날 때 빠뜨리기 쉽다.

이 전략은 운영과 같은 조건에서 검증된다는 게 가장 큰 장점이다. 대신 테이블 수가 많아지면 테스트마다 정리 비용이 쌓이고, 병렬 실행과는 맞지 않는다. 한 테스트가 테이블을 비우는 순간, 같은 DB를 쓰면서 동시에 돌고 있는 다른 테스트의 데이터도 같이 사라진다.

테스트마다 고유한 데이터

정리하지 않고, 대신 테스트끼리 데이터가 겹치지 않게 만드는 방법이다. 테스트마다 고유한 식별자로 데이터를 만들고, 조회와 검증도 그 식별자 범위 안에서만 한다.

@IntegrationTest
class OrderApiTest {

    @Test
    void 주문을_생성한다() {
        String userId = "user-" + UUID.randomUUID();   // 이 테스트만의 사용자

        orderClient.createOrder(userId, itemId);

        // 전체 개수가 아니라, 이 테스트가 만든 데이터 범위 안에서 검증
        assertThat(orderRepository.countByUserId(userId)).isEqualTo(1);
    }
}

정리 비용이 없고, 병렬로 돌려도 서로 간섭하지 않는다는 게 강점이다. 대신 검증 방식이 제한된다. orderRepository.count()처럼 전체를 세는 검증은 다른 테스트가 만든 데이터까지 세기 때문에 쓸 수 없고, 항상 이 테스트가 만든 데이터로 범위를 좁혀서 검증해야 한다. 그리고 데이터가 계속 쌓이기 때문에, 전체 실행이 끝난 뒤 한 번 정리하거나 테스트 실행마다 새 컨테이너를 쓰는 식으로 보완해야 한다. 유일성 제약이 걸린 자연키(이메일, 코드 등)도 테스트마다 고유하게 생성해야 한다.

병렬 실행과 격리

테스트가 많아지면 실행 시간을 줄이려고 병렬 실행을 고려하게 되는데, 병렬화 방식에 따라 필요한 격리 수준이 달라진다.

JVM 하나 안에서 병렬 실행

JUnit 5의 병렬 실행 기능을 켜면 같은 JVM 안에서 여러 테스트가 동시에 돈다.

# src/test/resources/junit-platform.properties
junit.jupiter.execution.parallel.enabled = true
junit.jupiter.execution.parallel.mode.default = concurrent

같은 JVM이라 스프링 컨텍스트, 커넥션 풀, DB가 전부 공유된다. 이 상태에서 테이블 정리 전략을 쓰면 테스트끼리 서로의 데이터를 지운다. 그래서 이 방식을 쓰려면 고유 데이터 전략이 사실상 필수다.

Gradle 포크로 병렬 실행

Gradle은 테스트를 여러 JVM(포크)으로 나눠서 병렬로 실행할 수 있다.

// build.gradle.kts
tasks.test {
    useJUnitPlatform()
    maxParallelForks = (Runtime.getRuntime().availableProcessors() / 2).coerceAtLeast(1)
}

포크마다 JVM이 따로라서 스프링 컨텍스트와 static 필드는 자연히 분리된다. 컨테이너를 static 필드로 띄우고 있다면 포크마다 자기 컨테이너를 띄우게 돼서 DB까지 분리된다. 이 경우엔 포크 안에서는 순차 실행이니까 테이블 정리 전략을 그대로 쓸 수 있다.

주의할 건 컨테이너에 withReuse(true)를 걸어둔 경우다. 재사용은 설정이 같은 컨테이너를 찾아서 공유하는 기능이라, 포크들이 전부 같은 컨테이너 하나에 붙는다. 그러면 JVM은 나뉘었는데 DB는 공유되는 상태가 되고, 한 포크의 테이블 정리가 다른 포크의 데이터를 지운다. 이때는 컨테이너는 공유하되, 포크마다 다른 데이터베이스를 쓰게 만들면 된다. Gradle은 각 포크에 org.gradle.test.worker라는 시스템 프로퍼티로 워커 번호를 넘겨준다.

public interface MySqlTestContainer {

    MySQLContainer<?> MYSQL = createAndStart();
    String DATABASE = "test_" + System.getProperty("org.gradle.test.worker", "0");

    private static MySQLContainer<?> createAndStart() {
        MySQLContainer<?> container = new MySQLContainer<>("mysql:8.0")
                .withUsername("root")        // 데이터베이스 생성 권한이 필요
                .withPassword("test")
                .withReuse(true);
        container.start();
        return container;
    }

    @DynamicPropertySource
    static void mysqlProperties(DynamicPropertyRegistry registry) {
        createDatabaseIfAbsent();
        registry.add("spring.datasource.url",
                () -> "jdbc:mysql://%s:%d/%s".formatted(
                        MYSQL.getHost(), MYSQL.getMappedPort(3306), DATABASE));
        registry.add("spring.datasource.username", MYSQL::getUsername);
        registry.add("spring.datasource.password", MYSQL::getPassword);
    }

    private static void createDatabaseIfAbsent() {
        try (Connection connection = MYSQL.createConnection("");
             Statement statement = connection.createStatement()) {
            statement.execute("CREATE DATABASE IF NOT EXISTS " + DATABASE);
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }
}

이러면 컨테이너는 하나만 뜨고, 포크 1은 test_1, 포크 2는 test_2처럼 각자의 데이터베이스를 쓴다. 컨테이너 기동 비용은 한 번만 내면서, 포크끼리는 완전히 격리된다.

DB 밖의 공유 상태

DB만 격리하면 끝날 것 같지만, 통합 테스트에는 다른 공유 상태도 많다.

Redis

Redis도 테스트 사이에 키가 남는다. 순차 실행이라면 테스트 전에 현재 DB를 비우면 된다.

public void cleanRedis() {
    try (RedisConnection connection = redisConnectionFactory.getConnection()) {
        connection.serverCommands().flushDb();
    }
}

다만 컨테이너를 여러 포크가 공유하는 상황에서 flushDb를 쓰면 다른 포크의 키까지 지운다. 이때는 포크마다 Redis의 DB 번호(standalone 기준 0~15)를 나눠 쓰거나, 키에 테스트별 prefix를 붙여서 고유 데이터 전략으로 가야 한다. Redis Cluster는 DB 번호를 나누는 기능이 없어서 prefix 방식만 쓸 수 있다.

Kafka

Kafka는 정리보다 분리가 현실적이다. 앞 테스트가 발행하고 미처 소비되지 않은 메시지가 토픽에 남아 있으면, 뒤 테스트의 컨슈머가 그 메시지를 먼저 읽어서 엉뚱한 결과가 나온다. 테스트마다 토픽 이름이나 컨슈머 그룹 ID를 고유하게 만들어서, 애초에 다른 테스트의 메시지를 보지 않게 하는 게 가장 확실하다.

@Test
void 주문_이벤트를_소비한다() {
    String orderId = UUID.randomUUID().toString();
    kafkaTemplate.send("order-created", orderId, new OrderCreatedEvent(orderId));

    // 이 테스트가 보낸 메시지(orderId)만 기준으로 검증
    await().atMost(Duration.ofSeconds(10))
           .untilAsserted(() -> assertThat(pointRepository.existsByOrderId(orderId)).isTrue());
}

토픽을 테스트마다 새로 만들기 어렵다면, 위처럼 메시지 키나 식별자를 고유하게 만들고 그 식별자 기준으로만 검증하는 것도 같은 효과를 낸다.

Mock

@MockitoBean(Spring Framework 6.2부터, 기존 @MockBean의 대체)으로 만든 목은 기본적으로 각 테스트가 끝난 뒤 자동으로 리셋된다. 그래서 테스트 사이에 stubbing이 남는 문제는 보통 안 생긴다. 문제는 목을 직접 만들어서 빈으로 등록했거나 static으로 들고 있는 경우다. 이런 목은 자동 리셋 대상이 아니라서 직접 Mockito.reset()을 호출해야 한다.

시간

현재 시간에 의존하는 로직은 테스트를 언제 돌리느냐에 따라 결과가 달라진다. 자정 근처에 돌리면 실패하는 테스트가 대표적이다. 코드에서 LocalDateTime.now()를 직접 부르지 말고 Clock 빈을 주입받아 쓰면, 테스트에서는 고정된 시계로 바꿔 끼울 수 있다.

@TestConfiguration
class FixedClockConfig {
    @Bean
    @Primary
    Clock fixedClock() {
        return Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC);
    }
}

스프링 컨텍스트 캐시

스프링은 설정이 같은 테스트끼리 컨텍스트를 재사용한다. 재사용되는 컨텍스트 안에 상태를 가진 빈(인메모리 캐시, 카운터 등)이 있으면, 그 상태가 테스트 사이에 그대로 이어진다. 이런 빈은 테스트 전에 상태를 초기화하는 방법을 따로 마련해야 한다.

컨텍스트를 아예 새로 만드는 @DirtiesContext도 있지만, 컨텍스트 재생성은 테스트 하나에 몇 초씩 드는 비싼 작업이라 최후의 수단으로 남겨두는 게 맞다. 그리고 테스트 클래스마다 @MockitoBean 조합이나 프로필이 조금씩 다르면, 설정이 다른 만큼 컨텍스트가 여러 개 만들어진다. 스프링은 기본적으로 컨텍스트를 최대 32개까지 캐시에 들고 있어서, 컨텍스트가 늘어날수록 메모리와 기동 시간이 같이 늘어난다. 통합 테스트는 공통 애노테이션(위의 @IntegrationTest 같은)으로 설정을 통일해서 컨텍스트 수를 줄이는 게 좋다.

그래서 어떻게 조합하는게 좋은데?

어떤 테스트냐, 그리고 병렬 실행을 어떻게 하느냐에 따라 조합이 달라진다.

리포지토리 슬라이스 테스트 (@DataJpaTest) -> 트랜잭션 롤백 (기본 동작 그대로)
서버를 띄우는 통합 테스트, 순차 실행 -> 테이블 정리 (테스트 전에, JUnit 확장으로)
서버를 띄우는 통합 테스트, JVM 내 병렬 실행 -> 고유 데이터 (정리 전략과 함께 쓸 수 없음)
Gradle 포크 병렬 + 컨테이너 재사용 -> 포크별 데이터베이스 분리 + 테이블 정리
Redis / Kafka -> 순차면 정리, 병렬이면 prefix·고유 식별자로 분리

나는 통합 테스트의 기본값으로는 테이블 정리(테스트 전) + Gradle 포크 병렬 + 포크별 데이터베이스 분리 조합을 많이 쓰지 않을까 싶다. 테스트 코드가 전체 개수 같은 자연스러운 검증을 그대로 쓸 수 있고, 운영과 같은 커밋 조건에서 검증되면서, 포크 단위로 병렬화해서 실행 시간도 줄일 수 있다. JVM 내 병렬 실행까지 필요할 만큼 테스트가 많아지면, 그때 고유 데이터 전략으로 넘어가면 된다.

정리

  • 격리가 깨지면 단독 실행은 통과하고 전체 실행은 실패한다.
    • 원인은 거의 항상 공유 상태다.
  • 트랜잭션 롤백은 빠르지만 테스트 스레드의 트랜잭션에만 적용된다.
    • 실제 서버로 요청하는 테스트, 비동기 처리, REQUIRES_NEW는 롤백되지 않고, flush 누락과 지연 로딩 문제를 숨길 수 있다.
  • 테이블 정리는 운영과 같은 조건에서 검증된다.
    • 테스트 전에 정리하고, 외래 키 검사 해제와 TRUNCATE는 같은 커넥션에서 실행해야 한다. 병렬 실행과는 맞지 않는다.
  • 고유 데이터는 병렬 실행에 강하지만, 검증을 항상 그 테스트가 만든 데이터 범위로 좁혀야 한다.
  • Gradle 포크 병렬에서 컨테이너를 재사용하면 DB가 공유된다.
    • 포크 번호로 데이터베이스를 나누면 컨테이너 하나로 격리할 수 있다.
  • Redis, Kafka, 목, 시간, 스프링 컨텍스트 캐시도 공유 상태다. DB만 격리해서는 끝나지 않는다.

처음엔 테스트가 가끔 실패하는 걸 테스트 환경이 불안정해서라고 생각했는데, 대부분은 테스트끼리 상태를 공유하고 있어서였다. 격리 전략은 하나를 고르는 문제가 아니라, 테스트 종류와 병렬화 방식에 맞춰 조합하는 문제인 것 같다.
