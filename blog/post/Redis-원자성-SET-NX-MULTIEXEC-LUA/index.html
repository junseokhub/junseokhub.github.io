Redis 원자성 (SET NX, MULTI/EXEC, LUA)

Database/NoSQL · 2026-07-06

Intro

Redis는 빠르다는 얘기를 많이 듣는데, 그것보다 먼저 알아야 할 게 명령 하나는 원자적이라는 특징인 것 같다. 근데 이걸 안다고 끝이 아니었다. 실제로 쓰다 보면 명령을 하나만 쓰는 게 아니라 여러 개를 조합해야 하는 상황이 훨씬 많은데, 그럴 때 이게 원자적인게 맞나? 하며 헷갈리기 쉬웠다.

그래서 언제까지가 원자적이고, 여러 명령을 조합해야 할 때는 뭘 써야 하는지(SET NX, MULTI/EXEC, Lua) 정리해보려고 한다.

명령 하나는 원자적이다

Redis는 명령을 처리할 때 기본적으로 싱글 스레드로 하나씩 순서대로 처리한다. 그래서 명령 하나는 중간에 다른 클라이언트가 끼어들 여지 없이 통째로 실행된다. INCR, SET, GETSET 같은 명령 하나짜리는 그 자체로 원자적이라고 보면 될 것 같다.

문제는 하나의 명령으로 표현이 안 되는 일을 하려고 할 때 생긴다.

명령 두 개를 조합하면 원자성이 깨진다

예를 들어 카운터를 늘리는데, 상한을 넘기면 늘리지 않는다를 하려면 값을 먼저 확인하고, 그 다음에 늘리는 두 단계가 필요하다.

Long current = redisTemplate.opsForValue().get(key);   // 1. 확인
if (current == null || current < limit) {
    redisTemplate.opsForValue().increment(key);         // 2. 증가
}

각 줄(get, increment)은 원자적이다. 근데 이 두 줄 사이는 원자적이지 않다. 이 사이에 다른 요청이 끼어들면 문제가 생긴다.

[요청 A] current 확인 (99, 한도 100) -> 아직 안 늘림
                    [요청 B] current 확인 (99) -> 아직 안 늘림
                    [요청 B] 증가 실행 -> 100
[요청 A] 증가 실행 -> 101   (한도를 넘겨버림)

확인할 때는 둘 다 99를 봤는데, 둘 다 늘려도 되겠다고 판단하고 각자 증가시키는 바람에 한도를 넘겨버린다. 확인하고 그 다음에 행동하는 흐름이 두 단계로 나뉘어 있고, 그 사이에 다른 요청이 끼어들 수 있다면 이런 문제가 생긴다.

그래서 어떻게 해결?

애초에 원자적인 명령 하나로 합치기 (SET NX)

가장 간단한 해법은, 확인과 행동을 아예 하나의 명령으로 합쳐버리는 거다. Redis에는 이런 조합형 명령이 이미 여러 개 있는데, 대표적인 게 SET key value NX다. "키가 없을 때만 설정한다"는 확인과 설정을 한 번에 원자적으로 해준다.

@Service
@RequiredArgsConstructor
public class FlagService {

    private final StringRedisTemplate redisTemplate;

    public boolean tryMarkDone(String key) {
        // SET key value NX 와 동일 
        // 이미 있으면 false, 없으면 설정하고 true
        Boolean success = redisTemplate.opsForValue()
                .setIfAbsent(key, "done", Duration.ofMinutes(10));
        return Boolean.TRUE.equals(success);
    }
}

이건 존재 여부를 확인하고 없으면 값을 넣는것처럼, Redis가 이미 명령 하나로 지원해주는 패턴일 때 쓸 수 있는 방법이다. 별도 스크립트도 필요 없고 코드도 짧아서, 표현하려는 로직이 이런 기본 명령 하나로 딱 맞아떨어진다면 제일 먼저 고려해볼 만한 것 같다. 문제는 카운터 상한 체크 같은 조건부 로직은 이런 기본 명령 하나로 표현이 안 된다는 거다. 이럴 땐 다른 방법이 필요하다.

여러 명령을 한 트랜잭션으로 묶기 (MULTI/EXEC)

Redis는 MULTI로 시작해서 EXEC로 끝내는 사이에 명령들을 큐에 쌓아두고, EXEC가 실행되는 순간 그 명령들을 한번에 순서대로, 중간에 다른 클라이언트가 끼어들지 못하게 실행해준다.

redisTemplate.execute(new SessionCallback<Object>() {
    @Override
    public Object execute(RedisOperations operations) {
        operations.multi();
        operations.opsForValue().get(key);
        operations.opsForValue().increment(key);
        return operations.exec();   // 여기서 큐에 쌓인 명령들이 한번에 실행됨
    }
});

근데 이걸 써보고 나서 알게 된 한계가 있다. MULTI ~ EXEC 사이에서는 명령들이 미리 큐에 쌓이기만 하고, 그 자리에서 바로 실행되면서 결과를 보고 분기하는 게 안 된다. 위 코드에서 get(key)의 결과를 보고 "상한 넘으면 increment 하지 말자"를 판단하고 싶어도, EXEC가 실행되기 전까지는 get의 실제 값을 알 수가 없다. 그러니까 MULTI/EXEC는 "이미 정해진 명령들을 한번에 묶어서 실행"하는 데는 좋지만, 값을 보고 그 자리에서 결정하는 조건부 로직에는 안 맞는다.

이 한계를 메우려고 WATCH를 같이 쓰는 방법이 있다. WATCH로 감시하던 키가 EXEC 시점까지 변경 안 됐으면 그대로 실행되고, 중간에 다른 클라이언트가 값을 바꿔버렸으면 EXEC 자체가 실패한다(그러면 애플리케이션에서 재시도하면 된다). 이건 낙관적 락이랑 똑같은 방식이다.미리 막는 게 아니라, 끝나고 나서 그 사이에 누가 건드렸는지를 확인하는 방식이다.

  • 보통 이 방식은 단순히 여러 명령을 순서대로, 끼어들지 않게 실행만 하면 될 때 적합하다. 조건부 분기가 필요한 순간엔 WATCH로 재시도 로직까지 직접 짜야 해서 코드가 금방 복잡해진다.

서버 안에서 조건 분기까지 하기 (Lua 스크립트)

값을 확인하고, 그 결과에 따라 다르게 행동하고 싶다면 Lua 스크립트를 쓰는 게 맞는 것 같다. Redis는 Lua 스크립트 하나를 통째로 원자적인 단위로 실행해준다.스크립트 안에서는 값을 읽고 그 자리에서 조건을 판단해서 분기할 수 있다.

-- increment_with_limit.lua
local current = tonumber(redis.call('GET', KEYS[1]) or "0")
if current < tonumber(ARGV[1]) then
    return redis.call('INCR', KEYS[1])
else
    return -1
end

@Service
public class CounterService {

    private final StringRedisTemplate redisTemplate;

    // 짧은 스크립트는 파일로 안 빼고 문자열로 바로 넘겨도 된다
    private static final RedisScript<Long> INCREMENT_WITH_LIMIT = RedisScript.of("""
            local current = tonumber(redis.call('GET', KEYS[1]) or "0")
            if current < tonumber(ARGV[1]) then
                return redis.call('INCR', KEYS[1])
            else
                return -1
            end
            """, Long.class);

    public CounterService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public boolean tryIncrement(String key, long limit) {
        Long result = redisTemplate.execute(
                INCREMENT_WITH_LIMIT,
                List.of(key),
                String.valueOf(limit)
        );
        return result != null && result >= 0;
    }
}

스크립트가 짧으면 이렇게 텍스트 블록(""")으로 바로 넣는 게 오히려 더 직관적인 것 같다. 파일(.lua)로 따로 빼는 건, 스크립트가 길어지거나 여러 서비스에서 같은 스크립트를 재사용해야 할 때 관리하기 편해지는 선택인 것 같다.

이 스크립트는 GET으로 확인 -> 조건 판단 -> INCR까지 전부 Redis 서버 안에서 한 번에 실행되기 때문에, 그 사이에 다른 요청이 끼어들 여지가 없다. 아까 카운터가 한도를 넘어버렸던 문제가 여기서는 안 생긴다.

Lua는 이렇게 조건 분기가 필요한 상황을 확실하게 해결해주지만, 공짜는 아니다. 스크립트 파일을 따로 관리해야 하고, 로직이 복잡해질수록 이 스크립트 자체를 테스트하고 디버깅하기가 애플리케이션 코드보다 훨씬 불편해진다. 그리고 스크립트 실행 중에는 Redis가 다른 명령을 처리하지 못하니까, 스크립트가 무겁거나 오래 걸리면 그동안 다른 요청들이 전부 밀린다.그래서 스크립트는 최대한 짧고 가볍게 짜는 게 중요한 것 같다.

그래서 언제 뭘 써야하지?

정리해보면 이런 순서로 생각하면 될 것 같다.

확인 + 행동을 한 번에 해야 하는데
  -> 기본 명령 하나로 표현 가능한가? (SET NX 같은 것) -> 예 -> 그걸로 끝
                                                -> 아니오
  -> 그냥 여러 명령을 순서대로 끼어들지 않게 묶기만 하면 되나? -> 예 -> MULTI/EXEC (+ 필요하면 WATCH)
                                                        -> 아니오 (조건 분기가 필요함)
  -> Lua 스크립트

정리

  • Redis 명령 하나는 원자적이지만, 명령을 여러 개 조합하면 그 사이에 다른 요청이 끼어들 수 있다.
  • 확인 + 행동이 기본 명령 하나로 표현되면 SET NX 같은 조합형 명령으로 충분하다.
  • 여러 명령을 그냥 순서대로 끼어들지 않게 묶기만 하면 될 땐 MULTI/EXEC(+ WATCH)로 되지만, 값을 보고 그 자리에서 분기하는 건 못 한다.
  • 값을 확인한 결과에 따라 분기까지 필요하면 Lua 스크립트로 서버 안에서 한 번에 처리해야 한다.
  • Lua는 표현력이 큰 만큼, 스크립트가 무거워지면 그동안 다른 요청이 다 밀린다는 대가가 있다.

원자성을 Redis니까 다 원자적이겠지라고 생각하고 넘어가면, 명령을 두 개 이상 엮는 순간부터 그 가정이 깨진다는 걸 몰랐던 것 같다. 조합하는 로직이 단순하면 SET NX, 조건 분기가 필요하면 Lua로 가는 것으로 기준만 잡아두면 헷갈릴 일이 줄어드는 것 같다.
