Lab/Coupon&Order · 2026-04-20

Intro

3편에서 데이터베이스 구성과 JWT 인증을 구현했다. 이번 편에서는 이 시리즈의 핵심인 선착순 쿠폰 발급 구현을 다룬다.

동시에 수천 명이 요청해도 정확히 재고만큼만 발급되어야 하고, 중복 발급이 없어야 한다. 이를 위해 Redis Lua 스크립트를 활용한 원자적 처리 방식을 적용했다. 단순해 보이는 기능이지만 동시성 문제를 올바르게 해결하기까지 고려해야 할 것들이 많다.

Redis Cluster 설정

Redis Cluster는 데이터를 여러 노드에 분산 저장한다. 키를 해시값으로 계산해 16384개의 슬롯 중 하나에 배치하는 방식이다.

문제는 Lua 스크립트에서 여러 키를 사용할 때 모든 키가 같은 슬롯에 있어야 한다는 점이다. 쿠폰 발급에서는 재고 키와 발급된 유저 SET 키 두 개를 동시에 다뤄야 하는데, 이 둘이 다른 슬롯에 있으면 스크립트 실행 자체가 불가능하다.

이를 해결하기 위해 hashtag를 사용했다. Redis는 키에 중괄호({})가 있으면 중괄호 안의 값만으로 슬롯을 결정한다.

// 중괄호 안의 "coupon:1"이 같으므로 -> 항상 같은 슬롯
"{coupon:1}:stock"
"{coupon:1}:users"

Lettuce 기반으로 Redis Cluster를 설정하고, 노드 변경을 자동으로 감지하도록 topology refresh도 활성화했다.

@Configuration
public class RedisConfig {

    @Bean
    public ReactiveRedisConnectionFactory reactiveRedisConnectionFactory(
            RedisProperties redisProperties) {
        RedisClusterConfiguration clusterConfig = new RedisClusterConfiguration(
                redisProperties.getCluster().getNodes()
        );
        clusterConfig.setPassword(redisProperties.getPassword());

        ClusterTopologyRefreshOptions topologyRefreshOptions =
                ClusterTopologyRefreshOptions.builder()
                        .enableAllAdaptiveRefreshTriggers()
                        .refreshPeriod(Duration.ofSeconds(30))
                        .build();

        ClusterClientOptions clientOptions = ClusterClientOptions.builder()
                .topologyRefreshOptions(topologyRefreshOptions)
                .build();

        LettuceClientConfiguration clientConfig = LettuceClientConfiguration.builder()
                .clientOptions(clientOptions)
                .build();

        return new LettuceConnectionFactory(clusterConfig, clientConfig);
    }

    @Bean
    public ReactiveRedisTemplate<String, String> reactiveRedisTemplate(
            ReactiveRedisConnectionFactory factory) {
        StringRedisSerializer serializer = new StringRedisSerializer();
        RedisSerializationContext<String, String> context = RedisSerializationContext
                .<String, String>newSerializationContext(serializer)
                .build();
        return new ReactiveRedisTemplate<>(factory, context);
    }
}

Lua 스크립트 동시성 처리

왜 Lua 스크립트?

Redis는 싱글 스레드로 동작한다. 즉, 한 번에 하나의 명령만 처리한다. 여기서 Lua 스크립트의 강점이 드러난다. Lua 스크립트는 Redis에서 원자적으로 실행된다. 스크립트가 실행되는 동안 다른 명령이 절대 끼어들 수 없다.

만약 Lua 스크립트 없이 개별 명령으로 처리하면 어떻게 될까.

1. SISMEMBER -> 중복 아님 확인
   (다른 요청이 끼어듦)
2. GET -> 재고 1개 확인
   (다른 요청이 재고를 가져감)
3. SADD -> 유저 추가
4. DECR -> 재고 -1 (이미 0인데 또 감소!)

이 사이에 다른 요청이 끼어들면 중복 발급이나 재고 초과가 발생한다. Lua 스크립트는 이 네 가지 명령을 하나의 트랜잭션처럼 처리해 이 문제를 완전히 해결한다.

스크립트 구현

private static final String ISSUE_COUPON_SCRIPT = """
        local isDuplicate = redis.call('SISMEMBER', KEYS[1], ARGV[1])
        if isDuplicate == 1 then
            return 0
        end
        local stock = tonumber(redis.call('GET', KEYS[2]))
        if stock == nil or stock <= 0 then
            return -1
        end
        redis.call('SADD', KEYS[1], ARGV[1])
        redis.call('DECR', KEYS[2])
        return 1
        """;
  • KEYS[1] -> {coupon:1}:users (발급된 유저 SET)
  • KEYS[2] -> {coupon:1}:stock (재고)
  • ARGV[1] -> userId
  • 반환값: 0 = 중복, -1 = 재고 없음, 1 = 성공

스크립트 흐름은 간단하다.

  1. SISMEMBER로 이미 발급받은 유저인지 확인
  2. GET으로 재고 조회
  3. SADD로 유저 SET에 추가 + DECR로 재고 차감

이 네 가지 명령이 원자적으로 실행되기 때문에 어떤 순서로 요청이 들어와도 정합성이 보장된다.

쿠폰 발급 서비스

@Service
@RequiredArgsConstructor
public class CouponIssueService {

    private final CouponIssueRepository couponIssueRepository;
    private final ReactiveRedisTemplate<String, String> reactiveRedisTemplate;

    @Transactional
    public Mono<CouponIssue> issueCoupon(Long couponId, Long userId) {
        List<String> keys = List.of(usersKey(couponId), stockKey(couponId));

        return reactiveRedisTemplate.execute(
                        RedisScript.of(ISSUE_COUPON_SCRIPT, Long.class),
                        keys,
                        List.of(String.valueOf(userId))
                )
                .next()
                .flatMap(result -> {
                    if (result == 0L) {
                        return Mono.error(new BusinessException(ErrorCode.COUPON_ALREADY_ISSUED));
                    }
                    if (result == -1L) {
                        return Mono.error(new BusinessException(ErrorCode.COUPON_OUT_OF_STOCK));
                    }
                    return couponIssueRepository.save(
                            CouponIssue.builder()
                                    .couponId(couponId)
                                    .userId(userId)
                                    .build()
                    ).onErrorMap(DuplicateKeyException.class,
                            e -> new BusinessException(ErrorCode.COUPON_ALREADY_ISSUED));
                });
    }

    private String stockKey(Long couponId) {
        return "{coupon:" + couponId + "}:stock";
    }

    private String usersKey(Long couponId) {
        return "{coupon:" + couponId + "}:users";
    }
}

Redis에서 1차로 중복과 재고를 체크하고, DB 저장 시 DuplicateKeyException이 발생하면 BusinessException으로 변환한다. DB의 UNIQUE(coupon_id, user_id) 제약이 2차 방어선이 된다.

쿠폰 생성 시에도 Redis에 재고를 초기화한다.

@Service
@RequiredArgsConstructor
public class CouponService {

    private final CouponRepository couponRepository;
    private final ReactiveRedisTemplate<String, String> reactiveRedisTemplate;

    @Transactional
    public Mono<Coupon> createCoupon(String name, String type,
                                     int discountValue, int totalStock) {
        return couponRepository.save(
                Coupon.builder()
                        .name(name)
                        .type(type)
                        .discountValue(discountValue)
                        .totalStock(totalStock)
                        .build()
        ).flatMap(coupon ->
                // DB 저장 후 couponId가 생긴 다음에 Redis 키 세팅
                reactiveRedisTemplate.opsForValue()
                        .set(stockKey(coupon.getId()), String.valueOf(totalStock))
                        .thenReturn(coupon)
        );
    }
}

flatMap을 사용하는 이유는 DB에 저장된 후 생성된 couponId로 Redis 키를 만들어야 하기 때문이다. map은 동기 변환이라 내부에서 또 다른 비동기 작업을 체이닝할 수 없다.

k6 부하 테스트 환경 구성

유저 생성 스크립트

부하 테스트 전에 테스트용 유저를 대량으로 생성해야 한다. k6의 setup-users.js로 1000명의 유저를 순차적으로 생성했다.

export const options = {
    vus: 1,           // 반드시 1 -> __ITER가 VU별 로컬 카운터라 여러 VU면 중복됨
    iterations: 1000,
};

export default function () {
    const username = `user_${__ITER}`;
    http.post(
        'http://localhost:8080/api/auth/register',
        JSON.stringify({ username, password: 'test1234' }),
        { headers: { 'Content-Type': 'application/json' } }
    );
}

vus: 1로 고정하는 이유가 있다. __ITER는 VU별 로컬 카운터라 여러 VU가 동시에 실행되면 같은 __ITER 값을 가질 수 있다. 예를 들어 VU가 10개면 ITER: 45, VU: 7과 ITER: 45, VU: 5가 동시에 존재해 user_45가 중복 생성되는 문제가 생긴다.

쿠폰 발급 부하 테스트 스크립트

export const options = {
    setupTimeout: '300s',
    stages: [
        { duration: '10s', target: 100 },
        { duration: '30s', target: 500 },
        { duration: '30s', target: 1000 },
        { duration: '10s', target: 0 },
    ],
    thresholds: {
        http_req_duration: ['p(95)<2000'],
        http_req_failed: ['rate<0.99'],
    },
};

export function setup() {
    const tokens = [];

    for (let i = 0; i < 1000; i++) {
        const loginRes = http.post(
            'http://localhost:8080/api/auth/login',
            JSON.stringify({ username: `user_${i}`, password: 'test1234' }),
            { headers: { 'Content-Type': 'application/json' } }
        );

        if (loginRes.status === 200) {
            tokens.push(loginRes.json('accessToken'));
        }
    }

    console.log(`준비된 토큰 수: ${tokens.length}`);
    return { tokens };
}

export default function (data) {
    const token = data.tokens[__VU % data.tokens.length];

    const res = http.post(
        'http://localhost:8080/api/coupons/1/issue',
        null,
        {
            headers: {
                'Authorization': `Bearer ${token}`,
                'Content-Type': 'application/json'
            }
        }
    );

    check(res, {
        'status is 201 or 409': (r) => r.status === 201 || r.status === 409,
    });
}

setup()에서 1000명 전원 로그인 후 토큰을 배열에 담고, 각 VU가 __VU % tokens.length로 서로 다른 토큰을 사용한다.

긍정적인 부분

쿠폰 100개가 정확히 100개만 발급됐다. Redis Lua 스크립트의 원자적 처리가 완벽하게 동작했다는 의미다. 중복 발급도 재고 초과도 없었다.

문제점

http_req_failed 95.94%가 충격적으로 보이지만, 실제로는 쿠폰 재고가 100개뿐이라 재고 소진 후 모든 요청이 409를 반환한 것이다. 409는 비즈니스 로직상 정상 응답이므로 실제 실패율은 아니다.

진짜 문제는 max: 60s 타임아웃이다. 일부 요청이 60초까지 걸렸다는 건 어딘가에 병목이 있다는 신호다. 재고가 100개뿐이라 100건 처리 후 나머지는 모두 Redis에서 즉시 튕겨내는 구조인데도 타임아웃이 발생했다.

이는 이번 테스트의 근본적인 한계이기도 하다. 재고가 너무 적어 실제 부하가 DB write까지 이어지지 않았다. 진짜 부하 테스트가 되려면 재고를 충분히 늘려서 DB write 병목을 확인해야 한다.
