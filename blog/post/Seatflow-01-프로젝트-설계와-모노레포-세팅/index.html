[Seatflow] 01. 프로젝트 설계와 모노레포 세팅

Lab/SeatFlow · 2026-05-11

Intro

티켓팅 서비스는 트래픽이 가장 극단적으로 몰리는 케이스 중 하나다. 공연 티켓 오픈 순간, 수만 명이 동시에 같은 좌석을 선점하려 한다. 서버는 빠르게 처리하면서도 중복 없이 정확한 결과를 보장해야 한다.

단순한 구조로는 이 문제를 해결하기 어렵다. 동시성 제어, 서비스 간 데이터 일관성, 장애 격리까지 고려하면 설계 단계에서 결정해야 할 것들이 생각보다 많다.

이 시리즈는 실제 사용자가 쓰는 티켓팅 플랫폼을 만든다는 가정으로 진행한다. 연습이지만 프로덕션 마인드로. 모든 결정에는 이유가 있어야 하고, 그 이유를 나중에 설명할 수 있어야 한다.

MSA

MSA(Microservices Architecture)는 하나의 애플리케이션을 독립적으로 배포 가능한 작은 서비스들로 나눠 구성하는 아키텍처 스타일이다. 각 서비스는 자신만의 비즈니스 도메인을 담당하고, 독립적인 DB를 갖고, 네트워크(HTTP 또는 메시지 큐)를 통해 서로 통신한다.

반대 개념은 모놀리식(Monolithic) 아키텍처다. 모놀리식은 모든 기능이 하나의 프로세스 안에서 동작한다. 코드베이스가 하나고, DB도 하나다.

[모놀리식]                          [MSA]
┌──────────────────────┐        ┌────────┐  ┌────────┐
│  예약 / 결제 / 인증  │           │  예약    │ │   결제  │
│  좌석 / 공연 / 사용자│     ->      └────────┘  └────────┘
│  전부 하나의 프로세스 │            ┌────────┐  ┌────────┐
└──────────────────────┘        │  인증   │  │  공연   │
                                └────────┘  └────────┘

왜 MSA?

모놀리식으로 시작해도 된다. 사실 많은 서비스가 그렇게 시작한다. 하지만 트래픽이 늘고 기능이 복잡해질수록 모놀리식은 한계를 드러낸다.

티켓팅 서비스로 구체적으로 생각해보면 이렇다.

배포 독립성. 오픈런 직전에 결제 로직을 급하게 수정해야 한다고 가정하자. 모놀리식은 전체 서비스를 재배포해야 한다. 예약, 공연 조회, 인증 전부 잠깐 멈춘다. MSA라면 payment-service만 배포한다. 나머지는 계속 살아있다.

장애 격리. 공연 정보를 보여주는 show-service가 느려졌다고 하자. 모놀리식은 DB 커넥션 풀이 고갈되면서 예약 API까지 응답 불가 상태가 된다. MSA라면 show-service가 죽어도 예약과 결제는 계속 된다.

서비스별 확장. 오픈런 순간에는 예약 서비스에 트래픽이 집중된다. 모놀리식은 전체 서버를 스케일 아웃해야 한다. MSA라면 reservation-service Pod만 늘리면 된다.

기술 선택의 자유. 좌석 선점에는 Redis가 필요하고, 공연 메타는 MongoDB가 자연스럽고, 대기열 서비스는 WebFlux가 맞다. 모놀리식에선 기술 스택을 통일해야 한다. MSA에선 서비스마다 최적의 스택을 고를 수 있다.

MSA의 트레이드오프

MSA가 무조건 좋은 건 아니다. 대가가 따른다.

분산 트랜잭션이 생긴다. 하나의 예약 처리가 DB 트랜잭션 하나로 끝나지 않는다. 여러 서비스에 걸쳐 일관성을 보장해야 한다. Saga 패턴이 필요한 이유다.

네트워크 레이턴시가 생긴다. 서비스 간 호출은 함수 호출이 아니라 HTTP 요청이다. 실패할 수 있고, 느릴 수 있다. Circuit Breaker, Retry, Timeout 전략이 필요해진다.

운영 복잡도가 높아진다. 모니터링할 프로세스가 6개로 늘어난다. 서비스 간 통신 오류를 추적하려면 분산 트레이싱이 필요하다. 로그를 한 곳에서 봐야 한다. 인프라에 투자가 필요하다.

이 복잡도를 감당할 수 있을 때 MSA를 선택하는 게 맞다. 이 프로젝트는 Kubernetes, Kafka, Grafana, OpenTelemetry까지 구성된 인프라가 이미 있다. 그 위에 MSA를 올린다.

목표

1만 RPS 환경에서 중복 예약 0건을 보장하는 티켓팅 MSA를 구축한다.

기술 스택

  • Framework: Spring Boot 3.5.13 + Spring MVC + Virtual Thread
  • Language: Java 21
  • Build: Gradle Kotlin DSL (멀티모듈 모노레포)
  • DB: MySQL (예약/결제/인증/사용자), MongoDB (공연 메타)
  • Cache: Redis Cluster (OpsTree Operator, leader 1 + follower 5)
  • Message Broker: Kafka (Strimzi, 3-broker KRaft)
  • Auth: 자체 JWT (RS256, access + refresh token)
  • Migration: Flyway
  • Infra: Kubernetes (개인 서버), Helm, ArgoCD
  • CI: Jenkins
  • Observability: Prometheus + Grafana + Loki + Tempo (OpenTelemetry)
  • Load Test: k6

Key Challenges

동시성 제어

오픈런 순간, 수만 건의 요청이 동시에 들어온다. 단순하게 구현하면 다음과 같은 race condition이 발생한다.

1. A가 A-15 좌석 확인 -> 잔여 1개
2. B가 A-15 좌석 확인 -> 잔여 1개
3. A가 선점 -> 잔여 0개
4. B가 선점 -> 잔여 -1개 (중복 선점!)

이를 해결하기 위해 Redis Lua 스크립트를 활용할 예정이다. Redis는 싱글 스레드로 동작하고, Lua 스크립트는 원자적으로 실행된다. 중간에 다른 명령이 절대 끼어들 수 없다.

분산 트랜잭션

MSA에서 예약 하나가 완료되려면 여러 서비스가 협력해야 한다. 예약 생성 -> 좌석 선점 -> 결제 처리. 중간에 결제가 실패하면 좌석 선점이 롤백되어야 한다. 이 흐름을 Saga 패턴으로 구현한다. Orchestrator 방식으로, reservation-service가 전체 흐름을 조율한다.

이벤트 유실

Kafka에 이벤트를 발행하기 전에 서비스가 죽으면 이벤트가 유실된다. Outbox 패턴으로 이를 방지한다. DB에 먼저 이벤트를 저장하고, 별도 스케줄러가 Kafka로 발행한다. 트랜잭션이 커밋된 이벤트만 발행된다.

Spring MVC vs WebFlux

처음엔 WebFlux를 고려했다. 비동기, 논블로킹, 높은 처리량. 그런데 Java 21의 Virtual Thread 덕분에 이 장점 대부분을 MVC에서도 얻을 수 있다.

spring:
  threads:
    virtual:
      enabled: true

한 줄로 Tomcat이 Virtual Thread 기반으로 동작한다. I/O 대기 중 OS 스레드를 블록하지 않는다. JPA, Lettuce, 기존 생태계 전부 그대로 쓸 수 있다.

WebFlux는 queue-service에서만 사용할 예정이다. SSE 기반의 대기열 서비스는 수만 개의 long-lived connection을 유지해야 한다. 이 워크로드에서는 WebFlux가 진짜 빛난다.

DB 분리 전략

MSA의 핵심 원칙은 Database per Service다. 서비스끼리 DB를 공유하면 결합도가 높아지고 장애가 전파된다. MySQL 인스턴스는 하나지만, 스키마와 유저를 분리해 논리적으로 격리했다.

CREATE DATABASE auth_db;
CREATE DATABASE user_db;
CREATE DATABASE reservation_db;
CREATE DATABASE seat_db;
CREATE DATABASE payment_db;

-- 각 서비스는 자기 DB에만 접근 권한
GRANT ALL PRIVILEGES ON auth_db.* TO 'auth_user'@'%';
GRANT ALL PRIVILEGES ON reservation_db.* TO 'reservation_user'@'%';
-- ...

reservation_user는 auth_db에 접근할 수 없다. 코드 실수로 다른 서비스의 DB를 건드리는 사고를 원천 차단한다.

MongoDB는 show-service 전용으로 show_db를 사용한다. 공연/좌석 메타는 중첩 구조가 많고 읽기 위주라 MongoDB가 자연스럽다.

모노레포 구조

레포 구성 전략 비교

MSA를 구성할 때 레포를 어떻게 나눌지부터 결정해야 한다. 크게 세 가지 선택지가 있다.

멀티레포(Polyrepo). 서비스마다 독립적인 GitHub 레포를 만든다. auth-service, reservation-service, seat-service 각각 별도 레포.

장점은 서비스가 완전히 독립적이라는 점이다. 각 팀이 자기 레포만 관리하고, 다른 서비스의 변경에 영향받지 않는다. 실제 대기업 MSA 환경에서 많이 쓰는 방식이다.

단점은 혼자 또는 소규모로 운영할 때 유지보수 비용이 급격히 늘어난다는 것이다.

# 이벤트 스키마 하나 바꾸면
reservation-service 레포 수정 -> PR -> 머지
seat-service 레포 수정 -> PR -> 머지
payment-service 레포 수정 -> PR -> 머지
... 6개 레포에 같은 작업 반복

모노레포(Monorepo). 모든 서비스를 하나의 레포에 넣는다. 단, 각 서비스는 여전히 독립적인 프로세스로 빌드/배포된다.

장점은 코드 공유와 크로스 서비스 리팩토링이 쉽다. 이벤트 스키마를 libs/common-events 모듈 하나에 정의하면 모든 서비스가 같은 버전을 쓴다. Spring Boot 버전을 올릴 때 루트 파일 한 줄만 바꾸면 된다.

단점은 레포가 커질수록 빌드 시간이 늘고, 한 서비스의 변경이 다른 서비스의 CI를 트리거하지 않도록 path filter를 잘 설정해야 한다.

모노리스(Monolith). 아예 하나의 Spring Boot 애플리케이션으로 만들고 패키지로만 나누는 방식. MSA를 포기하고 모놀리식으로 가는 선택이다.

모노레포를 선택한 이유

MSA의 장점(독립 배포, 장애 격리, 서비스별 스케일링)은 유지하면서, 혼자 운영하는 현실적인 부담을 줄이기 위해 모노레포를 선택했다.

멀티레포는 팀이 나뉘어 있고 서비스별로 릴리스 사이클이 다를 때 진가를 발휘한다. 지금 상황에서 레포 6개를 따로 관리하는 건 오버헤드만 커진다.

나중에 서비스가 성장해서 팀을 분리해야 하는 시점이 오면 그때 멀티레포로 전환하면 된다. 모노레포에서 멀티레포로 분리하는 건 어렵지 않다. 반대는 훨씬 어렵다.

루트 build.gradle.kts

공통 설정은 루트에서 한 번에 관리한다. Spring Boot 버전을 올릴 때 루트 파일 한 줄만 고치면 6개 서비스가 한꺼번에 반영된다.

plugins {
    java
    id("org.springframework.boot") version "3.5.13" apply false
    id("io.spring.dependency-management") version "1.1.7" apply false
}

allprojects {
    group = "com.seatflow"
    version = "0.0.1-SNAPSHOT"
    repositories { mavenCentral() }
}

configure(subprojects.filter { it.parent?.name == "services" }) {
    apply(plugin = "java")
    apply(plugin = "io.spring.dependency-management")

    java {
        toolchain {
            languageVersion = JavaLanguageVersion.of(21)
        }
    }

    dependencies {
        "compileOnly"("org.projectlombok:lombok")
        "annotationProcessor"("org.projectlombok:lombok")
        "testImplementation"("org.springframework.boot:spring-boot-starter-test")
        "testCompileOnly"("org.projectlombok:lombok")
        "testAnnotationProcessor"("org.projectlombok:lombok")
        "testRuntimeOnly"("org.junit.platform:junit-platform-launcher")
    }

    tasks.withType<Test> {
        useJUnitPlatform()
    }
}

configure(subprojects.filter { it.parent?.name == "services" })가 핵심이다. services:auth-service 같은 실제 서비스 모듈에만 공통 설정을 적용한다. Gradle이 자동 생성하는 중간 프로젝트 :services에는 영향을 주지 않는다.

서비스별 build.gradle.kts

공통은 루트가 담당하므로 각 서비스 파일은 해당 서비스의 의존성만 선언한다.

// reservation-service/build.gradle.kts
plugins {
    id("org.springframework.boot")
    id("io.spring.dependency-management")
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-actuator")
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    implementation("org.springframework.boot:spring-boot-starter-validation")
    implementation("org.springframework.boot:spring-boot-starter-web")
    implementation("org.springframework.kafka:spring-kafka")
    runtimeOnly("com.mysql:mysql-connector-j")

    testImplementation("org.springframework.kafka:spring-kafka-test")
}

gradle.properties

org.gradle.parallel=true
org.gradle.caching=true
org.gradle.configuration-cache=false
org.gradle.jvmargs=-Xmx2g -Dfile.encoding=UTF-8

configuration-cache=false로 설정했다. Testcontainers와 일부 Spring Boot 설정이 Configuration Cache와 충돌하는 경우가 있어 일단 꺼두었다. 빌드가 안정화되면 다시 켤 예정이다.

설계 결정들 (ADR)

왜 WebFlux가 아니라 MVC + Virtual Thread일까?

티켓팅의 핵심 워크로드는 짧은 HTTP 요청 + DB/Redis 트랜잭션이다. 스트리밍이나 long-lived connection이 주 워크로드가 아니다. Java 21 Virtual Thread가 이 케이스를 충분히 커버한다.

Spotify는 2025년 일부 백엔드를 WebFlux에서 Virtual Thread로 마이그레이션해서 지연시간 감소와 코드베이스 단순화를 모두 달성했다.

WebFlux는 queue-service에서만 사용한다. 수만 명이 동시 접속해서 "몇 번째 순서인지" SSE로 받아야 하는 워크로드는 WebFlux가 맞다.

왜 Keycloak이 아니라 자체 JWT??

Keycloak은 프로덕션급 보안과 빠른 구현을 제공한다. 하지만 JWT 내부 동작, access/refresh 토큰 전략, RS256 서명, 토큰 블랙리스트 운영을 직접 구현해야 진짜로 이해할 수 있다. 이 프로젝트의 목적상 자체 구현이 맞다.

왜 auth-service와 user-service를 분리했나?

인증(너 누구야?)과 사용자 정보(너 정보가 뭐야?)는 바뀌는 이유가 다르다. 소셜 로그인 추가는 auth-service만 변경된다. 프로필 필드 추가는 user-service만 변경된다. 보안 등급도 다르다. auth-service는 비밀번호 해시와 서명 키를 보유하므로 공격 표면을 분리하는 게 맞다.
