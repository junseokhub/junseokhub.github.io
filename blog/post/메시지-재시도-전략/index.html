메시지 재시도 전략

Architecture · 2026-07-03

Intro

메시지를 처리하다 보면 실패가 일어나기도한다. 잠깐 네트워크가 끊긴다거나, 받는 쪽이 잠깐 느려졌거나, 외부 시스템이 순간적으로 응답을 안주거나...등등 이런 일시적 실패를 한 번 실패했다고 끝내버리면, 잠깐 스쳐 지나갈 문제 때문에 멀쩡한 메시지를 놓치게 될 수 있다. 그렇다고 실패할 때마다 계속 다시 시도하게되면, 재시도들이 몰려서 상황을 더 악화시킬 수 있다.

그래서 실패한 메시지를 어떻게 다뤄야할지? 를 공부해보려고한다. 우선 내가 알아본 방법들은 백오프, Jitter, DLQ, 서킷브레이커가 있다. 백오프와 Jitter로 재시도 간격을 어떻게 해야할지? 계속 실패하는 메시지를 어떻게 처리할지? 애초에 재시도가 의미 없는 상황을 어떻게 감지하는지? 를 알아봐보자!

무작정 재시도

한 번 실패하면 그냥 버릴까?

메시지 처리 실패는 크게 두 종류로 나뉜다.

  1. 일시적 실패 (transient) - 네트워크 순간 끊김, 상대 서비스의 순간적 과부하, DB커넥션 풀 고갈 처럼 시간이 지나면 풀릴 수 있는 실패
  2. 영구적 실패 (permanent) - 메시지 형식이 잘못되어서 존재하지 않는 대상을 참조하는것과 같이 몇 번을 다시 해도 똑같이 실패하는 실패

이 중 일시적 실패를 한 번에 포기하면, 잠깐이면 성공했을 메시지를 버리는 셈이다. 그래서 재시도가 필요하다고 생각한다.

그냥 계속 재시도 한다면?

그렇다고 실패 즉시 곧바로 다시 시도하면 문제가 생길 수 있다.

while (true) {
  try {
    process(message);
    break;
  } catch (Exception e) {
    // 바로 재시도 (간격이 없을 때)
  }
}

다른 쪽에서 부하 때문에 실패를 돌려준 상황이면, 텀이 없는 재시도는 다른쪽에게 더 많은 요청을 빨리 쏟아붓게되는 일이 발생한다. 실패 -> 즉시 재시도 -> 더 큰 부하 -> 더 많은 실패로 이어지는 악순환이 생길것이다. 여러 사용자가 동시에 이 패턴을 타면 재시도끼리 부딪히며 결국 상황을 더 키우는데 이걸 retry storm이라고 한다.

그리고 영구적 실패는 진짜 말 그대로 영구적 실패이다. 재시도를 해봤자 의미가 없다. 그 메시지 자원만 계속 잡아먹으면서 뒤에 밀린 다른 메시지들의 처리를 결국 막게 된다. head-of-line blocking

실패하면 다시 시도한다의 답은 반은 맞고 반은 틀렸다고 생각한다. 틀린 반은 어떻게 벌리고 언제 결국 포기해야할 지를 결정하면 되지 않을까?

재시도 간격

백오프

고정 간격의 한계

가장 단순한 방법은 매번 같은 간격으로 재시도 하는 것이다.

실패 -> 1초 대기 -> 재시도 -> 실패 -> 1초 대기 ......

구현은 쉽지만, 상대가 아직 회복 중인데 계속 같은 빈도로 두드리면 오히려 방해가 될 수 있다.

지수 백오프 (Exponential Backoff)

재시도할 때마다 대기 시간을 점점 늘리는 방법이다. 보통 이전 대기 시간에 배수를 곱해서 늘린다.

1차 실패 -> 1초 대기
2차 실패 -> 2초 대기
3차 실패 -> 4초 대기
.....

long backoff(int attemp, long baseMillis, long maxMillis) {
  long delay = baseMillis * (1L << attempt); // base * 2^attempt
  return Math.min(delay, maxMillis); // 상한을 둔다.
}

간격을 계속 늘리기만 하면 몇 번 실패한 뒤엔 대기 시간이 지나치게 길어질 가능성이있다. 그래서 상한을 꼭 둬야한다.

Jitter

지수 백오프만으로는 부족할 수 있다. 같은 원인으로 동시에 실패한 여러 사용자가 있다면, 이들은 똑같은 백오프 공식을 타니까 똑같은 시점에 결국 다시 몰리게된다.

소비자 A, B, C 모두 T=0에 실패
-> 모두 T=1초에 동시 재시도
-> 다시 다같이 실패
-> 모두 T=3초에 동시 재시도
....반복...

간격은 벌어졌지만 모두 뭉쳐서 온다. 이걸 막으려고 계산된 대기 시간에 무작위성 즉, Jitter를 섞어주는 방법이다.

long delay = backoff(attempt, baseMillis, maxMillis);
long jittered = ThreadLocalRandom.current().nextLong(delay / 2, delay + 1);  // 예: full jitter 변형
  • Full Jitter
    • 0 ~ delay 사이에서 완전 무작위로 뽑는다. 뭉치는걸 잘 흩뜨리지만 어떤 재시도는 너무 빨리 또 어떤건 너무 늦게 올 수도 있다.
  • Equal Jitter
    • delay/2 ~ delay 사이에서 뽑느다. 최소 대기는 보장하면서 뭉치는것도 흩뜨릴 수 있다.

지수 백오프가 간격을 벌리는 역할을 맡고, Jitter가 그 간격 안에서 흔들어주는 역할을 한다. 그래서 둘이 보통 같이 많이 쓰인다.

그래서 시도하다 언제 포기할건데?

DLQ

그냥 무한정 안되는걸 붙들고 재시도할 수는 없다. 최대 재시도 횟수를 정해두고, 그걸 넘긴 메시지는 처리 큐에서 빼서 별도 장소로 보낸다. 이 장소를 우린 DLQ (Dead Letter Queue)라고 한다.

메시지 처리 시도 -> 성공 -> 끝
            -> 실패 -> 재시도 -> 백오프 후 재시도 -> 최대치 초과 -> DLQ로 이동 (원래는 큐에서 제거)

DLQ로 보내는 이유는 크게 두 가지가 있다.

  • 뒤에 밀린 메시지를 막지 않는다.
    • 계속 실패하는 메시지가 큐 앞을 계속 차지하게 되면, 그 뒤에있는 메시지들이 지나갈수 없게 된다. DLQ는 이런 메시지를 옆으로 빼서 흐름을 만들어준다.
  • 나중에 원인을 보고 재처리할 수 있다.
    • DLQ에 쌓인 메시지는 사라지지 않는다. 원인을 고친 뒤에 다시 넣어 재처리하거나, 수동으로 들여다볼 수 있다.

DLQ로 보냈다고 끝이 아니다. 누가? 언제? 어떻게? DLQ를 다시 처리 하는지가 별도의 문제로 남는다. 해당 편에서는 이정도로만 다루고 추후 DLQ에 대해선 더 깊게 알아보는 시간을 가질 예정이다.

서킷브레이커 (Circuit Breaker)

백오프는 한 메시지를 얼마나 끈질기게 다시 시도할지를 다룬다. 그런데 상대 시스템 자체가 완전 죽어있다면, 메시지 하나하나가 각자 백오프를 타며 재시도를 아무리 해봐야 결국 실패한다. 이럴땐 재시도 자체를 잠깐 멈추는게 낫다.

서킷브레이커는 실패율을 지켜보다가 일정 기준을 넘어버리면 회로를 끊어서 그 대상으로의 호출 자체를 일정 시간 차단해버린다.

CLOSED (정상) -> (실패율이 임계치를 넘으면) -> OPEN (차단) -> 모든 호출 즉시 실패처리, 재시도 자체를 안함

-> 일정시간 경과 -> HALF_OPEN (탐색) -> 일부만 흘려보내서 회복됐는지 확인하고

-> 성공이면 CLOSED 복귀, 실패면 다시 OPEN

서킷브레이커와 백오프는 다른 레이어에서 같이 일한다. 백오프는 개별 메시지 단위로 이번엔 좀 쉬었다가 다시 시도해보자 라면, 서킷브레이커는 대상 시스템 단위로 지금은 아예 시도할 때가 아닌거같아 이다. 서킷이 열려있는 동안은 개별 메시지의 백오프 타이머가 다 돼도 호출 자체가 나가질 않는다.

재시도가 만드는 부작용 (중복)

재시도는 보냈는지 확실하지 않아서 안보내지니까 다시 보내는 것이다. 그런데 실제로는 처리가 됐는데 그 결과를 보고받기 전에 타임아웃이 나서 재시도되는 경우도있다. 이러면 같은 메시지가 두 번 처리된다. 재시도 전략이 잘 짜여 있을수록 이 중복 가능성은 점점 더 커진다. 그만큼 끈질기게 재시도할 수록 사실은 처리됐는데 재시도가 될 수도 있는것이다. 그래서 재시도를 쓰는 순간 받는 쪽이 같은 메시지를 두 번 받더라도 결과가 달라지지 않게 만드는 장치가 있어야한다. 이 부분은 추후 자세히 다룰 예정이다.

그래서 언제쓰고 각각 장단점이 뭔데?

지수 백오프

실패 원인이 일시적일 가능성이 높을때에는 (네트워크, 순간 과부하, 커넥션 고갈 등) 재시도를 하는 이상 기본으로 가져가는게 좋다고 생각한다. 재시도 자체가 몇번 안되거나, 서버로 몰릴 걱정이 없는 내부 저지연 경로같은 경우엔 간격을 점점 늘리는거보다 단순하게 처리하는게 더 낫다.

  • 장점
    • 회복할 시간을 벌어준다.
    • 구현이 비교적 단순하다.
  • 단점
    • 파라미터(초기값, 배수, 상한)를 잘못잡게되면, 회복이 느려지거나 재시도가 무의미 해진다.
    • 재시도 사이 지연이 누적돼 전체 처리 완료 시간이 늘어난다.

Jitter

주로 같은 이벤트로 여러 사용자나 인스턴스가 동시에 실패할 수 있는 구조(파티션 다수, 다중 컨슈머, 팬아웃 등)이거나 실제로 뭉쳐져버리는게 문제가 되는 상황에 적합하다. 하지만 애초에 사용자가 하나라 동시에 실패하거나 재시도가 일어날 수 없을때는 jitter를 넣더라도 의미가 없다.

  • 장점
    • 동시 실패한 여러 소비자의 재시도가 다시 뭉치는걸 막아 순간 부하 스파이크를 줄일 수 있다.
  • 단점
    • 무작위성 때문에 개별 메시지의 재시도 시점을 예측하기 어려워진다.

DLQ

실패하는 메시지를 버리면 안되고, 큐의 흐름도 막으면 안될 때 사용하면 좋다. 최대 재시도 이후에도 원인파악이나 재처리 여지를 남겨야하는 경우엔 사용해보자. 하지만 메시지를 놓쳐도 무방하다면 (실시간 알림성, 로그 등) 굳이 DLQ까지 갈 필요가 없다. 오히려 부담이 이득보다 큰 상황이되어버린다.

  • 장점
    • 계속 실패하는 메시지가 뒤에 밀린 메시지를 막지 않는다. 메시지가 사라지지 않아서 나중에 원인 분석 및 재처리가 가능하다.
  • 단점
    • DLQ자체를 다시 처리하는 별도 운영 작업이 생긴다.
    • 방치하면 DLQ가 조용히 쌓이기만 하고 아무도 안보는 상태가 될 수 있다.

써킷 브레이커

재시도 대상이 외부 시스템(다른 서비스, 외부 API)이고, 그게 완전히 죽을수도 있어서 개별 메시지들의 재시도가 무의미한 부하로 쌓일수 있다고 판단되면 사용하는게 좋다. 하지만 호출 대상이 항상 즉시 응답하거나 실패하는 로컬 자원이라 죽어 있는 상태가 의미가 없다면, 또는 애초에 트래픽 규모가 작아서 재시도가 몰려도 크게 문제되지 않는다면 굳이 사용할 필요는 없다.

  • 장점
    • 이미 죽은 대상에 헛된 자원과 시간을 쓰는걸 막을 수 있다.
    • 그 사이 대상이 회복할 시간을 벌어줄 수 있다.
  • 단점
    • 상태 (CLOSED, OPEN, HALF_OPEN) 관리와 임계치, 타임아웃 튜닝이 필요하다.
    • 임계치를 잘못 잡으면 잠깐 흔들려도 회로가 너무 쉽게 열려버린다.

정리

  • 일시적 실패는 재시도로 복구하고, 영구적 실패는 재시도 해봐야 소용없다. (먼저 구분해보자)
  • 지수 백오프
    • 실패할수록 대기 시간을 늘려 회복할 시간벌 수 있다. (상한 조정 필수)
  • Jitter
    • 같은 백오프 공식을 타는 여러 사용자가 동시에 재시도로 몰리는 걸 무작위로 퍼뜨린다.
  • DLQ
    • 최대 재시도를 넘긴 메시지 큐를 밖으로 빼서, 뒤에 밀린 메시지를 막지않고 나중에 재처리할 여지를 남겨 놓는다.
  • 서킷브레이커
    • 개별 메시지의 백오프와 별개로, 대상 시스템 자체가 죽으면 호출을 아예 끊어버린다.
  • 재시도는 구조적으로 중복을 생성한다.
    • 받는 쪽 멱등성 없이 재시도만 넣는건 위험하다.

간격이 없이 재시도하는 건 재시도가 아니라 상황을 악화시킬 수 있다. 백오프로 간격을 벌리고, jitter로 그 간격을 퍼뜨리고, DLQ로 포기할 때를 정하고, 서킷브레이커로 아예 시도도 못하게 해야하는데 이걸 적재적소에 맞게 잘 쓸 수 있도록 충분학 숙지가 필요하다.

저걸로도 뭔가 해결이 안된다면?

대상이 진짜 오랜시간 죽어있거나, 실패가 애초에 재시도로 못고치는 경우 (로직 내 버그, 데이터 자체 문제 등)가 있을것 같은데, 이럴 땐 재시도 전략 과는 달리 다른 대응이 필요하다.

  • 격리 (Bulkhead)
    • 죽은 대상 하나 때문에 커넥션,스레드 풀이 바닥나서 다른 정상 요청까지 물려서 죽는일이 발생하지 않도록 리소스 풀 자체를 대상별로 나눠 놓는다.
  • Fallback / 우아한 저하
    • 실패한 기능을 완전히 막는 대신에 기본값이나 캐시된 결과 등으로 대체해서 전체 흐름은 돌게끔 한다.
  • 알림 / 에스컬레이션
