실시간 통신 방식

Computer Science · 2026-07-13

Intro

서버에서 생긴 변화를 클라이언트한테 실시간처럼 보여주고 싶을 때, 그냥 계속 물어보면 되지 않나싶어서 폴링부터 시작했는데, 알아볼수록 이 자리에 쓸 수 있는 방식이 생각보다 여러 개였다. 폴링, 롱폴링, SSE, WebSocket 등등.. 이름만 들어봤지 서로 뭐가 다른지, 언제 뭘 써야 하는지가 헷갈렸다.

그래서 이 네 가지가 실제로 어떻게 다르게 동작하는지, 각각 뭘 잘하고 뭘 못하는지 정리해보려고 한다.

종류

폴링 (Polling)

가장 단순한 방법이다. 클라이언트가 일정한 간격으로 계속 물어본다.

클라이언트 -> 요청 -> 서버: 새 거 있어? -> 응답: 없어
(3초 대기)
클라이언트 -> 요청 -> 서버: 새 거 있어? -> 응답: 없어
(3초 대기)
클라이언트 -> 요청 -> 서버: 새 거 있어? -> 응답: 있어, 여기

@GetMapping("/updates")
public ResponseEntity<List<Update>> getUpdates(@RequestParam Long lastSeenId) {
    List<Update> updates = updateService.findAfter(lastSeenId);
    return ResponseEntity.ok(updates);   // 없으면 빈 리스트 그대로 반환
}

구현이 제일 쉽고, 그냥 평범한 HTTP 요청-응답이라 서버도 클라이언트도 특별할 게 없다. 근데 새로운게 없어도 계속 요청을 보내야 해서, 클라이언트 수가 많아지면 대부분이 의미 없는 요청으로 서버에 부하를 준다. 그리고 간격을 짧게 잡을수록 실시간에 가까워지지만 그만큼 헛수고 요청이 늘고, 간격을 길게 잡으면 반대로 새 데이터가 생겨도 그 간격만큼 늦게 알게 된다.

롱폴링 (Long Polling)

폴링의 헛수고 요청 문제를 줄이려고 나온 방식이다. 클라이언트가 요청을 보내면, 서버가 새 데이터가 생길 때까지 응답을 미루고 있다가 뭔가 생기면 그때 응답한다.

클라이언트 -> 요청 -> 서버: (새 거 생길 때까지 응답 안 하고 대기)
                              ... 20초 후 새 데이터 발생 ...
서버 -> 응답: 여기 새 거
클라이언트 -> 즉시 다시 요청 -> 서버: (또 대기)

@GetMapping("/updates")
public DeferredResult<List<Update>> getUpdates(@RequestParam Long lastSeenId) {
    DeferredResult<List<Update>> result = new DeferredResult<>(30_000L);   // 최대 30초 대기
    updateService.subscribeUntilNewData(lastSeenId, updates -> result.setResult(updates));
    result.onTimeout(() -> result.setResult(List.of()));   // 타임아웃 나면 빈 응답
    return result;
}

폴링보다 헛수고 요청이 훨씬 줄어든다. 데이터가 생겼을 때만 응답이 오니까. 다만 서버 입장에서는 응답을 미루고 있는 커넥션(또는 요청 처리 스레드)을 그만큼 오래 붙잡고 있어야 한다. 동시 접속자가 많아지면 이 대기 중인 연결들이 서버 자원을 계속 잡아먹는다. 그리고 응답이 오면 클라이언트가 바로 다음 요청을 다시 보내는 구조라, 그 사이의 아주 짧은 순간에는 여전히 연결이 끊겨 있을 수 있다.

SSE (Server-Sent Events)

롱폴링은 응답 한 번 받으면 연결이 끝나고 다시 맺어야 했는데, SSE는 아예 연결을 하나 열어두고 그 위로 서버가 계속 데이터를 흘려보낸다. 클라이언트가 다시 요청을 보낼 필요가 없다.

@GetMapping(value = "/updates/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter streamUpdates() {
    SseEmitter emitter = new SseEmitter(Long.MAX_VALUE);   // 연결을 계속 열어둠
    updateService.onNewUpdate(update -> {
        try {
            emitter.send(update);
        } catch (IOException e) {
            emitter.completeWithError(e);
        }
    });
    return emitter;
}

const eventSource = new EventSource('/updates/stream');
eventSource.onmessage = (event) => {
    console.log('새 데이터:', event.data);
};

SSE는 HTTP 위에서 그대로 동작하기 때문에 별도 프로토콜이나 특별한 서버 설정 없이 기존 인프라(로드밸런서, 프록시 등)와 잘 어울린다. 그리고 연결이 끊기면 브라우저의 EventSource가 자동으로 재연결을 시도해준다는 것도 편한 점이다. 다만 SSE는 서버 -> 클라이언트 한 방향으로만 데이터가 흐른다. 클라이언트가 서버에 뭔가를 보내야 하는 상황이라면 이 스트림과는 별개로 일반 HTTP 요청을 따로 보내야 한다. 그리고 브라우저가 기본적으로 허용하는 SSE 연결 수에 제한이 있어서, 같은 도메인으로 여러 개의 SSE 연결을 동시에 열면 막힐 수 있다는 것도 알아둬야 하는 것 같다.

WebSocket

SSE가 한 방향이었다면, WebSocket은 양방향이다. 처음에 HTTP로 연결을 맺은 다음(handshake), 그 연결을 WebSocket 프로토콜로 업그레이드해서 그 위로 클라이언트와 서버가 서로 아무 때나 메시지를 주고받을 수 있다.

@Component
public class UpdateWebSocketHandler extends TextWebSocketHandler {

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) {
        // 클라이언트가 보낸 메시지 처리
    }

    public void broadcast(String payload) {
        // 서버가 원할 때 아무 세션에나 메시지를 보낼 수 있음
    }
}

// 클라이언트
const socket = new WebSocket('ws://localhost:8080/updates');
socket.onmessage = (event) => console.log('받음:', event.data);
socket.send('클라이언트에서 서버로 보내는 메시지');

양방향 실시간 통신이 필요하면(채팅, 협업 툴, 게임처럼 클라이언트도 계속 뭔가를 보내야 하는 경우) WebSocket이 제일 적합한 것 같다. 근데 그만큼 다루기가 더 까다롭다. HTTP와는 다른 프로토콜이라 일부 프록시나 로드밸런서에서 별도 설정이 필요할 수 있고, 연결이 끊겼을 때 재연결 로직도 SSE처럼 자동이 아니라 직접 구현해야 한다. 그리고 서버가 각 클라이언트의 연결(세션) 상태를 계속 들고 있어야 해서, 여러 서버 인스턴스로 확장할 때 이 클라이언트가 지금 어느 서버에 붙어 있는지를 신경 써야 하는 문제도 따라온다.

언제 뭘 쓸까?

정리해보면 이런 기준으로 나뉘는 것 같다.

  • 클라이언트가 서버에도 계속 뭔가를 보내야 하나? 그렇다면 SSE로는 안 되고 WebSocket이 필요하다. 아니라면(서버 -> 클라이언트 방향만 필요하다면) SSE로 충분하다.
  • 실시간성이 많이 중요하나? 몇 초 정도의 지연은 괜찮다면 폴링으로도 되고, 그 헛수고 요청조차 줄이고 싶으면 롱폴링, 진짜 즉시 반영돼야 한다면 SSE나 WebSocket 사용하면 될 것 같다.
  • 구현, 운영 복잡도를 얼마나 감당가능할까? 폴링이 제일 단순하고, WebSocket이 제일 복잡하다. SSE는 그 중간이면서 HTTP 인프라를 그대로 쓸 수 있다는 점에서 꽤 실용적인 것 같다.
서버->클라이언트 단방향이면 충분한가?
  -> 예 -> 실시간성이 꼭 필요한가?
              -> 예 -> SSE
              -> 아니오 (몇 초 지연 괜찮음) -> 폴링 또는 롱폴링
  -> 아니오 (양방향 필요) -> WebSocket

정리

  • 폴링 제일 단순하지만, 새 게 없어도 계속 물어봐야 해서 헛수고 요청이 쌓인다.
  • 롱폴링 새 데이터가 생길 때까지 응답을 미뤄서 헛수고를 줄이지만, 대기 중인 연결이 서버 자원을 그만큼 오래 잡는다.
  • SSE 연결을 열어두고 서버가 계속 흘려보낸다. HTTP 그대로라 다루기 편하고 자동 재연결도 되지만, 서버->클라이언트 단방향만 가능하다.
  • WebSocket 양방향이 가능한 유일한 선택지지만, 프로토콜이 다르고 연결 상태 관리도 직접 해야 해서 제일 복잡하다.

이름만 들었을 땐 그냥 다 비슷한 실시간 기술이라고 뭉뚱그려 생각했는데, 막상 파보니 각자 무슨 문제를 해결하려고 나왔는지가 뚜렷하게 달랐다. 방향(단방향/양방향)과 실시간성 요구 수준, 이 두 가지만 먼저 정하면 그중에 뭘 써야 할지는 자연스럽게 좁혀지는 것 같다.
