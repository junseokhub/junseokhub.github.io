페이지네이션 (Offset vs Cursor)

Database/RDB · 2026-11-26

Intro

목록 API를 처음 만들 때는 거의 항상 LIMIT 20 OFFSET 40 같은 쿼리로 시작한다. 페이지 번호를 그대로 OFFSET으로 바꾸면 되니 구현이 쉽고, Spring Data의 Pageable도 이 방식이다. 데이터가 적을 때는 아무 문제가 없다.

데이터가 천만 건이 되면 뒤쪽 페이지가 점점 느려지고, 무한 스크롤에서 같은 글이 두 번 보이거나 어떤 글이 빠지는 일이 생긴다. 페이지 번호 옆에 띄우는 전체 개수를 세는 쿼리가 목록 쿼리보다 느려지기도 한다. 이 문제들은 OFFSET이 어떻게 동작하는지를 알면 다 설명이 되고, 대부분은 커서 방식으로 바꾸면 사라진다. 다만 커서 방식에도 함정이 몇 개 있다.

이번엔 MySQL 8.4에 천만 건짜리 게시글 테이블을 만들고, OFFSET 방식의 한계와 커서 방식의 구현을 실험해본다. 각 실험은 가설, 절차, 관찰, 결과 순서로 정리했고, 결과 표의 관찰 칸은 직접 돌려서 채우도록 비워뒀다.

실험 환경

MySQL 8.4 단일 인스턴스에 버퍼 풀을 256MB로 작게 잡아서, 테이블이 메모리에 다 올라오지 못하게 했다. 게시글 천만 건을 20개 카테고리에 나눠 넣었다. created_at은 초 단위이고 1초에 3건씩 쌓이게 해서, 같은 시각을 가진 글이 일부러 여럿 생기게 했다. 실제 서비스에서도 초 단위 시각은 생각보다 자주 겹친다.

CREATE TABLE posts (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  category_id INT UNSIGNED    NOT NULL,
  title       VARCHAR(100)    NOT NULL,
  body        VARCHAR(300)    NOT NULL,
  created_at  DATETIME        NOT NULL,
  PRIMARY KEY (id),
  KEY idx_created (created_at),
  KEY idx_category_created (category_id, created_at)
);

목록은 최신순으로 보여준다. 정렬 기준은 created_at DESC, id DESC다. id를 붙인 이유는 커서 방식에서 다시 나온다.

Offset 방식

SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;      -- 3페이지

MySQL은 OFFSET만큼의 행을 건너뛰는 방법이 따로 없다. 정렬 순서대로 앞에서부터 OFFSET + LIMIT개의 행을 실제로 읽고, 앞의 OFFSET개를 버린 다음 남은 20개를 돌려준다. 100만 번째 페이지 근처를 보려면 100만 건 넘게 읽어야 한다는 뜻이다.

idx_created 인덱스는 created_at 하나로 만들었지만, InnoDB의 보조 인덱스에는 기본 키가 항상 뒤에 붙어 있다. 그래서 이 인덱스는 사실상 (created_at, id) 순서로 정렬돼 있고, ORDER BY created_at DESC, id DESC를 별도 정렬 없이 인덱스를 거꾸로 읽는 것만으로 처리할 수 있다.

페이지가 깊어질수록

  • 가설

    • OFFSET이 커질수록 읽는 행 수가 같이 늘어서 시간이 비례해서 늘어난다. 그리고 어느 지점부터는 옵티마이저가 인덱스를 버리고 테이블 전체를 읽어서 정렬하는 쪽으로 계획을 바꾼다. 보조 인덱스로 행을 하나씩 찾아가는 비용이 전체를 한 번 읽는 비용보다 커지는 지점이다.

  • 절차

    • OFFSET을 0, 1만, 10만, 100만, 500만으로 바꿔가며 EXPLAIN ANALYZE로 실행한다.
EXPLAIN ANALYZE SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 1000000;
OFFSET예상 실행 계획예상 읽은 행관찰 (시간 / 계획)
0Index scan (reverse)20
10,000Index scan (reverse)10,020
100,000Table scan + Sort로 바뀔 수 있음100,020 이상
1,000,000Table scan + Sort천만
5,000,000Table scan + Sort천만
  • 관찰 포인트
    • 첫 페이지는 1ms도 안 걸리는데, 깊은 페이지는 수 초가 걸린다. 같은 쿼리가 OFFSET 값 하나로 수천 배 차이가 난다. 그리고 계획이 Table scan + Sort로 바뀌는 지점부터는 OFFSET이 얼마든 테이블 전체를 읽는다. 사용자가 뒤쪽 페이지를 거의 보지 않더라도, 크롤러나 데이터를 내려받는 스크립트는 마지막 페이지까지 순서대로 넘긴다. 이런 요청 몇 개가 동시에 들어오면 DB 전체가 느려진다.

페이지를 넘기는 사이에 새 글이 들어오면

  • 가설

    • 1페이지를 본 뒤 새 글 5개가 올라오면, 2페이지의 처음 5개는 1페이지의 마지막 5개와 같다. 새 글이 앞에 끼어들면서 모든 글이 5칸씩 뒤로 밀렸기 때문이다.

  • 절차

    • 1페이지를 읽고, 새 글 5개를 넣은 뒤 2페이지를 읽는다.
SELECT id, title FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 0;

INSERT INTO posts (category_id, title, body, created_at)
VALUES (1, 'new-1', 'x', NOW()), (1, 'new-2', 'x', NOW()), (1, 'new-3', 'x', NOW()),
       (1, 'new-4', 'x', NOW()), (1, 'new-5', 'x', NOW());

SELECT id, title FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 20;
항목예상관찰
2페이지의 처음 5개1페이지의 마지막 5개와 같음

반대로 1페이지를 보는 사이 글이 지워지면, 2페이지의 처음 몇 개를 아무도 보지 못하고 지나간다. 무한 스크롤에서 같은 글이 두 번 나오거나 어떤 글이 빠지는 건 대부분 이 때문이다. OFFSET은 몇 번째부터라는 위치만 기억하는데, 그 사이에 위치가 바뀌었기 때문이다.

지연 조인으로 덜 읽기

OFFSET을 그대로 쓰면서 비용을 줄이는 방법이 있다. 먼저 인덱스만으로 해당 페이지의 id 20개를 찾고, 그 20개에 대해서만 나머지 컬럼을 가져오는 방식이다. 이걸 지연 조인(deferred join)이라고 부른다.

SELECT p.id, p.title, p.created_at
FROM posts p
JOIN (
    SELECT id FROM posts
    ORDER BY created_at DESC, id DESC
    LIMIT 20 OFFSET 1000000
) page ON page.id = p.id
ORDER BY p.created_at DESC, p.id DESC;

안쪽 쿼리는 id와 created_at만 필요해서 idx_created 인덱스만 읽고 끝난다(Covering index). 버리는 100만 건에 대해 테이블 본문을 읽지 않으니 훨씬 가볍다.

  • 가설

    • 지연 조인은 같은 OFFSET에서 훨씬 빠르고, Table scan + Sort로 바뀌지도 않는다. 하지만 여전히 OFFSET만큼 인덱스를 읽으므로 시간은 OFFSET에 비례해서 늘어난다.

  • 절차

    • 위 쿼리를 OFFSET 10만, 100만, 500만으로 EXPLAIN ANALYZE 한다.
OFFSET예상관찰 (시간)
100,000깊은 페이지 실험보다 크게 빠름, Covering index scan
1,000,000수백 ms ~ 1초대
5,000,000수 초

지연 조인은 이미 OFFSET 방식을 쓰고 있고 당장 API를 바꾸기 어려울 때 쓸 수 있는 개선책이다. 페이지 번호가 꼭 필요한 화면이라면, 지연 조인과 함께 갈 수 있는 최대 페이지를 제한하는 것도 같이 고려한다. 검색 엔진들이 결과를 수십 페이지까지만 보여주는 것도 같은 이유다.

전체 개수를 세는 비용

페이지 번호를 보여주려면 전체 개수가 필요하다. Spring Data의 Page도 목록 쿼리와 함께 COUNT(*) 쿼리를 실행한다.

SELECT COUNT(*) FROM posts;
SELECT COUNT(*) FROM posts WHERE category_id = 3;
쿼리예상관찰
전체 COUNT(*)수 초 (가장 작은 인덱스를 전부 읽음)
카테고리별 COUNT(*)수백 ms (그 카테고리의 인덱스 범위를 전부 읽음)

InnoDB는 MVCC 때문에 트랜잭션마다 보이는 행 수가 달라서, 테이블의 행 수를 따로 저장해두지 않는다. COUNT(*)는 매번 인덱스 하나를 처음부터 끝까지 센다. 그래서 목록은 20건만 읽는데 개수를 세느라 천만 건을 읽는 일이 생긴다.

대안은 상황에 따라 다르다.

  • 전체 개수를 보여주지 않는다. 다음 페이지가 있는지만 알면 되는 화면이라면 LIMIT 21로 한 건 더 읽어서, 21번째가 있으면 다음 페이지가 있다고 판단한다. Spring Data에서는 Page 대신 Slice를 반환하면 이렇게 동작한다.
  • 대략적인 개수를 보여준다. 정확할 필요가 없다면 information_schema.tables의 table_rows나 EXPLAIN의 예상 행 수를 쓴다. 통계 기반이라 실제와 꽤 다를 수 있다.
  • 개수를 따로 관리한다. 카테고리별 개수 테이블을 두고 글을 쓰고 지울 때 같은 트랜잭션에서 갱신하거나, 몇 분 단위로 다시 계산해서 캐시해둔다. 정확도와 쓰기 비용 사이에서 고른다.

Cursor 방식

커서 방식(keyset pagination)은 몇 번째부터가 아니라 어디서부터를 기억한다. 이전 페이지의 마지막 행이 가진 정렬 키 값을 받아서, 그보다 뒤에 있는 행부터 읽는다.

-- 첫 페이지
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 다음 페이지: 이전 페이지 마지막 행이 (created_at = '2026-02-08 10:00:00', id = 9000123)였다면
SELECT id, title, created_at FROM posts
WHERE created_at < '2026-02-08 10:00:00'
   OR (created_at = '2026-02-08 10:00:00' AND id < 9000123)
ORDER BY created_at DESC, id DESC
LIMIT 20;

이 WHERE 조건은 인덱스의 정렬 순서상 그 위치 바로 다음부터라는 뜻이다. 인덱스에서 그 위치를 바로 찾아 들어가서 20건만 읽고 멈추기 때문에, 몇 번째 페이지든 읽는 양이 같다. 그리고 위치가 아니라 값을 기준으로 하니, 앞에 새 글이 끼어들어도 다음 페이지가 밀리지 않는다.

정렬 키는 유일해야 한다

커서를 created_at 하나로만 만들면 어떻게 될까. 같은 시각의 글이 여러 개 있고 페이지 경계가 그 사이에 걸리면, created_at < 마지막 값 조건이 같은 시각의 남은 글들을 건너뛴다. <=로 바꾸면 이번엔 같은 시각의 글이 다음 페이지에 다시 나온다. 그래서 정렬 키의 마지막에는 항상 id처럼 유일한 컬럼을 붙여서, 정렬 순서가 완전히 하나로 정해지게 만든다.

시각만으로 만든 커서는 글을 빠뜨린다

같은 시각에 글 30건이 한꺼번에 올라온 상황을 만든다. 일괄 등록이나 이벤트성 트래픽에서 흔하다.

  • 가설

    • 첫 페이지 20건이 모두 같은 시각이면, created_at만으로 만든 커서는 다음 페이지에서 같은 시각의 나머지 10건을 건너뛴다. (created_at, id)로 만든 커서는 정확히 그 10건부터 이어서 가져온다.

  • 절차

    • '2027-01-01 12:00:00'에 burst 글 30건을 넣고 첫 페이지를 읽는다. 첫 페이지 마지막 행의 id를 :last_id로 두고 두 커서로 다음 페이지를 읽는다.
-- 1) created_at만으로 만든 커서
SELECT id, title, created_at FROM posts
WHERE created_at < '2027-01-01 12:00:00'
ORDER BY created_at DESC, id DESC LIMIT 20;

-- 2) (created_at, id)로 만든 커서
SELECT id, title, created_at FROM posts
WHERE created_at < '2027-01-01 12:00:00'
   OR (created_at = '2027-01-01 12:00:00' AND id < :last_id)
ORDER BY created_at DESC, id DESC LIMIT 20;
항목예상관찰
첫 페이지burst 글 20건
1) 시각만으로 만든 커서의 다음 페이지burst가 아닌 이전 글들 (burst 10건 누락)
2) (시각, id) 커서의 다음 페이지남은 burst 10건 + 이전 글 10건

행 비교 문법은 인덱스를 못 탄다

위의 조건은 행 비교 문법으로 더 짧게 쓸 수 있다.

WHERE (created_at, id) < ('2026-02-08 10:00:00', 9000123)

의미는 같다. 그런데 MySQL에서는 이 둘의 실행 계획이 다르다.

  • 가설

    • 행 비교 문법을 쓰면 옵티마이저가 인덱스에서 그 위치를 바로 찾아 들어가지 못하고, 인덱스를 처음부터 읽으면서 조건을 하나씩 검사한다. 커서가 뒤쪽일수록 OFFSET 방식만큼 느려진다. OR로 풀어 쓴 조건은 인덱스 범위 탐색으로 바로 들어간다.

  • 절차

    • 100만 번째 행의 (created_at, id)를 커서로 잡고 두 조건을 EXPLAIN ANALYZE로 비교한다.
EXPLAIN ANALYZE SELECT id, title, created_at FROM posts
WHERE (created_at, id) < (:c_at, :c_id)
ORDER BY created_at DESC, id DESC LIMIT 20;

EXPLAIN ANALYZE SELECT id, title, created_at FROM posts
WHERE created_at < :c_at OR (created_at = :c_at AND id < :c_id)
ORDER BY created_at DESC, id DESC LIMIT 20;
조건예상 실행 계획예상관찰 (시간 / 계획)
(created_at, id) < (?, ?)Index scan (reverse) → Filter, 100만 건을 읽음수 초
created_at < ? OR (created_at = ? AND id < ?)Index range scan (reverse)1ms 안팎
  • 관찰 포인트
    • MySQL 문서도 행 비교 문법이 인덱스를 충분히 활용하지 못할 수 있으니 OR/AND로 풀어 쓰라고 권한다. PostgreSQL에서는 행 비교 문법이 인덱스를 잘 타서 이 형태가 흔히 권장되는데, 그 예제를 MySQL에 그대로 옮기면 이 함정에 빠진다. EXPLAIN ANALYZE로 Index range scan인지 꼭 확인하는 게 좋을 것 같다.

깊이와 상관없는 시간

  • 가설

    • OR로 풀어 쓴 커서 조건은 커서가 앞쪽이든 뒤쪽이든 같은 시간이 걸린다.

  • 절차

    • 0, 100만, 500만, 900만 번째 행의 (created_at, id)를 각각 커서로 잡고, 위의 OR 조건 쿼리를 EXPLAIN ANALYZE 한다. 커서 값을 구하는 OFFSET 쿼리는 준비 과정이라 측정하지 않는다.
커서 위치예상관찰 (시간)
01ms 안팎
100만1ms 안팎
500만1ms 안팎
900만1ms 안팎

같은 위치를 OFFSET으로 읽은 깊은 페이지 실험과 비교하면 차이가 분명하다. 실제로는 페이지 본문을 디스크에서 읽어야 하는 경우 몇 ms가 더 걸릴 수 있지만, 그 시간도 위치와는 상관이 없다.

필터가 있을 때의 인덱스

카테고리별 목록이라면 등호 조건 컬럼을 인덱스 앞에 두고, 그 뒤에 정렬 키가 오는 인덱스가 필요하다. 실험 환경의 idx_category_created (category_id, created_at)이 그 역할이고, 여기에도 id가 뒤에 붙어 있다.

SELECT id, title, created_at FROM posts
WHERE category_id = 3
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;

정렬 기준이 인기순, 조회수순처럼 바뀌는 값이라면 이야기가 복잡해진다. 커서로 쓴 값이 페이지를 넘기는 사이에 바뀌면 같은 글이 다시 나오거나 빠질 수 있다. 이런 목록은 일정 시간 단위로 순위를 고정한 스냅샷을 만들어서 그걸 페이지네이션하는 식으로 푸는 경우가 많다.

이전 페이지

이전 페이지는 첫 행을 커서로 삼아 방향을 뒤집으면 된다. 비교 연산자와 정렬 방향을 반대로 바꿔서 20건을 가져온 다음, 애플리케이션에서 순서를 다시 뒤집는다.

SELECT id, title, created_at FROM posts
WHERE created_at > ? OR (created_at = ? AND id > ?)
ORDER BY created_at ASC, id ASC
LIMIT 20;

커서를 API로 내보내기

커서 값을 ?created_at=...&id=...처럼 그대로 노출하면, 클라이언트가 그 값을 조작하거나 정렬 기준이 바뀌었을 때 호환이 깨진다. 보통은 정렬 키 값을 묶어서 Base64로 인코딩한 불투명한 문자열 하나로 내보낸다. 클라이언트는 그 문자열을 다음 요청에 그대로 돌려주기만 한다.

public record PostCursor(LocalDateTime createdAt, long id) {

    private static final Base64.Encoder ENCODER = Base64.getUrlEncoder().withoutPadding();
    private static final Base64.Decoder DECODER = Base64.getUrlDecoder();

    public String encode() {
        String raw = createdAt + "|" + id;
        return ENCODER.encodeToString(raw.getBytes(StandardCharsets.UTF_8));
    }

    public static PostCursor decode(String token) {
        try {
            String raw = new String(DECODER.decode(token), StandardCharsets.UTF_8);
            String[] parts = raw.split("\\|", 2);
            return new PostCursor(LocalDateTime.parse(parts[0]), Long.parseLong(parts[1]));
        } catch (RuntimeException e) {
            throw new IllegalArgumentException("잘못된 커서", e);
        }
    }
}

조회 쪽은 size + 1건을 읽어서, 넘치는 한 건이 있으면 마지막 행으로 다음 커서를 만든다.

public CursorPage<PostSummary> findPage(@Nullable String cursor, int size) {
    int limit = size + 1;   // 한 건 더 읽어서 다음 페이지가 있는지 판단한다
    List<PostSummary> rows = (cursor == null)
            ? jdbc.query("""
                    SELECT id, title, created_at FROM posts
                    ORDER BY created_at DESC, id DESC
                    LIMIT ?
                    """, this::map, limit)
            : queryAfter(PostCursor.decode(cursor), limit);

    if (rows.size() <= size) {
        return new CursorPage<>(rows, null);    // 마지막 페이지
    }
    List<PostSummary> page = rows.subList(0, size);
    PostSummary last = page.get(size - 1);
    return new CursorPage<>(page, new PostCursor(last.createdAt(), last.id()).encode());
}

queryAfter는 앞의 OR 조건 쿼리에 c.createdAt(), c.createdAt(), c.id(), limit을 바인딩한다. 컨트롤러에서는 size에 상한(예: 100)을 둔다.

커서가 조작되는 게 걱정이라면 HMAC 서명을 붙여서, 서버가 만든 커서인지 검증하고 받는다. 커서에 정렬 기준이나 필터 값까지 담아두면, 클라이언트가 중간에 필터를 바꿔서 엉뚱한 커서를 보내는 경우도 걸러낼 수 있다.

Spring Data JPA의 keyset scrolling

Spring Data 3.1(Spring Boot 3.1)부터는 커서 방식이 내장돼 있다. 리포지토리 메서드가 ScrollPosition을 받고 Window를 돌려주게 선언하면 된다. Spring Boot 3.0 이하라면 이 기능이 없으니 위의 직접 구현을 쓴다.

public interface PostRepository extends JpaRepository<Post, Long> {

    Window<Post> findFirst20ByOrderByCreatedAtDescIdDesc(ScrollPosition position);
}

Window<Post> first = postRepository.findFirst20ByOrderByCreatedAtDescIdDesc(ScrollPosition.keyset());

if (first.hasNext()) {
    ScrollPosition next = first.positionAt(first.size() - 1);
    Window<Post> second = postRepository.findFirst20ByOrderByCreatedAtDescIdDesc(next);
}

Spring Data는 다음 페이지 조건을 행 비교 문법이 아니라 created_at < ? OR (created_at = ? AND id < ?) 형태의 OR/AND로 만든다. 그래서 행 비교 문법 실험의 함정은 피해 간다. hasNext()를 위해 한 건 더 읽는 것도 위의 직접 구현과 같다.

주의할 점이 하나 있다. 정렬 조건에 식별자가 없으면 Spring Data가 식별자를 정렬 마지막에 자동으로 붙이는데, 방향을 따로 지정하지 않으면 오름차순으로 붙인다. OrderByCreatedAtDesc만 쓰면 created_at DESC, id ASC가 되어, 인덱스를 거꾸로 읽는 것만으로는 이 순서가 나오지 않는다. 그래서 위처럼 IdDesc까지 직접 적어서 인덱스 순서와 맞춘다.

ScrollPosition을 API 응답으로 내보낼 때는 KeysetScrollPosition.getKeys()의 값을 꺼내 직접 커서 문자열로 인코딩하고, 요청에서 받은 커서는 ScrollPosition.forward(keys)로 복원한다.

커서 방식이 못 하는 것

커서 방식은 특정 페이지로 바로 가지 못한다. 47페이지를 보려면 1페이지부터 46번 넘겨야 한다. 그래서 무한 스크롤, 피드, 다음/이전만 있는 목록, 외부 API의 전체 데이터 내려받기에 잘 맞고, 페이지 번호를 눌러 이동하는 관리자 화면에는 맞지 않는다.

페이지 번호가 꼭 필요한 화면은 OFFSET을 쓰되, 갈 수 있는 최대 페이지를 제한하고 지연 조인으로 비용을 줄이는 게 현실적인 것 같다. 관리자 화면처럼 사용자가 적은 곳이라면 그 정도로 충분하고, 외부에 공개된 목록 API라면 크롤러가 마지막 페이지까지 순회할 수 있다는 전제로 커서 방식을 쓰는 게 안전하다.

정리

항목OffsetCursor
읽는 양OFFSET + LIMIT (깊을수록 늘어남)LIMIT (깊이와 무관)
중간에 데이터가 바뀌면중복되거나 빠짐영향 없음
특정 페이지로 이동가능불가능
전체 개수보통 같이 셈 (COUNT(*) 비용)보통 다음 페이지 유무만
정렬 키 요구사항없음유일해야 함 (마지막에 id)
잘 맞는 곳페이지 번호가 필요한 관리자 화면피드, 무한 스크롤, 외부 API, 전체 순회
  • OFFSET은 건너뛰는 게 아니라 읽고 버린다. 깊은 페이지일수록 비례해서 느려지고, 어느 지점부터는 테이블 전체를 읽는 계획으로 바뀐다.
  • OFFSET을 유지해야 한다면 지연 조인과 최대 페이지 제한으로 비용을 줄인다.
  • COUNT(*)는 매번 인덱스 하나를 전부 센다. 꼭 필요한지부터 따지고, 아니면 Slice처럼 다음 페이지 유무만 본다.
  • 커서의 정렬 키 마지막에는 유일한 컬럼을 붙인다.
  • MySQL에서는 커서 조건을 행 비교 문법이 아니라 OR/AND로 풀어 쓴다.
  • 커서는 정렬 키 값을 묶은 불투명한 토큰으로 내보낸다.

가장 의외였던 건 행 비교 문법 실험이었다. 행 비교 문법이 의미상 완전히 같고 더 깔끔해 보여서 당연히 그렇게 쓰려고 했는데, 실행 계획을 보니 인덱스를 처음부터 다 훑고 있었다. 커서 방식으로 바꿨으니 빨라졌겠지 하고 넘어갔다면 몰랐을 거다. 페이지네이션은 쿼리 모양만 보고 판단하기보다, 깊은 위치에서 EXPLAIN ANALYZE를 한 번은 돌려봐야 하는 영역인 것 같다.
