로그 수집과 trace 연계 (Loki, OpenTelemetry Collector, structured metadata, 유실 없는 수집)

Devops · 2026-11-15

Intro

[분산 트레이싱] 글에서 요청 하나가 어느 서비스의 어느 구간에서 느려졌는지를 trace로 볼 수 있게 했다. 그런데 trace는 어디서 느렸는지는 알려줘도 왜 느렸는지는 잘 알려주지 않는다. 캐시를 놓쳤는지, 재시도를 몇 번 했는지, 어떤 예외가 났다가 삼켜졌는지는 그 구간의 로그에 있다. 결국 장애를 볼 때는 느린 span 하나를 찾은 다음, 그 요청의 로그만 골라 보고 싶어진다.

이게 되려면 애플리케이션이 로그 한 줄마다 traceId를 남기고, 수집기가 로그를 빠짐없이 모아 저장소로 보내고, 저장소가 traceId로 그 줄들을 빨리 찾아줘야 한다. 같은 Collector에 로그 파이프라인을 더하고 저장소로 Loki를 붙여서, traceId를 어디에 둬야 하는지와 수집기가 재시작할 때 로그를 잃는 경우를 직접 재봤다. (Loki 3.7.8, OpenTelemetry Collector contrib 0.163.1)

로그 파이프라인의 구성

Spring Boot ── stdout(JSON, traceId 포함) ──> 컨테이너 런타임이 노드의 /var/log/pods/... 에 파일로 쓴다
  ──> 노드마다 뜬 수집기(DaemonSet)가 파일을 읽고 파싱한다
  ──> 저장소(Loki) ──> Grafana에서 조회. Tempo의 span ↔ Loki의 로그를 traceId로 오간다

애플리케이션은 stdout으로만 쓴다. 수집 방식을 바꾸거나 저장소가 죽어도 애플리케이션은 영향을 받지 않고, 죽기 직전에 찍은 로그도 파일에 남아 있으면 수집된다.

수집기 고르기

수집기특징대가
OpenTelemetry Collector로그, trace, 메트릭을 같은 파이프라인으로 다룬다설정이 길고, contrib 배포판은 바이너리가 크다
Grafana Alloy안에 OpenTelemetry Collector 부품이 들어 있다Grafana 생태계에 묶이고 설정 언어를 따로 익혀야 한다
Promtail예전의 Loki 전용 수집기2026년 3월 2일로 지원이 끝났다(EOL)
Fluent Bit, Vector가볍고 빠른 범용 로그 수집기trace, 메트릭은 다른 도구로 따로 모아야 한다

trace를 모으는 Collector가 이미 있으니 로그 파이프라인만 더했다. 수집기를 하나 더 운영하지 않아도 되고, trace와 로그가 같은 리소스 속성(service.name, k8s.namespace.name)을 달고 나가서 둘을 잇기 쉽다.

저장소 고르기

저장소색인하는 것대가
Loki라벨(서비스, 네임스페이스 등)만 색인하고 본문은 압축해서 오브젝트 스토리지에 둔다저장 비용이 싸다. 대신 본문 검색은 고른 라벨의 로그를 모두 훑는다
Elasticsearch, OpenSearch본문의 모든 단어를 색인한다아무 단어로나 빨리 찾지만 색인이 원본만큼 커진다
ClickHouse 기반(SigNoz 등)컬럼 저장소에 넣고 SQL로 찾는다집계가 빠르지만 운영할 저장소가 하나 더 생긴다

로그는 쓰기가 압도적으로 많고 대부분 다시 보지 않는다. 볼 때는 서비스와 시간 범위를 먼저 좁히니, 색인을 최소로 줄인 Loki가 이 사용 방식에 맞다.

라벨과 structured metadata

Loki에서 라벨 조합 하나가 스트림 하나다. 같은 스트림의 로그는 시간순으로 청크에 모여 압축되고, 색인에는 어떤 스트림이 어느 청크에 있는지만 들어간다. 그래서 라벨 값의 종류가 많아지면 스트림이 폭발한다.

traceId처럼 요청마다 다른 값은 Loki 3.x의 structured metadata에 둔다. 줄마다 키와 값을 붙여 저장하지만 색인하지 않고, | trace_id="..."로 거를 수 있다. OTLP로 받은 로그는 리소스 속성 몇 가지만 라벨이 되고, 나머지와 traceId, spanId는 structured metadata가 된다. (schema v13, tsdb 인덱스 필요)

실험 환경

lab-logs 네임스페이스에 단일 바이너리 Loki(데이터는 Longhorn PVC)와 실험 스크립트를 돌리는 파드를 띄웠다. 스크립트와 매니페스트는 길어서 뺐고, 결과만 옮긴다.

ready
  ingestion_rate_mb: 4
  max_global_streams_per_user: 5000
  max_label_names_per_series: 15

기본 제한은 테넌트마다 활성 스트림 5,000개, 수집 속도 초당 4MB, 스트림 하나의 라벨 15개다. traceId 라벨 실험이 이 숫자와 부딪힌다.

traceId를 라벨로 넣으면

  • 가설

    • 서비스 둘, 레벨 셋의 라벨이면 스트림은 6개뿐이다. traceId를 로그 줄 안에 두든 structured metadata로 붙이든 같다. 반면 traceId를 라벨로 넣으면 trace마다 새 스트림이 생기니, 활성 스트림 한도 5,000에서 거절될 것이다.

  • 절차

    • traceId를 줄 안에만 둔 로그(line), structured metadata로도 붙인 로그(meta)를 각각 50만 줄, 라벨로 넣은 로그(label)를 10만 줄 밀어 넣는다.

  • 결과

scenario=line  lines=500000 rejected_lines=0     elapsed=24.0s (20,807 lines/s) errors={}
scenario=meta  lines=500000 rejected_lines=0     elapsed=29.6s (16,878 lines/s) errors={}
scenario=label lines=100000 rejected_lines=84000 elapsed=3.8s  (26,224 lines/s) errors={'429 streams limit': 42}

loki_discarded_samples_total{reason="stream_limit",tenant="fake"} 82160
loki_ingester_memory_chunks 5013
series: 4980
  • 관찰 포인트
    • traceId를 줄 안에 두든 structured metadata로 붙이든 50만 줄이 모두 들어갔다. structured metadata 쪽이 23% 느렸던 건 줄마다 키와 값을 하나씩 더 보냈기 때문이다.

traceId를 라벨로 넣자 스트림이 4,980개 생긴 시점에서 한도에 걸려 10만 줄 중 82,160줄이 버려졌다. 들어간 줄도 스트림마다 몇 줄뿐이라 청크가 5,013개나 됐다.

스트림 한도를 올리면 거절은 멈춘다. 하지만 라벨 값마다 스트림, 청크, 색인 항목이 생기는 구조는 그대로라 메모리와 색인이 trace 수만큼 커진다. 요청마다 다른 값(traceId, 사용자 ID, 파드 이름)은 structured metadata나 본문에 두고, 라벨은 조회를 시작할 때 좁히는 값(서비스, 네임스페이스, 환경)만 둔다.

traceId로 로그 찾기

  • 가설

    • Loki는 라벨만 색인하니, traceId로 찾는 일은 고른 스트림을 시간 범위만큼 모두 훑는 일이다. 어떤 방식으로 거르든 읽는 양은 같고 줄마다 하는 일만 다르다. | json으로 줄 전체를 파싱하면 두 배 가까이 느릴 것이다.

  • 절차

    • 같은 trace 하나를 네 가지 질의로 다섯 번씩 찾고 p50을 잰다.
{scenario="line", service="docs-api"} |= "<tid>"                          # 줄 필터
{scenario="meta", service="docs-api"} | trace_id="<tid>"                  # structured metadata
{scenario="line", service="docs-api"} | json | traceId="<tid>"           # JSON 파싱 후 필터
{scenario="line", service="docs-api"} |= "<tid>" | json | traceId="<tid>" # 줄 필터 후 JSON
  • 결과
line filter       p50=  163.9ms found=10  bytes_processed=   62.9MB lines_processed=253,601
structured meta   p50=  191.5ms found=10  bytes_processed=   67.7MB lines_processed=253,474
json parse        p50=  334.2ms found=10  bytes_processed=   62.9MB lines_processed=253,601
line filter+json  p50=  158.9ms found=10  bytes_processed=   62.9MB lines_processed=253,601
  • 관찰 포인트
    • 네 방식 모두 trace의 로그 10줄을 정확히 찾았고, 모두 docs-api 스트림 1시간치(25만 줄, 63MB)를 다 읽었다. Loki에서 본문 조건의 비용은 찾은 줄 수가 아니라 고른 스트림과 시간 범위의 크기로 정해진다.

여기서 나오는 규칙은 둘이다.

  • 라벨과 시간 범위를 먼저 좁힌다
    • Tempo에서 로그로 넘어갈 때 그 trace의 서비스와 시간 범위(앞뒤 몇 분)를 같이 넘기면, 1시간치가 아니라 몇 분치만 훑는다.
  • 파싱은 거른 다음에 한다
    • |= "값"이나 structured metadata로 먼저 줄이고, 필요할 때만 | json을 붙인다.

structured metadata는 속도보다 정확함 때문에 쓴다. 줄 필터는 그 문자열이 어디에 있든 걸리지만, structured metadata 필터는 trace_id 필드의 값만 본다. OTLP로 받으면 traceId가 자동으로 structured metadata가 되니, 로그 형식이 서비스마다 달라도 같은 질의로 찾을 수 있다.

수집기가 재시작하면

  • 가설

    • 수집기가 파일을 어디까지 읽었는지 기억하지 못하면, 다시 뜰 때 start_at: end는 멈춰 있던 동안 쓰인 줄을 잃고 beginning은 이미 보낸 줄을 또 보낸다. 읽은 위치를 디스크(file_storage)에 저장하면 잃지도 겹치지도 않을 것이다.

  • 절차

    • 초당 150줄씩 3,000줄을 쓰는 동안 수집기를 6초 뒤에 멈추고 4초 뒤에 다시 띄운다. 줄마다 순번(seq)이 있어서 빠진 것과 겹친 것을 셀 수 있다.
extensions:
  file_storage:
    directory: /var/lib/otelcol
receivers:
  file_log:
    include: [/var/log/app.log]
    start_at: beginning
    storage: file_storage          # 읽은 위치를 저장한다. 이 줄이 없으면 start_at만 보고 다시 읽는다
  • 결과
restart-end:       lines=2281 distinct=2281 duplicates=0   missing=719
restart-beginning: lines=3821 distinct=3000 duplicates=821 missing=0
restart-storage:   lines=3000 distinct=3000 duplicates=0   missing=0
  • 관찰 포인트
    • end는 719줄을 잃었다. 멈춰 있던 동안 쓰인 줄에, 처음 뜰 때 이미 파일에 있던 줄까지 더해진 숫자다. beginning은 파일을 처음부터 다시 읽어서 821줄을 두 번 보냈다. 실제 노드라면 재시작할 때마다 몇 분치 로그가 한꺼번에 다시 들어가며 수집 속도 제한에도 걸린다. 읽은 위치를 저장하자 정확히 3,000줄이 들어갔다.

쿠버네티스에서는 이 저장 위치를 어디에 두느냐가 중요하다. 파드 안의 emptyDir에 두면 파드가 새로 뜰 때(DaemonSet 업데이트) 사라진다. 노드의 호스트 경로(/var/lib/otelcol)에 두어야 수집기 파드를 바꿔도 이어 읽는다.

Loki가 응답하지 않는 동안 재시작하면

  • 가설

    • Loki가 잠깐 죽어 있으면 수집기는 읽은 줄을 메모리 대기열에 쌓아두고 재시도한다. 그런데 읽은 위치는 이미 앞으로 가 있다. 이때 재시작하면 메모리 대기열의 줄만큼 잃을 것이다. 대기열도 디스크에 두면(sending_queue.storage) 잃지 않을 것이다.

  • 절차

    • Loki 앞에 3초부터 12초까지 503을 돌려주는 프록시를 두고, 그 사이 6초에 수집기를 멈췄다가 10초에 다시 띄운다. 세 번 반복한다.

  • 결과

restart-storage:       lines=2544 distinct=2544 duplicates=0 missing=456 (seq 366..821)
restart-storage-queue: lines=3000 distinct=3000 duplicates=0 missing=0
restart-storage:       lines=2559 distinct=2559 duplicates=0 missing=441 (seq 369..809)
restart-storage-queue: lines=3000 distinct=3000 duplicates=0 missing=0
restart-storage:       lines=2569 distinct=2569 duplicates=0 missing=431 (seq 426..856)
restart-storage-queue: lines=3000 distinct=3000 duplicates=0 missing=0

Exporting failed. Dropping data. {"error": "interrupted due to shutdown: ... responded with HTTP Status Code 503", "dropped_items": 29}
  • 관찰 포인트
    • 읽은 위치만 저장했을 때는 세 번 모두 430~460줄을 잃었다. 잃은 순번은 Loki가 503을 돌려주기 시작한 3초부터 수집기를 멈춘 6초까지 읽은 줄이다. 메모리 대기열에서 재시도를 기다리다 수집기가 내려가면서 사라졌고, 읽은 위치는 이미 그 뒤로 저장되어 있었다. 대기열을 디스크에 두자 세 번 모두 하나도 잃지 않았다.

하나 헷갈리는 게 있었다. 대기열을 디스크에 둔 쪽에서도 종료할 때 Exporting failed. Dropping data.가 찍혔는데, 실제로는 아무것도 잃지 않았다. 디스크 대기열에서는 보내는 데 성공해야 항목을 지우니, 중단된 요청은 다음에 다시 나간다. 로그 문구만 보고 유실을 판단하면 틀린다. 반대로 응답을 받기 전에 죽으면 같은 묶음을 다시 보낼 수 있다(최소 한 번 전달). 로그는 한두 줄 겹치는 쪽이 잃는 쪽보다 낫다.

클러스터에서 끝까지 이어 보기

  • 가설

    • 노드 수집기(DaemonSet)가 Spring Boot 형식의 컨테이너 로그를 읽으면, Loki의 라벨은 서비스, 네임스페이스, 컨테이너 이름뿐이다. 파드 이름, 로거, traceId, spanId는 structured metadata로 들어간다. 수집기를 다시 띄워도 같은 줄이 두 번 들어가지 않는다.

  • 절차

    • Spring Boot 구조화 로그(logstash 형식)와 같은 모양으로 찍는 데모 앱을 띄우고, 운영 구성과 같은 수집기를 DaemonSet으로 띄운다.

  • 결과

  • 관찰 포인트
    • 라벨은 컨테이너, 네임스페이스, 서비스 셋뿐이었고, traceId 하나로 요청 하나의 로그 세 줄이 나왔다. 수집기를 다시 띄워도 줄 수는 195 그대로였다.

이렇게 되기까지 두 군데서 막혔다. 첫째, Loki는 OTLP로 받을 때 k8s.pod.name을 기본 라벨로 만든다. 파드 이름은 배포할 때마다 바뀌니 스트림이 계속 새로 생긴다. limits_config.otlp_config에 규칙을 더해도 Loki가 기본 라벨 목록을 첫 번째 규칙으로 앞에 붙여서 라벨이 그대로 남았다. 기본 목록 자체에서 빼야 했다.

distributor:
  otlp_config:
    # 기본 목록에서 k8s.pod.name, service.instance.id를 뺐다. 빠진 속성은 structured metadata로 저장된다
    default_resource_attributes_as_index_labels:
      - service.name
      - service.namespace
      - deployment.environment
      - deployment.environment.name
      - cloud.region
      - k8s.cluster.name
      - k8s.namespace.name
      - k8s.container.name
      - k8s.deployment.name
      - k8s.statefulset.name
      - k8s.daemonset.name
      - k8s.cronjob.name
      - k8s.job.name

둘째, 장애 실험의 프록시를 처음 만들었을 때 Loki가 422를 돌려줬다. 수집기가 gzip으로 보내는데 프록시가 Content-Encoding 헤더를 넘기지 않아서였다. 수집기와 Loki 사이에 무언가를 끼울 때는 이 헤더를 확인하자.

운영 구성

Loki

운영에서는 청크와 인덱스를 오브젝트 스토리지에 두고 Loki는 상태를 거의 들고 있지 않게 한다. 노드를 잃어도 로그는 남는다.

schema_config:
  configs:
    - from: 2026-10-01
      store: tsdb
      object_store: s3
      schema: v13
      index: { prefix: index_, period: 24h }
compactor:
  working_directory: /loki/compactor
  retention_enabled: true                 # 보관 기간이 지난 청크를 지운다
  delete_request_store: s3
limits_config:
  retention_period: 744h                  # 31일
  allow_structured_metadata: true

retention_period만 두고 retention_enabled를 켜지 않으면 오브젝트 스토리지가 계속 자란다. 오브젝트 스토리지 키는 [시크릿 관리] 글처럼 Vault에서 받아 환경 변수로 넣는다.

수집기

extensions:
  file_storage:
    directory: /var/lib/otelcol           # 호스트 경로. 파드가 새로 떠도 남는다
receivers:
  file_log:
    include: [/var/log/pods/*/*/*.log]
    start_at: beginning
    storage: file_storage                 # 읽은 위치 저장
processors:
  memory_limiter: { check_interval: 1s, limit_percentage: 80, spike_limit_percentage: 20 }
exporters:
  otlp_http:
    endpoint: http://loki:3100/otlp
    sending_queue: { storage: file_storage }                    # 대기열도 디스크에
    retry_on_failure: { enabled: true, max_elapsed_time: 0s }   # 포기하지 않는다
  • 읽은 위치와 대기열은 둘 다 호스트 경로의 file_storage에 둔다.
  • memory_limiter를 맨 앞에 둔다. Loki가 오래 느려서 대기열이 커지면 OOM으로 죽기 전에 읽기를 늦춘다.
  • 헬스 체크 로그, 운영의 DEBUG 로그는 filter 프로세서로 수집기에서 버린다. 수집 속도 제한과 저장 비용은 둘 다 줄 수에 비례한다.
  • 라벨은 서비스, 네임스페이스, 컨테이너, 환경 정도만 둔다.

Grafana에서 trace와 로그 잇기

datasources:
  - name: Loki
    type: loki
    jsonData:
      derivedFields:                          # 로그 → trace
        - name: TraceID
          matcherType: label                  # structured metadata의 trace_id
          matcherRegex: trace_id
          datasourceUid: tempo
          url: '${__value.raw}'
  - name: Tempo
    type: tempo
    jsonData:
      tracesToLogsV2:                         # trace → 로그
        datasourceUid: loki
        spanStartTimeShift: -5m
        spanEndTimeShift: 5m
        customQuery: true
        query: '{service_name="${__span.tags["service.name"]}"} | trace_id="${__trace.traceId}"'

trace에서 로그로 넘어갈 때 서비스 이름과 span 앞뒤 5분을 같이 넣어서, 한 서비스의 10분치만 훑게 했다. 이 프로비저닝은 직접 띄워보지 못했으니 적용한 뒤 Explore에서 링크가 생기는지 확인하자.

Spring에서

Spring Boot 3.4부터는 속성 하나로 stdout을 JSON으로 바꾼다. 3.3 이하라면 logstash-logback-encoder의 LogstashEncoder를 쓰면 된다.

logging:
  structured:
    format:
      console: logstash          # 수집기의 파싱 설정과 맞춘다

Micrometer Tracing이 요청마다 MDC에 traceId, spanId를 넣고, 구조화 로그는 MDC 값을 JSON에 그대로 넣는다. 그래서 코드를 따로 쓰지 않아도 로그 한 줄마다 traceId가 남는다. 샘플링에서 빠진 요청도 trace context는 만들어지니, Tempo에서 trace는 못 찾아도 Loki에서 그 요청의 로그는 모을 수 있다. 다만 브리지와 버전에 따라 다를 수 있으니 샘플링 비율을 낮게 둔다면 확인하자.

log.atInfo()
   .setMessage("document loaded")
   .addKeyValue("documentId", documentId)   // JSON 필드로 따로 들어간다. 문장에 섞지 않는다
   .addKeyValue("cacheHit", true)
   .log();

SLF4J의 addKeyValue로 넣은 값은 JSON 필드가 되어 Loki에서 | documentId="42"처럼 거를 수 있다. 사용자 ID, 이메일, 토큰 같은 값은 남기지 않는다. 로그는 접근 권한이 느슨하고 오래 남는다.

정리

  • 애플리케이션은 stdout에 JSON으로 쓰고, 노드의 수집기가 파일을 읽어 Loki로 보낸다. trace용 OpenTelemetry Collector에 로그 파이프라인을 더하면 수집기를 하나 더 운영하지 않아도 된다.
  • traceId를 라벨로 넣자 스트림 한도에 걸려 10만 줄 중 82,160줄이 버려졌다. 요청마다 다른 값은 structured metadata나 본문에 둔다.
  • traceId로 찾는 비용은 훑는 양으로 정해진다. 서비스와 시간 범위를 먼저 좁히고, 파싱은 거른 다음에 한다.
  • 읽은 위치를 기억하지 못하는 수집기는 재시작할 때 로그를 잃거나(end) 두 번 보낸다(beginning).
  • Loki가 죽어 있는 동안 재시작하면 위치만 저장해서는 430~460줄을 잃었다. 내보내기 대기열도 디스크에 두면 0이었다.
  • OTLP로 받으면 Loki는 k8s.pod.name을 기본 라벨로 만든다. 기본 목록 자체에서 빼야 한다.
