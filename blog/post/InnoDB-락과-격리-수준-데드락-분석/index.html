InnoDB 락과 격리 수준, 데드락 분석

Database/RDB · 2026-10-12

Intro

분산 락이나 버전 번호로 동시성을 제어하는 코드를 짜다 보면, 정작 그 아래에서 DB가 어떤 락을 걸고 있는지는 모른 채로 지나가게 된다. 그러다 운영에서 Deadlock found when trying to get lock이 찍히면, 같은 행을 건드린 것도 아닌데 왜 데드락이 났는지 설명을 못 한다. 실제로 InnoDB는 우리가 조회한 행만 잠그는 게 아니라, 그 행 사이의 간격까지 잠그는 경우가 있었다.

이번엔 InnoDB가 어떤 락을 언제 거는지, 격리 수준이 그걸 어떻게 바꾸는지를 performance_schema.data_locks로 직접 들여다보고, 실무에서 자주 나오는 데드락 두 가지를 재현해서 로그를 읽는 법과 고치는 법까지 정리해보려고 한다.

각 실험은 가설, 절차, 관찰, 결과 순서로 정리했고, 결과 표의 관찰 칸은 직접 돌려서 채우도록 비워뒀다.

# 세션 C: SQL을 표준 입력으로 받아 실행
msql() {
  kubectl exec -i -n lab-mysql mysql-0 -- \
    bash -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -t lab 2>/dev/null'
}

격리 수준

격리 수준은 한 트랜잭션이 실행되는 동안 다른 트랜잭션이 커밋한 변경을 언제부터 볼 수 있는지를 정한다.

격리 수준Dirty ReadNon-Repeatable ReadPhantom Read
READ UNCOMMITTED발생발생발생
READ COMMITTED없음발생발생
REPEATABLE READ (InnoDB 기본값)없음없음일반 조회는 없음 (아래 설명)
SERIALIZABLE없음없음없음

SQL 표준에서는 REPEATABLE READ에서도 Phantom Read가 생길 수 있다고 정의하지만, InnoDB는 두 가지 장치로 이걸 대부분 막는다. 일반 조회는 트랜잭션의 스냅샷을 읽기 때문에 새로 들어온 행이 안 보이고, 잠그는 조회는 간격까지 잠가서 새 행이 들어오는 것 자체를 막는다. 이 두 장치가 이 글의 핵심이다.

일반 조회와 잠그는 조회

InnoDB의 읽기는 두 종류다.

  • 일반 조회 (consistent nonlocking read)
    • 그냥 SELECT. 락을 걸지 않고, undo log를 따라가서 스냅샷 시점의 값을 읽는다.
  • 잠그는 조회 (locking read)
    • SELECT ... FOR UPDATE, SELECT ... FOR SHARE, 그리고 UPDATE, DELETE. 스냅샷이 아니라 지금 커밋된 최신 값을 읽고, 읽은 레코드에 락을 건다.

REPEATABLE READ에서 스냅샷은 트랜잭션의 첫 일반 조회 시점에 만들어지고, 트랜잭션이 끝날 때까지 유지된다. READ COMMITTED에서는 일반 조회를 할 때마다 새 스냅샷을 만든다.

격리 수준에 따라 같은 조회의 결과가 바뀐다

  • 가설

    • READ COMMITTED에서는 다른 트랜잭션의 커밋이 곧바로 보이고, REPEATABLE READ에서는 트랜잭션이 끝날 때까지 처음 본 값이 유지된다.

  • 절차

-- [A]
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 10;   -- 100

-- [B] autocommit으로 바로 커밋
UPDATE account SET balance = 777 WHERE id = 10;

-- [A]
SELECT balance FROM account WHERE id = 10;   -- ?
COMMIT;

같은 절차를 A의 격리 수준만 REPEATABLE READ로 바꿔서 반복한다. 시작 전에 UPDATE account SET balance = 100 WHERE id = 10;로 되돌려 둔다.

격리 수준A의 두 번째 조회 결과예상
READ COMMITTED777
REPEATABLE READ100

같은 트랜잭션 안에서 일반 조회와 잠그는 조회가 다른 값을 본다.

  • 가설

    • REPEATABLE READ에서 일반 조회는 스냅샷 값을, 잠그는 조회는 최신 값을 본다. 그래서 한 트랜잭션 안에서 같은 행을 조회했는데 서로 다른 값이 나온다.

  • 절차

-- [A]
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT balance FROM account WHERE id = 20;              -- 100, 스냅샷 생성

-- [B]
UPDATE account SET balance = 500 WHERE id = 20;         -- 커밋됨

-- [A]
SELECT balance FROM account WHERE id = 20;              -- ? (일반 조회)
SELECT balance FROM account WHERE id = 20 FOR UPDATE;   -- ? (잠그는 조회)
SELECT balance FROM account WHERE id = 20;              -- ? (다시 일반 조회)
ROLLBACK;
조회예상관찰
일반 조회100
FOR UPDATE500
다시 일반 조회100

이게 실무에서 갱신 유실(lost update)이 생기는 지점이다. 애플리케이션이 일반 조회로 잔액 100을 읽고, 코드에서 100 - 10 = 90을 계산해서 UPDATE account SET balance = 90으로 쓰면, 그 사이 B가 커밋한 500은 그대로 덮여서 사라진다. REPEATABLE READ라고 해서 이걸 막아주지 않는다. 읽고 계산해서 쓰는 흐름에서는 처음부터 FOR UPDATE로 읽거나, UPDATE account SET balance = balance - 10처럼 DB 안에서 원자적으로 계산하거나, 버전 번호로 충돌을 감지해야 한다.

락의 종류

잠그는 조회가 실제로 거는 락은 몇 가지로 나뉜다.

  • 레코드 락 (Record Lock)
    • 인덱스 레코드 하나를 잠근다. data_locks에서 X,REC_NOT_GAP으로 보인다.
  • 갭 락 (Gap Lock)
    • 인덱스 레코드 사이의 간격을 잠근다.
    • 레코드 자체가 아니라 그 앞의 빈 공간에 새 레코드가 들어오는 걸 막는다. X,GAP으로 보인다.
  • 넥스트 키 락 (Next-Key Lock)
    • 레코드 락과 그 레코드 앞 간격의 갭 락을 합친 것.
    • REPEATABLE READ에서 범위를 잠글 때 기본으로 쓰는 락이다. data_locks에서는 그냥 X로 보인다.
  • 삽입 의도 락 (Insert Intention Lock)
    • INSERT가 간격에 레코드를 넣기 전에 거는 특수한 갭 락이다.
    • 같은 간격의 서로 다른 위치에 넣는 INSERT끼리는 충돌하지 않지만, 그 간격에 다른 트랜잭션의 갭 락이 있으면 기다린다. X,GAP,INSERT_INTENTION으로 보인다.
  • 의도 락 (Intention Lock)
    • 테이블 수준의 표시다.
    • 행에 X 락을 걸기 전에 테이블에 IX를 건다. 행 락끼리 충돌을 막는 게 아니라, 테이블 전체를 잠그려는 작업과의 충돌을 빨리 판단하기 위한 용도다.

여기서 반드시 기억할 규칙이 두 가지 있다.

첫째, 락은 행이 아니라 인덱스 레코드에 걸린다. 그리고 조건에 맞는 행이 아니라 스캔한 인덱스 레코드에 걸린다. 그래서 인덱스를 못 타는 조건으로 UPDATE하면, 조건에 맞든 안 맞든 스캔한 모든 레코드가 잠긴다. 둘째, 갭 락끼리는 서로 충돌하지 않는다. 갭 락의 목적은 간격에 새 레코드가 들어오는 것만 막는 거라, 두 트랜잭션이 같은 간격에 동시에 갭 락을 걸 수 있다. 이 성질이 뒤에 나올 데드락의 원인이 된다.

비관적 락과 낙관적 락은?

위 목록은 InnoDB가 실제로 거는 락의 종류다. 흔히 같이 언급되는 비관적 락과 낙관적 락은 락의 종류가 아니라, 애플리케이션이 동시성을 다루는 전략이다.

  • 비관적 락 (Pessimistic Lock)
    • 충돌이 날 거라고 가정하고, 읽는 시점에 먼저 잠근다.
    • 실제로는 SELECT ... FOR UPDATE(X 락)나 SELECT ... FOR SHARE(S 락)를 쓰는 것이라, 위의 레코드 락이나 넥스트 키 락이 그대로 걸린다.
    • JPA에서는 @Lock(LockModeType.PESSIMISTIC_WRITE)가 FOR UPDATE, PESSIMISTIC_READ가 FOR SHARE로 실행된다.
  • 낙관적 락 (Optimistic Lock)
    • 충돌이 드물다고 가정하고, 읽을 때는 아무것도 잠그지 않는다.
    • 쓸 때 UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?로 그 사이에 누가 바꿨는지 확인하고, 영향받은 행이 0이면 충돌로 판단한다.
    • DB 락을 아예 안 쓰는 건 아니다. 이 UPDATE 문장이 실행되는 짧은 순간에는 해당 레코드에 X 락이 걸린다.
    • JPA에서는 @Version 필드로 동작하고, 충돌 시 OptimisticLockingFailureException이 발생한다.

경합이 잦은 자원이라면 비관적 락이 낫다. 낙관적 락은 충돌할 때마다 트랜잭션을 처음부터 다시 실행해야 해서, 충돌이 많으면 재시도 비용이 락 대기보다 커진다. 반대로 충돌이 드물다면 낙관적 락이 락 대기 없이 처리량을 더 낼 수 있다.

조건별로 어떤 락이 걸리는지 관찰하기

  • 가설

    • 같은 FOR UPDATE라도 조건에 따라 레코드 락, 갭 락, 넥스트 키 락이 다르게 걸린다. 인덱스가 없는 조건은 테이블 전체를 잠근다.

  • 절차

    • 세션 A에서 아래 조회를 하나씩 실행하고, 각각 세션 C에서 locks로 확인한 뒤 ROLLBACK한다. 격리 수준은 REPEATABLE READ다.
-- [A] (1) PK로 존재하는 행 하나
START TRANSACTION;
SELECT * FROM account WHERE id = 30 FOR UPDATE;
-- [C] locks 실행 후 [A] ROLLBACK;

-- [A] (2) PK로 존재하지 않는 값
START TRANSACTION;
SELECT * FROM account WHERE id = 25 FOR UPDATE;
-- [C] locks 실행 후 [A] ROLLBACK;

-- [A] (3) PK 범위
START TRANSACTION;
SELECT * FROM account WHERE id BETWEEN 20 AND 30 FOR UPDATE;
-- [C] locks 실행 후 [A] ROLLBACK;

-- [A] (4) 유니크하지 않은 보조 인덱스
START TRANSACTION;
SELECT * FROM account WHERE owner = 'b' FOR UPDATE;
-- [C] locks 실행 후 [A] ROLLBACK;

-- [A] (5) 인덱스가 없는 컬럼으로 UPDATE
START TRANSACTION;
UPDATE account SET balance = balance + 1 WHERE balance > 1000;   -- 조건에 맞는 행은 0건
-- [C] locks 실행 후 [A] ROLLBACK;
조건예상관찰 (idx / mode / data)
(1) id = 30PRIMARY에 X,REC_NOT_GAP 30 하나
(2) id = 25PRIMARY에 X,GAP 30 (20과 30 사이 간격)
(3) id BETWEEN 20 AND 30범위 안 레코드와 그 사이 간격, 범위 경계 근처까지
(4) owner = 'b'idx_owner에 넥스트 키 락 + 다음 레코드 앞 갭, PRIMARY에 해당 행 레코드 락
(5) 인덱스 없는 balance > 1000PRIMARY의 모든 레코드에 X + supremum pseudo-record

(2)에서 LOCK_DATA가 25가 아니라 30으로 나오는 게 포인트다. 25라는 레코드는 존재하지 않으니까, InnoDB는 25가 들어갈 자리인 30 앞의 간격을 잠근다. (5)는 조건에 맞는 행이 한 건도 없는데도 테이블의 모든 레코드와 마지막 레코드 뒤의 무한대 간격(supremum pseudo-record)까지 잠긴다. 이 트랜잭션이 끝날 때까지 이 테이블에는 INSERT도 UPDATE도 못 한다는 뜻이다. 운영에서 인덱스 없는 조건의 UPDATE 하나가 서비스 전체를 멈추게 하는 이유다.

갭 락이 INSERT를 막는다. 그리고 READ COMMITTED에서는 안 막는다.

  • 가설

    • REPEATABLE READ에서 범위를 잠그면 그 범위 안으로의 INSERT가 막혀서 Phantom Read가 생기지 않는다. READ COMMITTED에서는 갭 락을 쓰지 않아서 INSERT가 바로 들어가고, 같은 트랜잭션에서 다시 잠그는 조회를 하면 새 행이 보인다.

  • 절차 (REPEATABLE READ)

-- [A]
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM account WHERE id BETWEEN 20 AND 40 FOR UPDATE;

-- [B]
INSERT INTO account VALUES (35, 'x', 0);   -- 대기하는지 확인

# [C]
locks    # B의 X,GAP,INSERT_INTENTION이 WAITING으로 보인다
waits

-- [A]
ROLLBACK;   -- B의 INSERT가 이제 실행된다

-- [B] 정리
DELETE FROM account WHERE id = 35;
  • 절차 (READ COMMITTED)
    • A와 B 모두 SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;를 먼저 실행하고 같은 절차를 반복한다. B의 INSERT가 바로 끝나면, A에서 같은 FOR UPDATE 조회를 다시 실행해본다.
격리 수준B의 INSERTA가 다시 조회했을 때 35가 보이나
REPEATABLE READ대기 (예상)
READ COMMITTED즉시 성공 (예상)보임 (예상)

READ COMMITTED가 갭 락을 거의 안 쓰는 대가가 이거다. 같은 트랜잭션 안에서 같은 범위를 잠그며 두 번 읽었는데 결과가 다르다. 대신 갭 락이 없으니 갭 락 때문에 생기는 대기와 데드락이 크게 줄어든다. 참고로 READ COMMITTED를 쓰려면 binlog 포맷이 ROW여야 한다. 갭 락 없이 STATEMENT로 기록하면 replica에서 같은 문장이 다른 결과를 낼 수 있기 때문이다.

데드락

두 트랜잭션이 서로 상대가 가진 락을 기다리면, 둘 다 영원히 진행할 수 없다. InnoDB는 이 순환을 감지하면(innodb_deadlock_detect, 기본 ON) 둘 중 하나를 희생자로 골라 트랜잭션 전체를 롤백하고 ERROR 1213을 돌려준다. 나머지 하나는 그대로 진행된다.

반대 순서로 잠그는 데드락

  • 가설

    • 두 트랜잭션이 같은 두 행을 서로 반대 순서로 수정하면 데드락이 난다.

  • 절차

-- [A]
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE id = 10;

-- [B]
START TRANSACTION;
UPDATE account SET balance = balance - 10 WHERE id = 20;

-- [A]
UPDATE account SET balance = balance + 10 WHERE id = 20;   -- B를 기다림

-- [B]
UPDATE account SET balance = balance + 10 WHERE id = 10;   -- A를 기다림 -> 순환

둘 중 한 세션에 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction이 나온다. 살아남은 쪽은 COMMIT 또는 ROLLBACK으로 정리한다.

데드락 로그 읽기

마지막으로 감지된 데드락은 SHOW ENGINE INNODB STATUS에 남는다.

echo "SHOW ENGINE INNODB STATUS\G" | msql | sed -n '/LATEST DETECTED DEADLOCK/,/TRANSACTIONS/p'

출력은 대략 이런 구조다.

* (1) TRANSACTION:
TRANSACTION 5001, ACTIVE 12 sec starting index read
UPDATE account SET balance = balance + 10 WHERE id = 20     <- (1)이 마지막으로 실행한 문장

* (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index PRIMARY of table `lab`.`account` ... lock_mode X locks rec but not gap
 0: len 8; hex 800000000000000a; ...                         <- id 10 (16진수 0a)

* (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY ... lock_mode X locks rec but not gap waiting
 0: len 8; hex 8000000000000014; ...                         <- id 20 (16진수 14)

* (2) TRANSACTION:
...
* (2) HOLDS THE LOCK(S): ... id 20
* (2) WAITING FOR THIS LOCK TO BE GRANTED: ... id 10

* WE ROLL BACK TRANSACTION (2)

읽는 순서는 이렇다.

  1. 각 트랜잭션의 마지막 문장을 본다. 여기 나오는 건 마지막 문장 하나뿐이라, 그 앞에서 락을 잡은 문장은 애플리케이션 코드에서 찾아야 한다.
  2. HOLDS와 WAITING FOR를 엇갈려 맞춰서 순환을 확인한다. (1)이 가진 걸 (2)가 기다리고, (2)가 가진 걸 (1)이 기다린다.
  3. index로 어느 인덱스의 락인지, lock_mode로 레코드 락인지(rec but not gap), 갭 락인지(gap before rec), 넥스트 키 락인지(둘 다 없이 X), 삽입 의도 락인지(insert intention)를 본다.
  4. hex 값으로 어떤 키 값인지 확인한다. 부호 있는 정수 PK는 최상위 비트가 뒤집혀서 저장되기 때문에 10이 800000000000000a로 보인다.

SHOW ENGINE INNODB STATUS는 가장 최근 데드락 하나만 보여주기 때문에, 운영에서는 모든 데드락을 에러 로그에 남기도록 켜두는 게 좋다.

echo "SET GLOBAL innodb_print_all_deadlocks = ON;" | msql
kubectl logs -n lab-mysql mysql-0 | grep -A 40 "deadlock"

없으면 넣는 패턴의 데드락

실무에서 가장 흔하게 만나는 데드락이다. 행이 있는지 잠그며 확인하고, 없으면 INSERT하는 코드다.

@Transactional
public void increase(long userId) {
    dailyLimitRepository.findByIdForUpdate(userId)        // SELECT ... FOR UPDATE
        .ifPresentOrElse(
            limit -> limit.increase(),
            () -> dailyLimitRepository.save(new DailyLimit(userId, 1)));   // 없으면 INSERT
}

  • 가설

    • 존재하지 않는 키를 FOR UPDATE로 조회하면 레코드 락이 아니라 갭 락이 걸린다. 갭 락끼리는 충돌하지 않으니 두 트랜잭션이 동시에 같은 간격을 잡을 수 있고, 그 상태에서 둘 다 INSERT하면 서로의 갭 락에 삽입 의도 락이 막혀서 데드락이 난다.

  • 절차

-- [A]
START TRANSACTION;
SELECT * FROM daily_limit WHERE user_id = 200 FOR UPDATE;   -- 없음 -> 100과 300 사이 갭 락

-- [B]
START TRANSACTION;
SELECT * FROM daily_limit WHERE user_id = 200 FOR UPDATE;   -- 대기하지 않는다! 갭 락끼리는 호환

# [C] 같은 간격(data = 300)에 두 트랜잭션의 X,GAP이 둘 다 GRANTED로 보이는지 확인
locks

-- [A]
INSERT INTO daily_limit VALUES (200, 1);   -- B의 갭 락 때문에 대기

-- [B]
INSERT INTO daily_limit VALUES (200, 1);   -- A의 갭 락 때문에 대기 -> 데드락
확인 항목예상관찰

  • 고치는 법
    • 확인과 삽입을 한 문장으로 합쳐서 갭 락을 잡고 기다리는 구간 자체를 없앤다.
INSERT INTO daily_limit (user_id, cnt) VALUES (200, 1)
ON DUPLICATE KEY UPDATE cnt = cnt + 1;

같은 실험을 A와 B 둘 다 이 문장으로 바꿔서 반복해본다. A가 먼저 INSERT하면 B는 A가 넣은 레코드에 막혀 기다리다가, A가 커밋한 뒤 UPDATE로 이어진다. 두 세션에서는 데드락이 나지 않는다.

방식두 세션 동시 실행 결과최종 cnt

INSERT ... ON DUPLICATE KEY UPDATE순차 처리 (예상)2 (예상)

다만 이 문장도 유니크 키 중복 검사 과정에서 락을 잡기 때문에, 동시에 세 개 이상의 트랜잭션이 같은 키로 몰리면 데드락이 날 수 있다. 확률을 크게 낮추는 것이지 0으로 만드는 건 아니라서, 뒤에 나올 재시도는 여전히 필요하다.

락 대기 타임아웃은 트랜잭션을 롤백하지 않는다.

데드락과 비슷해 보이지만 동작이 완전히 다른 에러가 있다. 순환이 아니라 그냥 오래 기다리다 시간이 초과되는 경우다(innodb_lock_wait_timeout, 기본 50초).

  • 가설

    • 데드락(1213)은 트랜잭션 전체를 롤백하지만, 락 대기 타임아웃(1205)은 실패한 문장 하나만 롤백하고 트랜잭션은 열린 채로 남는다. 그래서 그 상태에서 커밋하면 앞의 변경만 반영된다.

  • 절차

-- [A]
START TRANSACTION;
UPDATE account SET balance = 0 WHERE id = 10;   -- id 10을 잡고 놓지 않는다

-- [B]
SET SESSION innodb_lock_wait_timeout = 5;
START TRANSACTION;
UPDATE account SET balance = 999 WHERE id = 50;   -- 성공
UPDATE account SET balance = 999 WHERE id = 10;   -- 5초 뒤 ERROR 1205
SELECT id, balance FROM account WHERE id IN (10, 50);   -- id 50은 여전히 999인가?
COMMIT;

-- [A]
ROLLBACK;
SELECT id, balance FROM account WHERE id IN (10, 50);
확인 항목예상관찰
타임아웃 직후 B에서 id 50의 값999 (트랜잭션이 살아 있음)
B가 커밋한 뒤 id 50999로 반영됨
B가 커밋한 뒤 id 10B의 변경은 없음

두 계좌를 같이 바꿔야 하는 작업에서 한쪽만 반영된 상태가 커밋된 거다. 트랜잭션 전체를 롤백하게 만드는 innodb_rollback_on_timeout이라는 설정이 있지만 서버 시작 시에만 바꿀 수 있고 기본값은 OFF다. Spring의 @Transactional은 예외가 메서드 밖으로 전파되면 트랜잭션을 롤백하니까 보통은 안전한데, 이 예외를 catch해서 삼키고 다음 코드로 넘어가는 순간 위의 상황이 그대로 재현된다.

데드락을 줄이는 방법

데드락은 완전히 없앨 수 있는 대상이 아니라, 줄이고 나서 남는 건 재시도로 흡수하는 대상이다. 효과가 큰 것부터 정리하면 이렇다.

  1. 락을 거는 순서를 통일한다. 실험 5의 데드락은 순서만 맞추면 사라진다. 여러 행을 잠가야 하면 PK 순으로 정렬해서 잠근다.
@Transactional
public void transfer(long fromId, long toId, int amount) {
    long first = Math.min(fromId, toId);
    long second = Math.max(fromId, toId);
    Account a = accountRepository.findByIdForUpdate(first).orElseThrow();
    Account b = accountRepository.findByIdForUpdate(second).orElseThrow();
    // a, b 중 어느 쪽이 from인지 판단해서 처리
}

  1. 확인 후 삽입을 원자적인 한 문장으로 바꾼다. 실험 6처럼 INSERT ... ON DUPLICATE KEY UPDATE나 INSERT IGNORE로 갭 락을 잡고 기다리는 구간을 없앤다.

  2. 잠그는 조건에 인덱스를 건다. 락은 스캔한 레코드에 걸리기 때문에, 인덱스가 없으면 잠그는 범위가 테이블 전체로 커지고 그만큼 충돌 확률도 커진다. 실험 3의 (5)가 극단적인 경우다.

  3. 트랜잭션을 짧게 유지한다. 트랜잭션 안에서 외부 API를 호출하거나 무거운 계산을 하면, 그 시간만큼 락을 들고 있게 된다. 락이 필요한 부분만 트랜잭션으로 감싼다.

  4. 기다리지 않는 잠금을 쓴다. MySQL 8.0부터 FOR UPDATE NOWAIT(잠겨 있으면 바로 실패)와 FOR UPDATE SKIP LOCKED(잠긴 행은 건너뜀)를 지원한다. 작업 큐처럼 여러 워커가 처리할 행을 나눠 가져가는 경우에는 SKIP LOCKED가 대기 자체를 없애준다.

  5. 격리 수준을 READ COMMITTED로 바꾸는 것도 선택지다. 갭 락이 거의 사라져서 실험 6 같은 데드락과 INSERT 대기가 크게 줄어든다. 쓰기 경합이 많은 대규모 서비스에서 READ COMMITTED를 기본으로 쓰는 경우가 적지 않은 이유다. 대신 실험 4처럼 잠그는 조회에서 Phantom Read가 생기고, 반복 조회 결과가 바뀌는 걸 전제로 코드를 짜야 한다. 이미 REPEATABLE READ로 운영 중인 서비스라면 전환의 영향 범위가 넓으니 1~5번을 먼저 적용하고, 새로 시작하는 서비스라면 처음부터 READ COMMITTED + ROW binlog로 가는 걸 검토할 만하다.

남은 데드락은 재시도로 흡수한다.

위 방법으로 줄여도 데드락은 남는다. 데드락의 희생자는 트랜잭션 전체가 이미 롤백된 상태라, 같은 작업을 처음부터 다시 실행하면 대부분 성공한다.

Spring은 MySQL의 데드락(1213)과 락 대기 타임아웃(1205)을 각각 PessimisticLockingFailureException의 하위 예외로 변환한다. 재시도는 이 상위 타입을 기준으로 잡으면 된다.

@Service
@RequiredArgsConstructor
public class TransferFacade {

    private final TransferService transferService;   // @Transactional이 붙은 쪽

    @Retryable(
        retryFor = PessimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 50, multiplier = 2, random = true))
    public void transfer(long fromId, long toId, int amount) {
        transferService.transfer(fromId, toId, amount);
    }
}

여기서 중요한 건 재시도가 트랜잭션 바깥에 있어야 한다는 거다. 데드락이 나면 트랜잭션은 이미 롤백됐는데, 재시도가 트랜잭션 안쪽에 있으면 롤백된 트랜잭션 안에서 다시 시도하게 된다. 그래서 재시도를 맡는 TransferFacade와 트랜잭션을 맡는 TransferService를 별도 빈으로 나눴다. 위 코드는 Spring Retry(@EnableRetry 필요) 기준이고, Spring Framework 7부터는 코어에 @Retryable이 들어와서 별도 의존성 없이 같은 구조로 쓸 수 있다. 백오프에 무작위성을 섞는 이유는, 동시에 데드락이 난 트랜잭션들이 같은 타이밍에 다시 부딪히는 걸 막기 위해서다.

운영에서 감시할 지표

echo "SHOW GLOBAL STATUS LIKE 'Innodb_row_lock%';" | msql
echo "SELECT NAME, COUNT, STATUS FROM information_schema.INNODB_METRICS WHERE NAME = 'lock_deadlocks';" | msql

Innodb_row_lock_waits(락을 기다린 횟수), Innodb_row_lock_time_avg(평균 대기 시간), 그리고 데드락 누적 횟수를 추적하면, 배포 후에 락 경합이 갑자기 늘었는지를 알 수 있다. 클러스터에 Prometheus가 있다면 mysqld_exporter를 붙여서 이 값들을 Grafana에서 그래프로 보는 게 가장 편하다.

정리

  • InnoDB의 읽기는 두 종류다. 일반 조회는 락 없이 스냅샷을 읽고, 잠그는 조회(FOR UPDATE, UPDATE, DELETE)는 최신 값을 읽으며 락을 건다. 같은 트랜잭션 안에서도 둘의 결과가 다를 수 있고, 일반 조회로 읽고 계산해서 쓰면 갱신 유실이 생긴다.
  • 락은 행이 아니라 스캔한 인덱스 레코드에 걸린다. 인덱스 없는 조건의 UPDATE는 조건에 맞는 행이 없어도 테이블 전체를 잠근다.
  • REPEATABLE READ는 넥스트 키 락과 갭 락으로 범위를 잠가서 Phantom Read를 막는다. READ COMMITTED는 갭 락을 거의 안 쓰는 대신 Phantom Read를 허용한다.
  • 갭 락끼리는 충돌하지 않는다. 그래서 없는 키를 FOR UPDATE로 확인하고 INSERT하는 패턴은 동시에 실행되면 데드락이 난다. INSERT ... ON DUPLICATE KEY UPDATE로 한 문장으로 합치는 게 해법이다.
  • 데드락(1213)은 트랜잭션 전체를 롤백하지만, 락 대기 타임아웃(1205)은 문장 하나만 롤백한다. 예외를 삼키면 일부만 커밋된다.
  • 데드락은 락 순서 통일, 원자적 문장, 인덱스, 짧은 트랜잭션으로 줄이고, 남은 건 트랜잭션 바깥의 재시도로 흡수한다.

data_locks를 직접 보기 전까지는 FOR UPDATE가 조회한 행 하나만 잠근다고 생각했다. 실제로는 존재하지도 않는 키 때문에 간격이 잠기고, 그 간격을 두 트랜잭션이 동시에 잡을 수 있다는 게 데드락 대부분의 정체였다. 데드락 로그가 찍히면 이제 lock_mode 한 줄부터 읽어보게 될 것 같다.
